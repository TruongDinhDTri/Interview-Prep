🗺️ Part 1: Platform Selection — Decision Framework

When asked "How would you choose between platforms?" — don't say Kubernetes is always the answer. Show pragmatism:

Use CasePlatformWhyWhen to Move On
Side project / MVP / "ship today" Railway or Render Git-push deploy, managed Postgres, managed Redis, SSL, $5-25/mo, zero ops time When per-service pricing hurts or you need custom networking
EU data residency, low ops budget Hetzner VPS + Coolify / Dokku $4-20/mo, GDPR-clean, full control, simple container deploy When you need auto-scaling or multi-region
Need global low latency Fly.io Edge regions, Firecracker microVMs, deploy close to users When cost scales and you need more AWS integrations
Standard production app, AWS shop ⭐ AWS ECS Fargate or App Runner Managed containers, IAM integration, ALB, RDS — full AWS ecosystem with no K8s overhead When you need complex networking/RBAC across many teams → EKS
Heavy scale, complex networking, multiple teams EKS (Kubernetes) Maximum flexibility, massive ecosystem, multi-team RBAC Only when you have a dedicated platform team
🚫 The Kubernetes trap: Proposing Kubernetes for a standard CRUD app. "Adopting Kubernetes introduces immense overhead: networking (CNI plugins, service mesh), RBAC configuration, etcd management, node pool management, upgrade procedures. For a team of 3 engineers on one app, ECS Fargate gives 90% of the benefits with 10% of the complexity."
🔄 Part 2: Blue-Green vs Rolling — Visual Comparison
🎯 The problem both strategies solve

Your app runs on 3 servers (called instances). You have new code. How do you swap it in?

❌ The dumb way: shut all 3 down, install new code, boot up → 5 minutes of dead website.

So we need something smarter. There are exactly two ways, and this whole section just compares them.

🚦 First — what is a Load Balancer (ALB)?
The ALB is a doorman standing at the entrance, pointing customers to a server.
user → 🚦 ALB → "go to that server over there"
This doorman points wherever you tell him to. That's all you need to know — he is the main character of this whole page. 👮
🔵🟢 Blue-Green = "build a second shop next door"
You run a noodle shop (BLUE) and want a new menu.
  1. Build a whole second shop (GREEN) with the new menu. Customers keep eating at BLUE, oblivious.
  2. Taste-test GREEN yourself (smoke tests). Terrible? Tear it down — customers never knew. 😎
  3. Good? The doorman 👮 flips his sign: "everyone goes to GREEN now." ← instant.
  4. BLUE stays standing (not demolished yet).
🔄 Rolling = "renovate one table at a time"
One shop only. 3 tables (3 instances). Swap them one by one:
start: [old] [old] [old] step 1: [old] [old] [NEW] ← tables 1,2 still old menu step 2: [old] [NEW] [NEW] step 3: [NEW] [NEW] [NEW] ← done
That's exactly the red/green boxes you see below. 🎨
🔵🟢 Blue-Green🔄 Rolling
Infrastructure2 full sets (costs 2×) 💸1 set (cheap) 💰
The switchone flip, instantgradual, batch by batch
Rollback⚡ seconds — the doorman flips back (BLUE is still standing!)🐌 roll backwards, table by table. No undo button.
Old + new run together?No (in theory — see the bomb below)Yes, for minutes
Use whenbig, risky releaseseveryday default (ECS/K8s)

🔵🟢 Blue-Green Deployment

Infrastructure: Two full identical environments (Blue = current, Green = new)
BLUE ← ALB routes 100% traffic here
→ Deploy new code to Green (idle)
→ Run smoke tests on Green
GREEN ← Flip ALB: 100% traffic here instantly
→ Rollback: flip ALB back (seconds)
  • ✅ Zero overlap — old and new never run simultaneously
  • ✅ Instant rollback (one ALB switch)
  • ✅ Full environment to test before traffic flip
  • ❌ 2x infrastructure cost
  • ⚠️ Does NOT magically solve migrations — schema must still be backward-compatible

🔄 Rolling Deployment

Infrastructure: Same set of instances, replaced in batches
OLD v1
OLD v1
NEW v2
← Mid-deploy: old + new running simultaneously
NEW v2
NEW v2
NEW v2
← After: all instances updated
  • ✅ No extra infrastructure cost
  • ✅ Default for ECS, Kubernetes
  • ⚠️ Old + new code run simultaneously → migrations MUST be backward-compatible
  • ❌ Rollback = another rolling deploy (slower)
  • ❌ Harder to fully validate before serving traffic
⚠️ The Critical Misunderstanding: "We do blue-green, so migrations aren't a concern." WRONG. Blue-green still means you have old code (the Blue environment) running and pointing to the same database during and right after the flip. If your migration removed a column Blue was using, Blue breaks. Backward-compatible migrations are required for BOTH strategies.

💀 Unpacking that warning — the hardest idea on this page

Most people nod at that box without understanding it. Here it is, step by step.

① What gets duplicated — and what does NOT

Blue-green duplicates the servers running your code. It does NOT duplicate the database.

🔵 BLUE 🟢 GREEN (old code) (new code) │ │ └────────┬────────────┘ ▼ 🗄️ DATABASE (THERE IS ONLY ONE)
🍳 Two shops — but ONE kitchen. Why not duplicate the DB too? Because the data would instantly diverge: customer A orders at BLUE → the order lands in BLUE's database. Customer B orders at GREEN → it lands in GREEN's. Now your orders live in two different places. Who merges them? 😱 So: two shops, one shared kitchen. Mandatory.
② Why is BLUE still running after the flip?

This is where people get lost. "Flipping the doorman's sign" is NOT the same as shutting BLUE down.

before: 👮 sends users → 🔵 BLUE (GREEN idle, but ALIVE) after: 👮 sends users → 🟢 GREEN (BLUE has no users, but STILL ALIVE)

The doorman only redirects people. Both shops still have the lights on, and both are still plugged into the kitchen.

🔙 Why not kill BLUE immediately? Because BLUE is your rollback button. If GREEN misbehaves you flip back in 2 seconds. Kill BLUE and you've thrown away your undo. So BLUE lives on for hours or days — still connected to the database. ⚡
③ Now you can see the bomb 💥

You run a migration that drops the phone column. Watch the timeline:

🕐 10:00 DB has the `phone` column. BLUE is serving customers. 🕑 10:05 You run the migration: DROP COLUMN phone 🗄️ The DB no longer has `phone`. But BLUE (old code) is STILL RUNNING, STILL SERVING USERS. BLUE asks the DB: "give me the phone column" DB replies: "what phone? I don't have that." → 💥 BLUE EXPLODES. Site down. (and you haven't even flipped to GREEN yet!)
The migration ran against the shared kitchen — so it wrecked the shop that was still serving customers. Blue-green cannot save you, because it duplicates the shops, not the kitchen. 🍳
④ The fix — split it into two deploys

Never delete something that currently-running code still needs.

📅 Deploy #1 — change CODE only, don't touch the DB → new code stops using `phone` → ship it. The `phone` column still exists (just sits there unused) → old code still reads phone ✅ new code ignores it ✅ BOTH can live with this database. ← the bridge 📅 Deploy #2 — days later, once the old code is fully dead → nobody asks for `phone` anymore → NOW you drop the column. Safe. ✅
🎯 "Backward-compatible" simply means: after the migration runs, the OLD code still works. In Deploy #1 the column is still there, so the old code is happy. That's it.
⑤ Wait — this is the same shape as Expand–Contract 🤯

Put the two stories side by side. In Part 3: Migrations we were adding a column. Here we are dropping one. Same skeleton:

A. ADD a column (Migrations)B. DROP a column (Deployment)
Who is "the old"?old rows (still empty)old code (BLUE)
Who is "the new"?new rows (filled in)new code (GREEN)
First beatadd column, allow empty → old rows still validship new code, keep the column → old code still runs
What it creates🤝 a phase where old + new both work🤝 a phase where old + new both work
Final beatenforce NOT NULLdrop the column
Allowed only when…the old has vanished (no empty rows)the old has vanished (old code dead)

Same mould. Story A worries about old data; story B worries about old code. Both refuse to jump straight from old to new — they always insert a bridge:

❌ FORBIDDEN: ✅ ALWAYS: [ OLD ] ───💥──► [ NEW ] [ OLD ] ──► [ OLD + NEW ] ──► [ NEW ] jumping straight = boom ▲ the BRIDGE: both can live here. Stay until the OLD is fully dead.
🌉 Why must there be a bridge? Because you cannot change the code and the database at the same instant. One always moves first. During that gap, old and new are forced to coexist.
· Migrations: the DB moves first, old rows aren't filled yet → the column must allow empty.
· Deployment: the code moves first, old code isn't dead yet → the column must stay.
Same truth. Same cure. 🔥
💊 The pill to remember

ADDING is free. DELETING, TIGHTENING or RENAMING must WAIT.

  • Add a column / add room → breaks nobody → do it now.
  • Delete / tighten / rename → breaks whoever is still using it → wait until they're gone.

That is Expand (widen, free) → Contract (tighten, must wait). Both stories are the same pattern.

🧵 The closing line for the interview: "Blue-green and rolling solve code downtime. Neither solves database downtime — because the database is always shared between old and new. So backward-compatible migrations are mandatory for both strategies."
⚙️ Part 3: Gunicorn — Workers Formula + Why Not runserver

🚫 Never Use manage.py runserver in Production

The Django development server is: (1) single-threaded — one request at a time, (2) not security-audited, (3) not designed for load. It will collapse under real traffic. This is a hard filter question in every interview.

Gunicorn Workers Formula

workers = (2 × CPU_cores) + 1

Starting point for CPU-bound Django apps. Tune based on your request mix and memory available per container.

Example: 2 vCPU container → 5 workers. Add --max-requests 1000 --max-requests-jitter 50 to recycle workers and prevent memory leaks from growing unbounded.

# WSGI (synchronous — right for 95% of Django apps) gunicorn config.wsgi \ --bind 0.0.0.0:8000 \ --workers 3 \ --worker-class sync \ --max-requests 1000 \ --max-requests-jitter 50 \ --timeout 30 \ --keep-alive 5 # ASGI (async — websockets, SSE, or many slow upstream calls) uvicorn config.asgi:application \ --host 0.0.0.0 \ --port 8000 \ --workers 4 \ --loop uvloop # When to use ASGI instead of WSGI: # - WebSockets (real-time features) # - Server-Sent Events (live feeds) # - Many concurrent slow I/O calls per request (external APIs) # - For 95% of CRUD apps: WSGI (Gunicorn) is correct
🎯 Part 4: All Interview Questions Answered
⭐ HIGH FREQUENCY
Q1: "How do you deploy your Django app?" (Universal opening question of every senior interview)
▼
❌ WEAK
"I push to GitHub and Heroku/Railway deploys it." (Stops there. Can't go deeper if pressed.)

Shows you've used a tool but don't understand what's happening inside it.
✅ SOLID — LAYER IT
1
CI pipeline fires — push to main → GitHub Actions: tests vs real Postgres → lint → security scan → check --deploy → makemigrations --check
2
Image built + tagged with SHA → pushed to ECR. every deploy is immutable
3
Migrations as separate ECS one-off task — runs manage.py migrate before new service tasks start. Never inline with app startup.
4
ECS rolling update — new tasks start, pass /health/ check, ALB routes → old tasks drain. No downtime.
⟳
Rollback = re-deploy previous SHA image — ~90 seconds, no rebuild, no CI run. ECS updates task definition to prior image.
⚡ Production Signal Line — Full ECS Deploy
"For my current production app I use AWS ECS Fargate behind an ALB. Push to main triggers GitHub Actions: tests run vs real Postgres, image built and tagged with Git SHA, pushed to ECR. Deploy job: register new task definition, update service, ECS does rolling update — new tasks start, pass /health/ check, ALB routes to them, old tasks drain. Migrations run as a separate ECS task before new service tasks start. Rollback: re-deploy the previous SHA image — ~90 seconds, no rebuild."
⭐ HIGH FREQUENCY
Q2: "Describe what happens between git push and the user seeing the change."
▼
git push→ webhook fires→ Actions runner→ CI jobs→ build + ECR push→ ECS deploy→ user sees change
1
CI jobs: checkout → Python setup → install → lint → typecheck → security scan → check --deploy → makemigrations --check → Postgres service → pytest
2
If ALL pass: build Docker image → tag with git SHA → push to ECR. immutable artifact
3
Deploy job (main branch only): OIDC → ECR login → register new ECS task definition with new image SHA
4
Run migrations first: ECS one-off task → manage.py migrate completes before service tasks start
5
ECS rolling update: new tasks start → /health/ → ALB routes → old tasks drain. Total: ~5–10 min
⭐ HIGH FREQUENCY
Q3: "What's the difference between blue-green and rolling deployment?"
▼
RollingReplace instances in batches on same infra. Old + new coexist briefly. cheap Default for ECS/K8s. Rollback = another rolling deploy slow. Requires backward-compatible migrations.
Blue-GreenTwo full identical environments. Deploy to idle env, validate, flip ALB all at once. 2× infra cost Rollback = one ALB switch seconds. Used for large/risky releases.
🚫 Trap: "We do blue-green so migrations aren't a problem." Wrong. Blue env still runs during and after the switch — schema must be backward-compatible with Blue's code. Expand-contract required for BOTH strategies.
⭐ HIGH FREQUENCY
Q4: "How do you do a zero-downtime deploy?"
▼
1
Migrations before new code — schema must be backward-compatible with the version currently running. Never run migrations as part of app startup (race condition).
2
/health/ endpoint — returns 200 only when fully ready (DB connected, cache connected). ALB only routes traffic to healthy tasks.
3
Rolling update — ECS replaces tasks one by one, always keeping minimum healthy capacity. Never take everything down at once.
4
Connection draining — ALB drains in-flight requests before killing old tasks. Users don't see connection resets.
What breaks it: non-backward-compatible migration · no /health/ endpoint · all instances replaced simultaneously · migrations inline with app startup
⭐ HIGH FREQUENCY
Q5: "How would you roll back a bad deploy?"
▼
❌ WEAK
"We'd revert the PR and redeploy."

10+ minutes while production is broken. While you're reverting and waiting for CI, users are impacted.
✅ SOLID — SHA-based rollback
⟳
Re-deploy the previous SHA image from ECR — ~90 seconds one command, no rebuild, no CI run. ECS updates task definition to previous image.
⚠
If migration was destructive — can't rollback schema. Need a forward-fix instead. This is why we use expand-contract and never ship destructive schema changes alongside code changes.
⭐ HIGH FREQUENCY
Q6: "Why Gunicorn and not runserver? How many workers?"
▼
✗
runserver is single-threaded — one request at a time, not security-audited, collapses under real traffic. never in prod
✓
Gunicorn = production WSGI server — spawns multiple worker processes. Formula: (2 × CPU cores) + 1. 2 vCPU → 5 workers.
+
--max-requests 1000 --max-requests-jitter 50 — recycles workers to prevent memory growth. Jitter prevents all workers restarting simultaneously.
A
ASGI instead (Uvicorn) when: websockets · server-sent events · many concurrent slow upstream I/O calls. For 95% of CRUD apps: WSGI/Gunicorn is correct.
NICE TO KNOW
Q7: "Static files — where do they live and who serves them?"
▼
CI
collectstatic in CI/CD gathers all static files into STATIC_ROOT before building the image.
S3
S3 + CloudFront (preferred for scale) — CI uploads to S3, CloudFront CDN serves globally. Django never serves static STATIC_URL points to CloudFront. django-storages handles upload.
WN
WhiteNoise (simple/small scale) — Python middleware serving static files directly from Gunicorn. Adds compression + caching headers. Add to MIDDLEWARE after SecurityMiddleware. No extra infra.
🚫 Never: Serve static via Django views in production. Development-only (serve() function). No caching headers, no compression, poor performance.
🏆 The Six Things That Kill Candidates in These Interviews
  1. No specific stories — "I've used Docker" with no incident. Stories + numbers win.
  2. No numbers — "It was slow" → "P95 was 1.2s, we got it to 180ms with select_related + an index."
  3. Tools over outcomes — "We used Kubernetes and Sentry and Datadog" doesn't say what YOU did.
  4. Vague about own role — "We did X" is a flag. "I owned X" is what they're listening for.
  5. Can't read an error — "Exit code 137? Not sure, I restart." → FAIL. "OOMKilled, check memory limits." → PASS.
  6. No mental model of failure — If you've only built the happy path, you've only built half the system.
