🔑 Part 1: The Three-Way Distinction — CI vs CD (Delivery) vs CD (Deployment)

⚠️ Gate Question: Interviewers use this to filter. If you say "they're the same thing" — the interview is usually over. Know ALL THREE cold.

🔄

Continuous Integration

WHAT: Developers merge code to main frequently (multiple times a day). Every push triggers automated build + tests.

GOAL: Keep the trunk green. Catch regressions immediately.

"The pipeline tells you within minutes if your code broke something."

📦

Continuous Delivery

WHAT: Every passing build produces a deployable artifact that could go to prod with one button press. But a human gates the release.

WHEN TO USE: Right default for most teams — lets you batch risky changes, use deploy windows, or wait for feature flags.

"The artifact is always ready. Humans decide when."

🚀

Continuous Deployment

WHAT: Every green build on main automatically goes to production. Zero human gate.

REQUIRES: Strong test suite + feature flags + good observability + auto-rollback.

"Every commit ships. You need mature safeguards first."

The Trade-off in one sentence: Delivery = velocity with human safety gate. Deployment = maximum velocity, requires maximum safeguards. For most teams, Delivery is right — full Deployment is a goal you work toward, not a day-one choice.

📄 Part 3: GitHub Actions YAML — Line by Line

When asked to "walk through a GitHub Actions workflow for Django" — here's the exact YAML with what each section does and why:

# .github/workflows/ci.yml name: CI/CD Pipeline on: push: branches: [main] # Run on merge to main pull_request: branches: [main] # Run on every PR targeting main jobs: test: runs-on: ubuntu-latest # ── STEP 1: Spin up PostgreSQL service container ── services: postgres: image: postgres:15 # PINNED version — no surprises env: POSTGRES_DB: testdb POSTGRES_USER: testuser POSTGRES_PASSWORD: testpass options: >- # Health check — wait for DB ready --health-cmd pg_isready --health-interval 10s --health-timeout 5s --health-retries 5 ports: - 5432:5432 steps: # ── STEP 2: Checkout code ── - uses: actions/checkout@v4 # ── STEP 3: Setup Python with dep caching ── - uses: actions/setup-python@v5 with: python-version: '3.12' cache: 'pip' # Cache ~/.cache/pip by requirements hash # ── STEP 4: Install deps ── - run: pip install -r requirements.txt # ── STEP 5: Lint ── - run: ruff check . && black --check . # ── STEP 6: Type check ── - run: mypy . # ── STEP 7: Security scan ── - run: pip-audit && bandit -r . -x ./tests # ── STEP 8: Django deployment check ── - run: python manage.py check --deploy # ── STEP 9: Migration committed check ── - run: python manage.py makemigrations --check --dry-run # Fails if model changed but migration not committed — catches deploy bombs # ── STEP 10: Run tests vs REAL PostgreSQL ── - run: pytest --tb=short -q env: DATABASE_URL: postgres://testuser:testpass@localhost:5432/testdb DJANGO_SETTINGS_MODULE: config.settings.test build-and-push: needs: [test] # ← THIS is the gate. No test pass = no image if: github.ref == 'refs/heads/main' # Only build on main runs-on: ubuntu-latest permissions: id-token: write # For OIDC — no long-lived AWS keys contents: read steps: - uses: actions/checkout@v4 # ── OIDC: Get temporary AWS credentials (no stored keys!) ── - uses: aws-actions/configure-aws-credentials@v4 with: role-to-assume: arn:aws:iam::123456789:role/github-actions-role aws-region: ap-southeast-1 - uses: aws-actions/amazon-ecr-login@v2 # ── Build + tag with Git SHA for exact rollback ── - run: | IMAGE="$ECR_REGISTRY/$ECR_REPO:${{ github.sha }}" docker build -t $IMAGE . docker push $IMAGE echo "IMAGE=$IMAGE" >> $GITHUB_ENV # ── Deploy to ECS ── - uses: aws-actions/amazon-ecs-deploy-task-definition@v1 with: task-definition: task-def.json service: my-django-service cluster: production wait-for-service-stability: true
💡 Key pattern: needs: [test] is the dependency edge. The pipeline is a DAG — when the test job fails, GitHub Actions marks all downstream jobs as "skipped" (not cancelled). The Docker image is never built. ECR never receives the bad code. Production stays safe.
🎯 Part 4: All High Frequency Interview Questions — Answered
⭐ HIGH FREQUENCY
Q1: "What's the difference between Continuous Integration, Continuous Delivery, and Continuous Deployment?" (Gate question — if you say "they're the same thing" the interview is usually over.)
▼
❌ WEAK ANSWER
"CI/CD means automated testing and deployment. They go together."

That answer tells the interviewer you've heard the buzzword but can't distinguish the three. This is a filter question.
✅ SOLID ANSWER — THREE DISTINCT THINGS
CIMerge frequently to main with automated build + test on every push. Goal: keep the trunk green. Catches regressions within minutes.
DeliveryEvery green build = deployable artifact, but a human gates the release. One button press to prod. Default for most teams — lets you batch risky changes.
DeploymentEvery green build → prod automatically. No human gate. Requires: strong tests + feature flags + observability + auto-rollback. Goal to work toward, not day-one choice.
⭐ HIGH FREQUENCY
Q2: "Walk me through a GitHub Actions workflow for a Django project."
▼

The solid answer hits FIVE things:

  1. Trigger: on push to main and on pull_request targeting main
  2. PostgreSQL service container: Not SQLite — spin up postgres:15 with a health check that waits for pg_isready before tests run
  3. Dependency caching: Cache ~/.cache/pip based on the requirements.txt hash — this takes reruns from 4 minutes to 30 seconds
  4. The quality gates before tests: ruff/black, mypy, pip-audit, bandit, manage.py check --deploy, makemigrations --check --dry-run
  5. The blocking gate: needs: [test] on the build job — test fails = no Docker image, no deploy
🚫 Trap to avoid: Don't say you test against SQLite. "SQLite behaves fundamentally differently than PostgreSQL — different JSON field handling, concurrent transactions, date/time functions. Testing on a different engine guarantees eventual production bugs."
⭐ HIGH FREQUENCY
Q3: "What happens when a test fails in your pipeline? What gets blocked?"
▼
❌ WEAK ANSWER
"The pipeline goes red and I look at the logs."

Doesn't mention the blocking mechanism. Doesn't show understanding of how the DAG structure prevents deployment.
✅ SOLID ANSWER
1needs: [test] blocks the build job — test failure short-circuits the DAG. No Docker image built, nothing pushed to ECR.
2Required status check on main — PR gets a red check and is blocked from merging automatically. No manual intervention needed.
!No auto-retry on flaky tests — that hides bugs. Quarantine the test (@pytest.mark.skip), file a ticket, investigate root cause.
+Pin Postgres service to postgres:15 — prevents a base image bump from silently breaking tests between runs. pin versions
⚡ Production Signal Line
"Our pipeline tags every image with the Git SHA and pushes to ECR, so rollback is just re-deploying the previous tag — never a 'git revert and rebuild.' I also added makemigrations --check --dry-run as a required job so the build fails if someone forgets to commit a migration file."
⭐ HIGH FREQUENCY
Q4: "How do you handle secrets in CI? How does the pipeline access AWS without storing long-lived keys?"
▼

Three levels of answer — go from basic to OIDC:

❌ Never do this: Paste an AWS key into a workflow .yml file. Even in a "private" repo — git history is persistent, people get access to repos, and automated scanners find these within seconds.
✅ Basic (acceptable): GitHub Actions Secrets — encrypted at rest, injected as environment variables at job time, never visible in logs. Set in repo Settings → Secrets.
✅✅ Senior-level (OIDC): "We use OIDC federation — GitHub Actions presents a short-lived OIDC token to AWS, assumes an IAM role, and gets temporary credentials (max 1 hour). There's no long-lived AWS_ACCESS_KEY_ID stored anywhere. The role's trust policy is scoped to our specific repo and branch — token.actions.githubusercontent.com:sub: repo:org/repo:ref:refs/heads/main. Even if the token is somehow captured, it expires in under an hour and can only assume the specific role."
🚫 Trap: Long-lived AWS keys in CI become permanent exposure risks. When a developer leaves, keys are rarely rotated. When a repo becomes public accidentally, keys are scraped in seconds.
⭐ HIGH FREQUENCY
Q5: "Tell me about a time a deployment failed. What did you do?"
▼

The structure of a great answer: WHAT failed → WHY it failed → HOW you fixed it → WHAT you changed to prevent recurrence

"Our first blue-green deploy failed because the new code expected a column the migration hadn't applied yet — we'd put the migration in the same release as the code change. The new tasks failed health checks, ECS rolled back to the old tasks automatically — so no user impact, but the deploy failed. Postmortem: we split migrations into a pre-deploy phase that runs before traffic shifts. We made all code changes backward-compatible with the previous release for one cycle. And we added a smoke test that runs manage.py migrate --check and hits /health/ on the new tasks before the load balancer flips. We haven't had a deploy-induced outage since."

Why this works: Specific failure mode (migration/code coupling) + what saved you (ECS auto-rollback) + structural fix (pre-deploy migration phase) + prevention (smoke test). Concrete, teachable, professional.

NICE TO KNOW
Q6: "Why is OIDC preferable to long-lived AWS keys for CI? How does it work?"
▼

OIDC (OpenID Connect) is identity federation — GitHub acts as an identity provider. Here's how it works:

🐙
GitHub Actions Job
Requests OIDC token from GitHub
→
🪙
Short-lived JWT
Contains: repo, branch, workflow info
→
🔑
AWS STS AssumeRole
Verifies JWT, checks trust policy
→
⏱️
Temp Credentials
Valid ≤1hr. Scoped to specific role.

The benefit: No secret stored anywhere. The IAM role's trust policy can be scoped to your exact repo and branch — an attacker who compromises a different repo gets nothing. Credentials expire in under an hour. When a developer leaves, you don't need to rotate an access key they had.

NICE TO KNOW
Q7: "How do you handle flaky tests in CI? What's your strategy?"
▼
❌ Wrong answer: "We auto-retry the test X times." — This hides bugs. A test that passes on the second try is hiding a real problem.
✅ Right answer: "We quarantine it — mark it as @pytest.mark.skip or move it to a separate suite that doesn't block the main CI. File a ticket immediately. The test runs in a side pipeline so we can still measure flake frequency. Then we investigate: is it a timing issue? A real race condition in the code? An environment dependency (e.g., tests that depend on test order)? We fix the root cause, not the symptom. A flaky test that auto-retries is a lie in your test suite."
NICE TO KNOW
Q8: "How would you roll back a bad deploy? Walk me through the process."
▼
❌ WEAK ANSWER
"We'd revert the PR and redeploy."

This takes 10-15 minutes minimum. While you're reverting and CI is re-running, users are broken.
✅ SOLID ANSWER
1Every image tagged with Git SHA in ECR. Rollback = re-point ECS at the previous tag: aws ecs update-service --task-definition prev-sha
✓~90 seconds to roll back. No rebuild, no CI re-run, no git revert. Just deploy a known-good image. fast rollback
!If migration was destructive: rollback might break the schema. Use expand-contract — never ship destructive schema changes alongside code changes for exactly this reason.
⚠️ Part 5: Common Traps That Kill Candidates
🚫 Trap 1: Testing against SQLite
SQLite ≠ PostgreSQL. JSON fields, concurrent transactions, date functions behave differently. Always test on the same engine you deploy.
🚫 Trap 2: Auto-retrying flaky tests
Hides real bugs. Quarantine + investigate instead. A green test that passed on retry 3 is a lie.
🚫 Trap 3: Secrets in workflow YAML
Even in private repos. Use GitHub Secrets or OIDC. Never paste AWS_ACCESS_KEY_ID in a .yml file.
🚫 Trap 4: Building per environment
Image should be built ONCE, tagged with SHA, promoted across envs. Build-in-staging ≠ build-in-prod = "works in staging, breaks in prod."
🚫 Trap 5: No rollback story
"We'd revert the PR" takes 10+ minutes. Right answer: re-deploy previous SHA image in ~90 seconds.
🚫 Trap 6: Not waiting for DB health check
Postgres service container takes time to initialize. Without pg_isready health check, tests run before DB is ready → "Connection Refused" on first run.
🚫 Trap 7: CI = tests only
Production CI also runs: manage.py check --deploy, makemigrations --check --dry-run, ruff/black, mypy, pip-audit, bandit. Tests are one step.
🚫 Trap 8: Migration not committed
Model changed but migration file not added to commit. Deploy blows up on startup. makemigrations --check --dry-run in CI catches this.
🔥 Part 6: Production Signal Lines — The Exact Sentences That Win Interviews
🔥 CI/CD Signal Line

"Our pipeline tags every image with the Git SHA and pushes to ECR, so rollback is just kubectl set image or re-deploying the previous tag — never a 'git revert and rebuild.' I also added python manage.py makemigrations --check --dry-run as a required job so the build fails if someone forgets to commit a migration file."

Why it works: SHA tagging = rollback story. The migration check = you've been burned before and built prevention. Both are things you only add after incidents.

🔥 PostgreSQL in CI Signal Line

"To guarantee testing parity and prevent regressions, our GitHub Actions pipeline spins up a PostgreSQL service container, explicitly waits for the pg_isready health check, caches dependencies based on the lockfile hash, and runs the test suite against a real database rather than falling back on SQLite."

🔥 OIDC Signal Line

"We switched from GitHub Actions Secrets holding a long-lived AWS key to OIDC federation — the pipeline presents a short-lived OIDC token, assumes a scoped IAM role, and gets temporary credentials. There's no long-lived key stored anywhere. When our last junior dev left, we didn't have to rotate a single CI secret."
