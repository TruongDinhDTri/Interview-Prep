Secrets & Environment Variables

Three-layer secrets architecture. How secrets actually leak (7 vectors). OIDC vs long-lived keys. Exactly what to say when asked about a committed AWS key.

🏗️ Part 1: The Three-Layer Architecture

This is the complete answer to "Where do you store your SECRET_KEY and database credentials?"

🔑 Step 0 — What even is a "secret"?

A secret is a key to your house: your Django SECRET_KEY, the database password, an AWS key. Whoever holds that string of characters has full access — exactly like whoever picks up your house key can walk in. 🏠

🤔 So where do you keep the key?

Here's the catch: your code runs in three different places, and each place has a different level of danger:

💻 Your laptop (local dev)Only you are here. Low danger.
⚡ The build server (CI/CD)A robot runs your code; logs are readable. Medium danger.
🏭 The real server (production)The open internet. Hackers. 😈 Maximum danger.
🎯 The higher the danger, the fancier the key storage must be. That's all "Three-Layer Architecture" means — not three layers stacked on top of each other, but three different PLACES, each with its own way of hiding the key.

🖥️ Layer 1: Local Development

  • .env file — in .gitignore, NEVER committed
  • .env.example — committed, lists variable names with no values
  • Loaded via: django-environ or python-dotenv
  • Why OK here: Local only, not shared, not in git
🗝️ In plain words — "keep the key in your desk drawer." Low danger, so keep it simple: put the key in a .env file on your machine.
.env ← the REAL key. DB_PASSWORD=super_secret_123 .env.example ← a FAKE key. DB_PASSWORD=
· .env goes in .gitignore — never pushed to git. Push it and the whole world sees it. 💀
· .env.example is pushed, because it lists only variable NAMES, no values. A new teammate sees "ah, I need to fill in these 5 things" — without ever seeing a password.
It's like handing a friend a list saying "you'll need a front-door key and a back-door key" — instead of handing them the actual keys.
· django-environ is just the library that reads the .env file into Django.

⚡ Layer 2: CI/CD Pipeline

  • GitHub Actions Secrets — encrypted at rest, injected as env vars at job time
  • Never visible in logs — GitHub masks known secrets automatically
  • Better: OIDC federation for cloud providers — no long-lived keys stored at all
  • Org-level secrets for secrets shared across multiple repos
🤖 In plain words — "handing a key to a robot." The GitHub Actions robot needs an AWS key to deploy. Where does it live?

Basic way — GitHub Actions Secrets: you paste the key into GitHub's "Secrets" box. GitHub locks it in a vault (encrypted), hands it to the robot only while the job runs, then takes it back. Bonus: if the robot accidentally prints it in a log, GitHub blacks it out as ***. 🖤

Better way — OIDC: don't store a key at all.
🎫 Instead of giving the robot a permanent key, give it a visitor badge that expires in an hour. The robot shows the badge to AWS → AWS checks "yep, that's the robot from this exact repo" → issues a temporary key valid for 1 hour → it self-destructs.
🔥 No stored key = nothing to leak. That's the sentence that scores points in the interview.

🏭 Layer 3: Production

  • AWS Secrets Manager (or SSM Parameter Store) — secrets fetched at container startup, never on disk
  • Identity-based access: App's IAM role has secretsmanager:GetSecretValue on its own secret only
  • Values exported as env vars to the Django process — never in source
  • Rotation: Secrets Manager can auto-rotate credentials on a schedule
🏦 In plain words — "a bank vault." This is where the hackers are. The key must never sit on the server's disk.

AWS Secrets Manager is a central vault. The key lives inside the vault, not inside your server. When the app boots, it walks up to the vault, asks for the key, receives it, and holds it only in RAM. There is no key file on disk anywhere. ✅
💎 "Identity-based access" — the hardest line on this page. Read slowly.

Two completely different ways a vault can decide whether to open:

🔴 Old way: a PASSWORD
"whoever knows this string gets in"
The vault's password is abc123.
ANYONE who knows abc123 can open it — you, a teammate who quit, a hacker who found it on GitHub.

The vault doesn't care who you are. It only checks that you typed the right letters. 😰
🟢 New way: an IDENTITY
"only THIS exact one gets in"
The vault has a fingerprint scanner. 🖐️
It never asks for a password. It asks: "WHO are you?"

Only the app actually running on ECS has that fingerprint. A hacker could steal the entire vault and it's useless — they don't have the finger.
That "fingerprint" is what AWS calls an IAM role. And secretsmanager:GetSecretValue means: "this fingerprint may open exactly one drawer" — not the whole vault.
🎁 Three benefits fall out of that — these are the last three claims in the box below:
"Blast radius is isolated"App gets hacked → the attacker can open only that app's one drawer, never the others. One room burns, not the house. 🔥
"Rotation is automated"The vault changes the DB password itself every 30 days. The app never notices — it just shows its fingerprint and always receives the newest one.
"Nothing to rotate when a developer leaves"Someone quits → revoke their badge, done. No sprinting around changing every password in the company — because they never held a password. They only ever had an identity. 👋
🧵 The one sentence that ties all three layers together

Move from "something you KNOW" (a password — anyone who finds it can use it) to "something you ARE" (an identity — only you have it).
.env (local) → GitHub Secrets / OIDC (CI) → Secrets Manager + IAM role (prod).
The more dangerous the place, the more it leans on identity. 🔑→🖐️

💡 Notice: OIDC (Layer 2) and IAM roles (Layer 3) are the SAME idea — replace a secret string with a time-limited identity. Two layers, one principle.

The Key Principle: Identity-based access — the app proves who it is via its IAM role and gets the secret. Instead of "here's a password that anyone with the string can use," it's "only this specific ECS task role can read this secret." Blast radius is isolated, rotation is automated, there's nothing to rotate when a developer leaves.
🚨 Part 2: How Secrets Actually Leak — 7 Vectors

🚫 Vector 1: Committed .env (Most Common)

Developer adds .env to git, forgets to gitignore it. GitHub push protection catches it — but git push --no-verify bypasses protection. Automated bots scrape GitHub and find it within seconds (Comparitech: "just one minute").

🚫 Vector 2: Hardcoded in Source

"Just temporarily." Once committed, it's in git history forever. git rm does NOT remove from history. Only git filter-repo rewrites history, and even then — if anyone cloned/forked before, they have it.

🚫 Vector 3: Baked into Docker Image

ENV AWS_SECRET_KEY=... in Dockerfile. Image pushed to registry. Anyone with pull access can extract with docker history --no-trunc. Even if you remove the layer, it's in the registry's blob store.

🚫 Vector 4: In CI Logs

Secret accidentally echoed in a shell script (echo $AWS_SECRET_KEY). GitHub masks known secrets but NOT derivatives (base64 encoded, truncated). Visible in build logs.

🚫 Vector 5: DEBUG=True in Production

Django's debug page shows ALL loaded environment variables (except ones matching SECRET|PASS|TOKEN pattern). Any unhandled 500 error exposes your entire settings module to whoever triggered it.

🚫 Vector 6: In Sentry / Log Aggregation

Request bodies and tracebacks captured by error tracking can include passwords, tokens, PII. Configure scrubbing: send_default_pii=False and a custom before_send scrubber in Sentry config.

🚫 Vector 7: Force-pushed / Retained Git Commits

GitHub retains "oops commits" even after force-push for some time. Researchers have built tools to scrape them. Treat any pushed commit as permanently public — even after removal.

🚨 Part 3: Incident Response — Accidentally Committed AWS Key

When asked "What do you do if you accidentally commit an AWS access key?" — this is the step-by-step response:

  • ⚡
    Step 1: Assume immediate compromise Don't think "maybe no one saw it." Bots scrape GitHub continuously. If it was public for even 1 minute, assume it's been used. Comparitech's honeypot: AWS keys exploited "in just one minute."
  • 🔑
    Step 2: Revoke the key immediately in AWS IAM Console → IAM → Users → Security credentials → Make inactive / Delete. AWS also auto-applies AWSCompromisedKeyQuarantine policy when it detects leaked keys — but don't wait for that.
  • 🔍
    Step 3: Audit CloudTrail CloudTrail → filter by the compromised key's access key ID → look for unauthorized actions (EC2 launches, S3 access, IAM changes, anything in unusual regions).
  • 🧹
    Step 4: Rewrite git history Use git filter-repo (NOT git filter-branch) to remove the commit. Force-push. But remember: if the repo was public even briefly, the key is out. History rewrite only helps going forward.
  • 🔄
    Step 5: Rotate all dependent services Anything that was using the old key — update it to use new credentials. Check for any services that had the old key hardcoded.
  • 🛡️
    Step 6: Structural fix — move to OIDC The real fix: eliminate long-lived keys entirely. Move CI to OIDC federation. Move production to IAM roles (EC2/ECS instance profiles). Nothing to leak if no long-lived credentials exist.

⭐ HIGH FREQUENCY
Q2: "What's the difference between a .env file, platform environment variables, and a secrets manager?"
▼
.env filePlain text on disk, loaded at startup. great for local Zero infra. bad for prod Readable by anyone with server access, not versioned safely, doesn't rotate — if server is compromised, file is compromised.
Platform varsECS task env / Heroku config vars — injected at runtime, not on disk. better than files But visible via /proc/<pid>/environ on Linux. No rotation. Security posture depends on platform.
Secrets MgrCentralized — stores, rotates, audits access. App fetches via SDK at startup. Access via IAM roles, not passwords. Full audit log. Auto-rotation available. best option Blast radius isolated per-service.

⭐ HIGH FREQUENCY
Q4: "How do you give your CI pipeline access to AWS without storing long-lived keys?"
▼
1
OIDC federation — GitHub Actions acts as an identity provider. When a job runs, GitHub issues a short-lived JWT signed by GitHub's OIDC provider. no stored keys
2
AWS trusts GitHub's OIDC provider — configured in IAM with a trust policy that locks down: which repo, which branch, which environment. The job presents the token to AWS STS.
3
STS returns temp credentials ≤ 1hr — scoped to a specific IAM role. Credentials expire automatically. Nothing to rotate when a developer leaves. no blast radius
FLOW: GitHub OIDC JWT→ STS AssumeRoleWithWebIdentity→ Temp creds (≤1hr)→ Deploy to AWS
