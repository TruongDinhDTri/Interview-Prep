🔒 Part 1: PostgreSQL Lock Types — Why Migrations Cause Downtime

The root of every migration disaster: you didn't know which SQL operation acquires which lock.

🍜 First, forget SQL — think of a noodle shop

Your orders table is a packed noodle shop. Customers = your app reading & writing rows (SELECT, INSERT) — happening every second. A repairman = your migration, changing the shop's structure. When someone works, they hang a sign on the door. That sign is the lock. There are three signs:

🔴 ACCESS EXCLUSIVE — "SHOP CLOSED. EVERYONE OUT."
The repairman is jackhammering the floor. Diners already eating must leave. Nobody new gets in. No reads, no writes — your website is down. Hung by ALTER TABLE, DROP TABLE — anything that changes the table's shape. The dangerous sign.
🟡 SHARE UPDATE EXCLUSIVE — "PAINTER AT WORK"
Someone is painting the side wall. Customers keep eating, totally unaffected. The only person blocked is another repairman (so two migrations don't trip over each other). Reads ✅ writes ✅ — the safe sign.
🟢 ROW EXCLUSIVE — "THIS TABLE IS TAKEN"
You sit at table #5 and put a sign on table #5 only. The other 99 tables run as normal. This is what your app hangs on every single UPDATE. Harmless.
🎯 So where's the disaster? A migration is the repairman — and repairmen love hanging the 🔴 CLOSED sign, then working for three minutes. The whole art of safe migrations is one sentence: never hold the red sign for long.
Lock TypeWhat It BlocksWhen It HappensRisk
ACCESS EXCLUSIVE Everything — reads AND writes ALTER TABLE, DROP TABLE, ADD COLUMN NOT NULL (Postgres <11), most ALTER COLUMN MAXIMUM — all traffic blocked
SHARE UPDATE EXCLUSIVE Schema changes, VACUUM FULL CREATE INDEX CONCURRENTLY, VALIDATE CONSTRAINT LOW — reads/writes continue
ROW EXCLUSIVE Other row-level locks INSERT, UPDATE, DELETE (normal DML) MINIMAL — normal operations
💡 The Key Insight: PostgreSQL 11+ changed ADD COLUMN with a constant default to be metadata-only (no ACCESS EXCLUSIVE). But ADD COLUMN NOT NULL without a default (or with a non-constant default) still rewrites the table. This is why you always add as nullable first on large tables.
🔍 In plain words — why NOT NULL is the killer:
ADD COLUMN status VARCHAR(20) → just edits the catalog. milliseconds. SAFE ✅ ADD COLUMN status VARCHAR(20) NOT NULL → must go FILL all 50M old rows. minutes. DEATH ❌
NOT NULL means "this column may never be empty." Postgres panics: "I have 50 million old rows sitting there empty — you say empty is banned? Then I must go write a value into every single one of them first." So it hangs the 🔴 red sign and rewrites the whole table.
👉 The rule: on a big table, ALWAYS add the column as nullable first. That is the seed of the entire Expand–Contract pattern below.
🔄 Part 2: The Expand-Contract Pattern — 3 Deploys for Zero Downtime

The answer to "How do you add a non-nullable column to a 50M-row table without downtime?" — the single most asked migration question:

🎬 The concrete scenario (same noodle shop)

Table orders has 50 million rows. Your boss says: "Add a status column. And every order MUST have one — empty is forbidden." That "empty is forbidden" is NOT NULL — and it's what blows everything up. 💥

❌ The naive way (all in one shot): "Add column status, and forbid empty!"
Postgres freaks out: "I have 50M old rows, they're all empty, and you're banning empty?! Then I must go fill every single one first." → hangs the 🔴 CLOSED sign → grinds for 3 minutes → 3 minutes of dead website. Customers rage. Boss calls. 😱
✅ The core idea — read this twice:
Never change the shape AND fill the data at the same time. Changing shape → red sign. Filling data → takes forever. Glue them together = red sign held forever = death. Split them apart and both become harmless.

📋 After Deploy 1, the table looks like this — column exists, but it's completely empty:

orders ┌────┬──────────┬────────┐ │ id │ customer │ status │ ← the NEW column, currently empty ├────┼──────────┼────────┤ │ 1 │ An │ NULL │ NULL = an empty cell │ 2 │ Bình │ NULL │ │ 3 │ Cường │ NULL │ │ .. │ ... │ NULL │ (50 million rows — ALL empty) └────┴──────────┴────────┘

🔵 Deploy 1: EXPAND — "widen the table"

Do: add the status column, but allow it to be empty (null=True).

ALTER TABLE orders ADD COLUMN status VARCHAR(20)

Why it's safe: Postgres shrugs — "Empty is allowed? Then I don't touch a single one of the 50M old rows. I just write one line in the catalog."

⚡ Milliseconds. Zero rows touched. The 🔴 red sign is hung — but it's gone in a blink, so nobody notices.

🤝 The bridge it creates: old code (doesn't know status) and new code (writes status) both work now — the column allows empty, so old code just leaves it blank. That coexistence IS what makes zero-downtime possible.

Why "EXPAND"? You widen the table — make room — without forcing anything on anybody yet.

→

🟡 Deploy 2: BACKFILL — "fill it up"

Do: write 'pending' into those 50 million empty cells.

😱 One shot = death: UPDATE orders SET status='pending' touches all 50M rows in one go, holding the lock till the last row (~3 min). 🚚 Like carrying a 1-ton boulder — it jams the whole road.
✅ Batches instead:
UPDATE 5,000 rows → RELEASE LOCK → breathe UPDATE 5,000 rows → RELEASE LOCK → breathe ⋮ (10,000 times = 50M rows)
🧱 10,000 small bricks, not one boulder. Each batch holds only the harmless 🟢 sign, for ~1 second. The road is never blocked.
🔑 Why it must live OUTSIDE the migration file: Django wraps a whole migration file in ONE transaction — it runs everything, then releases the lock once. So batching inside a migration is pointless; Django fuses all 10,000 batches into one 3-minute lock.

👉 Batching only helps if each batch releases its lock — and to release it, you must escape the migration. Use a management command.

✔️ Verify: count the empty cells. Any left? Do not proceed. Zero left? Safe — because Deploy 3 bans empty, and one leftover would make it explode. 💥

→

🟢 Deploy 3: CONTRACT — "tighten the rule"

Do: now enforce "status may never be empty."

😱 The direct way (SET NOT NULL): Postgres must scan all 50M rows to check — while holding the 🔴 red sign. Cruel irony: the data is already correct, but checking means locking.
😷 The mask analogy: you announce "everyone must wear a mask" — but 50M customers are already seated. That's two separate jobs:
A. Post the rule on the door → ⚡ 1 second
B. Inspect the 50M already seated → 🐌 slow
-- Beat 1 = job A: post the rule, don't inspect ADD CONSTRAINT status_not_null CHECK (status IS NOT NULL) NOT VALID; ⚡ 🔴 blink -- Beat 2 = job B: now go inspect old rows VALIDATE CONSTRAINT status_not_null; 🐌 but 🟡 yellow!
⚠️ NOT VALID does NOT mean "the rule is invalid." It means "I haven't checked the OLD rows yet." The rule is already live — every new row is rejected from this instant.
🤔 Why does VALIDATE only need the yellow sign? A lock exists to stop others from ruining your work.

🔴 Direct way: no rule posted → a user sneaks in an empty row behind the scan 😈 → the scan's "all clean!" is a lie. Must block everyone.

🟡 After NOT VALID: the gate is already shut → nobody can sneak one in → the scan can't be ruined → no need to block anyone. (Bonus: VALIDATE only reads. 📖)

Why "CONTRACT"? You tighten the rule back down — empty is no longer allowed.

Django 5+ tip: prefer db_default over default — db_default is a real DB-level default, so no Python-level row rewrite.

🧵 The single thread running through all 3 deploys

A FAST job may hold the 🔴 red sign. A SLOW job must run under 🟡 yellow or 🟢 green.

  • Deploy 1: changes shape (red) — but it's fast ✅
  • Deploy 2: fills data (slow) — so it's batched down to green 🟢 ✅
  • Deploy 3: scans rows (slow) — so NOT VALID pushes it onto yellow 🟡 ✅

At no point do "red sign" and "slow job" ever stand together. That's the whole pattern. 🔥

DeployNameWhat it doesSign hungDuration
1🔵 EXPANDAdd column, empty allowed🔴 but instantaneousmilliseconds

3🟢 CONTRACTTighten the NOT NULL rule🟡 (thanks to NOT VALID)seconds of red, rest yellow

Expand → Fill → Contract. Three gentle beats instead of one lethal one. 🎯

🚫 The Disaster Pattern (what NOT to do): Adding a non-nullable column + RunPython backfill in the SAME migration file. Django wraps the migration in a transaction. The ACCESS EXCLUSIVE lock from ALTER TABLE is held for the entire duration of the RunPython. On 50M rows, that's multiple minutes of zero reads + zero writes.
In shop terms: you hang the 🔴 CLOSED sign to change the shape, then — still holding it — start filling 50 million rows. The sign stays up the entire time. This exact mistake is what the whole Expand–Contract pattern exists to prevent.
📋 Part 3: Pre-Migration Checklist — Memorize All 7 Steps
  • 1
    python manage.py sqlmigrate <app> <num> — Read the actual SQL. Know what DDL is about to run. Is it an ALTER TABLE? INDEX? Does it lock?
  • 2
    python manage.py makemigrations --check --dry-run — Fail if any model changed without a migration committed. Run this in CI so deploy bombs don't reach production.
  • 3
    Run on staging with a recent prod-data dump — Time it. A migration that takes 3 seconds on staging with 1,000 rows can take 45 minutes on prod with 50M rows.
  • 4
    Snapshot the prod database (or confirm PITR is enabled) — If the migration corrupts data, you need to restore. Point-in-time recovery before every major migration.
  • 5
    Check the migration is reversible — Every RunPython needs a reverse_code function. Even if it's migrations.RunPython.noop. Without it you can't roll back.
  • 6
    Ordering: additive migrations BEFORE code, destructive AFTER — New nullable column: deploy migration before new code. Removing a column: deploy code that stops using it first, then migration.
  • 7
    Have the rollback command ready — python manage.py migrate <app> <previous_migration_name>. Know it cold. Don't look it up while prod is burning.
🎯 Part 4: All Interview Questions Answered
⭐ HIGH FREQUENCY
Q1: "Walk me through how you'd add a new non-nullable column to a 50-million-row table in production."
▼
❌ WEAK — INSTANT DISQUALIFIER
"I add the field to the model, run makemigrations, and run migrate on production."

This answer ends the interview. PostgreSQL's ALTER TABLE ... ADD COLUMN ... NOT NULL acquires an ACCESS EXCLUSIVE lock — no reads, no writes — until the column is added and ALL 50M rows are backfilled. Multiple minutes of downtime.
✅ SOLID — EXPAND-CONTRACT (3 DEPLOYS)
1Deploy 1 — EXPAND: Add column as null=True. Postgres 11+ = metadata-only, milliseconds, no lock. Old code ignores it, new code can start writing it. safe
2Deploy 2 — BACKFILL: Management command, batches of 5,000 rows in separate transactions. NOT inside a migration file — migrations are transactional, backfill inside holds ACCESS EXCLUSIVE lock for entire duration. separate command
3Deploy 3 — CONTRACT: ADD CONSTRAINT ... CHECK ... NOT VALID → then VALIDATE CONSTRAINT. NOT VALID skips full-table scan. VALIDATE takes only SHARE UPDATE EXCLUSIVE — reads/writes continue. concurrent
⚡ Production Signal Line
"I once shipped a migration that combined a RunPython backfill with an AlterField to NOT NULL in the same file — because Django wraps each migration in a transaction, the ACCESS EXCLUSIVE lock queued behind the backfill and effectively froze writes on the orders table for ~45 minutes during business hours. We now split every non-trivial schema change into add-nullable → backfill in a management command in batches → constraint-with-NOT-VALID-then-VALIDATE, and we time every migration on a staging copy of prod data before it ships."
⭐ HIGH FREQUENCY
Q2: "What's the difference between a schema migration and a data migration? When would you use each?"
▼

Schema migration: Changes the database structure — adds/removes columns, tables, indexes, constraints. Generated by Django when you change models. Examples: AddField, RemoveField, AlterField, CreateModel.

Data migration: Transforms or moves existing data — doesn't change structure. Uses RunPython or RunSQL. Example: splitting a full_name column into first_name + last_name, backfilling a new status column based on existing data.

🚫 Critical trap: Never put a large data migration (RunPython over millions of rows) in the same migration file as an AlterField. The transaction holds schema locks for the entire data operation duration. Split them: schema migration in one file, data migration in a separate file, or better — as a management command that runs independently.
⭐ HIGH FREQUENCY
Q3: "Have you ever had a migration cause downtime? Walk me through it."
▼
!What failed: RunPython backfill + AlterField to NOT NULL in the same migration file. classic mistake
2Why: Django wraps each migration in a transaction. ACCESS EXCLUSIVE lock held for entire backfill duration — ~45 minutes of zero writes on the orders table during business hours.
3Fix: Rolled back with migrate <app> <previous> — worked because RunPython had a reverse function. Always write reverse_code.
✓Prevention: 3-deploy expand-contract, backfill as management command (separate transaction control), time on staging with prod data copy, 5-second statement-timeout on migration runner.
⭐ HIGH FREQUENCY
Q4: "What's your pre-migration checklist before running migrate in production?"
▼
1sqlmigrate <app> <num> — read the actual SQL. Know the lock type before touching prod. ACCESS EXCLUSIVE = danger.
2Run on staging with prod-data copy — time it. 3 seconds on staging can be 45 minutes on prod with 50M rows.
3Snapshot the database (or confirm PITR is enabled) before running. Data corruption needs a restore path.
4Verify reversibility — every RunPython needs a reverse_code function. RunPython.noop at minimum.
5Rollback command ready: manage.py migrate <app> <previous_name> — know it cold, don't look it up while prod is burning.
⭐ HIGH FREQUENCY
Q5: "What does python manage.py sqlmigrate app 0005 give you?"
▼

"It prints the raw SQL that Django will execute when you run that migration — without actually running it. This lets you review the exact DDL before touching the database."

Why it matters: You can see if it's going to run ALTER TABLE ... ADD COLUMN ... NOT NULL (table lock), or CREATE INDEX (vs CREATE INDEX CONCURRENTLY), or a simple INSERT/UPDATE. Lets you catch dangerous operations before they hit production.

In practice: I run sqlmigrate for every migration as part of the pre-migration checklist. If I see an operation that will lock a large table, I know I need to restructure the migration before deploying.

NICE TO KNOW
Q6: "How do you roll back a migration that included a RunPython?"
▼

python manage.py migrate <app> <previous_migration_name> — Django runs the RunPython's reverse function.

But: If the RunPython was written without a reverse function (just RunPython(forward_func) without a second argument), Django raises an exception — migration is irreversible.

# GOOD — reversible RunPython def forward(apps, schema_editor): Order = apps.get_model('orders', 'Order') Order.objects.update(status='pending') def backward(apps, schema_editor): Order = apps.get_model('orders', 'Order') Order.objects.update(status=None) migrations.RunPython(forward, backward) # At minimum — if backward is truly a no-op: migrations.RunPython(forward, migrations.RunPython.noop)
NICE TO KNOW
Q7: "Why is db_default preferred over default for new not-null columns in Django 5+?"
▼

default: Applied at the Python/ORM level. When you add a column with default=timezone.now, Django's ORM adds the current time to every new object — but the database doesn't know about the default. The migration has to UPDATE every existing row in Python, one by one (or in a batch), which is slow and locks the table.

db_default: A real database-level DEFAULT clause. The database engine handles it natively. In Postgres 11+, adding a column with a constant database default is metadata-only — no rewrite, no lock.

# Django 5+ — db_default sets a real DB-level DEFAULT class Order(models.Model): status = models.CharField( max_length=20, db_default='pending' # Real DB DEFAULT 'pending' — no row rewrite ) # vs old pattern: status = models.CharField( max_length=20, default='pending' # ORM-level — migration rewrites existing rows )
