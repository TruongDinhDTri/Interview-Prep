1. Database Schema Design — The Foundation 🏗️

🎯

Talking Point: "Business requirements first, then entities, then normalization, then optimization."

👉 Prevents data redundancy and inconsistency

👉 Creates maintainable, scalable data structures

👉 Establishes clear relationships between entities

The Complete Design Process 
1. Business Requirements  → Understand what the system needs to do
2. Identify Entities      → Map out objects (Users, Products, Orders)
3. Define Relationships   → One-to-Many, Many-to-Many, One-to-One
4. Normalize (1NF→3NF)    → Remove redundancy, ensure data integrity
5. Denormalize (if needed)→ Trade write speed for read performance

🧱

5 Schema Patterns (Lego Blocks) — Most systems are combinations of 5 patterns: Core Entity, One-to-Many, Many-to-Many, Activity/Event, Ownership. Train your brain to recognize them — schema design becomes almost automatic in interviews.

🧱 The 5 Schema Patterns — Master These, Design Any System
🧠

Interview superpower: When requirements say "Users can like posts, comment on posts, follow users" — your brain fires: Ownership → One-to-Many → Many-to-Many (self-referential). Then designing the schema becomes almost mechanical.

1

Core Entity Pattern — The "nouns" in requirements

Every requirement has nouns. Those nouns = core tables.

"Users can create posts"  → User, Post
"Users buy products"      → User, Product
"Users write reviews"     → User, Review

🧠 Mental rule: Look for nouns. Each noun becomes a table.

2

One-to-Many Pattern — "A can have multiple X"

The foreign key lives on the "many" side — always.

User → many Orders   → FK on Order  (order.user_id)
Post → many Comments → FK on Comment (comment.post_id)
Category → many Products → FK on Product (product.category_id)

🧠 Mental rule: "A has multiple X" → FK on X pointing to A.

3

Many-to-Many Pattern — Both sides can have multiple

Cannot store directly — must create a junction table. Add Through Model if the relationship carries its own data.

Students ↔ Courses       → Enrollment(student_id, course_id)
Users ↔ Posts (likes)    → Like(user_id, post_id)
Users ↔ Users (follows)  → Follow(follower_id, followed_id)
Orders ↔ Products        → OrderItem(order_id, product_id, quantity) ← Through Model

🧠 Mental rule: "many ↔ many" → junction table. If relationship has data → Through Model.

4

Activity / Event Pattern — Things that "happen"

If the requirement uses action verbs (logs in, sends, places, uploads) → event table. Always has created_at, usually has status.

User logs in     → LoginEvent(user_id, timestamp, ip_address)
User sends msg   → Message(sender_id, receiver_id, content, created_at)
User places order → Order(user_id, total, status, created_at)

🧠 Mental rule: Something "happens" or needs a timestamp → Activity pattern.

5

Ownership Pattern — "Who created/owns X"

A ForeignKey establishing creator/owner. Always user_id on the owned resource.

User creates Posts    → post.user_id    (owner FK)
User uploads Files    → file.user_id    (owner FK)
User owns Projects    → project.owner_id (owner FK)

🧠 Mental rule: "Users create/own X" → FK from X back to User. Always.

🎯 Real System Compositions

SystemEntitiesPatterns Used
Social Media User, Post, Comment, Like, Follow Ownership (user→post) + 1:N (post→comments) + M2M (users↔posts via Like) + M2M self (users↔users via Follow)
E-Commerce User, Product, Order, OrderItem, Review, Category Ownership + 1:N (user→orders, order→items) + M2M+Through (order↔product via OrderItem) + M2M (product↔category)
LMS Student, Course, Enrollment, Lesson, Assignment M2M+Through (student↔course via Enrollment with grade+date) + 1:N (course→lessons) + Activity (assignments)
✨

The Big Insight: Engineering often looks complex — but underneath it's simple patterns repeated everywhere. Once your mind sees those patterns, chaos becomes structure. Every system you'll ever design in an interview is just a combination of these 5.

🗣️ Interview-ready Answer

"My process starts with business requirements, not tables. First, I identify the core entities and their relationships — whether they're One-to-Many, Many-to-Many, or One-to-One. Then I apply normalization rules (up to 3NF) to ensure data integrity and reduce redundancy. Finally, if the system is read-heavy, I selectively denormalize specific fields to trade write speed for read performance. Most systems I've designed are just combinations of 5 patterns: Core Entity, One-to-Many, Many-to-Many, Activity/Event, and Ownership — once you recognize the pattern, the schema almost writes itself."

2. Normalization — Data Integrity Rules 📐

🎯

Talking Point: "Normalize first, denormalize when needed. Each normal form eliminates a different class of data anomaly."

👉 1NF: atomic values — no arrays, no lists

👉 2NF: eliminate partial dependency (composite PK problem)

👉 3NF: eliminate transitive dependency (non-key describes another entity)

1️⃣ First Normal Form (1NF) — Atomic Values

Rule: Each column should contain a single, indivisible value. No arrays, no lists, no comma-separated values.

❌ Violates 1NF:

idnameskills
1Wiganz"python,django,react"

✅ Fix:

Create a separate Skill table with M2M relationship.

💡

One-liner: "1NF: every column stores a single value — no arrays or lists."

2️⃣ Second Normal Form (2NF) — No Partial Dependency
📌

Rule: Non-key columns must depend on the ENTIRE composite PK — not just part of it.

⚡

Key insight: 2NF is only relevant with a composite PK.

If your table has a single id (auto-increment) as PK → you're automatically in 2NF. Partial dependency can only exist when you need two or more columns together to uniquely identify a row — like (order_id, product_id). This is a differentiator in interviews: most candidates don't know this constraint.

🔍 Discovery — The iPhone Table

Primary Key here is composite: (order_id, product_id) — need BOTH to identify 1 row.

order_idproduct_idproduct_namequantitycustomer_name
1101iPhone2Wiganz
1102AirPods1Wiganz
2101iPhone1Triết

Ask: "Does product_name depend on BOTH order_id + product_id? Or just one?"

💡

AHA #1 — Partial Dependency: product_name only needs product_id — doesn't care about order_id. iPhone is always "iPhone" regardless of which order.

AHA #2 — Full Dependency: quantity needs BOTH — Order 1 bought 2 iPhones, Order 2 bought 1 iPhone. Same product, different quantity per order.

❌ PARTIAL Dependency — product_name

order_id=1, product_id=101 → "iPhone"
order_id=2, product_id=101 → "iPhone"
order_id=3, product_id=101 → "iPhone"
                ↑ SAME every time.
                order_id is irrelevant.
                Only product_id matters.

iPhone is always iPhone — it doesn't matter which order you're looking at.

✅ FULL Dependency — quantity

order_id=1, product_id=101 → qty=2  ← Order 1
order_id=2, product_id=101 → qty=1  ← Order 2
order_id=3, product_id=101 → qty=5  ← Order 3
                ↑ DIFFERENT each time.
                Changing either order_id OR
                product_id changes the qty.

Need BOTH to know "how many of THIS product in THAT order."

🔑

The Test Question: "If I change only the order_id but keep the same product_id, does this column's value change?"

product_name: No → same product is still "iPhone" → Partial (fix it!)

quantity: Yes → different order can have different qty of same product → Full (correct!)

💀 Why Partial Dependency is Bad — 3 Anomalies

AnomalyThe Problem
UpdateiPhone renamed → must update 10,000 rows. Miss 1 → data inconsistency 💀
DeleteDelete last order of iPhone → lose all product info forever
InsertCan't add new product without creating a fake order first

✅ Fix: Split the Table

❌ BEFORE (violates 2NF):
OrderItems: (order_id, product_id, product_name, quantity, customer_name)

✅ AFTER (achieves 2NF):
OrderItems: (order_id, product_id, quantity)      ← only full-dep columns
Products:   (product_id, product_name)             ← product_name lives here
Orders:     (order_id, customer_name)              ← customer_name lives here

Now rename iPhone → update 1 row in Products. Done. ✅

🐍 Django Connection: ForeignKey = 2NF in Practice

# ❌ Violates 2NF — copying product_name directly
class OrderItem(models.Model):
    product_id = ...
    product_name = "iPhone"  # WRONG: copy into every row!
    quantity = models.IntegerField()

# ✅ 2NF correct — ForeignKey is the address, not a copy
class Product(models.Model):
    name = models.CharField(max_length=200)  # name lives HERE

class OrderItem(models.Model):
    product = models.ForeignKey(Product, on_delete=models.CASCADE)
    quantity = models.IntegerField()

# Django auto-JOINs: ForeignKey = store the address, not copy the data
order_item.product.name  # Django fetches from Product table
🏠

Metaphor: ForeignKey = lưu "địa chỉ nhà" thay vì copy toàn bộ nội thất vào chỗ mình. Khi hỏi order_item.product.name — Django đến địa chỉ đó lấy tên về.

💡

One-liner (Wiganz's own words): "2NF: non-key must fully depend on the entire composite PK — no partial dependency."

Bonus: Tables with a single auto-increment id PK are automatically in 2NF — partial dependency only exists with composite keys.

3️⃣ Third Normal Form (3NF) — No Transitive Dependency
📌

Rule: Non-key columns must depend DIRECTLY on the PK — not on another non-key column.

Transitive dependency = A→B→C where B is a non-key "middleman."

🔍 Discovery — The Customer City Table

order_id (PK)customer_idcustomer_namecustomer_cityquantity
1501WiganzHCMC2
2502TriếtHanoi1
3501WiganzHCMC5
🎯

AHA — Dependency is ONE-DIRECTIONAL:

Knowing order_id = 1 → you know customer_id = 501 ✅ (each order belongs to exactly 1 customer)

But knowing customer_id = 501 → you cannot determine order_id ❌ (Wiganz has order 1, order 3, and thousands more)

order_id=1 → customer_id=501   ✅ (1 order has 1 customer — deterministic)
customer_id=501 → order_id=???  ❌ (1 customer has N orders — ambiguous)

"A depends on B" = knowing B uniquely determines A. This is always a one-way street.

Ask: "Does customer_city depend on order_id (PK)? Or on customer_id?"

💡

AHA — Transitive Dependency: The trap is reading "depends on" like Vietnamese "phụ thuộc" = "có thể suy ra từ." In databases, it means functional dependency: knowing the left side uniquely determines the right side.

If you know order_id = 1, you can answer: the city is HCMC. So order_id → customer_city is true. Nothing wrong there.

But customer_city also has a closer source: customer_id → customer_city. And since order_id → customer_id, we get:

order_id ──→ customer_id ──→ customer_city
   PK          non-key            non-key
              (middleman)

That means order_id → customer_city is true transitively: A → B and B → C, therefore A → C.

3NF is not saying order_id → customer_city is false. It is saying: remove dependencies that go through a non-key middleman: PK → non-key → non-key.

Better wording: customer_city is directly functionally determined by customer_id, and therefore only transitively determined by order_id.

Tiếng Việt: customer_city được xác định trực tiếp bởi customer_id; còn order_id chỉ xác định customer_city thông qua customer_id.

Real-life check: EmployeeID → DepartmentID → DepartmentName. Knowing EmployeeID tells you the department name, but the department name is really decided by DepartmentID.

💀 Why Transitive Dependency is Bad

Wiganz moves from HCMC to Hanoi → must update every order row (Order 1 and Order 3 both have customer_city = HCMC). Miss one:

order 1    | Wiganz | Hanoi  ← updated
order 500  | Wiganz | HCMC   ← missed! 💀
order 3000 | Wiganz | Hanoi  ← updated

Wiganz lives in 2 cities simultaneously in the DB. 💀 Data inconsistency.

🏠

Metaphor — Căn nhà cho thuê: Order table là căn nhà. order_id là chủ nhà. customer_id là người thuê. customer_city là vợ của người thuê — không phải "vợ của căn nhà"! Người thuê dọn đi thì vợ đi theo, không ở lại căn nhà.

→ customer_city không quan tâm order_id. Nó chỉ "đi ké" customer_id vào ở trọ trong bảng Orders.

✅ Fix: Split the Table

❌ BEFORE (violates 3NF):
Orders: (order_id, customer_id, customer_name, customer_city, quantity)

✅ AFTER (achieves 3NF):
Orders:    (order_id, customer_id, quantity)
Customers: (customer_id, customer_name, customer_city)

Wiganz moves to Hanoi → update 1 row in Customers. Done. ✅

📏

Universal Rule — One Table = One Entity:

Ask about every column in your table:
"Does this column DESCRIBE this entity, or does it describe ANOTHER entity?"

Orders table:
  order_id    → describes the Order    ✅ keep it here
  quantity    → describes the Order    ✅ keep it here
  customer_id → pointer to Customer    ✅ keep it (it's a FK, not a description)
  customer_name → describes Customer   ❌ belongs in Customers table!
  customer_city → describes Customer   ❌ belongs in Customers table!

If a column belongs to another entity → put it in that entity's table + use ForeignKey here as a pointer. This is the fastest 3NF check you'll ever use.

🐍 Django Connection

# ❌ Violates 3NF — customer info stuck inside Orders
class Order(models.Model):
    customer_id = models.IntegerField()
    customer_name = models.CharField(...)  # belongs to Customer!
    customer_city = models.CharField(...)  # belongs to Customer!

# ✅ 3NF correct — ForeignKey, city lives in its own table
class Customer(models.Model):
    name = models.CharField(max_length=200)
    city = models.CharField(max_length=100)

class Order(models.Model):
    customer = models.ForeignKey(Customer, on_delete=models.CASCADE)
    quantity = models.IntegerField()

order.customer.city  # Django JOINs to get the city
💡

One-liner (Wiganz's own words): "3NF: non-key must depend DIRECTLY on PK — no transitive dependency through another non-key."

Quick rule: One table = one entity. Only store attributes OF that entity + foreign keys. Don't store attributes of other entities.

⚡ When to Denormalize

Keyword: Read-Heavy Systems

Problem: Highly normalized databases require many JOINs at query time → slow for dashboards/analytics.

Solution: Pre-compute and store aggregates as denormalized fields.

class User(models.Model):
    name = models.CharField(max_length=100)
    application_count = models.IntegerField(default=0)  # denormalized

# Keep in sync on write
user.application_count = F('application_count') + 1
user.save(update_fields=['application_count'])
AspectNormalizedDenormalized
ReadsSlower (JOINs or COUNTs)Faster (pre-computed)
WritesFasterSlower (must update aggregates)
Data IntegrityGuaranteedMust maintain manually

🗣️ Interview-ready Answer

"I always normalize first. 1NF for atomic values. 2NF removes partial dependency — non-key columns must depend on the ENTIRE composite primary key, not just part of it. 3NF removes transitive dependency — non-key columns must not describe another entity, they belong in that entity's table via ForeignKey. Both normal forms are fixed the same way: split into separate tables, reference with ForeignKey. For read-heavy dashboards, I selectively denormalize aggregated fields for performance — it's always a trade-off."

3. The N+1 Query Problem — Performance Killer 💀

🎯

Talking Point: "Fix N+1 before touching indexes — it's usually the fastest performance win."

👉 N+1 = 1 query to get list + N queries for each item = scales terribly

👉 It's a silent bug — code looks correct, results are correct, but it dies under load

👉 Fix: select_related() for FK/OneToOne → SQL JOIN

🔍 Discovery — How N+1 Happens (The "Gõ Cửa" Metaphor)

The Code

orders = Order.objects.all()
for order in orders:
    print(order.customer.name)

If there are 100 orders, how many SQL queries run?

Query 1: SELECT * FROM orders              → fetches all 100 orders
Query 2: SELECT * FROM customers WHERE id=1  → for order 1
Query 3: SELECT * FROM customers WHERE id=2  → for order 2
... × 100 times
──────────────────────────────────────────
TOTAL: 101 queries  ← this is N+1!

Why does order.customer.name trigger a query?
Django doesn't know ahead of time that you'll access .customer — so it lazy loads: asks the DB every single time you touch that attribute in the loop.

💀

The silent killer: Code looks identical. Results are correct. But each order.customer.name is secretly firing a SQL query. 10 orders? Fine. 10,000 orders? Server dies.

Metaphor: Going to the market for 100 items — making 100 separate trips vs. one trip with a big bag. Each round trip to DB costs network + IO overhead.

✅ Fix — select_related() Makes it 1 Query 
# ❌ N+1 — 101 queries
orders = Order.objects.all()
# SQL: SELECT * FROM orders
for order in orders:
    print(order.customer.name)
    # SQL: SELECT * FROM customers WHERE id = X  (×100!)

# ✅ select_related — 1 query with JOIN
orders = Order.objects.select_related('customer').all()
# SQL: SELECT orders.*, customers.*
#      FROM orders JOIN customers ON orders.customer_id = customers.id
for order in orders:
    print(order.customer.name)
    # 0 extra queries — data already in RAM!
💡

The key insight: The code in the for loop looks IDENTICAL. The entire difference is in what SQL Django generates before the loop. select_related changes how Django fetches, not how you write the loop.

⚡

Lazy Load vs Eager Load — Two Philosophies:

🦥 Lazy Load (Django default):

"I'll fetch related data only when you ask for it."

→ order.customer.name in a loop = Django fires a DB query each time you access .customer

Problem: N items in loop = N DB queries.

🚀 Eager Load (select_related):

"I know you'll need this, so I'll fetch it all NOW before the loop."

→ select_related('customer') = 1 JOIN query before the loop. Data already in RAM.

Result: No matter how many orders, 0 extra DB queries in loop.

What the JOIN Result Looks Like in RAM:

| order_id | quantity | customer_id | customer_name | customer_city |
|----------|----------|-------------|---------------|---------------|
| 1        | 2        | 501         | Wiganz        | HCMC          |
| 2        | 1        | 502         | Triết         | Hanoi         |
| 3        | 5        | 501         | Wiganz        | HCMC          |

Django loads this merged table once → order.customer.name reads from RAM. Zero DB calls in the loop.

💡

What does SELECT orders.*, customers.* actually mean?

orders.* = ALL columns from the orders table. customers.* = ALL columns from the customers table.

The JOIN merges them into one fat row per record. Django loads this entire merged table into RAM once. Then order.customer.name just reads the customer_name column from the already-loaded Python object — zero network roundtrips, zero DB queries.

This is why the code looks identical with or without select_related — the difference is entirely in what SQL runs before your loop starts.

🗣️ Interview-ready Answer

"The N+1 problem is when you run 1 query to fetch a list, then N separate queries for each item — usually caused by accessing a ForeignKey attribute inside a loop. Django lazy-loads by default: every order.customer.name fires a SQL query. Fix it with select_related() which does a SQL JOIN and loads everything in one query. It's a silent bug — code runs correctly but degrades catastrophically as data grows."

4. select_related vs prefetch_related — Choosing the Right Tool ⚡

🎯

Core idea: The real difference is not "1 query vs 2 queries." It is how the related objects get attached: the database attaches them with a JOIN, or Django attaches them later in RAM.

🔥

The real rule is NOT: ForeignKey → select_related().

The real rule is: If each object connects to exactly one related object (Many → One or One → One), JOIN is usually optimal → select_related().

If each object can connect to many related objects (One → Many or Many → Many), JOIN can multiply rows → prefetch_related().

🎯 The Confusing Part: "But the Result Looks the Same?"

Yes. For a normal ForeignKey like Order → Customer, select_related("customer") and prefetch_related("customer") can produce almost the same final Python experience.

for order in orders:
    print(order.customer.name)  # no extra query in both cases

That is what "almost the same result" means: after fetching, each Order object has a usable .customer. It does not mean the database work was the same.

Customer A
 ├── 500 Orders

Customer B
 └── 500 Orders

In both strategies, Django still ends up with about 1000 Order objects. The difference is the path used to attach the Customer object to each Order.

1️⃣ Cách 1 — select_related(): Database JOINs 
orders = Order.objects.select_related("customer")

Django asks the database to JOIN first:

SELECT *
FROM orders
JOIN customers
  ON orders.customer_id = customers.id;

The database returns one result set:

| order_id | customer_id | customer_name |
|----------|-------------|---------------|
| 1        | 1           | A             |
| 2        | 1           | A             |
| 3        | 2           | B             |

Then Django builds:

[
    Order(1, customer=A),
    Order(2, customer=A),
    Order(3, customer=B),
]
🔑

Key: the database attached customer data while returning the rows. Django just reads the joined result and creates objects.

2️⃣ Cách 2 — prefetch_related(): Django Maps in RAM

This also works for a ForeignKey:

orders = Order.objects.prefetch_related("customer")

But now Django does not ask the database to JOIN. It asks for separate result sets:

-- Query 1
SELECT * FROM orders;

-- Query 2
SELECT * FROM customers
WHERE id IN (1, 2);

Those result sets become separate Python objects:

orders_in_ram = [
    Order(1, customer_id=1),
    Order(2, customer_id=1),
    Order(3, customer_id=2),
]

customers_in_ram = [
    Customer(1, "A"),
    Customer(2, "B"),
]

Then Django builds a lookup and attaches them in RAM:

customer_map = {
    1: Customer(1, "A"),
    2: Customer(2, "B"),
}

Order(1).customer = customer_map[1]
Order(2).customer = customer_map[1]
Order(3).customer = customer_map[2]

Final Python result:

[
    Order(1, customer=A),
    Order(2, customer=A),
    Order(3, customer=B),
]
🎯

This is the "gần như cùng kết quả" part: the final objects look the same, and order.customer.name does not fire extra queries. But select_related() got there with a database JOIN; prefetch_related() got there with separate queries plus Python mapping.

❓ So Why Prefer select_related() for ForeignKey?

Because this relationship is simple:

Order  ── customer_id ──→  Customer
Many                         One

Each Order points to exactly one Customer. The JOIN condition is just:

orders.customer_id = customers.id

Databases are extremely good at this. If you use prefetch_related("customer") instead, Django has to do extra work:

  • run a second query for customers
  • build a dictionary like {customer_id: Customer}
  • attach each customer to each order in Python

So for Many → One, both can work, but select_related() is usually the cleaner and faster route.

💡

1000-order example: if A has 500 orders and B has 500 orders, both approaches still deal with 1000 Order objects. select_related() lets the database attach customer data to those 1000 rows. prefetch_related() loads 1000 orders + 2 customers separately, then Django attaches them in RAM. Same final experience, more Python-side work.

🧨 The Reverse Direction: Where JOIN Explodes

Now the base objects are customers, and each customer may have many orders:

Customer
   ↓
Many Orders
customers = Customer.objects.prefetch_related("orders")

If you tried to JOIN this into one result set, Customer A repeats once per order:

| customer | order |
|----------|-------|
| A        | 1     |
| A        | 2     |
| A        | 3     |
| ...      | ...   |
| A        | 500   |
| B        | 501   |
| B        | 502   |
| ...      | ...   |
| B        | 1000  |

You wanted 2 customers, but the JOIN result became 1000 rows. Customer name, email, phone, address, and every customer column are repeated again and again.

That is row explosion. It is exactly what prefetch_related() avoids:

-- Query 1: customers once
SELECT * FROM customers;

-- Query 2: all related orders once
SELECT * FROM orders
WHERE customer_id IN (1, 2);
Customer A
 ├── Order 1
 ├── Order 2
 └── ...

Customer B
 ├── Order 501
 └── ...
🔁 ManyToMany: Same Reason, Bigger Blast Radius

ManyToMany can multiply rows from both sides:

| student | course  |
|---------|---------|
| A       | Math    |
| A       | Physics |
| A       | English |
| B       | Math    |
| B       | Biology |

If a student has many courses and a course has many students, a JOIN can grow very quickly. So prefetch_related() is the natural tool: load the sets separately, then let Django map relationships in RAM.

🔥 The Rule You Should Actually Remember

Do not ask first:

"ForeignKey hay Reverse ForeignKey?"

Ask this:

"JOIN này có làm số dòng kết quả tăng lên mạnh không?"
Relationship shapeJOIN effectUseWhy
Many → One
Order → Customer		Does not increase beyond the order rowsselect_related()DB JOIN is simple and efficient
One → OneDoes not multiply rowsselect_related()One object connects to one object
One → Many

Short version: if each object connects to one object, JOIN. If each object can connect to many objects, prefetch.

🐍 Code — Both Tools in Action 
# Many → One: order belongs to one customer → select_related
orders = Order.objects.select_related("customer")
for order in orders:
    print(order.customer.name)  # 0 extra queries

# Also works, but usually extra work for a FK:
orders = Order.objects.prefetch_related("customer")
for order in orders:
    print(order.customer.name)  # same final object access, different fetch strategy

# One → Many: customer has many orders → prefetch_related
customers = Customer.objects.prefetch_related("orders")
for customer in customers:
    print(customer.orders.all())  # 0 extra queries, reads prefetched cache

# ManyToMany → prefetch_related
books = Book.objects.prefetch_related("authors")
for book in books:
    print(book.authors.all())  # 0 extra queries

# Chaining FK paths → select_related can follow many→one repeatedly
applications = Application.objects.select_related("user", "job__company")
for app in applications:
    print(app.user.name)
    print(app.job.company.name)

🗣️ Interview-ready Answer

"The real difference is how related objects get attached. select_related() uses a database JOIN and returns one result set, so it is best when each object points to one related object, like Order → Customer. prefetch_related() runs separate queries, gets separate result sets, then Django maps objects in RAM. For a ForeignKey, prefetch can still work and the final Python objects look almost the same, but it is usually extra work because the database can JOIN that case efficiently. For reverse FK and ManyToMany, a JOIN can multiply rows badly, so prefetch avoids row explosion. I decide by asking: will this JOIN make the result set much bigger than the objects I actually want?"

5. Indexing Strategy — Read vs Write Trade-offs 📊

🎯

Talking Point: "Index what you filter, sort, and join — but don't over-index. Every index slows down writes."

👉 Index = B-Tree structure → find rows in O(log n) instead of O(n) full scan

👉 Trade-off: READ faster, WRITE slower (must update index on every change)

👉 Rule: index if you read much more than you write on that column

📚 Metaphor — Phụ Lục Sách (Book Index)

You have a 1000-page book. Find "Django":

  • No index: Scan every page 1 → 1000 = Full Table Scan 💀
  • With index: Check appendix → "Django: pages 347, 521, 890" → jump straight there ✅
Book appendix:          DB Index (B-Tree):
Django → page 347       "Wiganz" → row 347
React  → page 521       "Triết"  → row 521
Python → page 890       "Nam"    → row 890
💡

When you add a new page to the book (INSERT row), you must rewrite the appendix. That's why indexes slow down writes — every INSERT/UPDATE/DELETE must update the B-Tree.

🌳 How B-Tree Works — O(log n)

B-Tree index on name column (sorted alphabetically — A=1, B=2... W=23):

                      [Minh→id:1]
                     /            \
          [Bình→id:4]              [Triết→id:5]
         /            \            /            \
    [An→id:3]      [Huy→id:6]  [Lan→id:7]   [Wiganz→id:2]

Query WHERE name = "Wiganz":

Minh  → "Wiganz" > "Minh"   → go RIGHT  (W=23 > M=13)
Triết → "Wiganz" > "Triết"  → go RIGHT  (W=23 > T=20)
Wiganz → FOUND! → row id=2  ✅  — only 3 steps!
Without index: scan 7 rows → 7 steps
With B-Tree:  3 steps
At 1 million rows:
  Full scan → 1,000,000 steps 💀
  B-Tree    → ~20 steps      ✅  (log₂ 1,000,000 ≈ 20)
💡

Complexity: Full Table Scan = O(n). B-Tree Index = O(log n). At 1M rows, that's 1,000,000 vs 20 steps. This is why indexes matter.

🎯

WHY sorted = fast — The Core Insight Behind O(log n):

B-Tree works because the data is SORTED. At every node, you make a binary decision: "my target is smaller → go LEFT, or larger → go RIGHT." You never check both sides. You eliminate half the remaining candidates at every step.

Searching "Wiganz" (W=23) in unsorted data:
  Scan An, Bình, Huy, Lan, Minh, Triết, Wiganz → 7 steps 💀

Searching "Wiganz" (W=23) in B-Tree (SORTED):
  [Minh M=13]  → W > M → go RIGHT  (eliminated left half ✅)
  [Triết T=20] → W > T → go RIGHT  (eliminated left half again ✅)
  [Wiganz]     → FOUND! → 3 steps ✅

Each step halves what's left:
  7 items → step 1 eliminates ~3, step 2 eliminates ~2, step 3 finds it.
  1,000,000 items → ~20 steps.  log₂(1,000,000) ≈ 20

This is why you can't use a B-Tree index on randomly ordered data — without sorting, you can't make that "bigger/smaller" decision, so you can't eliminate half at each step.

🔥 Composite Index — Leftmost Prefix Rule

Composite index ['category', 'price'] — B-Tree sorts by category first, then price:

B-Tree layout:
Electronics/100
Electronics/200
Electronics/500   ← sorted by category FIRST, then price within
Clothing/50
Clothing/150
Clothing/300

✅ Works:

WHERE category='Electronics'
  AND price=200

Knows to jump into "Electronics" section → find 200. Uses index!

❌ Fails:

WHERE price=200
  -- (no category)

Doesn't know which category section to enter → must scan everything. Index useless!

📖

Metaphor — Danh Bạ Điện Thoại (sorted by Họ → Tên):

Nguyễn An
Nguyễn Bình
Trần An
Trần Bình

Find "Nguyễn Bình" → jump to "Nguyễn" → find "Bình" ✅
Find "Bình" (without knowing the last name) → read every name from the start 💀
Leftmost Prefix Rule: skip the first column → index is useless.

🤖 What Django Auto-Indexes
FieldAuto-indexed?Why
ForeignKey✅ YesAlways used in JOINs and filters

primary_key✅ YesPK is always indexed

🎁

unique=True gives you a free index! When inserting a new email, DB must check "does this email already exist?" — without an index, that's a full table scan on every INSERT. So unique=True requires an index, and Django creates it automatically.

🐍 Django Index Syntax 
# Option 1 — single field index
class Product(models.Model):
    name = models.CharField(max_length=200, db_index=True)

# Option 2 — Meta.indexes (composite, partial)
class Application(models.Model):
    user = models.ForeignKey(User, on_delete=models.CASCADE)  # auto-indexed
    status = models.CharField(max_length=20)
    created_at = models.DateTimeField()

    class Meta:
        indexes = [
            models.Index(fields=['status', 'created_at']),  # composite
            models.Index(                                              # partial (PostgreSQL)
                fields=['created_at'],
                name='pending_apps_idx',
                condition=Q(status='PENDING')
            ),
        ]

🗣️ Interview-ready Answer

"A database index is a B-Tree data structure that lets the database find rows in O(log n) instead of a full O(n) table scan — like the appendix in a book. The trade-off: writes become slower because every INSERT, UPDATE, and DELETE must also update the B-Tree. My indexing strategy: target high-traffic WHERE and ORDER BY columns, foreign keys (auto-indexed in Django), and composite indexes matching common multi-column query patterns. I avoid indexing low-cardinality columns and write-heavy columns. And unique=True gives you a free index — worth remembering."

6. Many-to-Many Through Models — When Relationships Have Data 🔗

🎯

Talking Point: "Use through models when the relationship itself has attributes — when data is neither A's nor B's, but belongs to the connection between them."

👉 Default M2M only stores two IDs — can't add extra columns

👉 Through model = self-defined junction table with full control

👉 Key signal: data produces "???" when placed in either A or B alone

🔍 Discovery — When Does Data "Belong to the Relationship"?

The Question: Where does "grade" live in Student ↔ Course?

Wiganz enrolls in Python course and gets grade 9.5. Where to store it?

Student table?

Student: grade = ???

Wiganz takes 5 courses → which course's grade? 💀

Course table?

Course: grade = ???

100 students → which student's grade? 💀

💡

AHA — "???" in both tables = belongs to the RELATIONSHIP: grade only has meaning when you know BOTH the student AND the course. It lives in the connection, not in either side.

Student    ←→    Enrollment    ←→    Course
Wiganz          grade: 9.5           Python
                enrolled: 15/01
🔍 The E-commerce Example — Order ↔ Product (quantity)

Order #1: Wiganz buys iPhone × 2 + AirPods × 1. Where does quantity live?

In Order table?

Order: quantity = ???

Order has 2 products → quantity 2? or 1? 💀

In Product table?

Product: quantity = ???

iPhone in Order 1 → qty=2, in Order 2 → qty=5. Which one? 💀

Only makes sense when you know BOTH: "iPhone IN Order #1" → quantity = 2 ✅

Why not just add product_id to Order table?

| order_id | order_date | quantity | product_id |
|----------|------------|----------|------------|
| 1        | 15/01      | 2        | 1 (iPhone) |
| 1        | 15/01      | 1        | 2 (AirPods)| ← order_date duplicated!

Change order date → must update 2 rows. Miss one → data inconsistency. This IS a through model structure already! Just formalize it properly.

🔥

The Ultimate AHA — You Already Designed a Through Model Without Knowing It!

When you naturally think "I should add product_id to the Order table", you have instinctively arrived at a through model. You didn't need a lecture — the data forced you there.

Through models aren't a magical Django feature. They're just the structure you naturally reach when you realize a piece of data needs to know about BOTH sides. The only difference: formalizing it as an explicit model (OrderItem) gives you full ORM control and lets you add more relationship fields later.

Interview answer: "A through model is just a junction table I control myself. The signal is when data produces '???' in either table alone — that's when you know it belongs to the relationship."

# Default M2M — Django auto-creates junction (can't add columns)
class Student(models.Model):
    name = models.CharField(max_length=200)
    courses = models.ManyToManyField(Course)  # can't store grade here!

# ─────────────────────────────────────────

# Through model — self-defined junction table
class Student(models.Model):
    name = models.CharField(max_length=200)
    courses = models.ManyToManyField('Course', through='Enrollment')

class Course(models.Model):
    name = models.CharField(max_length=200)

class Enrollment(models.Model):   # Through model
    student = models.ForeignKey(Student, on_delete=models.CASCADE)
    course  = models.ForeignKey(Course,  on_delete=models.CASCADE)
    enrolled_date = models.DateField()    # belongs to relationship!
    grade         = models.FloatField()   # belongs to relationship!

    class Meta:
        unique_together = ['student', 'course']  # prevent duplicates

# ─────────────────────────────────────────

# E-commerce example
class OrderItem(models.Model):        # Through model for Order ↔ Product
    order   = models.ForeignKey(Order,   on_delete=models.CASCADE)
    product = models.ForeignKey(Product, on_delete=models.CASCADE)
    quantity   = models.IntegerField()
    unit_price = models.DecimalField(max_digits=10, decimal_places=2)

# Querying through models
enrollments = Enrollment.objects.filter(student=wiganz).select_related('course')
for e in enrollments:
    print(f"{e.course.name}: {e.grade} — {e.enrolled_date}")

🗣️ Interview-ready Answer

"I use through models when the ManyToMany relationship itself has data. The signal is: if you try to place a field in either table and get '???', it belongs to the relationship. For example, quantity in an Order-Product relationship: Order doesn't know which product's quantity, and Product doesn't know which order's quantity — it only makes sense together. The through model (OrderItem) stores both ForeignKeys plus the relationship's own fields. This is also how you avoid data duplication: without a through model, order_date would be repeated on every product row in the order."

One-liner answers — Wiganz's own words forged from discovery sessions. Use these for rapid review before interviews.

📐

1NF: "Every column stores a single atomic value — no arrays, no lists."

📐

2NF: "Non-key must depend on the ENTIRE composite PK — no partial dependency. ForeignKey is how Django implements this."

📐

3NF: "Non-key must depend DIRECTLY on PK — no transitive dependency through another non-key. One table = one entity."

💀

N+1: "1 query for list + N queries for each item = scales terribly. Fix: select_related() → SQL JOIN, 1 query total."

⚡

select_related vs prefetch_related: "Not FK vs reverse FK. Real rule: one related object → JOIN/select_related; many related objects → row explosion risk → prefetch_related."

📊

Index: "B-Tree: O(log n) reads, but writes slower. Index when read >> write. Composite index: leftmost prefix must match query columns."

🔗

Through Model: "If data gets '???' in both A and B → it belongs to the RELATIONSHIP → through model. Checklist: try A, try B, if both fail → through model."

5 Schema Patterns:

① Core Entity — nouns in requirements → tables

② One-to-Many — FK lives on the "many" side, always

③ Many-to-Many — junction table; if data on relationship → Through Model

④ Activity/Event — if something "happens" → has created_at + status

⑤ Ownership — "users create X" → user_id FK on X

Social Media = ①②③④⑤. E-commerce = ①②③④⑤. LMS = ①②③+Through. Every system = combinations of these 5.
