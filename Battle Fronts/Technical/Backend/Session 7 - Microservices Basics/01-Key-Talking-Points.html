🍕 Monolith — "The Single Chef Pizza Shop"

💡

The Story: Imagine a small pizza shop with one chef who does everything: knead dough, spread sauce, add toppings, bake, cut, deliver. With 5 orders/day → perfect. With 500 orders/day → chaos.

One problem in any step → ALL steps blocked. Want to upgrade the oven (one part)? Shut down the entire restaurant.

This is monolith. Perfect at small scale. Reveals weakness at scale.

💪 Strengths of Monolith — Don't Forget These!

✅

Interviewers bait candidates who only say negatives about monolith:

  • Simple local function calls — no network overhead (nanoseconds vs milliseconds)
  • ACID transactions across ALL modules trivially
  • Easy to debug — one process, one log stream
  • Simple deployment — one artifact, one CI/CD pipeline
  • No distributed systems complexity

❌ When Monolith Breaks Down

ProblemWhat Happens
50+ engineers, one codebaseMerge conflicts, deployment bottlenecks every Friday
One module needs 10x resourcesMust scale ENTIRE app — wasteful and expensive
Payment team wants to deploy 2amRequires redeploying whole app — high risk
Buggy Search deployCrashes Payment service too — same process

⚙️ Microservices — "Each Chef Has Their Own Kitchen"

[Auth Service]      → Auth DB (Postgres)
       ↕ REST/gRPC
[User Service]      → User DB (Postgres)
       ↕
[Order Service]     → Order DB (Postgres)
       ↕ async via Kafka
[Payment Service]   → Payment DB (Postgres)
       ↕
[Notification Svc]  → (stateless — no DB needed)

Each box = independent process, independent DB, independent deployment

Conway's Law — "Architecture = Org Chart"

🏢

"Any organization that designs a system will inevitably produce a design whose structure is a copy of the organization's communication structure." — Melvin Conway, 1967

Team StructureResulting Architecture
1 teamMonolith (natural)
Teams organized by function (Frontend / Backend / Data)N-tier architecture (3 monolithic layers)
Teams organized by domain (Amazon model: Checkout / Search / Reviews)Microservices naturally
📦

Jeff Bezos's famous mandate: Every team must expose functionality via a service API. No direct DB access. No shared memory. Teams communicate ONLY via APIs. This forced Conway's Law → architecture mirrored autonomous team structure.

Two-pizza rule: If a team can't be fed with two pizzas, it's too big (≈ 6-8 people). Each microservice owned by one two-pizza team.

✅ When to USE Microservices — The 4 Signals

1

Independent Scaling Requirements

Black Friday: Search needs 100x, Order needs 50x, User Profile needs 2x. Monolith solution: scale ENTIRE app 100x → wasteful. Microservices: scale each independently → 60-70% cost reduction.

2

Multiple Teams Working Simultaneously

50 engineers × 1 codebase → merge conflict hell, "why is main broken?", deployment bottleneck. 50 engineers × 8 services → each team deploys independently, no cross-team conflicts.

3

Different Technology Requirements

ML Recommendation: Python + PyTorch + GPUs. Payments: Java + Kafka + compliance. Real-time Chat: Node.js + WebSockets. In monolith: stuck with one language/framework. Microservices: each team picks what fits.

4

Fault Isolation Requirements

Without: Recommendation service memory leak → OOMKilled → ENTIRE app down → Payments can't process. With: Recommendation crashes → homepage shows no recommendations → Checkout, Payments, Search continue working. Blast radius: degraded UX on homepage only.

❌ When NOT to Use Microservices — The 4 Anti-Signals

⚠️

"Small team, early stage, unclear boundaries, no DevOps maturity → monolith is the right answer."

Anti-SignalWhy It Kills You
Small team (<10 engineers)2 weeks setting up Kubernetes/service discovery → 0 features shipped. Monolith: 10+ features in 2 weeks.
Unclear domain boundariesWrong service boundaries = expensive refactoring 6 months later when you understand the domain.
No DevOps maturityNeed: Kubernetes, service discovery, centralized logging, distributed tracing, health monitoring, N CI/CD pipelines. Without: can't debug anything.
Complex cross-service transactionsBusiness logic requiring atomic ops across 5 services → must implement Saga. 10x harder than a single ACID transaction.

🌳 Strangler Fig — How to Migrate Safely

💡

Never do a Big Bang rewrite — historically fatal. Use the Strangler Fig: new features → build as separate services. Existing features → extract one-by-one, starting with clearest boundaries. Route through API Gateway to either monolith or new service. Over 12-18 months, strangle the monolith.

Month 0:   [Monolith handles 100% of requests]
Month 3:   [API Gateway] → Search Service (new)
                         → Monolith (everything else)
Month 9:   [API Gateway] → Search Service + User Service (extracted)
                         → Monolith (remaining modules)
Month 18:  [API Gateway] → All services
                         → Monolith deprecated ✅

🚪 API Gateway & BFF Pattern

What Problem It Solves

❌

Without Gateway

Mobile app must know: User Service = port 3001, Orders = port 3002, ML = port 3003. Separate auth, CORS, rate limit per service. Client config breaks when services move.

✅

With Gateway

All requests → gateway.api.company.com. Gateway handles: routing, auth, rate limiting, CORS. Internal services hidden behind it.

What API Gateway Does

ResponsibilityDetail
Routing/api/users/* → User Service, /api/orders/* → Order Service
Authentication (centralized)Verify JWT once → forward user context headers. Invalid → 401 immediately, never reaches downstream.
Rate Limiting (centralized)100 req/min per IP — not implemented in every service separately.
Protocol TranslationClient speaks REST → internal services speak gRPC → Gateway translates.
Aggregation (BFF)Single client request → call multiple services → aggregate → one response.

BFF Pattern — Backend for Frontend

               ┌──────────────────┐
iOS/Android ──→│   Mobile BFF     │──→ User Service
               └──────────────────┘──→ Order Service
                                   (lean response — no analytics)

               ┌──────────────────┐
Web Browser ──→│    Web BFF       │──→ User Service + Order Service
               └──────────────────┘──→ Analytics Service
                                   (full response)
🚨

Anti-pattern: Don't put business logic in the API Gateway. It should be a dumb router + authenticator. Gateway knows WHERE to send requests, not WHAT to do with the data.

🗄️ Database Per Service

❌

WRONG: Shared Database

User/Order/Product Services all access same DB. Order Service adds column to users table → breaks User Service. User Service migration → must coordinate ALL teams. "Loosely coupled" in theory, tightly coupled via shared DB.

✅

RIGHT: Each Service Owns Its Data

User Service → users_db (Postgres). Order Service → orders_db (Postgres). Search → Elasticsearch. Cart → Redis. Changes to users_db: User Service team's decision alone.

Cross-Service Data Access (The Hard Part)

OptionHowProCon
Sync API callGET /users/{id}/emailAlways fresh dataOrder depends on User Service being up
Event-driven replicationUser publishes UserEmailChanged → Order caches copyOrder is fully autonomousEventual consistency (1-2s stale)

🔄 Saga Pattern — Distributed Transactions

The Problem: Why Monolith Transactions Don't Work in Microservices

✅ Monolith — Trivial ACID Transaction

with db.transaction():
    order = Order.create(...)
    payment = Payment.charge(...)
    inventory.reduce(...)
    notification.send(...)
# ANY failure → entire rollback atomically

❌ Microservices — Cannot Span 4 DBs

# Order created ✅
# Payment charged ✅
# Inventory update FAILS ❌
# → User paid for out-of-stock item
# → Inconsistent state

Saga: Choreography vs Orchestration

🎭 Choreography-based Saga (Event-driven)

Services communicate via events — no central coordinator.

Order Svc: creates order → publishes "OrderCreated"
Payment Svc: listens → charges card → publishes "PaymentSucceeded"
Inventory Svc: listens → reserves item → publishes "ItemReserved"
Notification Svc: listens → sends "Order Confirmed" email

FAILURE CASE: Inventory out of stock
Inventory Svc: publishes "InventoryFailed"
Payment Svc: listens → refunds → publishes "PaymentRefunded"
Order Svc: listens → cancels → publishes "OrderCancelled"
✅ Pros❌ Cons
Fully decoupledHard to track overall saga state
No single point of failureRisk of cyclic dependencies
Maximum autonomyDebugging events across 5 services = pain
🎯 Orchestration-based Saga (Command-driven)

A central Saga Orchestrator service coordinates the flow.

[Order Orchestrator] → "PaymentService.charge(123, 999)"
[Payment Service]    → returns success/failure
[Order Orchestrator] → "InventoryService.reserve(456, 1)"
[Inventory Service]  → FAILS
[Order Orchestrator] → "PaymentService.refund(123, 999)"  ← compensating tx
[Order Orchestrator] → "NotificationService.send('out-of-stock')"
✅ Pros❌ Cons
Single place to see entire flowOrchestrator = single point of failure
Easier to add/modify stepsCreates coupling to Orchestrator
Clear error handlingCan become a bottleneck
💡

When to use each:
Choreography → Simple flows, 2-3 services, want maximum decoupling
Orchestration → Complex flows, many steps, need visibility, business-critical

📡 Sync vs Async Communication

REST (HTTP/1.1 + JSON)gRPC (HTTP/2 + Protobuf)
FormatJSON (human-readable, larger)Binary (smaller, faster)
SpeedBaseline5-10x faster serialization
SchemaOptional (OpenAPI)Required (.proto files)
Browser supportNativeNeeds grpc-web proxy
Best forPublic APIs, external clientsInternal service-to-service
PatternUse When
Synchronous (REST/gRPC)Payment confirmation, authentication, reads — need immediate answer
Asynchronous (Kafka/RabbitMQ)Email notifications, fan-out (1 event → many consumers), different processing speeds, resilience
⚡

Rule of thumb:
Synchronous = "I need the answer before I can continue"
Asynchronous = "I just need to say it happened, you handle it whenever"

🔍 Service Discovery

🤔

The problem: Order Service needs to call Payment Service. In Kubernetes, Payment Service might be at 10.0.1.42:8080 (Pod 1), 10.0.1.87:8080 (Pod 2 just spun up), and Pod 1 just crashed → 10.0.1.42 is gone. How does Order Service know the current addresses?

ApproachHowBest For
Client-Side (Consul/Eureka)Services register on startup → caller queries registry → load balancesNon-Kubernetes, full control over LB logic
Server-Side (Kubernetes DNS)Stable DNS: payment-service.default.svc.cluster.local → kube-proxy LBs automaticallyKubernetes-native, language-agnostic

🔎 Distributed Tracing

😱

The nightmare without tracing: User reports "My order failed." Every service logs look OK individually. WHERE did it fail? Without distributed tracing: 2 hours of grepping through 5 log files.

Correlation ID Pattern

# API Gateway: generate correlation ID for every request
import uuid

def handle_request(request):
    correlation_id = request.headers.get('X-Correlation-ID') or str(uuid.uuid4())
    logger.info(f"[{correlation_id}] Processing order for user {user_id}")
    # Forward to downstream with same header
    requests.post('http://payment-service/charge',
                  headers={'X-Correlation-ID': correlation_id}, ...)

Query all logs by X-Correlation-ID = "abc-123" → see ALL log lines across ALL services → timeline showing exactly where and when the failure occurred.

Jaeger/Zipkin Visualization

Trace for request "abc-123-xyz":

Order Svc (0-100ms)
  ├── Payment Svc call (10-60ms) ✅
  └── Inventory Svc call (60-100ms)
        └── DB query (60-90ms) ✅
        └── Redis lock (90-100ms) ❌ TIMEOUT ← root cause visible instantly

For <10 engineers: strongly recommend a well-structured monolith — microservices overhead would consume most capacity just keeping infrastructure working. For 50+ engineers with clear domain boundaries and independent scaling needs — yes. And I'd migrate using the Strangler Fig pattern — never a Big Bang rewrite."
