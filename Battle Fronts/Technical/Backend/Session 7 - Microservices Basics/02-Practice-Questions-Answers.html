Q1: "You have a monolith serving 1M users. It's slow. When do you move to microservices?"

❌

Weak Answer: "When the app becomes too big, we should split it into microservices to scale better."

✅

Start with the right diagnostic question — not an immediate answer:

"First I'd want to understand why it's getting slow. 'Getting slow' could mean very different things with very different solutions. Is the database query performance degrading? That's an indexing/caching problem — doesn't need microservices. Is a specific module consuming too much CPU and starving other modules? That's a candidate for extraction. Is the deployment process so slow and risky that engineers can't ship features fast enough? That's a people/process problem that microservices might solve."

🔍 The 3 Signals That Actually Justify Extraction

  1. One component has a dramatically different scaling profile — Search needs 50x the resources of User service during peak. Scaling the entire monolith is wasteful.
  2. Teams are stepping on each other's deployments — 50 engineers waiting to deploy because codebase is one artifact. Coordination overhead justifies extraction.
  3. Clear domain boundary exists — you know where the seams are. Team can own it independently.

🌳 How to Migrate — Strangler Fig (Not Big Bang)

"I would NOT do a Big Bang rewrite — that's killed many companies. I'd use the Strangler Fig pattern: identify the service with the clearest boundary and biggest performance impact, extract it behind the existing API Gateway, run monolith and new service in parallel briefly to validate, then cut over. Over 12-18 months, strangle the monolith incrementally. Every step is reversible."

⚡

Strong closing: "A well-structured modular monolith with clear module boundaries can serve 1 million users without microservices overhead. The question isn't 'should we use microservices?' — it's 'what specific problem are we solving and is microservices the right tool?'"

Q2: "A user places an order. Walk me through what happens across your microservices."

❌

Weak Answer: "The order goes to Order Service, Payment Service charges the card, Notification Service sends email."

✅

First: acknowledge the distributed transaction challenge:

"This is a great question because placing an order spans multiple services — Order, Payment, Inventory, Notification — and we need to handle partial failures gracefully. In a monolith, one ACID transaction would handle all of this. In microservices, we need a Saga pattern."

✅ Happy Path (Orchestration-based Saga)

1. Client submits order → API Gateway authenticates JWT → routes to Order Service
2. Order Service creates order record with status PENDING → sends to Orchestrator
3. Orchestrator → PaymentService.charge(user=123, amount=999) → PAYMENT_SUCCESS
4. Orchestrator → InventoryService.reserve(product=456, qty=1) → INVENTORY_RESERVED
5. Orchestrator → Order Service: status → CONFIRMED
6. Orchestrator publishes OrderConfirmed → Notification Service sends email (async)

❌ Failure Path — This Separates Strong Answers

"What if Inventory Service fails after Payment already succeeded? The Orchestrator receives INVENTORY_FAILED. It executes compensating transactions: calls Payment Service 'Refund charge for user 123.' Payment Service refunds. Orchestrator updates Order status to CANCELLED. Notification Service sends 'Sorry, item out of stock' email."

💡

Key insight to add: "Compensating transactions must be idempotent — if the refund call fails and we retry, calling 'refund' twice must not double-refund. Payment Service must check if a refund already exists for this order ID."

Q3: "What is the Saga pattern and when do you need it?"

❌

Weak Answer: "Saga is a pattern for managing transactions across multiple microservices. You use it when you need to coordinate between services."

"The Saga pattern exists because distributed ACID transactions are practically impossible at scale. When you have Order Service, Payment Service, and Inventory Service each with their own database, you can't issue a BEGIN TRANSACTION across all three and have it roll back atomically. Two-Phase Commit (2PC) theoretically solves this, but it's slow, brittle, and blocks all participating services — terrible for high-throughput systems."

"Saga replaces the single ACID transaction with a sequence of local transactions, each with a corresponding compensating transaction that undoes its effect. Instead of 'lock everything, then commit or rollback atomically,' you 'commit each step, and if a later step fails, explicitly undo earlier steps.' Each step is locally atomic (ACID within its own DB), but the saga as a whole is only eventually consistent."

Two Flavors

ChoreographyOrchestration
CoordinationServices communicate via events, no central coordinatorCentral Orchestrator commands each step
CouplingFully decoupled — services only know about eventsAll services coupled to Orchestrator
VisibilitySaga state is implicit — hunt through scattered eventsOrchestrator holds full state — one place to debug
Best forSimple flows, 2-3 services, max decoupling neededComplex flows, many steps, business-critical, need visibility

When You Need Saga

🎯

"You need Saga whenever: a user action spans multiple services AND failure midway must leave the system in a consistent state. E-commerce: placing an order. Banking: transferring money. Travel: booking flight + hotel + car. Any workflow where 'partial success' is worse than 'complete failure'."

Q4: "Service A → B → C. Service C starts responding in 10 seconds. What happens?"

❌

Weak Answer: "Service C being slow will make B and A slow too. We should add a circuit breaker."

✅

Walk through the cascade step by step with NUMBERS:

"This is a cascading failure scenario. Let me trace what actually happens at the infrastructure level: C is slow (10s). B is waiting for C. B has a thread pool — say 100 threads. Each in-flight request to C occupies 1 thread for 10 seconds instead of the normal 50ms. At B's normal throughput of 100 requests/second, within 10 seconds B has exhausted all 100 threads. New requests from A start queuing. B's response time degrades. B starts returning 503s to A. Same thing then cascades to A — threads pile up, A exhausts its thread pool, A returns errors to original clients."

💡

Key insight: "Slow is often worse than down — a service that's down fails fast, a service that's slow holds threads hostage."

🛡️ The 3-Layer Defense

Layer 1: Timeouts — Don't Wait Forever

"B should not wait 10 seconds for C. Set a timeout based on C's P99 latency — if C normally responds in 200ms, set timeout at 500ms. After 500ms with no response, fail fast and free the thread. This limits blast radius immediately."

Layer 2: Circuit Breaker — Stop Calling Sick Services

"After 5 consecutive timeouts from C, B's circuit breaker opens. Now B stops calling C entirely and returns an immediate error (or cached fallback). This prevents B's thread pool from being exhausted at all. C gets breathing room to recover."

Layer 3: Bulkhead — Contain the Blast Radius

"B should have a separate, size-limited thread pool specifically for calls to C (say, 20 threads). If the C-pool fills up, it doesn't spill into threads handling calls to other services. Blast radius is contained to C-related functionality only — everything else continues normally."

Q5: "Should each microservice have its own database? What are the trade-offs?"

❌

Weak Answer: "Yes, each microservice should have its own database so they are independent."

"Yes — but the why is more important than the rule itself. The fundamental goal of microservices is loose coupling — the ability for teams to change, deploy, and scale their service without coordination. If two services share a database, you've created a coupling point at the data layer that defeats the purpose. Concretely: if Order and User Service share a users table, and User Service team wants to rename a column — they now have to coordinate with Order Service team, run a multi-phase migration, deploy both together. You've recreated the deployment coupling microservices were meant to eliminate."

Technology Freedom

ServiceDatabase ChoiceWhy
User ServicePostgresRelational, complex queries
Product SearchElasticsearchFull-text search optimized
Shopping CartRedisFast key-value, TTL support
AnalyticsClickHouse/RedshiftColumnar, aggregations

The Trade-off — Cross-Service Data Access

"Order Service needs user's email but can't query users_db directly. Two solutions: synchronous API call (GET /users/{id}) for fresh data — adds latency and creates runtime dependency. Or event-driven replication: User Service publishes UserEmailChanged events, Order Service caches email in its own DB — fully autonomous at cost of brief eventual consistency. Right choice depends on data freshness criticality: email → seconds of eventual consistency is fine. Account balance → synchronous call."

⚠️

Anti-pattern to call out: "The worst of both worlds: sharing a database 'just between two services temporarily.' That temporary exception becomes permanent. Design the API contract explicitly from day one."

Q6: "What is an API Gateway and what should NOT go into it?"

❌

Weak Answer: "API Gateway is a single entry point for all client requests. It handles routing and auth. Business logic should not go in it."

"Without an API Gateway, clients face a fragmented interface: mobile app must know User is at port 3001, Orders at 3002, ML at 3003. Each service has its own auth, rate limiter, CORS. When services move or scale, client config breaks. The Gateway provides a stable, unified contract to the outside world while internal topology changes freely."

✅ What Belongs in the Gateway

"Cross-cutting concerns that apply to ALL services: authentication (verify JWT once, forward user context via headers), rate limiting, SSL termination, request/response logging, CORS, and routing rules. The BFF variant — separate gateway per client type — is also powerful: Mobile BFF aggregates and slims down response, Web BFF provides full payload."

❌ What Should NOT Go In — This Is Where You Distinguish Yourself

🚨

Business logic must NEVER go in the API Gateway. "The moment you put 'if user is premium tier, allow more results' or 'calculate shipping cost' in the gateway, you've created a monolith disguised as an API Gateway. It becomes a single point of change for business decisions, requires coordinated deployment, and you lose the independent evolution benefit."

"The gateway should be a dumb pipe with smart routing — it knows WHERE to send requests, not WHAT to do with the data. If you find yourself writing complex join-like aggregation in the gateway, that's a sign you need a dedicated Aggregation Service or a better data model, not a smarter gateway."
