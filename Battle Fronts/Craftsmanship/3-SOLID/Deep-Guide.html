5 nguyên tắc để quản lý THAY ĐỔI

SOLID không phải để code "đúng" — code sai vẫn chạy. Nó để code dễ đổi mà không gãy. Sợi chỉ xuyên suốt cả 5: quản lý phụ thuộc và sự thay đổi.

⚡ Cú lật lớn — đọc trước khi vào từng chữ

SOLID KHÔNG phải 5 luật rời rạc phải học thuộc. Cả 5 trả lời CÙNG một câu hỏi: "khi yêu cầu thay đổi, code của tôi có gãy dây chuyền không?" S gom trách nhiệm để cô lập thay đổi · O–L–I–D quản lý cách các mảnh phụ thuộc nhau qua abstraction để đổi một mảnh không kéo đổ mảnh khác. Hiểu sợi chỉ này = suy ra được cả 5, không cần thuộc lòng.

S
Single Responsibility
Một class chỉ có MỘT lý do để thay đổi. (một trách nhiệm)
O
Open–Closed
Mở để mở rộng, đóng để sửa đổi. Thêm tính năng = thêm code, không sửa code cũ.
L
Liskov Substitution
Class con thay được class cha mà không phá hành vi. (subtype đáng tin)
I
Interface Segregation
Nhiều interface nhỏ, chuyên biệt — đừng ép ai implement method họ không cần.
D
Dependency Inversion
Phụ thuộc vào ABSTRACTION, không vào implementation cụ thể. (NestJS DI sinh ra cho cái này)
🧠 Quan trọng nhất cho interview: SRP (god class vi phạm nó) và DIP (lý do tồn tại của Dependency Injection). Nhưng đừng bỏ L — Liskov là câu bẫy kinh điển (Square/Rectangle).

S · Single Responsibility — một lý do để thay đổi
⚡ Cú lật — "trách nhiệm" KHÔNG phải "một việc nhỏ"

Ai cũng đọc "một class làm một việc" rồi hỏi "vậy method save() gọi validate() có phải 2 việc không?" — kẹt ngay. Định nghĩa đúng của Uncle Bob: "một class chỉ nên có MỘT lý do để thay đổi". Trách nhiệm = một lý do để thay đổi, đo bằng số nhóm người/nghiệp vụ có thể yêu cầu sửa class này.

"Lý do để thay đổi" = ai gõ cửa bắt anh sửa

Nối thẳng God Class (gốc 2): một class có nhiều "ông chủ" — bảo mật, kế toán, team in ấn — mỗi ông có quyền bắt anh mở file này ra sửa. Mỗi ông chủ = một lý do để thay đổi.

Soi Report: nó có mấy ông chủ?

calculate() đổi khi kế toán đổi công thức. saveAsPdf() đổi khi team in ấn đổi layout/font PDF. Hai ông chủ chẳng liên quan → hai lý do thay đổi → vi phạm SRP.

SRP = gom thứ đổi cùng lý do, tách thứ đổi khác lý do

Tách Report (logic) khỏi PdfExporter (trình bày). Giờ kế toán đổi công thức → chỉ mở Report; team in đổi PDF → chỉ mở PdfExporter. Không ai giẫm chân ai.

🧭 Metaphor — dao đa năng Thụy Sĩ: tiện vì gộp 10 công cụ, nhưng muốn mài mỗi lưỡi dao phải tháo cả con dao, và không thể đưa cái kéo cho người khác dùng riêng. Class ôm nhiều trách nhiệm y vậy: đụng một phần, rung cả khối.

Đau ở đâu

Merge conflict (nhiều team sửa cùng file) · đổi format PDF lỡ tay làm vỡ logic tính tiền · khó test riêng từng phần · khó tái dùng calculate() mà không kéo theo cả PDF.

❌ 2 lý do để đổi
class Report {
  calculate() {...}   // đổi khi logic đổi
  saveAsPdf() {...}   // đổi khi format đổi
}
✅ Tách trách nhiệm
class Report       { calculate() }
class PdfExporter  { export(report) }
// mỗi class một lý do để thay đổi

Chữa

Extract Class theo lý do thay đổi. Nó chữa được gốc bệnh vì mỗi lý do thay đổi giờ có một "nhà" riêng — thay đổi bị cô lập, không lan.

👃 Mũi ngửi

1
Test chữ "VÀ"
Kể việc class làm mà cần "VÀ" nhiều lần ("tính toán VÀ xuất PDF VÀ gửi mail") → nhiều trách nhiệm.
2
Đếm "ai gõ cửa"
Nhiều team/nghiệp vụ khác nhau có quyền bắt sửa file này.
3
Method chia phe không dùng chung field
2 nhóm method không đụng data của nhau = 2 class đang trốn trong 1.
↓ Interviewer đào tiếp — thủ sẵn
"SRP có phải là 'một class một method' không?"
Không. Một class có thể nhiều method miễn chúng phục vụ CÙNG một lý do thay đổi (cohesion cao). Số method/dòng không phải thước đo.
"Vậy 'responsibility' đo bằng gì cho khỏi mơ hồ?"
Bằng "axis of change" — trục biến thiên. Hỏi: những actor/nghiệp vụ nào có thể yêu cầu sửa? Mỗi actor là một trục. >1 trục = vi phạm.
"Tách nhỏ quá thì sao — 100 class 1 method?"
Đó là thái cực ngược (Shotgun Surgery, gốc 2). SRP là gom-thứ-đổi-cùng-lý-do NGANG với tách-thứ-đổi-khác-lý-do. Cohesion cao + coupling thấp, không phải "càng nhỏ càng tốt".
🎓 Bedrock — câu gốc của Uncle Bob

"Gather together the things that change for the same reason, and separate those that change for different reasons." SRP thực chất là định nghĩa của cohesion ở cấp class. Nói được câu này + đo bằng "actor/lý do thay đổi" = anh vượt tầng junior.

O · Open–Closed — thêm code mới, không sửa code cũ
⚡ Cú lật — OCP KHÔNG phải "cấm sửa code"

Một câu duy nhất: Thêm tính năng mới thì ĐỪNG ĐỤNG code cũ. Module MỞ để thêm hành vi mới (gõ thêm class/file mới) nhưng ĐÓNG với việc mổ code đã chạy ổn. (Sửa bug thì vẫn sửa thoải mái — OCP nói về mở rộng hành vi, không cấm vá lỗi.)

"Thêm code mới" vs "sửa code cũ" — nhìn cái FILE khi ông thêm Triangle

Sửa code cũ = chèn dòng vào giữa khối đã có → đụng tay vào cục đang chạy → dễ làm vỡ cái cũ (regression), phải test lại hết. Thêm code mới = gõ thêm một khối mới ở dưới, khối cũ y nguyên. OCP = ráng làm theo kiểu thứ hai.

❌ SỬA code cũ — chèn if vào GIỮA hàm đang chạy
def area(shape):
    if shape.type == "circle": return 3.14*shape.r**2   # dòng cũ
    if shape.type == "square": return shape.side**2     # dòng cũ
    if shape.type == "triangle": ...   # 👈 mở hàm cũ ra chèn = nguy hiểm
✅ THÊM code mới — mỗi hình 1 class, code cũ không đụng
class Circle:   def area(self): return 3.14*self.r**2
class Square:   def area(self): return self.side**2
class Triangle: def area(self): return 0.5*self.b*self.h  # 👈 chỉ THÊM
Polymorphism = "cùng 1 lời gọi, mỗi object làm kiểu riêng"

Ông xài mỗi ngày mà chưa biết tên: len("hi") ra 2, len([1,2,3]) ra 3 — cùng len(), mỗi kiểu tự đo theo cách của nó. Y hệt: gọi s.area(), Circle tính kiểu tròn, Square kiểu vuông. Code gọi không cần biết s là hình gì — object tự lo.

Nhờ polymorphism, hàm gọi khỏi hỏi "mày là ai"
def total(shapes):
    return sum(s.area() for s in shapes)   # cùng gọi .area(), khỏi if, khỏi hỏi loại
Interface = bản HỢP ĐỒNG ghi "phải có hàm nào"

Hàm total() DÁM gọi s.area() nhờ một lời hứa: "ai là Shape thì BẮT BUỘC có area()". Interface chính là lời hứa đó viết thành code. Class nào muốn vào nhóm Shape phải làm đủ hàm ghi trong hợp đồng.

Hợp đồng Shape — "đã là Shape thì phải có area()"
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self): ...        # LUẬT: đã là Shape thì BẮT BUỘC có area()

class Circle(Shape):   def area(self): return 3.14*self.r**2   # ký hợp đồng
class Triangle(Shape): def area(self): return 0.5*self.b*self.h
🎯 Nói cho đúng chữ — "implement" chứ không phải "kế thừa"

Interviewer hay soi: Circle/Triangle implement (ký hợp đồng) Shape, KHÔNG phải "kế thừa" Shape. Khác nhau: kế thừa (extends) = class lấy luôn code của cha. Implement = class chỉ hứa "tui sẽ có đủ mấy hàm này" rồi tự viết ruột. Circle với Triangle không mượn code của nhau — chúng chỉ cùng ký một hợp đồng area() rồi mỗi đứa tự tính. Nói "implement" = interviewer biết ông chắc gốc.

Vì sao interface làm OCP chạy được

②
Không interface → phải check type
Code gọi buộc phải if isinstance(s, Circle)… — biết từng class, thêm loại là sửa. Dính chặt, dễ vỡ.
③
Có interface → cứ gọi .area(), khỏi hỏi
Hợp đồng đảm bảo thằng nào cũng có area() → gọi thẳng, hết isinstance, hết if.
④
→ Thêm hình khỏi sửa code gọi
total() dựa vào hợp đồng area(), không dựa tên class → thêm Triangle, total() nguyên si. Đó là OCP.

🧭 Metaphor — ổ cắm điện: interface = hình dạng cái LỖ cắm (cố định). Mọi hình phải đúng hình đó (có area()) mới cắm vừa. Lỗ cố định → cắm thêm bao nhiêu hình mới cũng được mà total() khỏi sửa. Ổ cắm (interface) đóng; thiết bị cắm vào (class mới) mở vô hạn.

🔌 Ổ cắm KHÁC cái quạt chỗ nào — interface vs class (giải thích lớp 5)

Chốt cho hết mơ hồ: interface = ổ cắm, một lời hứa — và nó KHÔNG tự làm gì cả. Ổ cắm trên tường đâu có tự quay ra gió 😅 Nó chỉ ghi: "đúng hình 2 chấu này thì cắm vừa". Class mới là cái quạt THẬT — cắm điện vào là quay, vì bên trong nó ghi rõ quay CÁCH NÀO.

🔌
Interface = tờ hợp đồng / ổ cắm
Chỉ HỨA "phải có area()". Một mình thì vô dụng, không chạy được — chưa sờ được đồ thật.
⚙️
Class = người ký rồi làm thật / cái quạt
Ghi rõ làm KIỂU NÀO (Circle tính tròn, Square tính vuông). Bấm là chạy — đồ thật, sờ được.

👉 Một câu: Interface hứa "sẽ có gì" · Class làm "và làm KIỂU NÀY". Một ổ cắm → cắm được vô số quạt khác nhau — đó là chỗ OCP gặp Polymorphism: cùng một lỗ (hợp đồng area()), mỗi hình tự tính theo cách riêng.

Đau ở đâu (khi phạm OCP)

Mỗi loại mới phải mở & sửa hàm cũ → dễ vỡ (regression) · cùng logic phân loại lặp ở nhiều nơi (nối Shotgun Surgery, gốc 2) · switch phình vô tận, khó đọc.

🧵 Cùng một sợi dây → chữ D (DIP/DI)

Cái interface ổn định mà OCP dựa vào cũng chính là móng của DIP và DI — ba cái là một hành động: đẩy phần hay-đổi ra sau một interface ổn định. Phần DIP/DI (gọi-theo-vai-trò, đảo-chiều-mũi-tên, đầu-bếp-nhận-nguyên-liệu, ai-sở-hữu-interface) nằm đầy đủ ở chữ D · Dependency Inversion bên dưới — bấm mở nó để đọc trọn.

🎤 Trả lời trong interview — khung 4 nhịp

Mọi câu SOLID đi theo: ① Định nghĩa 1 câu → ② Vấn đề nó cứu → ③ Ví dụ ngắn → ④ Lợi ích.

🎤 OCP — đọc y như vầy (English)
①
"Open-Closed means my code is open to add new behavior, but closed to modifying existing, tested code."
②
"If I have an area() function with if-else on shape type, every new shape forces me to open it and add a branch — risking the shapes that already work."
③
"Instead I define a Shape interface requiring area(), and each shape implements it. Adding a Triangle is just a new class — the loop calling .area() never changes."
④
"So I extend by adding files, not editing old ones — no risk of breaking what already works."

Chữa

Polymorphism / Strategy pattern (gốc 5): điểm-hay-thay-đổi (loại shape) được đẩy ra sau một interface ổn định — phần biến thiên tách khỏi phần cố định, nên thêm loại mới chỉ là thêm class.

👃 Mũi ngửi

1
switch/if theo "type" phình
Mỗi lần thêm loại lại thêm một nhánh vào cùng chỗ.
2
Cùng switch lặp ở nhiều hàm
switch(type) xuất hiện ở tính giá, ở render, ở export — thêm loại phải sửa hết (Shotgun).
↓ Interviewer đào tiếp — thủ sẵn
"OCP nghĩa là không được sửa code nữa à?"
Không. Sửa bug vẫn sửa. OCP nói: khi thêm HÀNH VI mới (loại mới, luật mới), lý tưởng là thêm code chứ đừng mổ code đang chạy đúng.
"Làm sao biết chỗ nào cần 'mở'?"
Ở "trục biến thiên đã biết" — chỗ anh đoán chắc sẽ có thêm loại (payment method, shape, notification channel). Đừng mở CHỖ chưa có dấu hiệu biến thiên.
"OCP có mâu thuẫn YAGNI không?"
Có thể. Abstraction sớm cho biến thiên KHÔNG tới = over-engineering. Cân: chỉ áp OCP khi đã thấy ≥2-3 loại thật (Rule of Three, gốc 2), không phải phòng xa mù quáng.
"Interface là gì, giải thích ngắn?"
Một bản hợp đồng ghi các hàm bắt buộc phải có. Class nào ký hợp đồng thì buộc làm đủ hàm đó → code gọi tin hợp đồng, gọi thẳng, khỏi check type.
🎓 Bedrock

OCP đạt được nhờ abstraction + polymorphism (nối thẳng gốc 4 & 5). Câu chốt: "tôi không tiên tri mọi biến thiên; tôi áp OCP ở trục tôi ĐÃ thấy đổi ≥2 lần, còn lại giữ đơn giản." Đó là OCP có kỷ luật, không giáo điều.

L · Liskov Substitution — con phải THAY được cha, giữ hành vi
⚡ Nói MỘT CÂU cho dễ nhớ

"Chỗ nào code đang xài CHA, tui lén thay bằng CON — chương trình vẫn phải chạy đúng y như cũ." Đó là toàn bộ LSP. Con phải thay được cha mà không ai biết, không gì vỡ.

Vì sao kế thừa rồi mà con vẫn làm vỡ được?

Khi viết class Con(Cha), máy chỉ kiểm một thứ: "Con có ĐỦ hàm của Cha không?" → đủ → cho chạy. Máy KHÔNG bao giờ kiểm "mấy hàm đó có LÀM ĐÚNG như Cha không". → Con đủ tên hàm nhưng làm bậy bên trong, máy không biết. Đó chính là chỗ LSP bị phá.

Kế thừa cho HÌNH THỨC — LSP đòi thêm HÀNH VI

Kế thừa cho con cùng tên hàm (hình thức) — compiler lo. Nhưng con phải làm đúng lời hứa của cha (hành vi) — chỉ mình lo. LSP = luật nhắc giữ vế hành vi này. Con chỉ giống hình thức mà phá hành vi = phá LSP.

🔢 Ví dụ kinh điển — Rectangle & Square, trace bằng SỐ

Rectangle (chữ nhật): rộng w và cao h độc lập. Nó hứa: 🤝 "Đổi RỘNG thì CAO giữ nguyên." — Square (vuông) bắt buộc 4 cạnh bằng nhau, nên set_width phải đổi luôn chiều cao → nuốt lời hứa của cha.

❌ Square phá lời hứa của Rectangle (Python)
class Rectangle:
    def set_width(self, w):  self.w = w      # đổi rộng
    def set_height(self, h): self.h = h      # đổi cao
    def area(self):          return self.w * self.h

class Square(Rectangle):
    def set_width(self, w):  self.w = self.h = w   # 👈 ÉP cao bằng luôn!
    def set_height(self, h): self.w = self.h = h   # 👈 phá lời hứa

def test(r):
    r.set_width(5); r.set_height(4)   # ai cũng nghĩ area = 5×4 = 20
    print(r.area())
# Rectangle → 20 ✅   |   Square → 16 ❌ 😱
✅ Đừng ép "là" giả — cho cả hai là Shape (Python)
class Rectangle(Shape):
    def area(self): return self.w * self.h

class Square(Shape):
    def area(self): return self.side ** 2

# không ai kế thừa ai → không có lời hứa nào bị phá → không vỡ
🔴
Thả Rectangle thật
rộng=5, cao=4 (độc lập) → area = 20 ✅ đúng như hàm test tin.
🔴
Thả Square vào
set_width(5)→ cả 2 =5; rồi set_height(4)→ cả 2 =4 → area = 16 ❌ hàm test tính SAI mà không hề biết.
💡 Bài học giật mình — bug KHÔNG nằm ở Square

Square viết không sai. Cái sai là quyết định bắt Square kế thừa Rectangle. Toán học "vuông là chữ nhật" đúng, nhưng hành vi khác nhau (một đứa giữ chiều cao, một đứa không). Mô hình hóa theo danh từ ("là") mà quên hành vi → dính bẫy.

Đau ở đâu

Client buộc phải if isinstance(x, Square) để né → abstraction thành vô dụng · bug ẩn khó tìm (chỉ lộ khi đúng loại con đó chạy qua) · polymorphism/OCP sụp (không thay thế an toàn được nữa).

Chữa

Đừng mô hình hóa "is-a" chỉ vì toán học/từ vựng giống. Cho các loại cùng implement một abstraction đúng hành vi (Shape với area()), hoặc dùng composition. Chữa gốc vì ta không còn hứa một hợp đồng mà con không giữ nổi.

🎯 LSP KHÔNG chỉ cho kế thừa class — áp cho cả implement interface

Hiểu lầm phổ biến: "LSP chỉ về class-với-class". Sai. Chữ chìa khóa là subtype (kiểu con) = bất cứ thứ gì đứng thay được cho một kiểu. Có HAI cách tạo subtype — cả hai đều dính LSP:

🧬
Kế thừa class (extends)
Square(Rectangle) — Square là subtype của Rectangle.
📝
Implement interface
OldPrinter(Machine) — OldPrinter cũng LÀ subtype của Machine.

"Interface không có code nên miễn nhiễm" — sai. Interface không có code, nhưng có lời hứa hành vi: code gọi m.fax() tin "đã là Machine thì fax() fax được, không nổ". OldPrinter cho fax() raise → phá lời hứa → thả nó vào chỗ tin Machine = nổ = phá LSP, dù chẳng kế thừa dòng code nào. Hợp đồng ≠ code; hợp đồng = kỳ vọng hành vi.

🎤 Trả lời trong interview — khung 4 nhịp

🎤 LSP — đọc y như vầy (English)
①
"Liskov Substitution means: wherever my code uses a base type, I can pass a subtype instead and everything still works correctly — the caller never needs to know."
②
"The compiler only checks the subtype HAS the same methods. It never checks they BEHAVE the same. That gap is where LSP breaks."
③
"Classic example: Square extends Rectangle. A function sets width to 5 and height to 4, expecting area 20. A real Rectangle returns 20 — but a Square forces both sides equal, so it returns 16. The subtype silently breaks the caller."
④
"So I model by behavior, not by noun categories. If the child can't honor the parent's contract, I don't use inheritance — I use a shared abstraction like Shape, or composition."

Interviewer đào sâu → thả câu senior (nói đơn giản): "A subtype must not demand stricter input than the parent, and must not return weaker results than the parent promised." (Con không đòi hỏi khắt khe hơn cha, không trả về ít hơn cha hứa.)

"LSP chỉ áp cho inheritance thôi à?"
Không — áp cho mọi quan hệ subtype, kể cả implements interface. Bất kỳ chỗ nào code tin vào một kiểu và anh đưa một biến thể vào.
"Vì sao Rectangle/Square là ví dụ kinh điển?"
Vì nó cho thấy 'is-a' theo trực giác/toán học có thể sai theo HÀNH VI. Bài học: mô hình hóa theo hợp đồng hành vi, không theo phân loại danh từ.
"LSP liên quan gì tới OCP?"
OCP dựa trên polymorphism: thay con cho cha một cách an toàn. Nếu LSP gãy, thay thế không an toàn → OCP sụp theo. LSP là điều kiện để OCP đứng vững.
"Design by Contract nói gì về subtype?"
Con được phép: nới lỏng precondition (đòi input dễ hơn), siết chặt postcondition (trả kết quả mạnh hơn), và phải giữ invariant của cha. Làm ngược = phá LSP.
🎓 Bedrock — behavioral subtyping

LSP = behavioral subtyping (Barbara Liskov). Câu chốt: "con không chỉ cần cùng chữ ký, nó phải giữ được HỢP ĐỒNG của cha — precondition không mạnh hơn, postcondition không yếu hơn, invariant được bảo toàn." Nói được vế precondition/postcondition = anh vào hàng senior thật.

I · Interface Segregation — đừng ép ai làm method họ không cần
⚡ Nói MỘT CÂU cho dễ nhớ

"Đừng bắt một class ký cái hợp đồng có hàm mà nó KHÔNG dùng." Interface béo (fat interface) nhồi đủ thứ → MỌI class ký nó phải "khai" hết, kể cả hàm vô nghĩa với nó. ISP = giữ hợp đồng NHỎ, đúng nhu cầu.

💡 Chưa rõ interface là gì? Nó được định nghĩa kỹ (ổ cắm vs quạt, giải thích lớp 5) ở chữ O · Open–Closed bên trên — vì đó là nơi interface xuất hiện lần đầu. ISP dưới đây giả định anh đã nắm khái niệm đó.

Ký một interface = hứa làm ĐỦ HẾT hàm trong đó

Nhớ gốc: interface là hợp đồng "phải có đủ mấy hàm này". Nên nếu ai viết một hợp đồng to đùng, class nào ký cũng phải làm hết — kể cả hàm nó chẳng làm được.

Hậu quả: hàm GIẢ (raise NotImplementedError)

Máy in cùi bị ép ký hợp đồng có scan, fax → đành viết hàm giả raise NotImplementedError. Code tồn tại chỉ để thỏa interface, không có ý nghĩa thật. Đó là mùi ISP bị phá. 👃

🔗 Cú nối giật mình — interface béo đá thẳng qua LSP

Ai gọi machine.fax() tin nó fax được (hợp đồng hứa vậy) → gặp hàm giả raise → nổ. Con không giữ nổi hợp đồng cha → phá luôn LSP. Interface béo là cỗ máy đẻ ra vi phạm LSP — đó là chỗ chữ I và chữ L gặp nhau.

❌ Interface béo ép hàm giả (Python)
class Machine(ABC):        # 👈 hợp đồng TO: nhồi 3 việc
    @abstractmethod
    def print(self): ...
    @abstractmethod
    def scan(self): ...
    @abstractmethod
    def fax(self): ...

class OldPrinter(Machine):     # máy in cùi, chỉ IN được
    def print(self): ...           # ok, làm được
    def scan(self): raise NotImplementedError   # 👈 bịa cho có
    def fax(self):  raise NotImplementedError   # 👈 phá LSP 😱
✅ Chẻ hợp đồng to thành nhiều hợp đồng nhỏ
class Printer(ABC):
    @abstractmethod
    def print(self): ...
class Scanner(ABC):
    @abstractmethod
    def scan(self): ...

class OldPrinter(Printer):        # chỉ ký cái nó CẦN → hết hàm giả
    def print(self): ...
class AllInOne(Printer, Scanner):  # máy xịn ký nhiều hợp đồng nhỏ
    def print(self): ...
    def scan(self): ...
🐍 Note Python — interface viết bằng ABC

Python không có từ khóa interface (khác Java/TypeScript). Cách viết interface trong Python = class ...(ABC) với MỌI hàm đều @abstractmethod (toàn lời hứa, không ruột). Nếu nó có vài hàm ruột thật + vài hàm abstract → thành abstract class (nửa nạc nửa mỡ). Printer/Scanner ở trên toàn abstract → nên gọi là "interface" là đúng bài.

🧭 Metaphor — menu nhà hàng: menu nhồi 200 món ép mọi đầu bếp phải biết nấu hết. Menu chuyên (quán phở chỉ bán phở) để mỗi bếp giỏi đúng phần mình. Interface nhỏ = menu chuyên.

Đau ở đâu

Hàm giả rải khắp (raise/rỗng) · đổi một method mà cả đám class không dùng nó cũng phải build/deploy lại (coupling thừa) · đọc class không biết method nào thật sự dùng · lén phá LSP.

Chữa

Tách fat interface thành nhiều role interface nhỏ theo NHU CẦU client. Chữa gốc vì mỗi client chỉ phụ thuộc đúng cái nó cần — không còn hàm giả, không còn coupling thừa, không còn lén phá LSP.

🎤 Trả lời trong interview — khung 4 nhịp

🎤 ISP — đọc y như vầy (English)
①
"Interface Segregation means a client shouldn't be forced to depend on methods it doesn't use."
②
"If I have one fat interface — say Machine with print, scan, and fax — a simple printer is forced to implement scan and fax too, usually by throwing 'not supported'."
③
"Those fake methods are a smell, and they secretly break Liskov — anyone calling fax() on that printer crashes."
④
"So I split the fat interface into small, role-based ones — Printer, Scanner, Fax — and each class implements only what it actually does. No fake methods, no surprises."

D · Dependency Inversion — phụ thuộc abstraction, không implementation
⚡ Nói MỘT CÂU cho dễ nhớ

"Code logic quan trọng đừng gọi thẳng TÊN hãng cụ thể — gọi qua VAI TRÒ (interface)." OrderService đừng dính cứng GmailSender; nó chỉ cần "một thứ biết .send()". Nhưng cú lật SÂU nhất nằm ở chữ "Inversion" = ĐẢO CHIỀU MŨI TÊN (xem dưới).

Bệnh: logic dính cứng hạ tầng cụ thể

OrderService (cấp cao — luật đặt hàng) tự GmailSender() bên trong (cấp thấp — hạ tầng). Đổi Gmail→SendGrid phải mở OrderService ra sửa. Muốn unit-test phải gửi mail thật. Kẹt.

🔌 Linh hồn của DIP — chữ "Inversion" = đảo chiều MŨI TÊN (ai sở hữu interface?)

Hỏi vàng: cái ổ cắm trên tường — AI định hình dạng nó? → CĂN NHÀ, không phải hãng quạt. Nhà bảo "ổ tao 2 chấu", mọi thiết bị phải chế phích cho vừa. Nhà SỞ HỮU chuẩn ổ; thiết bị TUÂN THEO. Map qua code: OrderService (nhà) định ra "IMailer phải có send()"; Gmail (quạt) làm cho khớp.

Mũi tên = "ai phải BIẾT tới / import ai":

❌ Trước DIP — mũi tên SAI hướng
OrderService  ──import──►  GmailSender
  (logic xịn)                (đồ vặt)

# logic cúi đầu phụ thuộc đồ vặt hay thay
✅ Sau DIP — mũi tên ĐẢO lại 🔄
OrderService ──► IMailer ◄──import── GmailSender
 (logic xịn)   (nhà SỞ HỮU)            (đồ vặt)

# giờ Gmail cúi đầu import IMailer của logic

👉 Nhiều người dùng interface nhưng để nó nằm chung folder với Gmail → Gmail vẫn làm chủ, chưa đảo được gì. Interface phải thuộc lãnh thổ logic cấp cao mới là "inversion" thật.

DI = CƠ CHẾ thực hiện DIP (hình đầu bếp 🍳)

❌ Tự đẻ bên trong — mailer = GmailSender(): giống đầu bếp tự đi nuôi gà, trồng rau, xay bột rồi mới nấu — ôm hết vào người. Đổi Gmail→SendGrid phải mổ bụng đầu bếp ra sửa; muốn test phải giết gà thật (gửi mail thật).

✅ Nhận từ ngoài — def __init__(self, mailer): đầu bếp nói "đưa nguyên liệu đây, tao nấu — gà ở đâu ra kệ". Đổi provider = đưa nguyên liệu khác lúc gọi; test = đưa đồ giả (FakeSender) vào. Không đụng OrderService.

👉 Phân biệt: DIP là NGUYÊN TẮC (gọi theo vai trò + đảo chiều sở hữu interface) — thế cờ. DI là KỸ THUẬT (tiêm qua constructor) — nước đi. Đi nước DI để đạt thế DIP.

Đau ở đâu

Đổi provider (Gmail→SendGrid) = sửa class logic · KHÔNG unit-test được (không mock nổi cái tự-new bên trong) — nối thẳng Testing (gốc 6) · tái dùng logic ở ngữ cảnh khác rất khó vì nó kéo theo cả hạ tầng.

❌ Tự đẻ hạ tầng bên trong (Python)
class OrderService:
    def __init__(self):
        self.mailer = GmailSender()   # 👈 dính cứng Gmail
# đổi sang SendGrid = sửa class, khó test
✅ Inject abstraction do domain sở hữu
class IMailer(ABC):          # domain SỞ HỮU hợp đồng này
    @abstractmethod
    def send(self, to, body): ...

class OrderService:
    def __init__(self, mailer: IMailer):   # nhận từ ngoài
        self.mailer = mailer

OrderService(GmailSender())   # 🏭 production
OrderService(FakeSender())    # 🧪 test — inject mock (gốc 6)

Chữa

Định nghĩa interface do domain sở hữu, inject implementation qua constructor. Chữa gốc vì phần dễ-thay-đổi (hạ tầng) nằm sau một ranh giới ổn định, và logic trở nên test được (mock-able).

🎤 Trả lời trong interview — khung 4 nhịp

🎤 DIP — đọc y như vầy (English)
①
"Dependency Inversion means high-level business logic shouldn't depend on low-level details — both depend on an abstraction."
②
"If OrderService creates a GmailSender inside it, the logic is chained to Gmail — switching providers means editing it, and I can't test without sending real email."
③
"So OrderService depends on an IMailer interface it owns, and GmailSender implements it. The dependency arrow is inverted — infrastructure now depends on the domain's abstraction, not the other way around."
④
"This lets me swap providers or inject a mock in tests without ever touching the logic. It's the foundation of Clean and Hexagonal architecture."

Câu senior đóng đinh: "The key isn't just using an interface — it's WHO owns it. The high-level module owns the abstraction; the low-level module conforms to it." (Mấu chốt không phải "có xài interface" — mà là AI sở hữu nó. Module cấp cao sở hữu abstraction; cấp thấp tuân theo.)

↓ Interviewer đào tiếp — thủ sẵn
"DIP và DI khác nhau thế nào?"
DIP = nguyên tắc (phụ thuộc abstraction, đảo chiều sở hữu interface). DI = kỹ thuật/cơ chế cụ thể để tiêm phụ thuộc vào (constructor injection, IoC container). DI là một cách để đạt DIP.
"Ai nên SỞ HỮU cái interface IMailer?"
Module cấp cao (domain/OrderService) — đây là điểm cốt lõi của 'inversion'. Interface đặt ở tầng domain, implementation ở tầng hạ tầng. Nếu interface nằm chung package với SendGrid thì chưa đảo được gì.
"Có phải mọi thứ đều nên inject không?"
Không (YAGNI). Đảo những phụ thuộc HAY ĐỔI hoặc cần mock để test (I/O, external service). Thứ ổn định thuần túy (một hàm format ngày) không cần abstraction hóa.
"DIP giúp gì cho testing?"
Vì logic phụ thuộc interface, lúc test ta tiêm một mock/stub thay hạ tầng thật → unit test nhanh, cô lập, lặp lại được (nối FIRST, gốc 6).
🎓 Bedrock — chiều của mũi tên phụ thuộc

Câu chốt sâu nhất: "DIP không phải 'dùng interface cho sang' — nó đảo CHIỀU của mũi tên phụ thuộc để cả high-level lẫn low-level đều trỏ vào một abstraction do high-level sở hữu." Đây là nền của Clean/Hexagonal Architecture (ports & adapters). Nói được vế 'ai sở hữu interface' = anh trả lời ở tầng kiến trúc, không chỉ cú pháp.
