5 nguyên tắc để quản lý THAY ĐỔI

SOLID không phải để code "đúng" — code sai vẫn chạy. Nó để code dễ đổi mà không gãy. Sợi chỉ xuyên suốt cả 5: quản lý phụ thuộc và sự thay đổi.

S
Single Responsibility
Một class chỉ có MỘT lý do để thay đổi. (một trách nhiệm)
O
Open–Closed
Mở để mở rộng, đóng để sửa đổi. Thêm tính năng = thêm code, không sửa code cũ.
L
Liskov Substitution
Class con thay được class cha mà không phá hành vi. (subtype đáng tin)
I
Interface Segregation
Nhiều interface nhỏ, chuyên biệt — đừng ép ai implement method họ không cần.
D
Dependency Inversion
Phụ thuộc vào ABSTRACTION, không vào implementation cụ thể. (NestJS DI sinh ra cho cái này)
🧠 Quan trọng nhất cho interview: SRP (god class vi phạm nó) và DIP (lý do tồn tại của Dependency Injection).
② Smell → Fix (thấy tận mắt)

S — Single Responsibility

❌ 2 lý do để đổi
class Report {
  calculate() {...}   // đổi khi logic đổi
  saveAsPdf() {...}   // đổi khi format đổi
}
✅ Tách trách nhiệm
class Report       { calculate() }
class PdfExporter  { export(report) }

O — Open/Closed (bỏ if/else theo type)

❌ Mỗi loại mới phải sửa hàm
area(shape) {
  if (shape.type==='circle') ...
  if (shape.type==='square') ...
  // thêm 'triangle' → sửa ở đây 😱
}
✅ Polymorphism
interface Shape { area(): number }
class Circle implements Shape {...}
// thêm Triangle = thêm class mới,
// KHÔNG sửa code cũ

D — Dependency Inversion (đất của NestJS)

❌ Bám implementation cụ thể
class OrderService {
  mailer = new SendGridMailer(); // cứng
}
// đổi sang SES = sửa class, khó test
✅ Inject abstraction
class OrderService {
  constructor(private mailer: IMailer) {}
}
// đổi provider = đổi binding,
// test = inject mock
③ Trong code THẬT của anh

4
"Service này new-up SendGrid bên trong. Vấn đề gì? Nguyên tắc nào?"
→ Vi phạm DIP: bám implementation cụ thể → khó đổi, khó test. Inject IMailer. (áp dụng tại chỗ)
5
"DIP có phải overkill cho app nhỏ không?"
→ Đôi khi CÓ — YAGNI. DIP đáng khi cái phụ thuộc thật sự hay đổi hoặc cần mock để test. Trừu tượng hóa MỌI thứ = over-engineering. Đây là phán đoán, không phải luật cứng. (bedrock)
