Viết test TRƯỚC — để thiết kế, không phải để kiểm tra

TDD đảo ngược thứ tự: test trước, code sau. Nhưng bí mật lớn nhất — và là điều interview muốn nghe — là: TDD không phải kỹ thuật testing, nó là kỹ thuật THIẾT KẾ. Viết test trước ép anh nghĩ về interface, về cách dùng, trước khi nghĩ về implementation.

⚡ Cú lật lớn — vì sao anh từng fail gốc này

Người ta học TDD như "quy trình viết test" và trả lời phỏng vấn bằng định nghĩa Red-Green-Refactor thuộc lòng → interviewer đào tầng 3 ("kể MỘT vòng cụ thể anh làm") là lộ ngay. TDD thật là một cảm giác thiết kế: viết test trước = dùng code từ phía client trước khi có ruột → nếu khó viết test, anh CẢM được thiết kế đang tệ NGAY LẬP TỨC. Gốc này dạy anh kể được một vòng thật, có số, và giải thích vì sao mỗi nhịp tồn tại.

Cụ thể trong 30 giây — vì sao "test trước" LÀ thiết kế

Bỏ chữ "interface", "client" sang một bên. Xem code thật. Giả sử anh cần một hàm cộng — anh viết test TRƯỚC, lúc hàm còn chưa tồn tại:

test_cong — viết khi ruột chưa có
def test_cong():
    assert cong(2, 3) == 5   # "Ê cong, đưa 2 và 3 → mày PHẢI trả 5"

Chỉ để gõ được đúng dòng này — dù ruột chưa có — anh đã buộc phải quyết định 3 điều, trước khi nghĩ tới chuyện bên trong cộng kiểu gì:

  • Hàm tên cong (không phải tinh_tong, add, plus…)
  • Nó nhận 2 số, theo thứ tự (2, 3)
  • Nó trả về kết quả (nên mới == 5 được) — không phải in ra màn hình, không sửa biến ngoài

Ba quyết định đó = thiết kế CÁCH DÙNG trước CÁCH LÀM. Test chỉ là cái cớ ép anh làm điều đó. Chữ "client" trong sách = "kẻ gọi hàm", và test chính là kẻ gọi đầu tiên → nên test-first ép code phải dễ gọi.

🎯 Chỗ vàng — thiết-kế-xấu thành đau-tay tức thì

Nếu để test được cong(2,3)==5 mà anh phải dựng cả database + user session + load config… anh sẽ thấy đau tay NGAY lúc gõ test → "sao tính cái đơn giản mà cần đống rác này?". Đó là lúc TDD hét vào mặt anh: thiết kế đang tệ. TDD biến thiết-kế-xấu từ thứ vô hình thành thứ đau tay tức thì — đó là vì sao nó là kỹ thuật thiết kế.

Mổ tới xương — để kể được một vòng THẬT

Mỗi mục: cú lật → xây từ số 0 → code → interviewer đào tiếp → câu chốt senior. Bấm để mở.

🗺️ Bản đồ — bấm để nhảy & mở
🔴 RED 🟢 GREEN 🟡 REFACTOR 🎯 TDD là THIẾT KẾ 🎣 Fake it / Triangulation 🚫 Khi KHÔNG dùng TDD ⚠️ Lỗi hay gặp (TDD giả)
🔴 RED — viết test FAIL trước, và thiết kế interface tại đây
⚡ Cú lật — RED không phải "viết test", mà là "chứng minh test CÓ THỂ đỏ vì đúng lý do" + thiết kế

Nếu một test mới viết mà XANH ngay → nó vô dụng (không test gì, hoặc test sai). RED bắt anh thấy nó đỏ vì đúng lý do trước. Và bí mật: chính lúc viết test này, anh đang THIẾT KẾ interface — quyết tên hàm, tham số, kiểu trả về, từ phía người DÙNG, trước khi có ruột.

🔔 Đỏ để LÀM GÌ? — như bấm thử cái báo khói

Một test có một việc duy nhất: gào lên khi code sai. Nhưng làm sao biết nó BIẾT gào? Lắp báo khói lên trần xong, anh bấm nút test để nghe tiếng "bíp" — bằng chứng nó còn sống, thật sự phát hiện được. RED chính là tiếng "bíp" đó. Thấy test đỏ = chứng minh cái bẫy CÒN HOẠT ĐỘNG. Bỏ qua RED (viết test → xanh luôn) = lắp báo khói mà không bấm thử: nó xanh đó, nhưng anh không bao giờ biết xanh vì code đúng hay vì nó hỏng, chả kiểm tra gì → an toàn giả 🪤.

Viết test cho hành vi CHƯA có → phải đỏ

Hàm chưa tồn tại → test gọi nó sẽ fail. Đó là điều đúng. Đỏ = "tôi đã mô tả một hành vi mà hệ thống chưa làm được."

"Đỏ vì đúng lý do" = đỏ vì GIÁ TRỊ TRẢ VỀ SAI, không phải typo

"Lý do" = nguyên nhân khiến nó đỏ. Ta muốn đỏ vì đúng MỘT nguyên nhân: "hành vi chưa đúng — kết quả trả về sai với cái tôi mong" (dòng assert bắt được). KHÔNG phải đỏ vì gõ sai tên, quên import, lỗi cú pháp — mấy cái đó cũng đỏ, nhưng đỏ nhầm lý do → vô nghĩa.

2 loại đỏ — loại nào mới chứng minh được "thước đo"

Đỏ kiểu 1 (cong is not defined): test té NGAY khi gọi hàm, chưa chạy tới assert → mới nói được "chưa có gì để đo". Đỏ kiểu 2 (expected 5 but got 4): test chạy tới tận assert, và chính assert bắt được cái sai → chứng minh thước đo hoạt động. Kiểu 1 tạm ok ở bước đầu (hàm chưa đẻ), nhưng người giỏi đẩy nhanh tới kiểu 2.

RED = viết CALL-SITE trước = thiết kế outside-in

Viết applyDiscount(1_200_000) trong test TRƯỚC khi có hàm → anh vừa quyết: nó nhận một số, trả một số. Anh thiết kế API từ nhu cầu dùng, không từ implementation. Nếu để dựng được test phải setup 10 thứ → cảm ngay coupling xấu, sửa thiết kế trước khi viết ruột.

🔴 RED — test trước, chạy → FAIL (chưa có hàm)
it('giảm 10% khi total > 1tr', () => {
  expect(applyDiscount(1_200_000)).toBe(1_080_000);
});
// ❌ FAIL: applyDiscount is not defined — TỐT, test có ý nghĩa

Đau nếu bỏ RED

Test không bao giờ thấy đỏ → có thể nó không test gì (false safety) · viết test SAU code → test uốn theo implementation đã có, mất giá trị thiết kế.

↓ Interviewer đào tiếp
"Vì sao phải THẤY đỏ trước? Tôi tin test tôi đúng mà."
Vì test xanh-ngay có thể do: assert sai, test không chạy nhánh đó, hoặc code đã vô tình đúng. Thấy đỏ → xanh chứng minh CHÍNH test này phát hiện được sự khác biệt. Không thấy đỏ = an toàn giả.
"Đỏ vì compile error có tính là RED không?"
Tạm được ở bước đầu (hàm chưa tồn tại), nhưng lý tưởng là đỏ ở ASSERTION. Compile error chỉ nói 'chưa có gì', assertion fail nói 'hành vi chưa đúng' — cái sau mới xác nhận test đo đúng thứ.
"RED giúp thiết kế bằng cách nào?"
Anh viết cách DÙNG (call-site) trước → quyết interface từ góc client → API tự nhiên hơn. Nếu để dựng test phải setup 10 thứ → anh cảm ngay coupling xấu, sửa thiết kế trước khi viết ruột.

"Chạy test và TIÊN ĐOÁN nó fail thế nào." Test đỏ đúng như anh dự đoán = anh thật sự hiểu mình đang làm gì. RED không phải thủ tục — nó là một dự đoán được xác nhận.

🟢 GREEN — code TỐI THIỂU cho xanh, kể cả xấu
⚡ Cú lật — mục tiêu GREEN KHÔNG phải code đẹp, mà là XANH nhanh nhất

Ở GREEN anh đội mũ "make it work" — viết ít code NHẤT có thể để test xanh, kể cả xấu, kể cả hardcode. Đẹp để dành cho REFACTOR. Trộn hai việc = mất nhịp. Và: đừng viết code cho case chưa có test (YAGNI).

📝 Nền tảng — 1 test = 1 CÂU HỎI kiểm tra = 1 ví dụ

Một test chỉ soi MỘT tình huống cụ thể: assert cong(2,3)==5 nói đúng một câu — "đưa 2 và 3 → phải ra 5". Nó KHÔNG kiểm tra quy luật chung. Như chấm một học sinh bằng đúng một câu "2+3=?": nó trả "5" — anh vẫn chưa dám chắc nó BIẾT cộng (có thể học vẹt, đoán bừa, hay câu nào cũng phang 5). Muốn chắc → ra thêm câu khác. Mỗi test = một câu hỏi. Một câu chưa ghim chặt hành vi — như đóng 1 cây ghim, tấm poster vẫn xoay được; đóng cây ghim thứ 2 mới khoá cứng.

Chỉ viết đủ để pass test HIỆN TẠI

Không thêm nhánh "phòng xa", không tổng quát hóa sớm. Test đòi gì, đáp đúng thứ đó.

Được phép "fake it" — viết code GIẢ VỜ, trả hằng số

Fake it = viết code trả về sẵn đúng kết quả test đang đòi, KHÔNG thật sự làm logic — như thằng học sinh chép đáp án "5" chứ không cộng. Test đầu đòi applyDiscount(1_200_000)===1_080_000? Cứ return 1_080_000 cứng cho XANH. Rồi test thứ 2 (input khác) ra "đề lệch tủ" → cái fake trả sai → đỏ → buộc anh thay hằng số bằng logic thật. Lấy nhiều điểm để định vị lời giải = triangulation (toggle riêng).

Code xấu ở đây KHÔNG sao

Vì bước REFACTOR ngay sau sẽ dọn, và test xanh làm lưới. "Make it work" trước, "make it right" sau — hai mũ, không đội cùng lúc.

🟢 GREEN — code tối thiểu để pass
function applyDiscount(total) {
  if (total > 1_000_000) return total * 0.9;
  return total;
}
// ✅ PASS. Không thêm gì thừa.

Đau nếu vi phạm

Viết quá nhiều (gold-plating) → code không có test bảo vệ, phình rủi ro · nhảy thẳng sang tối ưu → mất bước nhỏ, khó truy khi đỏ.

↓ Interviewer đào tiếp
"Code xấu ở GREEN có sao không?"
Không — miễn test xanh. REFACTOR ngay sau sẽ dọn với lưới an toàn. Ép đẹp ngay ở GREEN là trộn hai việc, dễ vừa sai vừa bẩn.
"Vì sao phải TỐI THIỂU?"
YAGNI: code cho case chưa có test = code không được bảo vệ + có thể không bao giờ cần. Giữ bước nhỏ để mỗi lúc chỉ một thứ có thể sai.
"Return hằng số (fake) có phải gian lận?"
Không — đó là kỹ thuật hợp lệ ('fake it till you make it'). Nó giữ vòng lặp cực nhỏ; test tiếp theo (input khác) sẽ buộc anh thay hằng số bằng logic thật.
🎤 4 nhịp trả lời interview — "GREEN để làm gì? Sao lại cho phép code xấu?"

"Kent Beck: 'make it work → make it right → make it fast', đúng thứ tự. GREEN chỉ lo 'work'; 'right' là việc của REFACTOR với lưới test đã xanh. Nói được vế TÁCH make-it-work khỏi make-it-right = hiểu vì sao GREEN cho phép code xấu: không phải ẩu, mà cố ý hoãn cái đẹp để giữ nhịp."

"Make it work, make it right, make it fast" — theo THỨ TỰ. GREEN chỉ lo 'work'. Câu chốt: "tôi không tối ưu/đẹp hóa ở GREEN; tôi để REFACTOR làm 'right' với lưới test đã xanh." Nói được vế 'tách make-it-work khỏi make-it-right' = anh hiểu nhịp.

🟡 REFACTOR — dọn với lưới, KHÔNG đổi hành vi
⚡ Cú lật — bước hay bị BỎ, và bỏ nó thì TDD thoái hóa

Giờ test đã xanh = anh có LƯỚI. REFACTOR = dọn cấu trúc (đổi tên, tách hàm, bỏ lặp) mà KHÔNG đổi hành vi — test phải vẫn xanh suốt. Nhiều người bỏ bước này → code "green nhưng bẩn dần" → TDD thoái hóa thành test-first spaghetti.

📐 Định nghĩa NGHIÊM — "cấu trúc" vs "hành vi"

Hành vi = "đưa input gì → ra output gì", nhìn từ BÊN NGOÀI. Cấu trúc = cách code tổ chức BÊN TRONG (tên biến, tách hàm, bỏ lặp). Refactor = giữ nguyên hành vi, CHỈ đổi cấu trúc. Chữ "refactor" bị lạm dụng khủng khiếp ngoài đời — người ta gọi cả việc thêm tính năng / sửa hành vi là "refactor". SAI. Hành vi phải ĐÓNG BĂNG, chỉ hình dạng được đổi.

Đổi CẤU TRÚC, KHÔNG đổi HÀNH VI (nối gốc 7)

Đặt tên cho số ma (DISCOUNT_RATE), tách biểu thức, bỏ lặp — nhưng input→output giữ NGUYÊN. Đưa 1_200_000 vào, trước và sau đều ra 1_080_000. Các nước đi Extract Function / Rename / Extract Class… chính là công cụ của gốc 7.

Phép thử VÀNG — chạy lại bộ test cũ

Dọn xong, chạy lại ĐÚNG bộ test cũ: vẫn xanh hết → anh chỉ đổi cấu trúc, hành vi còn nguyên. Nếu một test đỏ → anh đã lỡ đổi hành vi → đó KHÔNG phải refactor, đó là gây bug.

Dám dọn không sợ nhờ cái LƯỚI 🍳

Test xanh = lưới an toàn. Chỉnh một tí → chạy test ngay → xanh thì chỉnh tiếp, đỏ thì undo liền. Không có lưới thì mỗi lần dọn là một lần nhắm mắt cầu may. Như dọn bếp NGAY khi vừa nấu xong (còn nhớ đồ ở đâu): nếm thấy ngon rồi (xanh) thì lau bếp không làm đổi vị món (không đổi hành vi).

Chỉ refactor khi ĐANG XANH — không bao giờ trên nền đỏ

Đây là bẫy tinh nhất của cả nhịp — xem box đỏ "Vì sao KHÔNG refactor trên nền đỏ" ngay dưới.

Nhịp HAY BỊ BỎ nhất → bỏ là TDD chết

Nhiều người làm RED→GREEN→(bỏ qua)→RED→GREEN… code lúc nào cũng xanh nhưng bẩn dần đều → đống "test-first spaghetti". Bỏ REFACTOR = không còn TDD, chỉ còn "test-first".

Khi nào DỪNG — đừng gold-plate

Dọn ĐỦ sạch cho bước kế tiếp là dừng, không đánh bóng tới hoàn mỹ vô hạn (gold-plating). Refactor phục vụ khả năng thay đổi tiếp theo, không phải để đẹp mắt.

🟡 REFACTOR — dọn, test vẫn xanh
// TRƯỚC (xanh nhưng xấu — 1000000 & 0.9 là số ma)
function applyDiscount(total) {
  if (total > 1000000) return total * 0.9;
  return total;
}
// SAU (hành vi Y HỆT, chỉ sạch hơn)
const DISCOUNT_THRESHOLD = 1_000_000;
const DISCOUNT_RATE = 0.1;
function applyDiscount(total) {
  const eligible = total > DISCOUNT_THRESHOLD;
  return eligible ? total * (1 - DISCOUNT_RATE) : total;
}
// ✅ 1_200_000 → 1_080_000 cả hai. Tên rõ (gốc 1), an toàn (gốc 6-7)
🔴 Vì sao KHÔNG refactor trên nền ĐỎ — bẫy tinh nhất

Màu của test là TÍN HIỆU: anh cần nó ĐỔI MÀU để biết mình vừa làm gì. Đang xanh → dọn một tí → chạy test: vẫn xanh = an toàn; chuyển đỏ = 🚨 "động tác vừa rồi làm gãy hành vi" → undo. Chính cái xanh→đỏ đó là chuông báo.

Nhưng nếu BẮT ĐẦU trên nền đỏ — giả sử code đang bug total * 0.8 nên test đỏ (ra 960k, mong 1.080k) — anh nhảy vào dọn, lỡ tay đổi > thành >=, chạy lại → vẫn đỏ. Nó đỏ vì bug 0.8 cũ? Vì động tác dọn vừa rồi đẻ bug mới? Hay vừa sửa được 0.8 nhưng gãy chỗ khác? Anh KHÔNG phân biệt được — màu không đổi, chuông đã kêu sẵn nên tiếng mới chìm vào tiếng cũ. Bug-có-sẵn và bug-mới trộn chung một màu đỏ = mất khả năng truy nguyên.

🔔 Nối metaphor báo khói (nhịp RED): refactor trên XANH = sửa nhà lúc báo khói đang IM → gây cháy là "BÍP" liền, biết ngay. Refactor trên ĐỎ = sửa nhà lúc báo khói đang hú sẵn → đám cháy mới chìm trong tiếng hú cũ. Cần sự im lặng (xanh) làm nền thì một tiếng bíp mới có nghĩa → đỏ thì làm XANH trước (việc của GREEN) rồi mới dọn. Đừng dọn khi đang chảy máu.

Nợ kỹ thuật tích tụ dưới lớp "toàn xanh" · code ngày càng khó đọc/đổi · vòng sau chậm dần vì phải bơi trong code bẩn.

🎯 TDD là kỹ thuật THIẾT KẾ — câu chốt interview muốn nghe
⚡ Cú lật LỚN NHẤT — TDD không phải hoạt động QA/testing

Nếu anh coi TDD là "cách viết test cho nhiều/đúng hơn" → anh trả lời sai trọng tâm. TDD là kỹ thuật THIẾT KẾ: test chỉ là sản phẩm PHỤ; sản phẩm CHÍNH là một thiết kế decoupled, dễ dùng. Cơ chế: viết test trước = dùng API trước khi có ruột + code khó test làm anh đau NGAY → buộc thiết kế tốt.

Viết test trước = viết CALL-SITE trước = quyết interface theo nhu cầu

Anh mô tả "tôi muốn dùng thứ này thế nào" trước khi xây ruột → API sinh ra từ góc người dùng, tự nhiên và tối giản hơn.

Code khó test → anh CẢM đau ngay → buộc decouple (nối DIP)

Muốn test OrderService mà nó new SendGridMailer() bên trong → không mock nổi → đau NGAY ở bước viết test → anh sửa thành inject (DIP, gốc 3). TDD biến "thiết kế xấu" thành nỗi đau tức thì, không để nó ẩn.

😖 Khó test → thiết kế đang tệ
class OrderService:
    def place(self, order):
        mailer = SendGridMailer()  # tạo CỨNG bên trong
        mailer.send(order.email)
# test? không thay SendGrid bằng bản giả được
# → chạy test là GỬI MAIL THẬT 😱
😌 Dễ test → thiết kế tốt (DIP)
class OrderService:
    def __init__(self, mailer):  # TIÊM từ ngoài
        self.mailer = mailer
    def place(self, order):
        self.mailer.send(order.email)
# test: đưa FakeMailer vào → kiểm tra
# mà KHÔNG gửi mail thật ✅

👆 Nỗi đau "không test được" ở bản trái chính là feedback — nó chỉ đúng vào chỗ coupling xấu, ép anh lật sang bản phải. Không TDD thì cái coupling này ẩn tới lúc bảo trì mới lộ.

Test là sản phẩm phụ; thiết kế tốt là sản phẩm chính

Cuối vòng anh có cả hai: một bộ test hồi quy + một thiết kế đã được "ép" phải decoupled để test được. Cái sau mới là giá trị lớn.

🧭 Metaphor: thiết kế cái REMOTE (nút bấm, cách cầm — trải nghiệm dùng) TRƯỚC khi thiết kế mạch điện bên trong. Test-first = bắt đầu từ trải nghiệm dùng.

↓ Interviewer đào tiếp

🎣 Fake it & Triangulation — hai chiến thuật đi từ đỏ sang xanh
⚡ Cú lật — có KỸ THUẬT để giữ bước cực nhỏ, không phải "nghĩ ra cả hàm"

Beck cho 3 cách đi từ RED sang GREEN: Fake it (trả hằng số rồi dần thay bằng logic), Triangulation (thêm test case thứ 2 ép tổng quát hóa), và Obvious implementation (nếu rõ ràng thì viết thẳng). Mục tiêu: giữ bước nhỏ đến mức luôn kiểm soát được.

Fake it — pass test đầu bằng hằng số

Test đòi sum(2,3)===5? Cứ return 5. Nghe ngớ ngẩn, nhưng nó giữ vòng lặp XANH và cực nhỏ.

Triangulation — test thứ 2 ép generalize

Thêm sum(4,7)===11 → hằng số 5 không đủ → anh BUỘC phải viết return a+b. Hai điểm xác định một đường thẳng — hai test "tam giác hóa" ra logic thật.

Obvious implementation — rõ thì viết thẳng

Không phải lúc nào cũng fake. Nếu logic hiển nhiên (a+b) và anh tự tin → viết thẳng. Fake it dành cho lúc chưa chắc/muốn bước nhỏ.

1️⃣ Fake it (pass test đầu)
function sum(a, b) {
  return 5;   // đủ pass sum(2,3)
}
2️⃣ Triangulate → logic thật
// thêm test: sum(4,7) === 11
function sum(a, b) {
  return a + b;  // hằng số hết đủ → generalize
}
🪤 Vì sao 1 test CHƯA ĐỦ — test thứ 2 là cái BẪY bắt code gian lận

Với CHỈ test sum(2,3)==5, hàng loạt code RÁC vẫn XANH — bộ test không phân biệt nổi hàng thật với hàng giả:
• return a + b → ✅ (đúng thật)
• return 5 → ✅ (rác)
• return a * b - 1 → ✅ vì 2×3−1=5 (rác)
• return 2 + 3 → ✅ (rác)

Thêm test sum(4,7)==11 → ba thằng rác chết sạch (5≠11 · 27≠11 · 5≠11), chỉ a+b sống sót. Đó là toàn bộ tác dụng của test thứ 2: mỗi test thêm vào = một cái BẪY nữa; càng nhiều bẫy, càng ít chỗ cho code gian lận trốn. "Triangulation" chỉ là cái TÊN cho việc này — không phải phép thuật gì.
↓ Interviewer đào tiếp

Nó giữ bước CỰC nhỏ: luôn có test xanh làm mốc, giảm rủi ro viết sai một mạch dài. Đây là kỷ luật 'baby steps', không phải lười.
"Khi nào fake, khi nào viết thẳng?"

"Triangulation lúc nào cần?"
Khi một ví dụ chưa đủ ràng buộc để suy ra logic tổng quát. Thêm ca thứ 2 (thứ 3) buộc code phải tổng quát thay vì khớp cứng một ca.

🚫 Khi KHÔNG nên TDD — công cụ, không phải tôn giáo
⚡ Cú lật — biết KHI NÀO KHÔNG dùng mới là senior

TDD toả sáng ở logic có hợp đồng rõ (business rules, thuật toán, bug fix). Nó vụng ở chỗ anh CHƯA biết mình muốn gì, hoặc hành vi khó assert. Trả lời "TDD cho mọi thứ, luôn luôn" = dấu hiệu học vẹt, không có kinh nghiệm thật.

Chỗ TDD KHÔNG hợp (hoặc phải điều chỉnh)

1
Spike / prototype khám phá — "chưa biết mình muốn gì"
Gọi một API lạ chưa biết nó trả về gì, hay chưa chọn được cách làm (thư viện A hay B? nổi không?). Đích còn di chuyển → viết test trước là vô nghĩa. Vọc tự do để HỌC, rồi VỨT prototype và TDD lại phần giữ.
2
UI thuần visual / animation
"Trông đẹp" khó assert bằng test tự động. Dùng review mắt / snapshot có chọn lọc, không TDD từng pixel.
3
Code throwaway / script một lần
Ví dụ: script đổi format 1000 file CSV, chạy đúng MỘT lần rồi xoá. Không có "về sau" để bảo vệ → chi phí test > lợi ích. Không phải mọi dòng đều đáng bọc test.
🎯 Thước đo 1 câu — spike hay TDD?

Tự hỏi: "Ngay lúc này tôi viết được dòng assert … == … mà TỰ TIN nó đúng không?" — KHÔNG (chưa biết đáp án) → đang spike, đừng TDD. CÓ (biết chắc đích) → TDD ngay. Dấu hiệu nhìn code: spike đầy print (đang HỎI), code TDD đầy assert (đang KHẲNG ĐỊNH).

🔍 SPIKE — vọc để HỌC (print, KHÔNG assert), rồi VỨT
r = requests.get("...openweather.../weather?q=Hanoi")
print(r.json())   # chỉ để XEM nó trả gì — chưa biết đáp án nên KHÔNG assert được
# → thấy {"main":{"temp":298.15}} — À, temp ở main.temp, đơn vị KELVIN!
# "chưa biết" đã thành "đã biết" → vứt spike, giờ mới TDD được:
def test_doi_kelvin():
    assert to_celsius(298.15) == 25   # giờ viết assert được vì đã biết đích

"Spike xong thì làm gì?"

"Bug fix nên TDD thế nào?"

"'Spike then stabilize': vọc tự do chỗ mơ hồ để học, rồi VỨT code thăm dò và harden bằng test — đừng để nó lọt thẳng vào production không test. Và cảnh giác 'nothing is more permanent than a temporary solution': code throwaway mà sống dai thì phải bọc test lại."
🎓 Bedrock

Câu chốt: "TDD là công cụ, không phải tôn giáo. Tôi TDD chỗ có hợp đồng rõ (logic/rules/bug), explore tự do chỗ mơ hồ rồi hardening bằng test sau. Biết CHỌN chỗ dùng mới là kỹ sư, không phải người đọc sách." Nói vầy tránh được cả hai bẫy: chê TDD lẫn sùng TDD mù quáng.

⚠️ Lỗi hay gặp — "TDD giả" — chính là chỗ anh vừa fail
⚡ Cú lật — interviewer đào tầng sâu để phân biệt TDD THẬT với TDD GIẢ

Rất nhiều người nói "tôi làm TDD" nhưng thực ra làm "test-after" hoặc bỏ nhịp. Interviewer giỏi sẽ hỏi "kể MỘT vòng cụ thể gần đây" — người làm giả sẽ mô tả chung chung, không kể được thứ tự/cảm giác đỏ→xanh/số cụ thể. Đây là chỗ dễ trượt nhất.

6 lỗi làm TDD "giả"

1
Test-after gọi là TDD
Viết code trước, test sau, rồi nói "tôi TDD". Mất TOÀN BỘ giá trị thiết kế (test uốn theo code có sẵn).
2
Bỏ bước RED
Không bao giờ thấy test đỏ → không biết test có thật sự bắt lỗi không → an toàn giả.
3
Bỏ bước REFACTOR
Chỉ RED→GREEN mãi → code bẩn dần dưới lớp "toàn xanh".
4
Test dính implementation
Assert vào nội tạng (thứ tự lời gọi nội bộ) → vỡ mỗi lần refactor dù hành vi không đổi → người ta bỏ TDD vì "test phiền".
5
Bước quá to
Viết cả hàm phức tạp rồi mới test → mất baby-steps, khó truy khi đỏ.
6
Mock quá nhiều
Mock cả logic của mình → test giòn + không phản ánh hành vi thật (nối Mocking gốc 6).
⭐ Đào lỗi #4 — test HÀNH VI (WHAT), đừng test CÁCH LÀM (HOW)

Đây là lỗi tinh nhất, và là lý do nhiều team "làm TDD" xong GHÉT TDD. Test bám vào NỘI TẠNG (code gọi hàm nào bên trong) → mỗi lần refactor là test vỡ oan dù hành vi y hệt → người ta chửi "test phiền" → bỏ luôn REFACTOR → TDD chết. Lưới đáng lẽ đỡ anh lại RÁCH mỗi lần anh dọn.
❌ Test dính CÁCH LÀM — vỡ khi refactor
def test_apply_discount():
    service.apply_discount(order)
    assert service._rate_calc.called_once()
# soi hàm nội bộ nào được gọi → đổi tên
# helper là test đỏ oan, dù kết quả đúng
✅ Test HÀNH VI — refactor thoải mái
def test_apply_discount():
    assert apply_discount(1_200_000) == 1_080_000
# chỉ quan tâm ĐẦU VÀO → ĐẦU RA
# bên trong đổi kiểu gì cũng kệ → lưới bền

👆 Luật: test cái WHAT (input này → output kia), đừng test cái HOW (bên trong gọi gì, thứ tự nào). Test hành vi thì refactor tự do; test nội tạng thì tự trói tay mình. Lỗi #4 và #6 (mock quá nhiều) là anh em — cả hai làm test dính cách-làm → giòn.

↓ Interviewer đào tiếp — chỗ anh phải kể được VÒNG THẬT
"Làm sao tôi biết anh TDD thật hay chỉ đọc lý thuyết?"
Kể MỘT vòng cụ thể: hành vi gì, test đầu viết ra sao, thấy đỏ với message gì, code tối thiểu nào làm xanh, refactor gì. Có SỐ, có thứ tự, có cảm giác. Người làm giả chỉ nói 'red green refactor' chung chung.
"Test-after có phải TDD không?"
Không. TDD = test DRIVES design (test trước, lái thiết kế). Test-after chỉ là 'có test' — hữu ích nhưng mất phần thiết kế cốt lõi của TDD.
"Dấu hiệu một codebase 'TDD giả'?"
Test bám sát implementation (vỡ khi refactor), không có test nào từng đỏ trong lịch sử, thiếu hẳn bước refactor (code bẩn nhưng xanh), hoặc test viết cùng commit sau code lớn.
🎤 4 nhịp trả lời interview — "Làm sao tôi biết anh TDD thật hay chỉ đọc lý thuyết?"
1
Lật cái hiểu lầm
"Ai cũng đọc được định nghĩa 'red-green-refactor'. Cái đó fake được. Bằng chứng TDD thật không nằm ở định nghĩa — nằm ở việc tôi kể được MỘT vòng cụ thể có số, có thứ tự, có message đỏ."
2
Kể một vòng THẬT
"Ví dụ tôi thêm hàm tính phí trễ hạn: test đầu assert tính_phí(trễ 5 ngày)==50k → chạy đỏ, message 'not defined' → viết tối thiểu return 50000 cho xanh → thêm test trễ 10 ngày==100k, return cứng chết → generalize thành số_ngày*10000 → refactor rút hằng số. Test xanh suốt."
3
Cái bẫy phải nhắc — TDD giả
"Tôi tránh mấy dấu hiệu giả: test-after gọi là TDD (mất giá trị thiết kế), bỏ RED (an toàn giả), bỏ REFACTOR (bẩn dần), và nhất là test dính implementation — assert vào nội tạng thì vỡ mỗi lần refactor, nên tôi test HÀNH VI chứ không test cách-làm."
4
Câu chốt senior
"TDD thật để lại một dấu vết tôi CẢM được: tôi nhớ thiết kế đã đổi thế nào khi viết test trước. Đó là bằng chứng không thể fake — và là lý do tôi luôn có sẵn một vòng thật để kể, không chỉ đọc định nghĩa."
🎓 Bedrock — vá đúng chỗ anh fail

TDD thật để lại một DẤU VẾT anh CẢM được: anh nhớ được thiết kế đã đổi thế nào khi viết test trước. Câu chốt cho phỏng vấn: đừng chỉ đọc định nghĩa — kể một vòng RGR CỤ THỂ anh từng làm (hàm gì, input/output, đỏ ra sao, xanh bằng code nào, dọn gì). Đó là bằng chứng không thể fake. Làm bài tập ③ để có sẵn một câu chuyện thật.

Build một feature bằng TDD trong Asset_Platform

Đây là bài tập QUAN TRỌNG NHẤT — nó cho anh câu chuyện thật để kể ở tầng 3 & toggle "Lỗi hay gặp".

🔨 Vết sẹo capstone — build MỚI bằng TDD (40 phút)

Mấy gốc trước anh đào sẹo trong code CŨ. Gốc này tạo sẹo MỚI: chọn một hàm thuần nhỏ cần thêm vào Asset_Platform (vd: tính phí, validate một rule, format một giá trị) và làm đúng TDD:

  • 🔴 Viết test cho 1 hành vi → chạy → thấy nó FAIL (đỏ thật, đọc message).
  • 🟢 Viết code tối thiểu (fake it nếu muốn) → test PASS (xanh).
  • 🟡 Refactor → test vẫn xanh.
  • ↻ Lặp cho hành vi/edge-case tiếp theo (đúng ngưỡng? số âm? 0? — triangulate).

→ Ghi lại vòng đó như một câu chuyện có SỐ (hàm gì, input/output, đỏ message gì, xanh bằng code nào, dọn gì). Đây chính xác là câu interviewer hỏi ở tầng 3 — và là thứ đã làm anh fail. Có sẵn một vòng thật = không fail lại.

⚠️ Sân tập: nhánh riêng. Nếu Asset_Platform khó áp TDD (code dính chặt) → đó cũng là một bài học: code khó test = thiếu DIP (gốc 3).
④ Why-Ladder (cho Mock)

Interviewer đào sâu thế nào

7 bậc — đây là gốc anh MỚI fail. Leo tới đỉnh, đặc biệt tầng 3 (kể vòng thật) và tầng 7 (TDD giả).

1
"TDD là gì? Red-Green-Refactor?"
→ Viết test trước (red/fail), code tối thiểu cho pass (green), rồi dọn (refactor). (định nghĩa)
2
"Tại sao viết test TRƯỚC? Có vẻ ngược."
→ Vì TDD là kỹ thuật THIẾT KẾ, không phải testing. Test trước ép nghĩ về interface/cách dùng trước implementation; code khó test → cảm đau ngay → buộc decouple. (lý do — câu chốt)
3
"Anh từng làm TDD thật chưa? Kể MỘT vòng cụ thể."
→ DẪN SẸO Asset_Platform CÓ SỐ: "hàm applyDiscount — test 1_200_000 → 1_080_000 đỏ vì chưa có hàm; viết if > 1tr return *0.9 cho xanh; refactor tách hằng số..." (kinh nghiệm — CHỖ ANH TỪNG FAIL, phải kể được cụ thể)
4
"Tại sao bước RED quan trọng — sao không viết code luôn?"
→ RED chứng minh test thật sự fail được. Test không bao giờ đỏ = có thể test sai/vô dụng, cho an toàn giả. Đỏ vì đúng lý do (assertion). (áp dụng)
5
"Fake it / triangulation là gì? Code xấu ở GREEN có sao?"
→ Fake it = pass test đầu bằng hằng số; triangulation = thêm ca thứ 2 ép generalize; code xấu ở GREEN OK vì REFACTOR dọn với lưới. Kiểm soát kích thước bước. (chiều sâu kỹ thuật)
6
"Một vòng TDD dùng lại các gốc khác thế nào?"
→ Capstone: tên test rõ = Clean Code (g1); code tối thiểu = YAGNI/SOLID (g3); mock được = DIP (g3); test = Testing (g6); dọn = Refactoring (g7); kết quả không smell (g2). (synthesis)
7
"TDD hợp mọi chỗ không? Làm sao biết ai TDD giả?"
→ Không hợp spike/UI-visual/throwaway (công cụ, không tôn giáo). TDD giả = test-after, bỏ RED/REFACTOR, test dính implementation. Người làm thật kể được vòng cụ thể có số. (bedrock)
Đậu gốc này khi

Anh nói "TDD là thiết kế, không phải testing" VÀ giải thích được cơ chế (tầng 2), kể được MỘT vòng RGR cụ thể có số từ Asset_Platform (tầng 3 — chỗ anh từng fail), giải thích RED + fake-it/triangulation (tầng 4-5), nối capstone về 7 gốc (tầng 6), và phân biệt TDD thật/giả (tầng 7). Leo hết = vá xong vết fail.

🎓 Capstone — gốc cuối gói cả 8

Một vòng TDD chạm vào TẤT CẢ những gì anh đã học. Khi anh làm được TDD trôi chảy, nghĩa là 7 gốc kia đã nằm trong tay.
