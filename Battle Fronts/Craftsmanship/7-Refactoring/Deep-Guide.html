Refactoring

📖 Neo canon: Refactoring — Martin Fowler · Working Effectively with Legacy Code — Feathers
① Khái niệm② Deep-dive③ Trong code của anh④ Why-Ladder
① Khái niệm (framework-agnostic)

Đổi cấu trúc, KHÔNG đổi hành vi

Refactoring là cải thiện cấu trúc bên trong mà KHÔNG thay đổi hành vi bên ngoài. Input ra sao, output vẫn vậy — chỉ ruột đẹp hơn. Đây là gốc gom cả 6 gốc trước lại: anh ngửi smell (gốc 2), áp SOLID/OOP/patterns (3-5), và test (gốc 6) là tấm lưới để dọn an toàn.

⚡ Cú lật lớn — refactoring là một KỶ LUẬT có định nghĩa hẹp

"Refactor" bị dùng bừa để chỉ "sửa code lung tung cho đẹp". Định nghĩa THẬT (Fowler) hẹp và nghiêm: thay đổi cấu trúc mà KHÔNG đổi hành vi quan sát được, theo từng bước NHỎ, có test làm lưới sau mỗi bước. Không có test + không giữ hành vi = không phải refactoring, mà là viết lại (rewrite) — rủi ro hoàn toàn khác.

⚠️ Quy tắc vàng (interview test ngay): "Refactor và thêm feature là HAI việc tách rời. Không bao giờ làm cùng lúc." Trộn chung = không biết bug do refactor hay do feature mới.

Điều kiện tiên quyết: TEST trước

Có test xanh ✅
→
Refactor từng bước nhỏ
→
Test vẫn xanh ✅

Không có test = không phải refactoring, mà là "đập ra sửa và cầu nguyện". Test là cái phân biệt refactor an toàn với canh bạc. (Legacy code = code không có test — Feathers.)

Mỗi nước đi: cú lật → xây từ số 0 → code trước→sau (hành vi y hệt) → dấu hiệu kích hoạt → interviewer đào tiếp → câu chốt senior. Bấm để mở.

🗺️ Bản đồ — bấm để nhảy & mở
✂️ Extract Function 📦 Extract Class 🏷️ Rename 🔀 Replace Conditional 🎒 Parameter Object 🕸️ Legacy (không test)
✂️ Extract Function/Method — nước đi cơ bản & hay dùng nhất
⚡ Cú lật — tách theo Ý ĐỊNH, không theo độ dài

Không phải "hàm dài thì chặt bớt". Extract Function là: khi một ĐOẠN code có một Ý ĐỊNH riêng (một "chương" trong câu chuyện), kéo nó thành một hàm có TÊN nói lên ý định đó. Hàm cha đọc như mục lục; chi tiết lùi xuống (nối Long Method gốc 2).

Tìm đoạn có một ý định riêng

Trong printOwing: đoạn "tính total" và đoạn "in chi tiết" là hai ý định khác nhau, đang trộn trong một hàm.

Kéo ra thành hàm có tên nói ý định

calcTotal(orders), printDetails(invoice, total). Cái tên thay cho comment (nối Clean Code gốc 1).

Từng bước nhỏ, chạy test sau mỗi lần

Tách một hàm → chạy test → xanh → tách hàm tiếp. KHÔNG tách cả 3 chỗ một phát rồi mới test.

🧭 Metaphor — viết mục lục cho một chương sách dài: thay vì một khối văn dài dằng dặc, chia thành các mục có tiêu đề. Người đọc lướt tiêu đề (hàm cha) hiểu mạch, cần chi tiết thì đọc mục con.

❌ Trước
printOwing(invoice) {
  printBanner();
  // tính total
  let total = 0;
  for (const o of invoice.orders)
    total += o.amount;
  // in chi tiết
  console.log(`name: ${invoice.name}`);
  console.log(`total: ${total}`);
}
✅ Sau (hành vi y hệt)
printOwing(invoice) {
  printBanner();
  const total = calcTotal(invoice.orders);
  printDetails(invoice, total);
}
// mỗi hàm một việc, đọc như mục lục
// test cũ vẫn xanh = an toàn

Mỗi bước nhỏ → chạy test → xanh → bước tiếp. Không "dọn hết một phát". Đó là kỷ luật refactoring.

👃 Dấu hiệu kích hoạt

1
Comment chia đoạn bên trong hàm
// tính total, // in chi tiết — mỗi comment đó là một hàm chờ được tách.
2
Phải cuộn/nhiều tầng trừu tượng
Hàm trộn tầng cao (nghiệp vụ) với tầng thấp (vòng lặp cộng dồn).
↓ Interviewer đào tiếp
"Tách nhỏ tới mức nào là đủ?"
Tới khi mỗi hàm ở MỘT mức trừu tượng và tên nói đúng việc. Không phải 'càng nhỏ càng tốt' — tách quá vụn (hàm 1 dòng gọi 1 lần, tên dài hơn thân) cũng hại khả năng đọc.
"Khi nào INLINE (ngược lại) một hàm?"
Khi hàm quá tủn mủn, tên không thêm nghĩa gì so với thân, chỉ gọi một chỗ → inline lại cho đỡ nhảy. Refactoring có cả hai chiều.
"Extract Function có đổi hành vi không?"
Không được — đó là bản chất refactoring. Cẩn thận biến local/closure/this khi kéo ra để output y hệt. Test là lưới xác nhận.
🎓 Bedrock

Câu chốt: "tôi extract theo Ý ĐỊNH (mỗi hàm một mức trừu tượng, tên = ý định), từng bước nhỏ có test sau mỗi bước; và tôi cũng inline ngược khi một hàm không thêm nghĩa. Refactoring hai chiều." Đây là move nền tảng, dùng trong hầu hết mọi refactor lớn hơn.

📦 Extract Class — tách god class theo trách nhiệm
⚡ Cú lật — cắt ở ĐƯỜNG DAO tự nhiên, không cắt tùy tiện

Extract Class chữa God Class (gốc 2) / vi phạm SRP (gốc 3). Nhưng cắt ở ĐÂU? Không tùy tiện: cắt theo nhóm method + field đi cùng nhau (cohesion). Nhóm nào dùng chung một cụm field mà không đụng cụm khác → đó là một class đang trốn bên trong.

Tìm nhóm method + field "chơi với nhau"

Trong một class to, các method chia phe: nhóm A đụng passwordPolicy, hash; nhóm B đụng mailer, template. Hai phe không dùng chung field.

Ranh giới "không chung field" = đường dao

Đường ranh giữa hai phe chính là chỗ tách. Kéo nhóm B + field của nó ra class riêng (UserNotifier).

Class cũ GIỮ tham chiếu tới class mới (delegation)

Class cũ giờ ủy thác (delegate) việc gửi mail cho UserNotifier. Từng bước: tạo class mới → dời một method → chạy test → dời tiếp.

🧭 Metaphor — tách một nhân viên ôm-nhiều-nghề: gom việc "kế toán" cho một người, "tuyển dụng" cho người khác — chia theo NGHỀ (nhóm việc dùng chung kỹ năng), không chia bừa giữa chừng một nghề.

❌ God class trộn nghề
class UserService {
  hashPassword() {...}    // phe bảo mật
  verifyPassword() {...}  // phe bảo mật
  sendWelcome() {...}     // phe mail
  sendReset() {...}       // phe mail
}
✅ Extract theo đường dao cohesion
class PasswordHasher { hash(); verify(); }
class UserNotifier { sendWelcome(); sendReset(); }
class UserService {
  constructor(hasher, notifier) {} // delegate
}

👃 Dấu hiệu kích hoạt

1
Method chia phe không dùng chung field
Hai nhóm method thao tác hai cụm dữ liệu tách biệt = hai class.
2
Kể việc class cần chữ "VÀ" nhiều lần
Nhiều trách nhiệm / nhiều lý do thay đổi (nối SRP gốc 3).
↓ Interviewer đào tiếp
"Làm sao biết cắt ở ĐÂU?"
Nhìn cohesion: nhóm method + field nào bám chặt nhau, tách biệt với nhóm khác. Ranh giới 'không dùng chung data' là đường dao tự nhiên. Đừng cắt giữa một nhóm gắn kết.
"Rủi ro khi tách là gì?"
Làm gãy hành vi hoặc tạo coupling ngược (hai class mới gọi nhau lằng nhằng). Nên có test bọc trước, dời từng method một, test sau mỗi bước.
"Extract Class nối SRP thế nào?"
Đây chính là cách THỰC HIỆN SRP: mỗi class mới có một lý do để thay đổi. Extract Class là 'động từ', SRP là 'trạng thái đích'.
🎓 Bedrock

Câu chốt: "tôi tách theo cohesion — nhóm method+field bám nhau thành một class, ranh giới không-dùng-chung-data là đường dao. Class cũ delegate sang class mới, dời từng bước có test." Nối được Extract Class ↔ God Class (g2) ↔ SRP (g3) = anh cho thấy hiểu xuyên gốc.

🏷️ Rename — refactoring "rẻ mà lời nhất"
⚡ Cú lật — đổi tên là hành động thiết kế, không phải chuyện vặt

Đổi tên nghe tầm thường, nhưng nó là refactoring có ROI cao nhất: tên tồi bắt MỌI người đọc giải mã MỖI lần. Một cái tên tiết lộ ý định = tài liệu sống không bao giờ lỗi thời (nối Clean Code gốc 1). Khi anh KHÔNG đặt được tên tốt → đó là dấu hiệu anh chưa hiểu rõ cái mình viết.

Tên tồi = chi phí đọc lặp lại vô hạn

d, tmp, handle(), data — mỗi người đọc phải suy ra nghĩa mỗi lần. Nhân với số lần đọc = chi phí khổng lồ.

Đổi tên = viết lại tài liệu bằng chính code

activeUsers, daysSinceLogin — đọc là hiểu, không cần comment. Tên không lỗi thời như comment.

Không đặt được tên tốt = chưa hiểu / làm quá nhiều việc

Nếu một hàm khó đặt tên vì nó "làm nhiều thứ" → tín hiệu cần Extract trước, rồi mỗi phần đặt tên dễ.

🧭 Metaphor — dán nhãn đúng lên hộp đồ: hộp ghi "đồ linh tinh" bắt anh mở ra tìm mỗi lần. Hộp ghi "dây sạc + tai nghe" thì với tay là biết. Tên biến/hàm là cái nhãn đó.

❌ Tên bắt giải mã
const d = u.filter(x => x.s === 1);
if (diff > 7) {...}
✅ Tên tiết lộ ý định
const activeUsers = users.filter(
  u => u.status === Status.Active);
if (daysSinceLogin > INACTIVE_THRESHOLD) {...}

👃 Dấu hiệu kích hoạt

1
Tên viết tắt / mơ hồ
d, tmp, res, mgr, handle(), process() — cần giải mã.
2
Comment giải thích tên
Nếu phải comment "biến này là số ngày..." → hãy đặt tên đó vào biến.
↓ Interviewer đào tiếp
"Đổi tên có phá gì không?"
Trong scope nội bộ + có IDE/test bọc thì an toàn (IDE đổi mọi tham chiếu). Nguy hiểm nếu là API public/tên serialize (DB column, JSON field, event name) — cần versioning/migration, không đổi bừa.
"Không đặt được tên tốt thì làm gì?"
Đó là tín hiệu chưa hiểu rõ hoặc hàm làm quá nhiều việc. Extract/tách trách nhiệm trước, rồi mỗi mảnh đặt tên dễ hơn. Tên khó = mùi thiết kế.
"Vì sao Rename là ROI cao nhất?"
Chi phí thấp (IDE làm), rủi ro thấp (scope nội bộ), lợi ích lặp lại mỗi lần đọc mãi về sau. Code được đọc nhiều hơn viết (gốc 1) nên cải thiện khả năng đọc là đầu tư lời nhất.
🎓 Bedrock

Câu chốt: "tên là tài liệu sống — tôi đổi tên để tiết lộ ý định; khi KHÔNG đặt nổi tên tốt, đó là tín hiệu cần tách trách nhiệm trước. Cẩn thận với tên public/serialize (cần migration)." Coi Rename là hành động thiết kế = anh trên tầm 'chuyện vặt'.

🔀 Replace Conditional with Polymorphism — switch theo type → class
⚡ Cú lật — để mỗi LOẠI tự biết việc của nó, thay vì một switch trung tâm phán xử

Khi switch/if theo type lặp và phình, thay bằng polymorphism: mỗi loại là một class tự implement hành vi. Đây là move biến code thành Strategy (gốc 5) / tuân OCP (gốc 3). NHƯNG chỉ đáng khi số loại còn tăng — 2 case ổn định thì đừng.

Một switch trung tâm = mọi loại nhồi một chỗ

switch(type){ case 'vnpay'... case 'momo'... } — thêm loại phải mở switch. Nếu switch này lặp ở nhiều hàm → thêm loại sửa nhiều chỗ (Shotgun gốc 2).

Tạo interface + mỗi loại một class

interface Fee { calc() }; VnpayFee, MomoFee mỗi cái tự tính. Kiến thức của mỗi loại về đúng nhà nó.

Thay switch bằng dispatch đa hình

Code gọi fee.calc() — runtime tự chọn đúng class. Thêm loại = thêm class, switch biến mất (OCP).

🧭 Metaphor — bỏ ông tổng quản phán xử mọi việc: thay vì một người đọc bảng rồi quyết cho từng loại, để mỗi loại là một chuyên gia tự làm phần mình. Thêm loại mới = thuê thêm một chuyên gia, không sửa ông tổng quản.

❌ switch theo type (phình)
calc(type, amt) {
  switch(type) {
    case 'vnpay': return amt*.01;
    case 'momo':  return amt*.015;
  } // thêm loại = sửa đây (và mọi switch khác)
}
✅ Polymorphism
interface Fee { calc(amt): number }
class VnpayFee implements Fee { calc(a){return a*.01} }
class MomoFee  implements Fee { calc(a){return a*.015} }
fee.calc(amt); // thêm loại = thêm class

👃 Dấu hiệu kích hoạt

1
switch(type) / if theo type phình
Mỗi loại mới thêm một nhánh.
2
Cùng switch lặp ở nhiều hàm
Tính giá, render, export đều switch theo type → thêm loại sửa hết (Shotgun).
↓ Interviewer đào tiếp
"Khi nào KHÔNG nên làm move này?"
Khi chỉ 2 case ổn định, không mở rộng — một if/else đơn giản dễ đọc hơn 3 file class (YAGNI). Polymorphism đáng khi trục 'loại' còn biến thiên.
"Polymorphism vs lookup table (map)?"
Nếu chỉ chọn một GIÁ TRỊ theo key → map/lookup gọn hơn. Nếu mỗi loại có HÀNH VI phức tạp riêng → polymorphism. Đừng dùng class nặng cho việc map đơn giản.
"Move này ra pattern nào?"
Strategy (nếu client chọn) hoặc State (nếu theo trạng thái nội bộ). Đây là cầu nối gốc 7 → gốc 5.
🎓 Bedrock

Câu chốt: "tôi thay switch-theo-type bằng polymorphism khi trục loại CÒN biến thiên — để thêm loại là thêm class (OCP), kiến thức mỗi loại ở đúng nhà nó. Nhưng 2 case ổn định thì giữ if cho gọn (YAGNI); và map đơn giản thì dùng lookup, không class hóa." Biết cả 'khi nào KHÔNG' = anh không nhồi pattern.

🎒 Introduce Parameter Object — gom param list dài thành object có tên
⚡ Cú lật — danh sách param dài thường GIẤU một khái niệm chưa đặt tên

Gom param không chỉ để "gọn". Nhóm param hay đi cùng nhau (start, end · lat, lng · street, city, zip) thường là một khái niệm domain chưa được đặt tên. Gom lại + đặt tên (DateRange, Coordinate, Address) làm lộ ra khái niệm đó (nối Long Parameter List gốc 2).

Param nhiều + hay đi thành cụm

createBooking(userId, roomId, start, end, guests, note, promoCode, currency) — start,end luôn đi cùng, xuất hiện ở nhiều hàm.

Gom cụm thành object CÓ TÊN domain

DateRange {start, end} — không phải Args vô nghĩa. Tên object tiết lộ khái niệm; còn có thể gắn luật (start < end) vào đó (nối Value Object gốc 2).

Gọi bằng tên field, thêm field không phá chữ ký

createBooking(dto) — gọi bằng tên, không lo đảo thứ tự; thêm field mới vào dto không đổi chữ ký hàm.

🧭 Metaphor — form có nhãn vs đọc thứ tự qua điện thoại: "cho tôi số 2, đế 1, topping 3..." dễ nhầm ô; một form ghi rõ tên mỗi ô thì không. Parameter Object là cái form đó.

❌ Param list dài
createBooking(
  userId, roomId, start, end,
  guests, note, promoCode, currency
) {...}
// đảo start↔end? compiler im lặng 💣
✅ Parameter Object
createBooking(dto: CreateBookingDto) {...}
// gọi bằng TÊN field, thêm field ≠ phá chữ ký;
// DateRange có thể tự giữ luật start < end

👃 Dấu hiệu kích hoạt

1
4-5+ param, nhiều param cùng kiểu cạnh nhau
string, string, string → dễ truyền nhầm, compiler không cứu.
2
Cùng cụm param xuất hiện ở nhiều hàm
Dấu hiệu chắc: cụm đó là một khái niệm nên có tên.
↓ Interviewer đào tiếp
"Gom bừa mọi param vào một object có ổn không?"
Không. Chỉ gom cụm THẬT SỰ thuộc về nhau (một khái niệm). Nhét mọi thứ vào một 'bag' không tên = chỉ giấu mùi, không chữa. Object phải có tên domain nghĩa.
"Đặt tên object thế nào?"
Theo khái niệm domain nó biểu diễn: DateRange, Money, Address. Nếu không nghĩ ra tên nghĩa → có thể chúng KHÔNG thật sự thuộc về nhau.
"Move này nối gốc nào?"
Long Parameter List (g2) là smell kích hoạt; kết quả có thể thành Value Object (g2) nếu gắn luật; và cải thiện khả năng đọc (g1).
🎓 Bedrock

Câu chốt: "param list dài thường là một khái niệm domain đang ẩn — tôi gom cụm-đi-cùng-nhau thành object CÓ TÊN (không phải bag vô nghĩa), có thể gắn luật vào đó. Gọi bằng tên field, thêm field không phá chữ ký." Nhìn ra 'khái niệm ẩn' = tư duy domain modeling, trên tầm 'gom cho gọn'.

🕸️ Refactor code KHÔNG có test (Legacy) — bài toán khó nhất
⚡ Cú lật — "legacy code = code KHÔNG CÓ TEST" (Feathers)

Định nghĩa của Michael Feathers không phải "code cũ" — mà là code không có test. Vấn đề: refactoring ĐÒI test làm lưới, nhưng legacy thì CHƯA có test. Nghịch lý: muốn thêm test lại thường phải sửa code (để test được), mà sửa code chưa test = nguy hiểm. Cách thoát: characterization test + seam.

Bọc "characterization test" — ghi lại hành vi HIỆN TẠI

Chưa cần biết hành vi ĐÚNG hay không — viết test chụp lại hành vi ĐANG CÓ (kể cả bug). Nó là lưới: "sau khi tôi dọn, hành vi có đổi không?"

Tìm "seam" — điểm chèn để test được mà ít sửa

Seam = chỗ có thể thay đổi hành vi mà không sửa tại chỗ (vd inject một phụ thuộc qua tham số thay vì new bên trong). Tạo seam tối thiểu để chèn test.

Có lưới rồi → refactor từng bước như thường

Khi characterization test xanh, anh quay về vòng an toàn: Extract/Rename từng bước, test sau mỗi bước.

🧭 Metaphor — gắn dây bảo hiểm TRƯỚC khi leo: không ai leo vách đá trơn (legacy) tay không. Characterization test là sợi dây: nó không làm anh leo giỏi hơn, nhưng nếu trượt (đổi hành vi ngoài ý muốn) nó giữ anh lại.

⚠️ Đừng "refactor" legacy khi CHƯA có lưới. Sửa code không test = "đập ra sửa và cầu nguyện" (rewrite trá hình), không phải refactoring. Bọc characterization test trước, luôn luôn.
❌ Khó test — dính cứng (không seam)
class Report {
  run() {
    const db = new Postgres(); // dính cứng
    ... // không chèn test được
  }
}
✅ Tạo seam → chèn characterization test
class Report {
  constructor(private db: Db) {} // seam!
  run() {...}
}
// test: inject fake db, chụp lại output hiện tại

↓ Interviewer đào tiếp
"Characterization test là gì?"
Test ghi lại (chụp) hành vi HIỆN TẠI của code để làm mốc — kể cả hành vi đó có thể sai. Mục đích không phải xác nhận đúng, mà là 'sau khi tôi dọn, hành vi có đổi ngoài ý muốn không'.
"Seam là gì?"
Một điểm anh có thể thay đổi hành vi mà không sửa code tại chỗ đó — vd inject qua constructor/tham số thay vì new. Tạo seam tối thiểu để chèn test vào code khó test.
"Nếu bọc test cũng đòi sửa code chưa test thì sao?"
Đó là nghịch lý legacy. Giải: làm thay đổi NHỎ NHẤT + an toàn nhất để tạo seam (Feathers gọi các kỹ thuật 'sprout'/'wrap'), đủ để chèn test, rồi mới refactor mạnh tay.
🎓 Bedrock

Câu chốt: "legacy = code không có test (Feathers). Tôi không refactor legacy tay không — tôi bọc characterization test qua một seam (thường là inject phụ thuộc), có lưới rồi mới dọn từng bước." Nói được characterization test + seam = anh cho thấy đã ĐỐI MẶT code thật, không chỉ code sạch trong sách.

③ Trong code THẬT của anh

Refactor thật trong Asset_Platform

Đây là gốc của capstone — làm trọn vòng, có test làm lưới.

🔨 Vòng lặp build→fail→refactor đầy đủ (30 phút)

  • 1. Chọn một con mồi anh đã đánh dấu ở gốc 2 (god class / long method) trong apps/api.
  • 2. Lưới — viết/đảm bảo có test cho hành vi hiện tại (gốc 6); nếu chưa test được → tạo seam + characterization test. Chạy → xanh.
  • 3. Dọn — Extract Method/Class/Rename từng bước nhỏ, chạy test sau mỗi bước.
  • 4. Xác nhận — test vẫn xanh = hành vi không đổi = refactor thành công.

→ Đây là vết sẹo đậm nhất. Ghi Scar-Journal đầy đủ: trước/sau, áp gốc nào, test cứu anh ra sao. Câu chuyện này dùng được cho cả Why-Ladder của gốc 2, 3, 6, 7.

⚠️ Sân tập: làm trên branch riêng / copy. Mục tiêu là HỌC vòng lặp, không phải ship.
④ Why-Ladder (cho Mock)

Interviewer đào sâu thế nào

7 bậc — leo được tới đỉnh mà tự suy ra = đậu gốc này.

1
"Refactoring là gì?"
→ Cải thiện cấu trúc bên trong mà không đổi hành vi bên ngoài; từng bước nhỏ, có test làm lưới. (định nghĩa)
2
"Tại sao cần test trước khi refactor?"
→ Test là lưới đảm bảo hành vi không đổi. Không test = canh bạc/rewrite, không phải refactor. (lý do — nối gốc 6)
3
"Kể một lần anh refactor code thật."
→ DẪN SẸO Asset_Platform: god service → extract class, có test bọc, từng bước nhỏ. (kinh nghiệm)
4
"Anh vừa refactor VÀ thêm feature trong một PR — ổn không?"
→ Không. Tách hai việc: nếu bug, không biết do refactor hay feature. Commit/PR riêng. (áp dụng)
5
"Refactor code CHƯA CÓ test thì làm sao cho an toàn?"
→ Legacy (Feathers): bọc characterization test qua một seam (inject phụ thuộc) để chụp hành vi hiện tại, có lưới rồi mới dọn. (chiều sâu — chỗ hay lộ ai chỉ đọc lý thuyết)
6
"Refactoring nối các gốc khác thế nào?"
→ Ngửi smell (g2) → chọn move (Extract/Rename/Replace) áp SOLID/OOP/patterns (g3-5) → test làm lưới (g6). Refactoring là 'động từ' thực thi mọi gốc kia. (synthesis)
7
"Code chạy tốt, sao phải refactor? Không phí thời gian?"
→ Trả "nợ kỹ thuật" — code dễ đổi = mọi feature sau rẻ hơn. Nhưng cân deadline: refactor CƠ HỘI (khi đang sửa vùng đó) hợp lý hơn refactor toàn bộ tùy hứng. Phán đoán kỹ sư. (bedrock)
Đậu gốc này khi

Anh nối refactoring với test (tầng 2), dẫn vòng lặp thật (tầng 3), biết tách refactor khỏi feature (tầng 4), biết xử legacy bằng characterization test + seam (tầng 5), nối refactoring xuyên các gốc (tầng 6), và cân nợ kỹ thuật vs deadline (tầng 7).

Gốc 7 / 8 — dọn an toàn rồi. Gốc cuối gói tất cả thành một vòng lặp. ♻️
