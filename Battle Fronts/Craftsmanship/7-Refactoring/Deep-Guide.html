Đổi cấu trúc, KHÔNG đổi hành vi

Refactoring là cải thiện cấu trúc bên trong mà KHÔNG thay đổi hành vi bên ngoài. Input ra sao, output vẫn vậy — chỉ ruột đẹp hơn. Đây là gốc gom cả 6 gốc trước lại: anh ngửi smell (gốc 2), áp SOLID/OOP/patterns (3-5), và test (gốc 6) là tấm lưới để dọn an toàn.

🧔 "Fowler" là ai?

Martin Fowler — tác giả cuốn Refactoring (1999). Trước ông, dev vẫn dọn code theo bản năng, mỗi người một kiểu. Đóng góp của ông: đặt TÊN cho từng nước đi + viết công thức từng bước. Như cờ vua ♟️ — trước có "Sicilian Defense", người ta chỉ nói được "đẩy con tốt ra"; sau khi có tên, một chữ mang cả nước đi + lý do. Vì vậy interviewer nghe "tôi tách nó ra cho gọn" = junior; nghe "đây là Extract Class vì vi phạm SRP" = senior. Cùng hành động, khác ở vocabulary.

⚡ Cú lật — refactoring là KỶ LUẬT có định nghĩa HẸP

"Refactor" bị dùng bừa cho "sửa code cho đẹp". Định nghĩa THẬT (Fowler): đổi cấu trúc mà KHÔNG đổi hành vi quan sát được, theo bước NHỎ, có test làm lưới mỗi bước. Thiếu test hoặc đổi hành vi = không phải refactoring, mà là viết lại (rewrite) — rủi ro khác hẳn.

🔬 Mổ định nghĩa — 4 mảnh

"Đổi CẤU TRÚC mà không đổi HÀNH VI QUAN SÁT ĐƯỢC, theo BƯỚC NHỎ, có TEST làm lưới."
Cấu trúc vs Hành vi — căn nhà 🏠

Hành vi (ngoài): bấm chuông → kêu. KHÔNG được đổi. · Cấu trúc (trong): dây điện đi đường nào. Sắp lại thoải mái. Refactoring = đi lại dây trong tường — người trong nhà không hề biết, chuông vẫn kêu y hệt.

Trước
def f(x):
    return x*0.1 if x>1000 else 0
Sau — hành vi Y HỆT
def calculate_discount(total):
    if total > VIP_THRESHOLD:
        return total * VIP_RATE
    return 0

f(2000) và calculate_discount(2000) đều = 200. Ruột đổi hết, hành vi không nhúc nhích → đây là refactoring ✅

"QUAN SÁT ĐƯỢC" — chữ bị bỏ qua nhất 🍜

Fowler nói "không đổi hành vi quan sát được" — cố ý. Nếu bắt "không đổi gì hết" thì refactoring bất khả thi. Quan sát bởi ai? Bởi CALLER (code gọi hàm từ ngoài) — nó chỉ thấy input → output, exception, và side-effect (ghi DB, gửi mail). Như khách ăn phở: thấy vị + giá + thời gian chờ, không thấy bếp sắp nồi ở đâu.

"BƯỚC NHỎ" 🐜 — thu nhỏ vùng nghi phạm

❌ Đổi 400 dòng → test đỏ → 400 dòng nghi phạm, mò 2 tiếng. ✅ Đổi 5 dòng → test → 🟢 → 5 dòng nữa → 🔴? → thủ phạm trong 5 dòng vừa đổi, sửa 30s. Kích thước bước = kích thước vùng debug. Mua an toàn bằng cách mua NHỎ — cùng tư duy Binary Search bên Coding.

"TEST làm lưới" 🎪 — không lưới thì đổi TÊN hoạt động

Đu dây có lưới = nhào lộn; không lưới = liều mạng — hoạt động khác hẳn dù động tác giống. Cái xác định anh làm gì không phải động tác, mà là cái xảy ra khi sai: có test → đỏ trong 3s; không test → khách hàng phát hiện giùm 💀

💣 Vì sao "dọn cho đẹp THÔI" là sai

Refactoring là 2 vế, anh chỉ tự kiểm được vế đầu:

Vế ① code đẹp hơn

👁️ Mắt kiểm được.

Vế ② hành vi KHÔNG đổi ← lời hứa thật

🚫 Chỉ TEST kiểm được.

Chứng minh: một cú dọn "đẹp" mà âm thầm sập

Trước — return thoát CẢ HÀM → 1 bill
def bill_first_vip(users):
    for u in users:
        if u.is_vip:
            send_bill(u)
            return "done"
    return "none"
Sau — Extract đẹp, reviewer duyệt… và SAI
def handle_vip(u):
    send_bill(u)
    return "done"

def bill_first_vip(users):
    for u in users:
        if u.is_vip:
            handle_vip(u)   # return chỉ thoát handle_vip
    return "none"       # LUÔN trả "none" 💀
Vế ① ✅ đẹp thật. Vế ② ❌ hành vi đã đổi — mắt không thấy. return giờ nằm trong handle_vip → nó chỉ thoát hàm con, vòng lặp chạy tiếp → gửi bill cho MỌI VIP (50 VIP = 50 hoá đơn), và giá trị "done" trả về không ai hứng → rơi mất, Python im re. Cái tên bill_first_vip — chữ first — giờ nói dối. Đọc bằng mắt không bắt được; chỉ test bắt được.

📌 Nhắc: return = ra khỏi hàm đang đứng trong. Dời nó sang hàm khác → nghĩa tự đổi (từ "dừng tất cả" thành "xong phần tôi, chạy tiếp"). Đây là lý do bẫy control-flow khi Extract Function — xem mục ②.

🗣️ Câu chốt — đóng đinh vế ②

"Test là cái DUY NHẤT biến 'tôi TIN hành vi không đổi' thành 'tôi BIẾT hành vi không đổi'. Bỏ test = mất vế ② = không còn là refactoring, chỉ còn là sửa code." Không test → làm xong mà không phân biệt được mình vừa refactor hay vừa tạo bug. Cái gì không phân biệt được kết quả thì không có quyền gọi tên nó.

🎩🎩 Two Hats — quy tắc vàng (thi ngay)

⚠️ "Refactor và thêm feature là HAI việc tách rời, không làm cùng lúc." Một lúc chỉ đội MỘT mũ.
🎩 Mũ REFACTOR
  • Sắp lại code cũ
  • KHÔNG thêm chức năng / test mới
  • Test cũ xanh suốt
🎩 Mũ FEATURE
  • Thêm code mới + chức năng
  • CÓ viết test mới
  • Test mới đỏ → xanh (TDD)

Commit refactor: clean up registration mà vừa tách hàm vừa thêm validate = đội 2 mũ. Nổ thì không biết do tách hàm hay do validate, không revert riêng được. Tách 2 commit → git revert đúng thủ phạm, giữ lại thằng kia 🎯

Điều kiện tiên quyết: TEST trước

Có test xanh ✅
→
Refactor từng bước nhỏ
→
Test vẫn xanh ✅

Không có test = không phải refactoring, mà là "đập ra sửa và cầu nguyện". Test là cái phân biệt refactor an toàn với canh bạc. (Legacy code = code không có test — Feathers.) → Nếu code chưa có test, việc đầu tiên không phải dọn — mà là phủ test lên đã (characterization test), rồi mới dọn. Đó là bullet 🕸️ Legacy ở mục ②.

"Refactoring là sửa code cho gọn" — sai ở đâu?
3 chỗ: "gọn" = thẩm mỹ cá nhân → biến refactoring thành cãi nhau về gu · không nhắc giữ hành vi → chưa biết ĐƯỜNG BIÊN · không nhắc test → chưa biết ĐIỀU KIỆN. Dịch ra: "tôi hay dọn code theo cảm tính".
def check(n): print(n); return "stop" — gọi trong for i in items: if i > 2: check(i), rồi return "end". Với [1,2,3,4,5] in ra gì? Trả về gì? "stop" đi đâu?
In 3, 4, 5. Trả về "end" (không in ra — phải print(run(...)) mới thấy). "stop" KHÔNG BAO GIỜ được in — nó là giá trị trả về, không ai hứng → rơi xuống đất, Python im re.
Câu chốt senior khi được hỏi "refactoring là gì?" — đọc lại từ trí nhớ, 4 ý.
① đổi ruột, không đổi cái caller thấy · ② bước nhỏ, test xanh mỗi bước · ③ là kỷ luật hẹp, không phải "dọn cho đẹp" · ④ không trộn với thêm feature (Two Hats).
② Deep-dive từng nước đi

Mổ từng move tới xương

Mỗi nước đi: cú lật → xây từ số 0 → code trước→sau (hành vi y hệt) → dấu hiệu kích hoạt → interviewer đào tiếp → câu chốt senior. Bấm để mở.

✂️ Extract Function/Method — nước đi cơ bản & hay dùng nhất
⚡ Cú lật — tách theo Ý ĐỊNH, không theo độ dài

Không phải "hàm dài thì chặt bớt". Extract Function là: khi một ĐOẠN code có một Ý ĐỊNH riêng (một "chương" trong câu chuyện), kéo nó thành một hàm có TÊN nói lên ý định đó. Hàm cha đọc như mục lục; chi tiết lùi xuống (nối Long Method gốc 2).

Nhìn ra "chương" — mỗi ý định là một chương

Đọc print_owing dưới đây: nó có 3 chương ngăn bằng dòng trống — 🅰️ in banner, 🅱️ tính total, 🅲️ in chi tiết. Chia được KHÔNG phải vì hàm dài, mà vì mỗi khúc có một ý định riêng. Đó là cú lật.

2 câu = chữ ký hàm (đây là 90% kỹ thuật)

Trước khi bê một chương ra, trả lời đúng 2 câu:

❓ Câu 1 — cái gì chảy VÀO? Hàm mới cần biết gì từ ngoài → thành tham số.
❓ Câu 2 — cái gì chảy RA? Code phía dưới cần lấy gì → thành return.

Với chương 🅱️: vào = orders, ra = total → def calc_total(orders) → return total. Nắm "vào/ra" là nắm gần trọn move; phần còn lại chỉ là copy-paste.

Từng bước nhỏ, chạy test sau mỗi lần

Tách 1 chương → chạy test → 🟢 → tách chương tiếp. KHÔNG tách cả 3 một phát rồi mới test — đỏ thì 3 chỗ nghi phạm; tách từng cái thì thủ phạm chính là chương vừa tách.

❌ Trước — 3 chương trộn
def print_owing(invoice):
    print("**** Khách nợ ****")   # 🅰️

    total = 0                       # 🅱️
    for o in invoice["orders"]:
        total += o["amount"]

    print(f"Tên: {invoice['name']}")  # 🅲️
    print(f"Nợ:  {total}")
✅ Sau — hàm cha đọc như mục lục
def print_owing(invoice):
    print_banner()
    total = calc_total(invoice["orders"])
    print_details(invoice, total)

def calc_total(orders):   # vào=orders
    total = 0
    for o in orders:
        total += o["amount"]
    return total          # ra=total

🧭 Metaphor: viết mục lục cho chương sách dài — lướt tiêu đề (hàm cha) hiểu mạch, cần chi tiết thì đọc mục con.

🛑 Bẫy chí mạng — control-flow. Trước khi bê một đoạn ra, quét xem nó có return / break / continue không. Mấy thằng này điều khiển luồng của hàm CHA; dời sang hàm con thì chúng chỉ còn điều khiển hàm con → hành vi âm thầm đổi. VD: if o["amount"]<0: return "invalid" đang thoát cả print_owing; bê vào calc_total thì nó chỉ thoát calc_total, cha vẫn chạy tiếp. Fix: hàm con trả cờ về, hàm cha tự quyết: total = calc_total(...); if total=="invalid": return ... — return nằm lại đúng phòng. Đoạn "sạch" (chỉ tính + gán, không control-flow) thì bê thoải mái.

↓ Interviewer đào tiếp
"Tách nhỏ tới mức nào là đủ?"
Tới khi mỗi hàm ở MỘT mức trừu tượng và tên nói đúng việc. Không phải 'càng nhỏ càng tốt' — tách quá vụn (hàm 1 dòng, tên dài hơn thân) cũng hại khả năng đọc.
"Extract một đoạn có return giữa vòng lặp — có an toàn không?"
KHÔNG. return đó điều khiển luồng hàm cha; bê ra thì chỉ thoát hàm con → hành vi đổi. Phải cho hàm con trả cờ về, cha tự quyết định thoát.
"Khi nào INLINE (ngược lại) một hàm?"
Khi hàm quá tủn mủn, tên không thêm nghĩa gì so với thân, chỉ gọi một chỗ → inline lại cho đỡ nhảy. Refactoring có cả hai chiều.
🎤 4 nhịp trả lời interview — "Extract Function là gì / khi nào dùng?"
1
Lật cái hiểu lầm
"Extract Function không phải 'hàm dài thì chặt cho ngắn'. Tôi tách theo Ý ĐỊNH: khi một đoạn có một mục đích riêng, tôi kéo nó ra thành hàm có TÊN nói lên ý định đó — hàm cha đọc như mục lục."
2
Cơ chế — vào/ra
"Kỹ thuật gọn trong 2 câu: cái gì chảy VÀO thành tham số, cái gì code phía dưới cần lấy thì RETURN ra. Đó là chữ ký hàm; xác định đúng vào/ra là xong 90%."
3
Cái bẫy phải nhắc
"Trước khi cắt tôi quét control-flow — return/break/continue. Chúng điều khiển luồng hàm CHA; bê sang hàm con thì nghĩa đổi, hành vi âm thầm sai. Nếu buộc phải tách, cho hàm con trả cờ về để cha tự quyết định thoát."
4
Câu chốt senior
"Tôi làm từng bước nhỏ, chạy test sau mỗi lần — test là lưới chứng minh hành vi không đổi. Và refactoring hai chiều: khi một hàm quá tủn mủn, tên không thêm nghĩa, tôi Inline ngược lại. Extract Method chỉ là cùng move khi code nằm trong class — dữ liệu vào qua self thay vì param."
🎓 Bedrock

Câu chốt: "tôi extract theo Ý ĐỊNH, xác định vào (param) / ra (return), quét control-flow trước khi cắt, làm từng bước nhỏ có test; và inline ngược khi hàm không thêm nghĩa. Refactoring hai chiều." Move nền tảng, dùng trong hầu hết mọi refactor lớn hơn.

📦 Extract Class — tách god class theo trách nhiệm
⚡ Cú lật — cắt ở ĐƯỜNG DAO tự nhiên, không cắt tùy tiện

Extract Class chữa God Class (gốc 2) / vi phạm SRP (gốc 3). Nhưng cắt ở ĐÂU? Không tùy tiện: cắt theo nhóm method + field đi cùng nhau (cohesion). Nhóm nào dùng chung một cụm field mà không đụng cụm khác → đó là một class đang trốn bên trong.

Tìm nhóm method + field "chơi với nhau"

Trong một class to, các method chia phe: nhóm A đụng passwordPolicy, hash; nhóm B đụng mailer, template. Hai phe không dùng chung field.

Ranh giới "không chung field" = đường dao

Đường ranh giữa hai phe chính là chỗ tách. Kéo nhóm B + field của nó ra class riêng (UserNotifier).

Class cũ GIỮ tham chiếu tới class mới (delegation)

Class cũ giờ ủy thác (delegate) việc gửi mail cho UserNotifier. Từng bước: tạo class mới → dời một method → chạy test → dời tiếp.

🧭 Metaphor — tách một nhân viên ôm-nhiều-nghề: gom việc "kế toán" cho một người, "tuyển dụng" cho người khác — chia theo NGHỀ (nhóm việc dùng chung kỹ năng), không chia bừa giữa chừng một nghề.

❌ God class trộn nghề
class UserService {
  hashPassword() {...}    // phe bảo mật
  verifyPassword() {...}  // phe bảo mật
  sendWelcome() {...}     // phe mail
  sendReset() {...}       // phe mail
}
✅ Extract theo đường dao cohesion
class PasswordHasher { hash(); verify(); }
class UserNotifier { sendWelcome(); sendReset(); }
class UserService {
  constructor(hasher, notifier) {} // delegate
}

Nhìn cohesion: nhóm method + field nào bám chặt nhau, tách biệt với nhóm khác. Ranh giới 'không dùng chung data' là đường dao tự nhiên. Đừng cắt giữa một nhóm gắn kết.
"Rủi ro khi tách là gì?"
Làm gãy hành vi hoặc tạo coupling ngược (hai class mới gọi nhau lằng nhằng). Nên có test bọc trước, dời từng method một, test sau mỗi bước.
"Extract Class nối SRP thế nào?"
Đây chính là cách THỰC HIỆN SRP: mỗi class mới có một lý do để thay đổi. Extract Class là 'động từ', SRP là 'trạng thái đích'.

🔌 Sau khi tách: DI vs DIP — đừng nhầm (chỗ 90% dev lẫn)

Khi class cũ delegate sang class mới, nó nhận class mới thế nào? Đây là chỗ ăn điểm senior:

DI — Dependency InjectionDIP — Dependency Inversion Principle
Là gìKỹ thuật: truyền dependency từ ngoài vàoNguyên tắc: phụ thuộc abstraction, không phụ thuộc concrete
Câu hỏi"Ai tạo ra nó?" (ngoài, không tự new)"Nó thuộc kiểu gì?" (interface, không phải class cụ thể)
Một dòng mang CẢ HAI
def __init__(self, mailer: IMailer):
    # mailer truyền vào qua param  → DI
    # kiểu là IMailer (abstraction) → DIP
    self.mailer = mailer

Bỏ type hint → vẫn DI nhưng mất DIP. Đổi thành self.mailer = EmailSender() bên trong → mất cả hai. Extract Class chỉ cần DI để refactor an toàn; nâng lên DIP (phụ thuộc IMailer) là bonus — vừa nới coupling vừa mock được lúc test (nối gốc 6).

🔀 Replace Conditional with Polymorphism — switch theo type → class
⚡ Cú lật — để mỗi LOẠI tự biết việc của nó, thay vì một switch trung tâm phán xử

Khi switch/if theo type lặp và phình, thay bằng polymorphism: mỗi loại là một class tự implement hành vi. Đây là move biến code thành Strategy (gốc 5) / tuân OCP (gốc 3). NHƯNG chỉ đáng khi số loại còn tăng — 2 case ổn định thì đừng.

Một switch trung tâm = mọi loại nhồi một chỗ

switch(type){ case 'vnpay'... case 'momo'... } — thêm loại phải mở switch. Nếu switch này lặp ở nhiều hàm → thêm loại sửa nhiều chỗ (Shotgun gốc 2).

Tạo interface + mỗi loại một class

interface Fee { calc() }; VnpayFee, MomoFee mỗi cái tự tính. Kiến thức của mỗi loại về đúng nhà nó.

Thay switch bằng dispatch đa hình

Code gọi fee.calc() — runtime tự chọn đúng class. Thêm loại = thêm class, switch biến mất (OCP).

🧭 Metaphor — bỏ ông tổng quản phán xử mọi việc: thay vì một người đọc bảng rồi quyết cho từng loại, để mỗi loại là một chuyên gia tự làm phần mình. Thêm loại mới = thuê thêm một chuyên gia, không sửa ông tổng quản.

❌ switch theo type (phình)
calc(type, amt) {
  switch(type) {
    case 'vnpay': return amt*.01;
    case 'momo':  return amt*.015;
  } // thêm loại = sửa đây (và mọi switch khác)
}
✅ Polymorphism
interface Fee { calc(amt): number }
class VnpayFee implements Fee { calc(a){return a*.01} }
class MomoFee  implements Fee { calc(a){return a*.015} }
fee.calc(amt); // thêm loại = thêm class

👃 Dấu hiệu kích hoạt

1
switch(type) / if theo type phình
Mỗi loại mới thêm một nhánh.
2
Cùng switch lặp ở nhiều hàm
Tính giá, render, export đều switch theo type → thêm loại sửa hết (Shotgun).
↓ Interviewer đào tiếp
"Khi nào KHÔNG nên làm move này?"
Khi chỉ 2 case ổn định, không mở rộng — một if/else đơn giản dễ đọc hơn 3 file class (YAGNI). Polymorphism đáng khi trục 'loại' còn biến thiên.
"Polymorphism vs lookup table (map)?"
Nếu chỉ chọn một GIÁ TRỊ theo key → map/lookup gọn hơn. Nếu mỗi loại có HÀNH VI phức tạp riêng → polymorphism. Đừng dùng class nặng cho việc map đơn giản.
"Move này ra pattern nào?"
Strategy (nếu client chọn) hoặc State (nếu theo trạng thái nội bộ). Đây là cầu nối gốc 7 → gốc 5.

🔌 Wiring — code gọi chọn đúng class kiểu gì?

Sau khi mỗi loại thành một class, cần MỘT chỗ map type → class. Cái switch không biến mất 100% — nó co lại thành 1 dòng registry:

✅ Registry + dispatch đa hình
REGISTRY = {
    "vnpay": VnpayPay,
    "momo":  MomoPay,
    "applepay": ApplePay,   # thêm loại = +1 class, +1 dòng ở đây
}
def get_payment(t): return REGISTRY[t]()

payment = get_payment("applepay")
fee = payment.calc_fee(amt)   # runtime tự gọi ApplePay.calc_fee — KHÔNG if

Trước: switch lặp ở 3 hàm (Shotgun). Sau: chỉ còn 1 chỗ đăng ký. Code gọi không biết nó cầm Vnpay hay Apple — chỉ biết đó là một PaymentMethod → đó là polymorphism (một lời gọi, nhiều hành vi).

🎒 Introduce Parameter Object — gom param list dài thành object có tên
⚡ Cú lật — danh sách param dài thường GIẤU một khái niệm chưa đặt tên

Gom param không chỉ để "gọn". Nhóm param hay đi cùng nhau (start, end · lat, lng · street, city, zip) thường là một khái niệm domain chưa được đặt tên. Gom lại + đặt tên (DateRange, Coordinate, Address) làm lộ ra khái niệm đó (nối Long Parameter List gốc 2).

Param nhiều + hay đi thành cụm

createBooking(userId, roomId, start, end, guests, note, promoCode, currency) — start,end luôn đi cùng, xuất hiện ở nhiều hàm.

Gom cụm thành object CÓ TÊN domain

DateRange {start, end} — không phải Args vô nghĩa. Tên object tiết lộ khái niệm; còn có thể gắn luật (start < end) vào đó (nối Value Object gốc 2).

Gọi bằng tên field, thêm field không phá chữ ký

createBooking(dto) — gọi bằng tên, không lo đảo thứ tự; thêm field mới vào dto không đổi chữ ký hàm.

🧭 Metaphor — form có nhãn vs đọc thứ tự qua điện thoại: "cho tôi số 2, đế 1, topping 3..." dễ nhầm ô; một form ghi rõ tên mỗi ô thì không. Parameter Object là cái form đó.

❌ Param list dài
createBooking(
  userId, roomId, start, end,
  guests, note, promoCode, currency
) {...}
// đảo start↔end? compiler im lặng 💣
✅ Parameter Object
createBooking(dto: CreateBookingDto) {...}
// gọi bằng TÊN field, thêm field ≠ phá chữ ký;
// DateRange có thể tự giữ luật start < end

string, string, string → dễ truyền nhầm, compiler không cứu.
2
Cùng cụm param xuất hiện ở nhiều hàm

"Gom bừa mọi param vào một object có ổn không?"

"Đặt tên object thế nào?"
Theo khái niệm domain nó biểu diễn: DateRange, Money, Address. Nếu không nghĩ ra tên nghĩa → có thể chúng KHÔNG thật sự thuộc về nhau.
"Move này nối gốc nào?"
Long Parameter List (g2) là smell kích hoạt; kết quả có thể thành Value Object (g2) nếu gắn luật; và cải thiện khả năng đọc (g1).

🎁 Nâng cấp — gắn luật vào constructor → thành Value Object

Que thử một cụm có đáng gom: ① luôn đi cùng nhau ở nhiều hàm? ② ghép ra một tên có nghĩa? Qua cả hai thì gom. start_date + end_date → DateRange. Rồi nhét luật domain vào constructor:

✅ DateRange tự giữ luật
class DateRange:
    def __init__(self, start, end):
        if start >= end:
            raise ValueError("start phải trước end")  # luật sống 1 chỗ
        self.start, self.end = start, end

Vì mọi DateRange đều chui qua __init__, một DateRange sai (start > end) không thể tồn tại trong hệ thống — luật từ rải rác ở mọi hàm co về một nhà. Đây chính là Value Object (gốc 2, chữa Primitive Obsession): object nhỏ bọc một khái niệm domain + tự bảo vệ invariant của mình.

🕸️ Refactor code KHÔNG có test (Legacy) — bài toán khó nhất
⚡ Cú lật — "legacy code = code KHÔNG CÓ TEST" (Feathers)

Hỏi 10 người, 9 người nói legacy = "code cũ / code đời trước". Michael Feathers (tác giả Working Effectively with Legacy Code) định nghĩa lại: legacy code = code không có test. Tuổi không liên quan.

Vì sao? Cái làm code đáng sợ để sửa không phải nó già — mà là khi anh sửa, KHÔNG có gì báo cho anh biết mình vừa làm gãy cái gì. Code có test: sửa xong chạy test → 🔴 báo liền "gãy chỗ này". Code không test: sửa xong → im lặng → 2 tuần sau khách hàng báo giùm 💀

🔥 Câu ăn điểm interview: "Code tôi viết SÁNG NAY mà không có test → đã là legacy. Code viết 10 NĂM TRƯỚC mà test phủ đầy → không phải legacy. Legacy không nói về tuổi code, mà nói về việc có lưới an toàn để sửa hay không."

🧩 Trước hết phải chắc: HÀNH VI vs CẤU TRÚC

Cả gốc 7 xoay quanh câu "đổi cấu trúc, không đổi hành vi" — nên phải phân biệt cho dứt điểm hai chữ này (đây là chỗ dễ rối nhất):

🟢 HÀNH VI = cái NGƯỜI GỌI (caller) cảm nhận được

2 câu hỏi: ① chạy hàm xong tôi NHẬN được gì? (kết quả return / lỗi ném ra) · ② có gì BÊN NGOÀI bị thay đổi không? (gửi mail, ghi DB, tạo file — gọi là side-effect). Gộp: "hàm này LÀM RA gì mà caller cảm nhận được".

🔵 CẤU TRÚC = cách code được VIẾT bên trong

Caller KHÔNG thấy: đặt biến ở đâu, chia mấy hàm, lấy db chỗ nào, tên biến gì. Là "hình dạng code bên trong".

🎯 Cây thước đo vàng: "Caller có cảm nhận khác không?" — Có → đổi hành vi. Không → chỉ đổi cấu trúc. Refactoring = đổi cấu trúc, giữ hành vi.

⚠️ Vì sao hành vi phải tính cả side-effect, không chỉ kết quả? send_email() có thể return None (kết quả rỗng) nhưng gửi một mail thật — cái mail đó là hành vi. Chỉ tính "hành vi = kết quả" thì tưởng hàm này "chả làm gì". Với hàm thường (chỉ tính rồi return) thì hành vi ≈ kết quả là đủ 90%.

🐍 Nghịch lý con-rắn-cắn-đuôi — vì sao legacy là bài KHÓ NHẤT

Anh có hàm legacy, muốn refactor. Luật mục ① bảo: viết test trước. Anh ngồi viết test:

❌ Legacy — dính cứng, không cắm test được
class Report:
    def run(self):
        db = Postgres()              # tự tạo DB THẬT ngay bên trong
        rows = db.query("SELECT ...")
        return format(rows)

# test: gọi report.run() → nó tự Postgres() → ĐÂM thẳng vào DB thật
# không có DB → crash; có DB → chậm, bẩn, mỗi máy một kết quả
# muốn nhét DB GIẢ vào? → không với tới được, vì run() tự tạo bên trong
Muốn refactor run() → cần test Muốn test run() → phải nhét fake DB vào Muốn nhét fake DB → phải SỬA dòng `db = Postgres()` ← sửa code! Nhưng sửa code này → chính là "sửa code CHƯA test" = cái nguy hiểm đang tránh 💀 → con rắn tự cắn đuôi: muốn test phải sửa, muốn sửa an toàn phải test

🔌 Cách thoát — "seam" (cái ổ cắm)

Định nghĩa Feathers: "A seam is a place where you can alter behavior without editing in that place." — seam là nơi anh đổi được hành vi mà không phải sửa code ngay tại nơi đó.

✅ Tạo seam = nhận db từ ngoài thay vì tự tạo
class Report:
    def __init__(self, db):     # ← SEAM: cái "ổ cắm" nhận db từ ngoài
        self.db = db
    def run(self):
        rows = self.db.query("SELECT ...")   # run() giữ NGUYÊN, khỏi mổ nữa
        return format(rows)

Report(Postgres()).run()   # chạy thật
Report(FakeDb()).run()     # test: hành vi run() ĐỔI mà run() không bị sửa 1 chữ

Cái "chỗ đổi được hành vi mà không sửa run()" = chỗ truyền db vào (constructor / lúc gọi Report(...)). Đó chính là seam. Trước đây run() cứng với Postgres(); giờ nó nhận bất cứ db nào — thật lúc chạy, giả lúc test.

🧠 "Không seam" vs "Có seam"

Không seam: muốn đổi db thì phải mổ đúng vào dòng db = Postgres() bên trong run(). Có seam: có sẵn ổ cắm ở constructor → thay từ NGOÀI, khỏi mổ run(). Seam tách CHỖ QUYẾT ĐỊNH hành vi (bên ngoài, ở Report(...)) ra khỏi CHỖ DÙNG hành vi (bên trong run()).

🐍 "Nhưng tạo seam vẫn là SỬA code chưa test mà?!" — Đúng. Feathers thừa nhận: để phá thế bí, anh buộc phải làm MỘT thay đổi khi chưa có test, không né được. Mẹo là chọn cái sửa AN TOÀN NHẤT: có 2 hạng thay đổi —
• Hạng cấu trúc (dời db = Postgres() ra constructor): chỉ đổi CHỖ lấy db, caller nhận report y hệt → giữ hành vi → rủi ro cực thấp, IDE làm được.
• Hạng hành vi (đổi query SELECT ... WHERE active=1): caller nhận ít dòng hơn → cảm nhận khác → đổi hành vi → BẮT BUỘC cần test.
→ Chọn hạng cấu trúc (giữ hành vi) để mở seam. Đánh cược canh bạc cực nhỏ (dời 1 dòng) → đổi lấy lưới an toàn cho MỌI bước sau.

🕸️ Có seam rồi → bọc characterization test → dọn thoải mái

Characterization test — CHỤP hành vi HIỆN TẠI làm mốc

Không hỏi "code chạy ĐÚNG không?" mà hỏi "code đang chạy RA SAO?" rồi chụp lại — kể cả nó đang có bug. Mục tiêu: phát hiện thay đổi ngoài ý muốn sau khi dọn, không phải sửa đúng-sai.

Có lưới rồi → về vòng an toàn

Characterization test xanh = có lưới → giờ Extract/Rename/Extract Class từng bước nhỏ, test sau mỗi bước, đúng kỷ luật mục ①.

🧭 Metaphor — gắn dây bảo hiểm TRƯỚC khi leo: characterization test là sợi dây; nó không làm anh leo giỏi hơn, nhưng trượt (đổi hành vi ngoài ý muốn) thì nó giữ anh lại.

🔗 Nối cả session — DI xuất hiện 3 TRẬN

Cái "seam" (nhận db từ ngoài thay vì new bên trong) chính là DI anh gỡ hồi Extract Class. Một kỹ thuật, ba mục đích: Extract Class → để delegate · Testing (gốc 6) → để mock · Legacy (đây) → để phá thế bí, chèn test. Nối được như vầy = hiểu xuyên gốc.

↓ Interviewer đào tiếp
"Legacy code là gì?"
Code không có test (Feathers) — không phải code cũ. Code viết sáng nay không test đã là legacy; code 10 năm phủ test đầy thì không. Vấn đề là thiếu lưới an toàn để sửa, không phải tuổi.
"Characterization test là gì?"
Test CHỤP hành vi HIỆN TẠI làm mốc — kể cả hành vi đó có thể sai. Mục đích không phải xác nhận đúng, mà là 'sau khi tôi dọn, hành vi có đổi ngoài ý muốn không'.
"Seam là gì?"
Nơi đổi được hành vi mà không sửa code TẠI chỗ đó — vd inject qua constructor thay vì new bên trong. Cái 'ổ cắm' cho phép thay đồ từ ngoài, khỏi mổ vào trong.
"Bọc test cũng đòi sửa code chưa test thì sao?"
Đúng nghịch lý — không né được. Chọn thay đổi AN TOÀN NHẤT: hạng cấu trúc (giữ hành vi, như dời dependency ra constructor), tránh hạng hành vi (đổi logic/query). Thay đổi giữ-hành-vi rủi ro thấp, đủ để mở seam.
🎤 4 nhịp trả lời interview — "Refactor code không có test thế nào?"
1
Định nghĩa lại legacy
"Trước hết, legacy theo Feathers là code KHÔNG CÓ TEST — không phải code cũ. Code tôi viết sáng nay không test cũng là legacy. Cái đáng sợ không phải tuổi, mà là sửa mà không có lưới nào báo tôi vừa làm gãy gì."
2
Nêu nghịch lý
"Refactoring đòi test làm lưới, nhưng legacy chưa có test. Và để viết test, tôi thường phải sửa code trước — vì phụ thuộc bị dính cứng, ví dụ new DB ngay trong hàm nên không nhét fake vào được. Catch-22: cần test để sửa an toàn, mà cần sửa để thêm được test."
3
Cách thoát — seam + characterization
"Tôi tạo một SEAM: điểm đổi được hành vi mà không sửa tại chỗ — thường là inject dependency qua constructor thay vì new bên trong. Tôi chọn thay đổi an toàn nhất, loại GIỮ hành vi (chỉ đổi cấu trúc), để rủi ro thấp nhất. Có seam rồi tôi bọc characterization test — chụp hành vi hiện tại làm mốc, kể cả bug."
4
Câu chốt senior
"Có lưới rồi tôi mới refactor mạnh tay — Extract, Rename từng bước, test sau mỗi bước. Điểm mấu chốt: seam chính là DI; khó test thường là tín hiệu coupling chặt, thiếu DIP. Nói được seam + characterization test là cho thấy tôi đã đối mặt code thật, không chỉ code sạch trong sách."
🎓 Bedrock

Câu chốt: "legacy = code không có test (Feathers). Tôi không refactor legacy tay không — chọn một thay đổi giữ-hành-vi để mở seam (thường là inject phụ thuộc), bọc characterization test làm lưới, rồi mới dọn từng bước." Nói được characterization test + seam + phân biệt hành vi/cấu trúc = anh đã ĐỐI MẶT code thật.

Interviewer đào sâu thế nào

7 bậc — leo được tới đỉnh mà tự suy ra = đậu gốc này.

1
"Refactoring là gì?"
→ Cải thiện cấu trúc bên trong mà không đổi hành vi bên ngoài; từng bước nhỏ, có test làm lưới. (định nghĩa)
2
"Tại sao cần test trước khi refactor?"
→ Test là lưới đảm bảo hành vi không đổi. Không test = canh bạc/rewrite, không phải refactor. (lý do — nối gốc 6)
3
"Kể một lần anh refactor code thật."
→ DẪN SẸO Asset_Platform: god service → extract class, có test bọc, từng bước nhỏ. (kinh nghiệm)
4
"Anh vừa refactor VÀ thêm feature trong một PR — ổn không?"
→ Không. Tách hai việc: nếu bug, không biết do refactor hay feature. Commit/PR riêng. (áp dụng)
5
"Refactor code CHƯA CÓ test thì làm sao cho an toàn?"
→ Legacy (Feathers): bọc characterization test qua một seam (inject phụ thuộc) để chụp hành vi hiện tại, có lưới rồi mới dọn. (chiều sâu — chỗ hay lộ ai chỉ đọc lý thuyết)
6
"Refactoring nối các gốc khác thế nào?"
→ Ngửi smell (g2) → chọn move (Extract/Rename/Replace) áp SOLID/OOP/patterns (g3-5) → test làm lưới (g6). Refactoring là 'động từ' thực thi mọi gốc kia. (synthesis)
7
"Code chạy tốt, sao phải refactor? Không phí thời gian?"
→ Trả "nợ kỹ thuật" — code dễ đổi = mọi feature sau rẻ hơn. Nhưng cân deadline: refactor CƠ HỘI (khi đang sửa vùng đó) hợp lý hơn refactor toàn bộ tùy hứng. Phán đoán kỹ sư. (bedrock)
Đậu gốc này khi

Anh nối refactoring với test (tầng 2), dẫn vòng lặp thật (tầng 3), biết tách refactor khỏi feature (tầng 4), biết xử legacy bằng characterization test + seam (tầng 5), nối refactoring xuyên các gốc (tầng 6), và cân nợ kỹ thuật vs deadline (tầng 7).
