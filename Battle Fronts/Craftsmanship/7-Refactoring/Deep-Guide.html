Đổi cấu trúc, KHÔNG đổi hành vi

Refactoring là cải thiện cấu trúc bên trong mà KHÔNG thay đổi hành vi bên ngoài. Input ra sao, output vẫn vậy — chỉ ruột đẹp hơn. Đây là gốc gom cả 6 gốc trước lại: anh ngửi smell (gốc 2), áp SOLID/OOP/patterns (3-5), và test (gốc 6) là tấm lưới để dọn an toàn.

⚠️ Quy tắc vàng (interview test ngay): "Refactor và thêm feature là HAI việc tách rời. Không bao giờ làm cùng lúc." Trộn chung = không biết bug do refactor hay do feature mới.

Điều kiện tiên quyết: TEST trước

Có test xanh ✅
→
Refactor từng bước nhỏ
→
Test vẫn xanh ✅

Không có test = không phải refactoring, mà là "đập ra sửa và cầu nguyện". Test là cái phân biệt refactor an toàn với canh bạc. (Legacy code = code không có test — Feathers.)

Dọn theo từng bước nhỏ, an toàn

Extract Method — từng bước, test sau mỗi bước

❌ Trước
printOwing(invoice) {
  printBanner();
  // tính total
  let total = 0;
  for (const o of invoice.orders)
    total += o.amount;
  // in chi tiết
  console.log(`name: ${invoice.name}`);
  console.log(`total: ${total}`);
}
✅ Sau (hành vi y hệt)
printOwing(invoice) {
  printBanner();
  const total = calcTotal(invoice.orders);
  printDetails(invoice, total);
}
// mỗi hàm một việc, đọc như mục lục
// test cũ vẫn xanh = an toàn

Mỗi bước nhỏ → chạy test → xanh → bước tiếp. Không "dọn hết một phát". Đó là kỷ luật refactoring.

③ Trong code THẬT của anh

Refactor thật trong Asset_Platform

🔨 Vòng lặp build→fail→refactor đầy đủ (30 phút)

Đây là gốc của capstone — làm trọn vòng:

  • 1. Chọn một con mồi anh đã đánh dấu ở gốc 2 (god class / long method) trong apps/api.
  • 2. Lưới — viết/đảm bảo có test cho hành vi hiện tại (gốc 6). Chạy → xanh.
  • 3. Dọn — Extract Method/Class từng bước nhỏ, chạy test sau mỗi bước.
  • 4. Xác nhận — test vẫn xanh = hành vi không đổi = refactor thành công.

→ Đây là vết sẹo đậm nhất. Ghi Scar-Journal đầy đủ: trước/sau, áp gốc nào, test cứu anh ra sao. Câu chuyện này dùng được cho cả Why-Ladder của gốc 2, 3, 6, 7.

⚠️ Sân tập: làm trên branch riêng / copy. Mục tiêu là HỌC vòng lặp, không phải ship.
④ Why-Ladder (cho Mock)

Interviewer đào sâu thế nào

1
"Refactoring là gì?"
→ Cải thiện cấu trúc bên trong mà không đổi hành vi bên ngoài. (định nghĩa)
2
"Tại sao cần test trước khi refactor?"
→ Test là lưới: đảm bảo hành vi không đổi. Không test = canh bạc, không phải refactor. (lý do — nối gốc 6)
3
"Kể một lần anh refactor code thật."
→ DẪN SẸO Asset_Platform: god service → extract class, có test bọc, từng bước nhỏ. (kinh nghiệm)
4
"Anh vừa refactor VÀ thêm feature trong một PR — ổn không?"
→ Không. Tách hai việc: nếu bug, không biết do refactor hay feature. Commit/PR riêng. (áp dụng)
5
"Code chạy tốt, sao phải refactor? Không phải phí thời gian?"
→ Refactor trả "nợ kỹ thuật" — code dễ đổi = mọi feature sau rẻ hơn. Nhưng cân với deadline: refactor cơ hội (khi đang sửa vùng đó) hợp lý hơn refactor toàn bộ tùy hứng. Đây là phán đoán kỹ sư. (bedrock)
