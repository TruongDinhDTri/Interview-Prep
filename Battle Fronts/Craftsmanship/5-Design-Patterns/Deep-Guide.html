Giải pháp mẫu cho vấn đề lặp lại

Design pattern không phải code copy-paste — nó là công thức đã được kiểm chứng cho một bài toán thiết kế hay tái diễn. Học pattern = học từ vựng chung: nói "dùng Strategy ở đây" thì cả team hiểu ngay.

⚡ Cú lật lớn — pattern là TỪ VỰNG, không phải mục tiêu

Đa số pattern hay dùng thực chất là áp dụng cụ thể của SOLID + composition: Strategy/Decorator = OCP + composition; Factory/Adapter = DIP. Học pattern KHÔNG phải để nhồi vào code cho "xịn" — mà để có TÊN GỌI CHUNG cho các giải pháp anh vốn đã suy ra được từ nguyên tắc. Hiểu gốc (SOLID/OOP) → pattern chỉ là đặt tên.

⚠️ Bẫy interview lớn nhất: nhồi pattern vào mọi chỗ. Pattern là để GIẢI một vấn đề có thật, không phải để khoe. Dùng sai chỗ = over-engineering = một code smell mới.

🎯 Strategy — pattern interview hỏi nhiều nhất
⚡ Cú lật — đóng gói MỖI thuật toán vào một class, đổi được lúc runtime

Strategy = lấy một "họ thuật toán/hành vi" (mỗi nhánh if theo type), đóng mỗi cái vào một class cùng interface, để đổi hành vi lúc runtime + thêm loại mới không sửa code cũ. Đây là OCP (gốc 3) + composition (gốc 4) hiện hình.

🧗 Con đường tự đẻ ra Strategy — đi lại con đường, đừng học thuộc

Đừng nhớ định nghĩa. Nhớ cái đau rồi tự bò ra pattern — 5 bước dưới đây là đúng hành trình đã dẫn tới nó. Đọc lại 100000 ngày sau vẫn tự dựng lại được.

😰 Cái đau bắt đầu: một hàm, một đống if

Tính phí cổng thanh toán: fee(type, amount) với if vnpay… if momo… if stripe…. Chạy ngon 6 tháng, đã test kỹ, tin được. Rồi sếp chạy vào bàn: "tháng sau thêm ZaloPay 2%, PayPal 3.5%, Apple Pay 2.2%…"

💣 Vì sao thêm loại mới = NGUY HIỂM (không chỉ "phiền")

Thêm mỗi cổng = phải MỞ cái hàm đang chạy đúng ra nhét thêm một if. Mà mở code cũ ra sửa = đặt cược lại toàn bộ thứ đã test: lỡ tay sửa nhầm số phí Momo lúc 11h đêm → sập cái chẳng liên quan gì tới ZaloPay. Đây chính là vi phạm Open–Closed: thêm hành vi lẽ ra phải THÊM code, không phải MỔ code đang sống.

📦 Thuốc: mỗi hành vi một "hộp" riêng, độc lập

Thay vì nhốt 3 công thức chung một hàm, cho mỗi cổng một class-hộp riêng: VnpayFee, MomoFee, StripeFee. Hộp Momo không biết hộp Vnpay tồn tại. Thêm ZaloPay = ĐẺ một hộp mới 📦🆕, KHÔNG mở hộp cũ → code cũ ngủ yên, hết đánh cược.

🔌 Lỗ hổng → interface: bắt mọi hộp cùng MỘT cái nút

Nếu mỗi hộp có nút tên khác nhau (calc() / layPhiMomo() / calcStripeFee()) → checkout lại phải if/else để bấm đúng nút → if/else quay về ám 👻. Chữa: BẮT mọi hộp cùng một nút calc(amount). Cái "luật ngầm: hộp nào cũng phải có calc()" đó CHÍNH LÀ interface — FeeStrategy. Cùng hình dạng ⟹ tráo đổi được (interchangeable).

🔄 Kết: checkout mù loại — tráo hộp nào cũng chạy

checkout chỉ gọi strategy.calc(500000) — không cần biết đang cầm hộp nào: Vnpay→5000, Momo→7500, Stripe→14500. Khách đổi cổng lúc chạy = truyền hộp khác vào (runtime). Thêm cổng = thêm hộp, checkout BẤT ĐỘNG. Đó là OCP + composition mang một cái tên: Strategy.

🎯 Gói lại 3 ý chính

Mỗi nhánh if theo type là một HÀNH VI riêng

if vnpay... if momo... if stripe... — mỗi nhánh là một cách tính phí. Chúng cùng "hình dạng" (nhận amount, trả phí) nhưng khác ruột.

Tách mỗi hành vi thành class implement chung interface

FeeStrategy { calc(a) } → VnpayFee, MomoFee, StripeFee. Mỗi class giữ đúng công thức của nó.

Client GIỮ một reference tới interface — đổi = đổi hành vi

checkout(strategy) nhận một FeeStrategy. Đổi cổng = truyền strategy khác (runtime). Thêm cổng = thêm class (code checkout không đụng → OCP).

🧭 Metaphor — chọn phương tiện đi cùng quãng đường: đi bộ / xe máy / máy bay — cùng "đi từ A tới B" (interface), mỗi cách một chiến lược. Đổi phương tiện = đổi strategy, không đổi mục tiêu.

❌ Switch phình theo mỗi loại mới
fee(type, amount) {
  if (type==='vnpay') return amount*.01;
  if (type==='momo')  return amount*.015;
  if (type==='stripe') return amount*.029;
  // thêm cổng = sửa hàm (vi phạm O)
}
✅ Strategy
interface FeeStrategy { calc(a): number }   // luật ngầm = interface
class VnpayFee  implements FeeStrategy { calc(a){ return a*.01;  } }
class MomoFee   implements FeeStrategy { calc(a){ return a*.015; } }
class StripeFee implements FeeStrategy { calc(a){ return a*.029; } }

function checkout(s: FeeStrategy, amount) { return s.calc(amount); }
checkout(new MomoFee(), 500000);   // → 7500 · checkout mù loại, hộp nào cũng bấm calc()
// thêm cổng = thêm 1 class, checkout & class cũ KHÔNG đụng ↓
class ZalopayFee implements FeeStrategy { calc(a){ return a*.02; } }

Strategy biến if/else thành các class cắm-rời. Nối thẳng Open/Closed (gốc 3). Đây là pattern interview hỏi nhiều nhất.

↓ Interviewer đào tiếp
"Có phải mọi if/else đều nên thành Strategy?"
Không. 2 case ổn định, không đổi → một if/else đơn giản tốt hơn 5 file Strategy (YAGNI). Strategy đáng khi số loại còn tăng hoặc cần hoán đổi lúc runtime.
"Strategy khác State pattern chỗ nào?"
Cấu trúc giống nhau (đều delegate qua interface), khác Ý ĐỊNH: Strategy do CLIENT chọn thuật toán; State đổi theo TRẠNG THÁI nội bộ và các state tự chuyển lẫn nhau.
"Ai quyết định chọn strategy nào?"
Thường là client, một Factory (theo type), hoặc DI container. Việc CHỌN tách khỏi việc DÙNG — bản thân đó cũng là tách trách nhiệm.

🎤 Trả lời trong interview — khung 4 nhịp

Đi theo: ① Định nghĩa 1 câu → ② Vấn đề nó cứu → ③ Ví dụ ngắn → ④ Lợi ích. Đọc verbatim (English):

🎤 Strategy — đọc y như vầy (English)
①
"The Strategy pattern is a family of interchangeable behaviors, each separated into its own class but implementing the same interface — so the client can swap the behavior at runtime."
②
"Without it, one function branches with if-else on a type — like a payment gateway — so every new gateway forces me to open that tested function and add a branch, risking the ones that already work."
③
"Instead I define a FeeStrategy interface with calc(amount); VnpayFee, MomoFee, StripeFee each implement it. checkout() just calls strategy.calc() — adding ZaloPay is just one new class, and checkout never changes."
④
"So I extend by adding classes, not editing old ones — new behavior with zero risk to what already works, and I can switch the algorithm at runtime."

🔎 Chiếu về ví dụ của mình: ① = mỗi cổng một hộp cùng nút calc() · ② = if vnpay… if momo… → lỡ tay sửa nhầm Momo · ③ = 📦🆕 ZalopayFee, checkout không đụng · ④ = thêm hộp = an toàn = OCP 🔒

🎓 Bedrock

Định nghĩa 1 câu (thủ sẵn): "Strategy = một họ hành vi tráo-đổi-được (interchangeable behaviors), mỗi cái tách thành một class riêng nhưng cùng một interface, để đổi lúc runtime và thêm loại mới không sửa code cũ."

Câu chốt: "Nó là OCP + composition mang tên." Nói được nó = OCP-hiện-hình + biết khi nào KHÔNG cần (2 case ổn định thì một if/else còn tốt hơn 5 file Strategy — YAGNI) = anh hiểu gốc, không nhồi pattern.

🏭 Factory — tập trung việc TẠO đối tượng
⚡ Cú lật — tách "quyết định TẠO cái gì" khỏi "DÙNG nó"

Factory gom LOGIC TẠO đối tượng vào một chỗ. new ConcreteClass() rải khắp = mọi nơi biết class cụ thể + đổi cách tạo phải sửa N chỗ. Factory để client xin "cho tôi một FeeStrategy loại X" mà không tự new.

🍜 Metaphor — nhà hàng (tách bạch Factory ↔ Strategy): khách nói "cho món NƯỚNG". 🏭 Factory = anh phục vụ: nghe chữ "nướng" → chạy vào bếp kêu đúng ĐẦU BẾP NƯỚNG ra (dịch chữ → đúng người), chứ phục vụ không nấu. 🎯 Strategy = ông đầu bếp: được kêu ra rồi thì NẤU theo kiểu của mình (cùng nút nấuMón()). Factory TÌM đúng người → Strategy DÙNG người đó. Hai khâu nối tiếp, không giẫm chân nhau.

🧗 Con đường tự đẻ ra Factory — đi lại con đường, đừng học thuộc

Factory sinh ra ĐÚNG chỗ Strategy để hở. Đi lại 5 bước này là tự dựng lại được nó 100000 ngày sau.

🕳️ Lỗ hổng Strategy để lại: có CHỮ, cần HỘP

Strategy lo "tính phí NHƯ THẾ NÀO" (mỗi hộp một calc()). Nhưng khách chọn cổng lúc runtime → tay mình chỉ cầm một chữ type="momo". Ai biến chữ "momo" → một hộp new MomoFee()? Strategy KHÔNG trả lời câu đó.

🩹 Cách ngây thơ: nhét if/else chọn hộp ngay tại checkout

if type==="momo" hop=new MomoFee()… Chạy được. Cục "dịch chữ → hộp" nằm ngay trong checkout. Ừ thì ổn… cho tới bước sau.

💥 Hộp còn cần ở nơi khác → cục chọn bị COPY 3 nơi

xuatHoaDon, ghiLog cũng cần đúng hộp theo type → cùng cục if/else-chọn-hộp bị dán lại 3 nơi. Thêm ZaloPay = sửa 3 chỗ, quên 1 = bug âm thầm (hóa đơn đúng, log sai). Tên bệnh: Shotgun Surgery — y hệt cái nguy hiểm đầu buổi, nhưng nhân bản.

🏭 Thuốc: gom cục chọn-hộp vào MỘT chỗ, ai cần thì gọi

taoFee(type) — một chỗ duy nhất biết "chữ → hộp nào". checkout/hóa đơn/log chỉ gọi taoFee(). Thêm ZaloPay = thêm 1 dòng ở 1 chỗ, phần còn lại bất động. Cái "xưởng chuyên đẻ hộp theo đơn" đó = Factory.

⚖️ Sự thật thẳng: Factory VẪN phải sửa — nhưng gom về 1 ô an toàn

Thêm ZaloPay vẫn mở taoFee thêm 1 dòng → KHÔNG OCP-hoàn-hảo. Nhưng OCP-hoàn-hảo là bất khả thi ở biên giới nơi loại-mới xuất hiện (phải có một chỗ "học" được nó tồn tại). Factory không xoá thay đổi — nó DỒN thay đổi vào 1 ô nhỏ, an toàn (chỉ đẻ hộp), còn checkout/hóa đơn/log thì đóng tuyệt đối. Đổi "OCP hoàn hảo" (với không tới) lấy "thiệt hại gom về 1 dòng".

🎯 Gói lại 3 ý chính

new ConcreteX() rải khắp = coupling khắp nơi

Mỗi nơi new VnpayFee() đều dính vào class cụ thể. Đổi constructor / thêm cấu hình khởi tạo = sửa mọi chỗ.

Gom quyết định tạo vào MỘT factory

FeeFactory.create(type) — chỉ một chỗ biết "type nào → class nào". Thêm loại = sửa một chỗ (registry).

Client xin factory, không biết class cụ thể (nối DIP)

Client chỉ thấy interface FeeStrategy + factory. Nó không import class cụ thể → phụ thuộc abstraction.

❌ cục chọn-hộp copy khắp nơi
function checkout(type, amount) {
  let hop;
  if(type=="momo")  hop=new MomoFee();
  if(type=="vnpay") hop=new VnpayFee();
  return hop.calc(amount);
}
// xuatHoaDon(), ghiLog() LẶP y chang
// → thêm ZaloPay = sửa 3 chỗ (Shotgun)
✅ Factory
// 🏭 MỘT chỗ biết "chữ → hộp". Ai cần thì gọi.
function taoFee(type): FeeStrategy {
  if(type=="momo")  return new MomoFee();
  if(type=="vnpay") return new VnpayFee();
  throw new Error("Cổng lạ: "+type);
}
checkout(type, amount){ return taoFee(type).calc(amount); }
// hóa đơn & log cũng chỉ gọi taoFee() — hết copy
// thêm ZaloPay = thêm 1 dòng TRONG taoFee ↓ (1 chỗ)
if(type=="zalopay") return new ZalopayFee();

↓ Interviewer đào tiếp
"Factory Method vs Abstract Factory vs simple factory?"
Simple factory = một hàm/class create(type). Factory Method = subclass quyết định tạo gì (override một method tạo). Abstract Factory = tạo cả một HỌ sản phẩm liên quan (vd UI theme: button+checkbox cùng phong cách).
"Vì sao không new khắp nơi?"
Vì new ConcreteX là coupling cứng tới class cụ thể (vi phạm DIP), khó đổi cách tạo, khó test (không thay được bằng mock). Factory cô lập điểm tạo.
"Factory nối Strategy thế nào?"
Rất hay đi cùng: Factory TẠO ra đúng Strategy theo type, rồi client DÙNG strategy đó. Factory lo 'tạo cái nào', Strategy lo 'làm thế nào'.
"Factory vẫn có if/else / vẫn sửa khi thêm loại — chẳng phải vẫn vi phạm OCP à?"
Đúng, technically có. Nhưng OCP-hoàn-hảo (không bao giờ sửa) là bất khả thi ở biên giới nơi loại-mới bước vào: phải có MỘT chỗ "học" được nó tồn tại. Factory không XOÁ thay đổi, nó CONTAIN thay đổi vào 1 ô nhỏ an toàn (chỉ đẻ hộp); toàn bộ phần còn lại (checkout, hóa đơn, log) vẫn đóng tuyệt đối. Đổi "OCP hoàn hảo" (với không tới) lấy "thiệt hại gom về 1 dòng".

Đi theo: ① Định nghĩa 1 câu → ② Vấn đề nó cứu → ③ Ví dụ ngắn → ④ Lợi ích. Đọc verbatim (English):

🎤 Factory — đọc y như vầy (English)
①
"A Factory puts the logic of creating objects in one place — you give it a type, it returns the right concrete instance behind a shared interface."
②
"Without it, `new ConcreteClass()` and the type-selection if-else get copied everywhere — checkout, invoicing, logging — so adding a new type means editing every one of those tested places."
③
"Instead I have one createFee(type) that maps the type to the right FeeStrategy, and everyone calls it. Adding ZaloPay is one line in the factory — checkout, invoicing, logging never change."
④
"So the whole system depends only on the interface, never on concrete classes, and a new type touches exactly one small, isolated place instead of scattering edits."

🔎 Chiếu về ví dụ của mình: ① = taoFee("momo") trả về hộp MomoFee · ② = cục chọn-hộp copy ở checkout + hóa đơn + log · ③ = thêm 1 dòng trong taoFee, chỗ khác bất động · ④ = sửa 1 chỗ nhỏ vô hại thay vì mổ N chỗ 🔒

🔫 Đòn thủ sẵn khi bị đào: "Factory vẫn sửa — vẫn phá OCP mà?"

Đọc thẳng: "It does, technically — but a perfectly closed system is impossible where a brand-new type enters: something must learn it exists. The factory doesn't remove that change, it contains it to one small, isolated spot. The rest of the app — checkout, invoicing, logging — stays fully closed. I trade unreachable 'perfect OCP' for damage contained to a single line."

🎓 Bedrock

Định nghĩa 1 câu (thủ sẵn): "Factory tập trung LOGIC TẠO đối tượng vào một chỗ — đưa nó một type, nó trả về đúng object cụ thể sau một interface chung, để phần còn lại phụ thuộc INTERFACE chứ không phải class cụ thể."

📡 Observer — một phát, nhiều nghe (one-to-many)
⚡ Cú lật — Subject KHÔNG biết ai đang nghe

😰 Cái đau: một sự kiện, một đống việc phải làm theo

📇 "BIẾT" trong code = viết tên nó ra để gọi

🧨 Vì sao đau: ông sếp ôm danh sách, thêm việc = phình sếp

🔄 Cú lật: đảo chiều "ai biết ai" — sếp chỉ HÉT một tiếng

Sếp mệt: "sao TAO phải biết tên từng đứa? Tao hét 📣 'XONG RỒI!', đứa nào quan tâm tự lo." Đảo chiều: nhân viên tự GIƠ TAY đăng ký (subscribe), sếp chỉ phát (notify) rồi kệ. Sếp giữ một danh sách — ai muốn nghe thì tự push tên mình vào.

🔒 Kết: thêm việc mới = tự subscribe, subject BẤT ĐỘNG

↓ Interviewer đào tiếp
"Observer khác Pub/Sub (event bus) thế nào?"
Observer: subject giữ trực tiếp danh sách observer (biết chúng qua interface). Pub/Sub: có một BROKER/event bus trung gian, publisher và subscriber không biết nhau chút nào → decouple mạnh hơn, dễ mở rộng qua tiến trình/mạng.
"Push vs pull model?"
Push: subject gửi kèm dữ liệu trong notify. Pull: subject chỉ báo 'có đổi', observer tự hỏi lại data cần. Push tiện, pull linh hoạt/ít coupling dữ liệu.
"Rủi ro lớn nhất của Observer?"
Memory leak: quên unsubscribe → subject giữ tham chiếu observer mãi (lapsed listener). Và thứ tự notify / cascade update khó lường. Luôn có đường unsubscribe.

🎤 Observer — đọc y như vầy (English)
①
"Observer lets one subject notify a list of subscribers when something happens; the subscribers register themselves, and the subject never hardcodes who they are."
②

🔫 Đòn thủ sẵn khi bị đào: "What's the danger with Observer?"

🧗 Con đường tự đẻ ra Adapter — đi lại con đường, đừng học thuộc

Đừng nhớ định nghĩa. Nhớ cái đau rồi tự bò ra pattern — 5 bước dưới đây là đúng hành trình đã dẫn tới nó. Đọc lại 100000 ngày sau vẫn tự dựng lại được.

😰 Cái đau: app quen một hình dạng, vendor cho hình dạng khác

Cả app anh (nối tiếp buổi Strategy) gọi phí qua strategy.calc(amount) — đó là hình dạng app đã quen. Sếp bảo: "tích hợp Stripe SDK thật vào." Nhưng Stripe chỉ hiểu stripe.createCharge({amount, currency}). Hai tên khác, hai hình dạng khác — không khớp.

💣 Nước ngu #1 — bẻ cong CẢ APP theo Stripe

Sửa hết .calc() → .createCharge() khắp app: codebase to = 1000 chỗ. Đây là Shotgun Surgery (sửa 1 thứ, đụng dao ngàn nơi) + tệ hơn: app anh thành nô lệ của vendor. Mai đổi Adyen → 1000 chỗ nữa. ❌

🚫 Nước ngu #2 — bẻ cong Stripe theo app

"Vậy sửa tên createCharge → calc trong SDK Stripe cho khớp?" — KHÔNG được: code của người ta, thư viện của người ta. Mà lỡ fork sửa được thì npm update phát → bay sạch. Kẹt cứng hai đầu: app sửa được nhưng quá đắt, Stripe thì cấm sửa.

🔌 Chỗ thứ ba: nhét một "cục chuyển" vào KHE GIỮA

Không đụng app, không đụng Stripe → chỉ còn khoảng trống ở giữa. Một class-cục-chuyển: (a) có method calc() đúng hình dạng app quen → app gọi được, khỏi sửa 1000 chỗ; (b) bên trong nó gọi thẳng stripe.createCharge(). Nó không tự tính gì — nó chuyền việc cho Stripe.

🎭 Kết: đội lốt interface app quen — đổi vendor = 1 cục chuyển mới

StripeAdapter implements FeeStrategy → với checkout() nó nhìn y hệt MomoFee, không biết Stripe nấp bên trong. Đổi qua Adyen = viết AdyenAdapter mới; app (1000 chỗ) bất động, vendor cũ bất động. Cái class-cục-chuyển đó mang một cái tên: Adapter.

❌ Nước ngu: domain gọi thẳng SDK (1000 chỗ dính vendor)

✅ Adapter — cục chuyển ở giữa
interface FeeStrategy { calc(amount): number }  // hình dạng app QUEN
class StripeAdapter implements FeeStrategy {
  constructor(private stripe) {}          // ôm Stripe bên trong
  calc(amount) {                           // CỬA VÀO: hình dạng A (app gọi)
    return this.stripe.createCharge({      // CỬA RA: hình dạng B (Stripe hiểu)
      amount, currency: 'vnd'
    });                                    // ↑ thân method NÀY = động tác "convert A→B"
  }
}
// app vẫn gọi checkout(new StripeAdapter(stripe), 500000) — mù vendor
// đổi vendor = 1 adapter mới, app & vendor cũ BẤT ĐỘNG ↓
class AdyenAdapter implements FeeStrategy {
  calc(amount){ return this.adyen.submitPayment(amount); }
}

① Adapter khác Strategy chỗ nào? (cả hai đều implements FeeStrategy!)

Vỏ ngoài y hệt — bí mật nằm ở TRONG thân method: MomoFee.calc(a){ return a*.015 } — logic đẻ ra ngay tại đây, nó là đầu bếp tự nấu. Còn StripeAdapter.calc(a){ return stripe.createCharge(...) } — không có logic riêng, chỉ chuyền cho Stripe, nó là thông dịch viên. Strategy giải quyết sự đa dạng hành vi CỦA MÌNH; Adapter giải quyết sự lệch hình dạng với một thằng LẠ. Câu hỏi mỗi đứa trả lời: Strategy = "tui có nhiều cách tự-làm X, cho tráo"; Adapter = "có thằng ngoài làm X rồi mà nói sai tiếng, cho tui dịch để nhét vô."

② "converts the interface of a class" — convert KHÔNG phải sửa Stripe

Interface thật của Stripe y nguyên đời đời, không ai đụng. "Convert X into Y" trong tiếng Anh = "trình bày / làm cho X xài được dưới hình dạng Y", KHÔNG phải "sửa X" — như convert dollars into euros (đô không bị hủy), convert Word to PDF (file Word không đổi). Chữ "convert" xảy ra tại cục chuyển: nhận cú gọi .calc() rồi trình lại thành createCharge(). Không phẫu thuật ai hết.

③ "interface of a class" — createCharge là method mà, sao gọi interface?

Chữ interface có 2 nghĩa: ① từ khóa TS/Java (interface FeeStrategy {…}); ② nghĩa gốc = "mặt tiếp xúc" = cách anh nói chuyện với một thứ (nó có method tên gì, nhận gì, trả gì). GoF dùng nghĩa ②. createCharge là một method — nhưng hình dạng của nó là một phần "mặt tiếp xúc" của Stripe. Như: method = một cái nút bấm; interface (②) = toàn bộ mặt điều khiển gồm các nút. Nên "interface của Stripe" = cách phải gọi nó, không cần Stripe viết từ khóa interface.

🎤 Adapter — đọc y như vầy (English)

"An Adapter converts the interface of a class into another interface the client expects — so two things that otherwise couldn't work together, because their shapes don't match, now can. ②

Đừng nhớ định nghĩa. Nhớ cái đau rồi tự bò ra pattern — 5 bước dưới đây là đúng hành trình đã dẫn tới nó. Đây là ý khó nhất trong cả bộ pattern; đọc lại 100000 ngày sau vẫn tự dựng lại được.

😰 Cái đau: quán cà phê + topping tùy chọn

Espresso 20k. Topping thêm: Sữa +5k, Đường +2k, Kem +8k. Khách phối tự do. Cách ngây thơ: coi mỗi món khách gọi là một khối liền → đẻ một class cho mỗi combo: MilkEspresso (cost = 25k), MilkKemEspresso (cost = 33k)…

💥 Đếm ra → "subclass bùng nổ"

3 topping, mỗi cái có/không = 2×2×2 = 8 class. Thêm 1 topping (trân châu) → 16. Rồi 32, 64… 2ⁿ — gấp đôi mỗi lần thêm topping. Chưa kể: đổi giá sữa 5k→6k phải mở nửa số class (mọi class có sữa) ra sửa. Bài toán sai từ gốc: cố đúc sẵn mọi tổ hợp, mà tổ hợp là vô hạn.

💡 Đổi lối: khách đâu nghĩ "khối liền" — họ nghĩ "THÊM từng lớp"

Khách nghĩ: "cho ly espresso… rồi thêm sữa… rồi thêm kem." Từng lớp chồng lên. Vậy làm mỗi topping thành một cục biết: ôm ly đang có, rồi cộng thêm giá của mình. Cục Sua nhận một ly → trả giá ly đó + 5k.

🪆 Chỗ lú nhất: "Sua vừa LÀ ly, vừa ÔM ly" — như búp bê Nga

Nghe như ma trơi ("ly chứa ly"?), nhưng giống búp bê Nga: mỗi con vừa LÀ búp bê, vừa CHỨA búp bê — chả lạ. Tách 2 mẩu: (ÔM) Sua giữ ly bên trong để cộng giá. (LÀ) — mấu chốt: "LÀ một ly" KHÔNG nghĩa "là espresso thật", mà chỉ nghĩa "bấm .cost() ra được giá". new Sua(new Espresso()).cost() → 25000 → bấm ra giá → Sua đủ tư cách "là một ly".

🎁 Kết: vì Sua CŨNG "là ly" → bọc chồng vô hạn, thu ngân bấm 1 nút

Vì Sua tự nó cũng là ly → Kem bọc Sua y hệt bọc ly thường: new Kem(new Sua(new Espresso())). Thu ngân bấm đúng một .cost() ở ngoài → dội vào trong cộng dồn = 33000, chẳng cần biết 1 lớp hay 10 lớp. 4 cục (Espresso, Sua, Duong, Kem) phối ra vô hạn combo — thêm topping = thêm 1 cục, không gấp đôi class. Cái cục vừa-là-vừa-bọc đó tên: Decorator.

🎯 Gói lại 3 ý chính

Nhiều tính năng tùy chọn → subclass bùng nổ (2ⁿ)

Đúc sẵn mỗi combo một class → mỗi topping mới gấp đôi số class. Sai từ gốc.

Decorator bọc object gốc, giữ CÙNG interface

Sua implements Coffee: nó vừa LÀ Coffee (bấm .cost() ra giá), vừa ÔM một Coffee bên trong + cộng giá của mình. Thu ngân vẫn chỉ thấy "một Coffee".

Bọc CHỒNG nhiều lớp tùy ý (runtime)

new Kem(new Sua(new Espresso())) — mỗi lớp thêm một hành vi. Thêm topping = thêm một decorator, ghép lúc chạy. Thêm bằng CODE MỚI, không mổ class cũ (OCP).

🧭 Metaphor — búp bê Nga / topping / mặc thêm áo: cùng "một ly", anh bọc thêm từng lớp tùy ý; cùng "một người", mặc thêm áo khoác/khăn tùy trời. Bọc thêm lớp, KHÔNG đúc một loại người mới cho mỗi kiểu ăn mặc.

❌ Subclass cho mọi tổ hợp (2ⁿ class)
class Espresso        { cost(){ return 20000; } }
class MilkEspresso    { cost(){ return 25000; } }
class MilkKemEspresso { cost(){ return 33000; } }
// mỗi combo = 1 class → 3 topping = 8, 4 = 16… 2ⁿ 😱
// đổi giá sữa = mở NỬA số class ra sửa
✅ Decorator (bọc chồng)
interface Coffee { cost(): number }  // luật: phải bấm .cost() ra số
class Espresso implements Coffee { cost(){ return 20000; } }
class Sua implements Coffee {         // Sua CŨNG là Coffee
  constructor(private inner: Coffee) {}  // ÔM một Coffee bất kỳ
  cost(){ return this.inner.cost() + 5000; }
}
class Kem implements Coffee {
  constructor(private inner: Coffee) {}
  cost(){ return this.inner.cost() + 8000; }
}
new Kem(new Sua(new Espresso())).cost();  // → 33000 · bấm 1 nút, dội vào trong
// thêm topping = thêm 1 cục, KHÔNG gấp đôi class

🧠 Mấy chỗ dễ tẩu hỏa (đã gỡ trong buổi) — đọc kỹ kẻo lú lại

① "mỗi combo = 1 class" nghĩa là gì?

Cách ngây thơ coi mỗi món khách-có-thể-gọi là một class có sẵn phép cộng riêng: MilkKemEspresso.cost(){ return 20000+5000+8000 }. Khách phối topping tự do → số món khả dĩ = số tổ hợp → mỗi tổ hợp phải ngồi viết tay một class. Đó là lý do nó nổ 2ⁿ.

② new Espresso() trả về VẬT THỂ, không phải con số

new Espresso() = làm ra một ly (object) — thứ CÓ nút .cost(); muốn ra giá phải bấm nút: new Espresso().cost() → 20000. Vì vậy khi bọc phải chuyền VẬT THỂ (thứ có .cost()), không chuyền con số: new Sua(20000) ❌ — số trơn không có .cost() → Kem bọc lên gọi .cost() sẽ gãy, hết bọc chồng. Chuyền object → bọc vô hạn ✅.

③ "vừa LÀ vừa CHỨA" hết lạ — và "LÀ một Coffee" nghĩa là gì

Búp bê Nga: vừa LÀ búp bê vừa CHỨA búp bê — bình thường. "LÀ một Coffee" KHÔNG nghĩa "là espresso thật", chỉ nghĩa "trả lời được câu .cost()". Với thu ngân, "một ly cà phê" = "thứ nào bấm .cost() ra giá". Sua bấm ra 25000 → đủ tư cách là ly → nên Kem bọc được Sua hệt bọc ly thường. Số 20000 không có .cost() → không phải "ly".

🏷️ Ba chữ "sang chảnh" chỉ là nhãn dán: interface Coffee = luật thu ngân ("phải bấm .cost() ra số") · implements Coffee = "cục này thề tuân luật" (nên nó là một ly) · private inner: Coffee = "ôm một ly bên trong" (ly bất kỳ, miễn tuân luật).

↓ Interviewer đào tiếp
"Decorator khác Inheritance chỗ nào?"
Inheritance quyết lúc COMPILE, cứng, mỗi tổ hợp một class. Decorator quyết lúc RUNTIME, ghép chồng tùy ý, tránh bùng nổ class. Decorator = composition thay cho inheritance để thêm hành vi.
"Middleware/Interceptor (Express/Nest) có phải Decorator?"
Rất gần: chuỗi middleware bọc quanh request/handler, mỗi lớp thêm hành vi (auth, log, cache) trước/sau — đúng tinh thần decorator/chain. (Lưu ý: @Decorator syntax của TS là metadata, khác pattern này.)
"Thứ tự bọc có quan trọng không?"
Có. Cache(Log(x)) khác Log(Cache(x)) — cái nào chạy trước ảnh hưởng hành vi (vd log có thấy cache hit không). Thứ tự là một quyết định thiết kế.
"Decorator khác Adapter chỗ nào? (cả hai đều 'bọc')"
Khác ở interface trước/sau khi bọc. Decorator: interface GIỮ NGUYÊN — bọc xong vẫn là Coffee, chỉ THÊM hành vi (cộng giá). Adapter: interface ĐỔI — vào bằng B (createCharge) ra bằng A (calc), mục tiêu là tương thích chứ không thêm gì. Cùng "bọc", khác mục đích: Decorator thêm, Adapter dịch.

🎤 Trả lời trong interview — khung 4 nhịp

Đi theo: ① Định nghĩa 1 câu → ② Vấn đề nó cứu → ③ Ví dụ ngắn → ④ Lợi ích. Đọc verbatim (English):

🎤 Decorator — đọc y như vầy (English)
①
"The Decorator pattern wraps an object in another object that shares the same interface, adding behavior before or after — so I can add features at runtime, in any combination, without a subclass explosion."
②
"Without it, optional features that combine freely force one subclass per combination — three toppings is already eight classes, a fourth doubles it to sixteen, it grows as 2 to the n. And changing one feature means editing half of those classes."
③
"A coffee example: Espresso, Milk, Cream all implement a Coffee interface with cost(). Milk holds a Coffee inside and returns inner.cost() plus its own. Because Milk is itself a Coffee, I can stack: new Cream(new Milk(new Espresso())) — one cost() call cascades inward."
④
"So four small classes compose into unlimited combinations; adding a topping is one new class, not doubling the count. It's composition instead of inheritance, and it obeys Open–Closed: I extend by adding, never editing what works."

🔎 Chiếu về ví dụ của mình: ① mỗi topping một cục cùng nút .cost() · ② 3 topping = 8 class, +1 → 16, 2ⁿ 😱 · ③ 🪆 new Kem(new Sua(new Espresso())) = 33000, bấm 1 nút · ④ thêm topping = thêm 1 cục = OCP 🔒

🔫 Đòn thủ — khi interviewer vặn "sao không dùng kế thừa cho gọn?"

Đọc verbatim: "Inheritance fixes the combination at compile time — one class per combination — so it explodes as 2 to the n and can't be recomposed at runtime. Decorator uses composition: each layer wraps the next through the same interface, so combinations are built dynamically and each feature lives in exactly one class. That's why real frameworks model cross-cutting concerns — logging, caching, auth — as a middleware chain, which is Decorator in practice."

🎓 Bedrock

Định nghĩa 1 câu (thủ sẵn): "Decorator bọc một object bằng một object khác cùng interface, thêm hành vi trước/sau — để thêm tính năng lúc runtime, phối tự do, mà không đẻ subclass bùng nổ (2ⁿ)."

Chốt hiểu-gốc (khỏi lú lại): mấu chốt là "LÀ một Coffee" = "bấm được .cost()", không phải "là espresso thật" — nhờ vậy cục bọc tự nó cũng là Coffee → bọc chồng vô hạn, client bấm 1 nút. Phải chuyền object (có .cost()), không chuyền số.

Câu chốt: "Decorator giữ interface + thêm hành vi bằng cách bọc — tuân OCP và dùng composition thay inheritance để tránh bùng nổ class. Middleware chain là hiện thân thực tế." Phân biệt sắc với Adapter: cùng "bọc", nhưng Decorator giữ nguyên interface + THÊM hành vi; Adapter đổi interface để tương thích. Nói được cặp này = anh nắm structural patterns rõ.

☝️ Singleton (+ bẫy) — interview thích hỏi MẶT TRÁI
⚡ Cú lật — Singleton thường bị coi là ANTI-PATTERN

Singleton đảm bảo một class chỉ có MỘT instance + một điểm truy cập toàn cục. Nghe tiện — nhưng interview thường hỏi để xem anh có biết mặt trái: nó là global mutable state trá hình (coupling ẩn + khó test + vấn đề đa luồng). Biết mặt trái mới là điểm cộng.

🧗 Con đường tự đẻ ra Singleton (và tự chê nó) — đi lại con đường

Singleton đặc biệt: đây là pattern duy nhất interview hỏi để nghe anh CHÊ nó. Nên hành trình có hai cái đau — một cái nó cứu, một cái nó tự gây ra. Đọc lại 100000 ngày sau vẫn tự dựng lại được.

😌 Cái đau lành: cả app cần dùng CHUNG một cục Config

Config (API key, URL DB, setting) — cả app đọc nó. Anh muốn mọi nơi xài đúng MỘT bản, không new Config() rải rác (50 bản → mỗi bản một giá trị → loạn). Anh cần một cách gọi "đưa tao cục Config CHUNG" — gọi đâu cũng ra đúng nó.

🔑 Chiêu Singleton: khoá cửa + giữ một bản + một cửa lấy

private constructor() khoá — cấm ngoài new (ép chỉ một bản). private static instance = ô cất bản duy nhất trên chính class. static getInstance() = cửa duy nhất: lần đầu tạo, lần sau trả bản cũ. → "một instance + gọi được KHẮP NƠI". Nghe tiện dã man 😏.

🤥 Độc #1 — phụ thuộc ẨN (chữ ký nói dối)

function tinhGia(order){ Config.getInstance().taxRate … } — nhìn chữ ký tưởng chỉ cần order, thực ra lén xài Config. Đọc chữ ký KHÔNG biết nó phụ thuộc gì → coupling ẩn rải khắp app. So với tinhGia(order, config) — khai tường minh, nhìn là biết.

🔒 Độc #2 — kẹt test (không thay được đồ giả)

Muốn test taxRate=0? Hàm tự gọi getInstance() lấy Config thật bên trong → anh đứng ngoài (file test) không nhét được Config giả vào. Kẹt cứng với bản thật. Singleton = "kẻ giết unit test".

💉 Thuốc + sự thật senior: tách "một bản" khỏi "toàn cục"

Thay vì để hàm tự đi lấy, ĐƯA Config vào qua tham số (Dependency Injection): tinhGia(order, config). Hết ẩn (chữ ký khai thật) + test được (nhét đồ giả). Mấu chốt: "một instance" ≠ "điểm truy cập toàn cục". Muốn một bản chung? Để DI container giữ một bản (singleton scope) rồi inject — giữ cái tốt, bỏ cái độc.

🎯 Gói lại 3 ý chính

getInstance() trả về một instance duy nhất

Lần đầu tạo, các lần sau trả lại cùng object. Ai gọi ở đâu cũng lấy được — đó là "điểm truy cập toàn cục".

Nhưng đó là GLOBAL STATE trá hình

Bất kỳ code nào cũng gọi X.getInstance() được → phụ thuộc ẨN (không khai qua constructor). Đọc chữ ký hàm không biết nó dùng Singleton nào.

Global state = khó test + đa luồng + coupling ẩn

Test không thay được nó bằng mock (nó tự tạo mình). State dùng chung giữa các test → rò rỉ giữa test. Đa luồng → race khi khởi tạo.

🎭 Metaphor — thanh kiếm đạo cụ sân khấu (cùng MỘT kiếm, hai cách tới tay): vở kịch có 1 thanh kiếm thật (một instance — đúng). Cách độc (Singleton): kiếm treo hậu đài, diễn viên tự lén chạy ra vớ — bảng kê đạo cụ đầu cảnh (= chữ ký hàm) KHÔNG ghi → nói dối; muốn tập bằng kiếm xốp (= mock) cũng không được vì họ luôn vớ kiếm thật. Cách lành (DI): vẫn đúng kiếm đó, nhưng quản đạo cụ trao tận tay — bảng kê ghi đủ (tường minh), tập thì đưa kiếm xốp (test được). "Một bản" = tốt; "ai cũng tự với tới lấy" = độc.

☝️ Singleton cổ điển
class Config {
  private static instance: Config;
  static getInstance() {
    if (!Config.instance) Config.instance = new Config();
    return Config.instance;
  }
}
Config.getInstance().set(...); // gọi được KHẮP NƠI

🧠 Mấy chỗ dễ tẩu hỏa (đã gỡ trong buổi) — đọc từng dòng code trên

① private vs static — hai gạch nền

private = "chỉ code BÊN TRONG class được sờ, ngoài cấm" (như cái khoá 🔒). static = thuộc tính/hàm thuộc về chính class (một bản chung, gọi qua tên class), KHÔNG thuộc từng object. Ẩn dụ: class là khuôn bánh, mỗi new là một cái bánh. Thứ thường viết lên từng bánh (mỗi cái một giá trị); thứ static viết lên chính cái khuôn (một bản chung). Singleton cần đúng MỘT bản dùng chung → nên viết lên khuôn = static. 🍪

② private static instance: Config — bóc từng chữ

instance = TÊN cái ô (tự đặt). : Config = KIỂU — dán nhãn "ô này chỉ chứa vật loại Config" (như tuoi: number, ten: string). Ghép cả dòng: "một ô tên instance, nằm trên khuôn (static), người ngoài cấm sờ (private), chỉ chứa được một Config." Lúc đầu ô rỗng.

③ private constructor() — khoá cửa tạo mới

Bình thường new Config() chạy constructor. Đặt nó private = khoá: ngoài gõ new Config() → LỖI. Chỉ code bên trong class (tức getInstance()) mới được new. Đây là cách ép chỉ một bản, không ai lén đẻ bản thứ hai.

④ Tách "một bản" (①) khỏi "điểm truy cập toàn cục" (②)

Singleton dán chặt 2 thứ: ① bao nhiêu bản (một — TỐT) + ② cách lấy (ai cũng tự getInstance() — ĐỘC). Bỏ ② giữ ①: vẫn một bản, nhưng trao tận tay (inject) thay vì để tự lén lấy. Đó là toàn bộ câu "senior".

⚠️ Vì sao bị coi anti-pattern: (1) global mutable state — ai cũng đổi, khó truy; (2) phụ thuộc ẨN — không khai qua constructor nên test/đọc code không thấy; (3) không mock được → khó unit test (nối gốc 6); (4) race condition khi khởi tạo đa luồng.

✅ Cách làm đúng thời nay — inject thay vì tự lấy

Cần "một instance dùng chung"? Để DI container quản (singleton scope) và inject qua constructor/tham số. Vẫn một instance, nhưng phụ thuộc TƯỜNG MINH + test thay được bằng mock. Vấn đề không phải "một instance" — mà là "điểm truy cập toàn cục + tự quản".

❌ Tự lén lấy (hidden dependency)
function tinhGia(order) {
  const thue = Config.getInstance().taxRate; // lén, chữ ký nói dối
  return order.total * (1 + thue);
}
tinhGia(order); // test taxRate=0? KẸT — luôn lấy Config thật 🔒
✅ Inject (tường minh + test được)
function tinhGia(order, config) {   // chữ ký NÓI THẬT: cần config
  return order.total * (1 + config.taxRate);
}
tinhGia(order, realConfig);       // code thật: 1 bản dùng chung (DI)
tinhGia(order, { taxRate: 0 }); // test: nhét đồ giả ✅
↓ Interviewer đào tiếp
"Vì sao Singleton bị coi anti-pattern?"
Global mutable state (khó suy luận), hidden dependency (không qua constructor → test/đọc khó), không mock được (khó test), coupling ẩn khắp code, và race lúc khởi tạo đa luồng.
"DI thay Singleton thế nào?"
Container tạo & giữ MỘT instance (singleton scope) rồi INJECT vào nơi cần qua constructor. Vẫn một instance dùng chung, nhưng phụ thuộc tường minh + test thay được. Tách 'một instance' khỏi 'truy cập toàn cục'.
"Khi nào Singleton CHẤP NHẬN được?"
Khi stateless hoặc chỉ đọc (logger, config immutable), phạm vi nhỏ, không cần thay trong test. Ngay cả vậy, inject vẫn tốt hơn truy cập toàn cục cứng.

🎤 Singleton — đọc y như vầy (English)
①
"Singleton guarantees a class has exactly one instance plus a global access point to it — a private constructor locks out new, a static field holds the one instance, and getInstance() hands it back."
②
"But interviewers usually ask it to hear the downside: it's global mutable state in disguise. Any function can reach in with getInstance(), so the dependency is hidden — the signature doesn't declare it — and you can't swap it for a mock in a test. Plus lazy init races across threads."
③
"If tinhGia(order) grabs Config.getInstance() inside, its signature lies and I can't test it with taxRate=0. If instead I write tinhGia(order, config), the dependency is explicit and I just pass a fake config in the test."
④
"The real problem isn't 'one instance' — it's the global access point plus self-managed lifecycle. If I need one shared instance, I let a DI container own it as a singleton scope and inject it — one instance, but explicit and testable."

🔎 Chiếu về ví dụ của mình: ① khoá cửa + ô static + getInstance · ② hàm lén getInstance() → chữ ký nói dối + kẹt test · ③ 🎭 tự vớ kiếm thật vs được trao (thay kiếm xốp lúc tập) · ④ tách "một bản" (tốt) khỏi "toàn cục" (độc) → inject

🔫 Đòn thủ — khi interviewer vặn "nhưng đôi khi cần một bản dùng chung mà?"

Đọc verbatim: "Absolutely — needing one shared instance is legitimate. What I avoid is the global access point, not the single instance. The classic Singleton fuses two separate things: 'how many' (one) and 'how you get it' (a global door everyone reaches into). I keep the first and drop the second — a DI container holds the single instance and injects it, so the dependency stays explicit and I can substitute a fake in tests. Same one instance, none of the global-state pain."

🎓 Bedrock

Định nghĩa 1 câu (thủ sẵn): "Singleton = một class chỉ có đúng MỘT instance + một điểm truy cập toàn cục; nhưng nó là global mutable state trá hình nên thường bị coi anti-pattern."

Câu chốt phân biệt senior: "vấn đề của Singleton KHÔNG phải 'một instance' — mà là ĐIỂM TRUY CẬP TOÀN CỤC + tự quản vòng đời. Tôi muốn một instance thì để DI container quản và inject, giữ phụ thuộc tường minh và test được." Nhớ tách rõ: "một bản" = TỐT · "ai cũng tự với tới lấy" = ĐỘC. Trả lời được mặt trái + giải pháp thay thế = đúng thứ interviewer săn — đây là pattern duy nhất họ hỏi để nghe anh CHÊ.

Interviewer đào sâu thế nào

7 bậc — leo được tới đỉnh mà tự suy ra = đậu gốc này.

1
"Design pattern là gì?"
→ Giải pháp mẫu đã kiểm chứng cho vấn đề thiết kế lặp lại; là từ vựng chung của team. (định nghĩa)
2
"Kể vài pattern và nhóm của nó."
→ Strategy/Observer (behavioral), Factory/Builder (creational), Adapter/Decorator (structural). (phân loại)
3
"Anh từng dùng pattern nào trong dự án?"
→ DẪN SẸO Asset_Platform: NestJS DI/Provider, hoặc Strategy cho xử lý nhiều loại, hoặc Adapter bọc SDK. Tại sao chọn. (kinh nghiệm)
4
"Hàm này có 5 if theo payment type — pattern nào?"
→ Strategy; mỗi cổng một class, nối Open/Closed. Factory tạo strategy theo type. (áp dụng tại chỗ)
5
"Adapter khác Decorator khác Facade thế nào?"
→ Adapter ĐỔI interface cho khớp; Decorator GIỮ interface + thêm hành vi; Facade ĐƠN GIẢN HÓA nhiều thứ sau một mặt tiền. Cùng 'bọc', khác ý định. (phân biệt sâu)
6
"Các pattern này nối với SOLID nào?"
→ Strategy/Decorator = OCP + composition; Factory/Adapter = DIP; Observer = decouple nguồn/bên nghe. Pattern là SOLID mang tên. (synthesis)
7
"Khi nào KHÔNG nên dùng pattern? Vì sao Singleton bị chê?"
→ Khi vấn đề chưa có thật (YAGNI) — pattern thêm gián tiếp = phức tạp. Singleton = global state ẩn, khó test → dùng DI thay. Pattern giải vấn đề, không tạo vấn đề. (bedrock)
