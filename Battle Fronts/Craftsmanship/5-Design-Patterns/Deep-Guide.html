Giải pháp mẫu cho vấn đề lặp lại

Design pattern không phải code copy-paste — nó là công thức đã được kiểm chứng cho một bài toán thiết kế hay tái diễn. Học pattern = học từ vựng chung: nói "dùng Strategy ở đây" thì cả team hiểu ngay.

⚡ Cú lật lớn — pattern là TỪ VỰNG, không phải mục tiêu

Đa số pattern hay dùng thực chất là áp dụng cụ thể của SOLID + composition: Strategy/Decorator = OCP + composition; Factory/Adapter = DIP. Học pattern KHÔNG phải để nhồi vào code cho "xịn" — mà để có TÊN GỌI CHUNG cho các giải pháp anh vốn đã suy ra được từ nguyên tắc. Hiểu gốc (SOLID/OOP) → pattern chỉ là đặt tên.

⚠️ Bẫy interview lớn nhất: nhồi pattern vào mọi chỗ. Pattern là để GIẢI một vấn đề có thật, không phải để khoe. Dùng sai chỗ = over-engineering = một code smell mới.

🗺️ Bản đồ — bấm để nhảy & mở
🎯 Strategy 🏭 Factory 📡 Observer 🔌 Adapter 🎁 Decorator ☝️ Singleton (+bẫy)
🎯 Strategy — pattern interview hỏi nhiều nhất
⚡ Cú lật — đóng gói MỖI thuật toán vào một class, đổi được lúc runtime

Strategy = lấy một "họ thuật toán/hành vi" (mỗi nhánh if theo type), đóng mỗi cái vào một class cùng interface, để đổi hành vi lúc runtime + thêm loại mới không sửa code cũ. Đây là OCP (gốc 3) + composition (gốc 4) hiện hình.

Mỗi nhánh if theo type là một HÀNH VI riêng

if vnpay... if momo... if stripe... — mỗi nhánh là một cách tính phí. Chúng cùng "hình dạng" (nhận amount, trả phí) nhưng khác ruột.

Tách mỗi hành vi thành class implement chung interface

FeeStrategy { calc(a) } → VnpayFee, MomoFee, StripeFee. Mỗi class giữ đúng công thức của nó.

Client GIỮ một reference tới interface — đổi = đổi hành vi

checkout(strategy) nhận một FeeStrategy. Đổi cổng = truyền strategy khác (runtime). Thêm cổng = thêm class (code checkout không đụng → OCP).

🧭 Metaphor — chọn phương tiện đi cùng quãng đường: đi bộ / xe máy / máy bay — cùng "đi từ A tới B" (interface), mỗi cách một chiến lược. Đổi phương tiện = đổi strategy, không đổi mục tiêu.

❌ Switch phình theo mỗi loại mới
fee(type, amount) {
  if (type==='vnpay') return amount*.01;
  if (type==='momo')  return amount*.015;
  if (type==='stripe') return amount*.029;
  // thêm cổng = sửa hàm (vi phạm O)
}
✅ Strategy
interface FeeStrategy { calc(a): number }
class VnpayFee implements FeeStrategy {...}
class MomoFee  implements FeeStrategy {...}
// thêm cổng = thêm class, không sửa cũ
checkout(strategy: FeeStrategy) {...}

Strategy biến if/else thành các class cắm-rời. Nối thẳng Open/Closed (gốc 3). Đây là pattern interview hỏi nhiều nhất.

🎮 Demo trực quan: đổi strategy lúc runtimeChọn VNPay/Momo/Stripe — cùng checkout(), phí đổi theo strategy; thêm cổng mới mà checkout không sửa (Open/Closed). Mở ↗

👃 Khi nào dùng

1
Nhiều thuật toán cho cùng một việc
Tính phí / sắp xếp / validate theo nhiều cách có thể hoán đổi.
2
switch/if theo type hay thêm nhánh
Trục biến thiên "loại" rõ ràng và còn mở rộng tiếp.
↓ Interviewer đào tiếp
"Có phải mọi if/else đều nên thành Strategy?"
Không. 2 case ổn định, không đổi → một if/else đơn giản tốt hơn 5 file Strategy (YAGNI). Strategy đáng khi số loại còn tăng hoặc cần hoán đổi lúc runtime.
"Strategy khác State pattern chỗ nào?"
Cấu trúc giống nhau (đều delegate qua interface), khác Ý ĐỊNH: Strategy do CLIENT chọn thuật toán; State đổi theo TRẠNG THÁI nội bộ và các state tự chuyển lẫn nhau.
"Ai quyết định chọn strategy nào?"
Thường là client, một Factory (theo type), hoặc DI container. Việc CHỌN tách khỏi việc DÙNG — bản thân đó cũng là tách trách nhiệm.
🎓 Bedrock

Câu chốt: "Strategy đóng gói một họ thuật toán biến thiên sau một interface, để đổi lúc runtime và mở rộng không sửa code cũ. Nó là OCP + composition mang tên." Nói được nó = OCP-hiện-hình + biết khi nào KHÔNG cần = anh hiểu gốc, không nhồi pattern.

🏭 Factory — tập trung việc TẠO đối tượng
⚡ Cú lật — tách "quyết định TẠO cái gì" khỏi "DÙNG nó"

Factory gom LOGIC TẠO đối tượng vào một chỗ. new ConcreteClass() rải khắp = mọi nơi biết class cụ thể + đổi cách tạo phải sửa N chỗ. Factory để client xin "cho tôi một FeeStrategy loại X" mà không tự new.

new ConcreteX() rải khắp = coupling khắp nơi

Mỗi nơi new VnpayFee() đều dính vào class cụ thể. Đổi constructor / thêm cấu hình khởi tạo = sửa mọi chỗ.

Gom quyết định tạo vào MỘT factory

FeeFactory.create(type) — chỉ một chỗ biết "type nào → class nào". Thêm loại = sửa một chỗ (registry).

Client xin factory, không biết class cụ thể (nối DIP)

Client chỉ thấy interface FeeStrategy + factory. Nó không import class cụ thể → phụ thuộc abstraction.

🧭 Metaphor — quầy pha chế: anh gọi "cho americano", quầy lo pha và đưa ra. Anh không tự vào bếp lắp máy. Factory = cái quầy: anh nói cần gì, nó lo tạo.

❌ new rải khắp nơi
// chỗ này chỗ kia đều:
new VnpayFee(); new MomoFee();
// đổi cách tạo = sửa N chỗ
✅ Factory
class FeeFactory {
  create(type): FeeStrategy {
    return this.registry[type];
  }
}
// một chỗ duy nhất biết cách tạo

👃 Khi nào dùng

1
new class cụ thể rải nhiều nơi
Tạo đối tượng có logic (chọn loại, cấu hình) lặp lại khắp code.
2
Client cần một sản phẩm nhưng không nên biết class cụ thể
Muốn phụ thuộc interface, để cách tạo thay đổi tự do.
↓ Interviewer đào tiếp
"Factory Method vs Abstract Factory vs simple factory?"
Simple factory = một hàm/class create(type). Factory Method = subclass quyết định tạo gì (override một method tạo). Abstract Factory = tạo cả một HỌ sản phẩm liên quan (vd UI theme: button+checkbox cùng phong cách).
"Vì sao không new khắp nơi?"
Vì new ConcreteX là coupling cứng tới class cụ thể (vi phạm DIP), khó đổi cách tạo, khó test (không thay được bằng mock). Factory cô lập điểm tạo.
"Factory nối Strategy thế nào?"
Rất hay đi cùng: Factory TẠO ra đúng Strategy theo type, rồi client DÙNG strategy đó. Factory lo 'tạo cái nào', Strategy lo 'làm thế nào'.
🎓 Bedrock

Câu chốt: "Factory cô lập ĐIỂM QUYẾT ĐỊNH TẠO — thêm loại chỉ sửa factory, phần còn lại phụ thuộc interface (DIP). NestJS Provider/DI container thực chất là một factory tổng quát." Nối được Factory↔DIP↔NestJS = anh cho thấy hiểu xuyên suốt.

📡 Observer — một phát, nhiều nghe (one-to-many)
⚡ Cú lật — Subject KHÔNG biết ai đang nghe

Observer: một Subject phát sự kiện khi state đổi; nhiều Observer tự đăng ký nhận. Điểm cốt: subject không gọi thẳng từng observer (coupling), nó chỉ "notify" — ai subscribe thì nhận. Loose coupling one-to-many.

Khi state đổi, NHIỀU thứ cần phản ứng

Order chuyển "đã thanh toán" → cần: gửi mail, cập nhật dashboard, ghi log, trừ kho. Nhiều bên quan tâm một sự kiện.

Đừng để subject gọi thẳng từng cái (coupling)

Nếu Order tự gọi mailer.send(), dashboard.update()... nó phải BIẾT hết + thêm bên nghe mới phải sửa Order (Shotgun, gốc 2).

Observer tự SUBSCRIBE; subject chỉ NOTIFY

order.subscribe(observer). Khi đổi state → notify() lặp qua danh sách. Subject chỉ biết "có ai đó implement update()" — không biết cụ thể. Thêm bên nghe = subscribe thêm, không sửa subject.

🧭 Metaphor — kênh YouTube: anh bấm subscribe; kênh ra video mới thì hệ thống báo cho MỌI subscriber. Kênh không cần giữ danh sách tên từng người hay gọi từng người — nó chỉ "phát", ai đăng ký thì nhận.

❌ Subject gọi thẳng từng bên (coupling)
class Order {
  pay() {
    mailer.send(...);      // Order phải biết mailer
    dashboard.update(...); // ...và dashboard
    logger.log(...);       // thêm bên = sửa Order
  }
}
✅ Observer
class Order {
  private obs: Observer[] = [];
  subscribe(o) { this.obs.push(o); }
  pay() { this.notify('paid'); }
  notify(e){ this.obs.forEach(o => o.update(e)); }
}
// thêm bên nghe = subscribe, KHÔNG sửa Order
🎮 Demo trực quan: Subject phát, Observer nhậnĐổi trạng thái Order — xem Email/SMS/Dashboard/Logger cùng sáng lên khi nhận sự kiện. Thêm/bớt observer để thấy subject không hề đổi. Mở ↗

👃 Khi nào dùng

1
Một sự kiện, nhiều bên quan tâm
Và số bên còn thay đổi → không muốn sửa nguồn phát mỗi lần.
2
Muốn tách nguồn sự kiện khỏi bên xử lý
Event-driven, reactive UI, domain events.
↓ Interviewer đào tiếp
"Observer khác Pub/Sub (event bus) thế nào?"
Observer: subject giữ trực tiếp danh sách observer (biết chúng qua interface). Pub/Sub: có một BROKER/event bus trung gian, publisher và subscriber không biết nhau chút nào → decouple mạnh hơn, dễ mở rộng qua tiến trình/mạng.
"Push vs pull model?"
Push: subject gửi kèm dữ liệu trong notify. Pull: subject chỉ báo 'có đổi', observer tự hỏi lại data cần. Push tiện, pull linh hoạt/ít coupling dữ liệu.
"Rủi ro lớn nhất của Observer?"
Memory leak: quên unsubscribe → subject giữ tham chiếu observer mãi (lapsed listener). Và thứ tự notify / cascade update khó lường. Luôn có đường unsubscribe.
🎓 Bedrock

Câu chốt: "Observer đảo chiều phụ thuộc thời gian — subject không gọi observer trực tiếp, nó phát sự kiện; bên nghe tự đăng ký. Đó là nền của event-driven và reactive." Biết thêm rủi ro (unsubscribe/leak) = anh cho thấy đã DÙNG thật, không chỉ đọc.

🔌 Adapter — đổi interface cho khớp, không sửa class gốc
⚡ Cú lật — dịch giữa hai interface không khớp

Adapter đứng GIỮA: client mong interface A, thư viện/legacy cho interface B. Adapter implement A, bên trong gọi B — không sửa class gốc, không sửa client. Thường dùng để bọc 3rd-party / legacy cho khớp domain của mình.

Client mong một interface; thứ có sẵn cho interface khác

App của anh gọi IPayment.charge(); nhưng StripeSDK cho stripe.createCharge() hình dạng khác. Không khớp.

Adapter implement interface client cần, gọi B bên trong

StripeAdapter implements IPayment { charge(){ this.stripe.createCharge(...) } }. Nó "dịch" lời gọi.

Client dùng A, không biết B tồn tại

Đổi Stripe → Adyen = viết adapter mới cho IPayment. Domain code (dùng IPayment) không đụng.

🧭 Metaphor — ổ chuyển phích cắm: phích dẹt (VN) cắm ổ tròn (EU) — không đổi ổ tường, không đổi phích, chỉ thêm cục chuyển ở giữa. Adapter đúng là "cục chuyển" giữa hai interface.

❌ Domain gọi thẳng SDK (dính vendor)
class Checkout {
  pay() {
    stripe.createCharge({amt, cur}); // SDK rò vào domain
  }
}
// đổi Stripe→Adyen = sửa domain khắp nơi
✅ Adapter
interface IPayment { charge(amt): void }
class StripeAdapter implements IPayment {
  charge(amt){ this.stripe.createCharge({amt}); }
}
// domain dùng IPayment; đổi vendor = adapter mới

👃 Khi nào dùng

1
Tích hợp thư viện 3rd-party / legacy
Interface của nó không khớp cái domain anh muốn.
2
Muốn đổi vendor mà không sửa domain
Cô lập vendor sau một ranh giới do mình định nghĩa.
↓ Interviewer đào tiếp
"Adapter khác Facade thế nào?"
Adapter: đổi MỘT interface cho khớp cái client cần (mục tiêu: tương thích). Facade: cung cấp một interface ĐƠN GIẢN che một hệ thống con phức tạp (mục tiêu: đơn giản hóa). Adapter dịch; Facade gói gọn.
"Adapter khác Decorator?"
Decorator giữ NGUYÊN interface, thêm hành vi. Adapter ĐỔI interface (từ B sang A), không thêm hành vi. Cùng 'bọc' nhưng mục đích khác.
"Adapter liên quan gì tới testing (gốc 6)?"
'Don't mock what you don't own': bọc 3rd-party bằng adapter (interface của mình), rồi test bằng cách mock adapter/interface — không mock SDK ngoài. Adapter tạo ranh giới mock được (nối DIP).
🎓 Bedrock

Câu chốt: "Adapter là ranh giới chống 3rd-party rò vào domain — domain phụ thuộc interface của MÌNH, adapter dịch sang API vendor. Đổi vendor = viết adapter mới, domain bất động." Đây là ports-and-adapters (Hexagonal), nối thẳng DIP (gốc 3).

🎁 Decorator — thêm hành vi ĐỘNG bằng cách bọc
⚡ Cú lật — thêm tính năng bằng BỌC, không bằng subclass

Decorator bọc một object bằng một object khác CÙNG interface, thêm hành vi trước/sau. Mục tiêu: thêm tính năng lúc runtime, tùy tổ hợp, không đẻ subclass bùng nổ (nếu dùng kế thừa cho mọi tổ hợp thì số class nổ theo cấp số nhân).

Nhiều tính năng tùy chọn → subclass bùng nổ

Coffee + sữa? + đường? + kem? Nếu mỗi tổ hợp một subclass → MilkSugarCoffee, MilkKemCoffee... nổ tung.

Decorator bọc object gốc, giữ CÙNG interface

MilkDecorator cũng là Coffee, nó GIỮ một Coffee bên trong + thêm giá/mô tả sữa. Client vẫn thấy một Coffee.

Bọc CHỒNG nhiều lớp tùy ý

new Sugar(new Milk(new Espresso())) — mỗi lớp thêm một hành vi. Muốn thêm topping = thêm một decorator, ghép runtime.

🧭 Metaphor — topping pizza / mặc thêm áo: cùng "cái pizza", anh thêm từng topping tùy ý; cùng "một người", mặc thêm áo khoác/khăn tùy trời. Bọc thêm lớp, không đúc một loại người mới cho mỗi kiểu ăn mặc.

❌ Subclass cho mọi tổ hợp
class Espresso {}
class MilkEspresso {}
class MilkSugarEspresso {}
// mỗi tổ hợp = 1 class → nổ tung 😱
✅ Decorator (bọc chồng)
interface Coffee { cost(): number }
class Milk implements Coffee {
  constructor(private inner: Coffee) {}
  cost(){ return this.inner.cost() + 5; }
}
new Milk(new Sugar(new Espresso()));

👃 Khi nào dùng

1
Tính năng tùy chọn ghép tự do
Log, cache, nén, mã hóa thêm quanh một hành vi cốt lõi.
2
Không muốn sửa class gốc
Thêm hành vi từ ngoài (OCP) thay vì mổ class.
↓ Interviewer đào tiếp
"Decorator khác Inheritance chỗ nào?"
Inheritance quyết lúc COMPILE, cứng, mỗi tổ hợp một class. Decorator quyết lúc RUNTIME, ghép chồng tùy ý, tránh bùng nổ class. Decorator = composition thay cho inheritance để thêm hành vi.
"Middleware/Interceptor (Express/Nest) có phải Decorator?"
Rất gần: chuỗi middleware bọc quanh request/handler, mỗi lớp thêm hành vi (auth, log, cache) trước/sau — đúng tinh thần decorator/chain. (Lưu ý: @Decorator syntax của TS là metadata, khác pattern này.)
"Thứ tự bọc có quan trọng không?"
Có. Cache(Log(x)) khác Log(Cache(x)) — cái nào chạy trước ảnh hưởng hành vi (vd log có thấy cache hit không). Thứ tự là một quyết định thiết kế.
🎓 Bedrock

Câu chốt: "Decorator giữ interface + thêm hành vi bằng cách bọc — tuân OCP (thêm không sửa) và dùng composition thay inheritance để tránh bùng nổ class. Middleware chain là hiện thân thực tế." Phân biệt được với Adapter (đổi interface) = anh nắm structural patterns rõ.

☝️ Singleton (+ bẫy) — interview thích hỏi MẶT TRÁI
⚡ Cú lật — Singleton thường bị coi là ANTI-PATTERN

Singleton đảm bảo một class chỉ có MỘT instance + một điểm truy cập toàn cục. Nghe tiện — nhưng interview thường hỏi để xem anh có biết mặt trái: nó là global mutable state trá hình (coupling ẩn + khó test + vấn đề đa luồng). Biết mặt trái mới là điểm cộng.

getInstance() trả về một instance duy nhất

Lần đầu tạo, các lần sau trả lại cùng object. Ai gọi ở đâu cũng lấy được — đó là "điểm truy cập toàn cục".

Nhưng đó là GLOBAL STATE trá hình

Bất kỳ code nào cũng gọi X.getInstance() được → phụ thuộc ẨN (không khai qua constructor). Đọc chữ ký hàm không biết nó dùng Singleton nào.

Global state = khó test + đa luồng + coupling ẩn

Test không thay được nó bằng mock (nó tự tạo mình). State dùng chung giữa các test → rò rỉ giữa test. Đa luồng → race khi khởi tạo.

🧭 Metaphor — công tắc tổng của cả tòa nhà: tiện vì ai cũng với tới, nhưng một người gạt là CẢ tòa nhà ảnh hưởng, và không ai biết ai vừa gạt. Trạng thái toàn cục là vậy: tiện truy cập, khó truy trách nhiệm.

☝️ Singleton cổ điển
class Config {
  private static instance: Config;
  static getInstance() {
    if (!Config.instance) Config.instance = new Config();
    return Config.instance;
  }
}
Config.getInstance().set(...); // gọi được KHẮP NƠI
⚠️ Vì sao bị coi anti-pattern: (1) global mutable state — ai cũng đổi, khó truy; (2) phụ thuộc ẨN — không khai qua constructor nên test/đọc code không thấy; (3) không mock được → khó unit test (nối gốc 6); (4) race condition khi khởi tạo đa luồng.

✅ Cách làm đúng thời nay

Cần "một instance dùng chung"? Để DI container quản (singleton scope) và inject qua constructor. Vẫn một instance, nhưng phụ thuộc TƯỜNG MINH + test thay được bằng mock. Vấn đề không phải "một instance" — mà là "điểm truy cập toàn cục + tự quản".

↓ Interviewer đào tiếp
"Vì sao Singleton bị coi anti-pattern?"
Global mutable state (khó suy luận), hidden dependency (không qua constructor → test/đọc khó), không mock được (khó test), coupling ẩn khắp code, và race lúc khởi tạo đa luồng.
"DI thay Singleton thế nào?"
Container tạo & giữ MỘT instance (singleton scope) rồi INJECT vào nơi cần qua constructor. Vẫn một instance dùng chung, nhưng phụ thuộc tường minh + test thay được. Tách 'một instance' khỏi 'truy cập toàn cục'.
"Khi nào Singleton CHẤP NHẬN được?"
Khi stateless hoặc chỉ đọc (logger, config immutable), phạm vi nhỏ, không cần thay trong test. Ngay cả vậy, inject vẫn tốt hơn truy cập toàn cục cứng.

Câu chốt phân biệt senior: "vấn đề của Singleton KHÔNG phải 'một instance' — mà là ĐIỂM TRUY CẬP TOÀN CỤC + tự quản vòng đời. Tôi muốn một instance thì để DI container quản và inject, giữ phụ thuộc tường minh và test được." Trả lời được mặt trái + giải pháp thay thế = đúng thứ interviewer săn.
