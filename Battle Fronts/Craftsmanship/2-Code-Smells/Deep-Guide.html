Code Smells

📖 Neo canon: Refactoring — Martin Fowler (catalog of smells)
① Khái niệm② Smell → Fix③ Trong code của anh④ Why-Ladder
① Khái niệm (framework-agnostic)

Mùi hôi — triệu chứng, không phải bệnh

Code smell không phải bug — code vẫn chạy. Nó là triệu chứng bề mặt báo hiệu một vấn đề sâu hơn về thiết kế. Học gốc này = học NGỬI trước khi học dọn (gốc Refactoring sẽ dọn).

"If it stinks, change it." — Fowler. Smell không bắt buộc phải sửa ngay, nhưng nó là tín hiệu để DỪNG và NHÌN.

Danh mục mùi hay gặp nhất (interview yêu thích)

② Smell → Fix (thấy tận mắt)

Ngửi ra mùi → chỉ tay vào nó

A. God Class — class biết quá nhiều

❌ Smell
class UserService {
  validateEmail() {...}
  hashPassword() {...}
  saveToDb() {...}
  sendEmail() {...}
  generateInvoice() {...}
  exportCsv() {...}
  callPaymentGateway() {...}
  // 15 methods, 5 domains 😱
}
✅ Hướng dọn (Extract Class)
class UserService     { create, update }
class PasswordHasher   { hash, verify }
class UserNotifier     { sendWelcome }
class InvoiceService   { generate, export }
// mỗi class một trách nhiệm

God class = nam châm của thay đổi. Mỗi domain đổi đều phải mở nó ra → rủi ro cao, khó test, khó chia việc.

B. Long Parameter List

❌ Smell
createBooking(
  userId, roomId, start, end,
  guests, note, promoCode, currency
) {...}
✅ Parameter Object
createBooking(dto: CreateBookingDto) {...}
// 8 tham số → 1 object có tên,
// dễ validate, dễ mở rộng
③ Trong code THẬT của anh

Đi ngửi mùi trong Asset_Platform

🔍 Săn 2 con mồi (15 phút)

Mở /Users/tritdd/Work/Asset_Platform/apps/api. Tìm:

  • Một god service — NestJS service nào có nhiều method chạm nhiều domain (auth + DB + email + payment...). Kể tên việc của nó — đếm chữ "VÀ".
  • Duplicated code — đoạn logic (map DTO, format, check quyền) lặp ở 2-3 service/controller. Đánh dấu chỗ trùng.

→ Chưa cần dọn (gốc Refactoring lo). Gốc này chỉ cần NGỬI ĐÚNG và GỌI TÊN. Ghi vào Scar-Journal: mùi gì, ở đâu.

④ Why-Ladder (cho Mock)

Interviewer đào sâu thế nào

1
"Code smell là gì?"
→ Triệu chứng bề mặt, không phải bug, báo hiệu vấn đề thiết kế sâu hơn.
2
"Kể vài mùi anh biết."
→ God class, long method, duplicated code, long param list, feature envy... (gọi tên trôi chảy).
3
"Kể một god class anh từng gặp."
→ DẪN SẸO từ Asset_Platform: "service X ôm validate + DB + email + payment, một thay đổi nhỏ bắt mở cả file..." (kinh nghiệm)
4
"Class này có 12 method chạm 4 domain — mùi gì? Sửa sao?"
→ God class. Extract Class theo trách nhiệm. (áp dụng tại chỗ)
5
"Duplication có phải LÚC NÀO cũng xấu?"
→ Không. Rule of Three: lặp 2 lần còn chịu được; lặp 3 lần mới trừu tượng hóa. Trừu tượng SAI còn tệ hơn duplication (Sandi Metz). (bedrock)
Đậu gốc này khi

Anh ngửi và gọi tên được mùi tại chỗ (tầng 4) + dẫn được 1 god class thật từ Asset_Platform (tầng 3) + hiểu duplication không phải lúc nào cũng xấu (tầng 5).
