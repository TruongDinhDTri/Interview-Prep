① Khái niệm (framework-agnostic)

Tấm lưới để anh dám đổi code

Test không phải để "chứng minh code đúng". Nó là tấm lưới an toàn: nó cho anh can đảm refactor mà không sợ phá thứ khác. Không có test = mỗi lần sửa là một canh bạc.

Test Pyramid — cái họ vả anh hôm phỏng vấn

E2Eít · chậm · giòn · qua cả hệ thống
Integrationvừa · nhiều module ráp nhau (DB, API)
UnitNHIỀU · nhanh · rẻ · một đơn vị cô lập
🧠 Ý nghĩa kim tự tháp: nhiều unit (đáy), ít E2E (đỉnh). Vì unit nhanh+rẻ+ổn định; E2E chậm+đắt+flaky. Lật ngược (nhiều E2E) = "ice cream cone" anti-pattern: chạy 20 phút, hay đỏ vu vơ.

F.I.R.S.T — dấu hiệu unit test tốt

Fast — chạy mili giây
Isolated — không phụ thuộc test khác
Repeatable — chạy đâu cũng cùng kết quả
Self-validating — pass/fail rõ, không đọc tay
Timely — viết đúng lúc (lý tưởng: trước code — gốc 8 TDD)
📌 Mocking: thay phụ thuộc thật (DB, API, mailer) bằng đồ giả để test đơn vị cô lập. Mock nhiều quá = test dính chặt implementation, dễ vỡ. Mock đúng ranh giới (I/O, external).

Test dở → test tốt

A. Cấu trúc AAA (Arrange–Act–Assert)

❌ Test rối, test nhiều thứ
it('works', () => {
  const r = svc.register(dto);
  expect(r.id).toBeDefined();
  expect(mailer.sent).toBe(true);
  expect(db.count()).toBe(1);
  // tên vô nghĩa, 3 assert 3 lý do fail
})
✅ AAA, một hành vi/test
it('tạo user khi dto hợp lệ', () => {
  // Arrange
  const dto = makeValidDto();
  // Act
  const user = svc.register(dto);
  // Assert
  expect(user.id).toBeDefined();
})

B. Mocking đúng ranh giới

❌ Gọi DB/mail thật trong unit test
it('register', async () => {
  await svc.register(dto);
  // chạm Postgres + SendGrid thật
  // → chậm, flaky, gửi mail thật 😱
})
✅ Mock phụ thuộc ngoài
const mailer = { send: jest.fn() };
const svc = new UserService(repo, mailer);
await svc.register(dto);
expect(mailer.send).toHaveBeenCalled();
// nhanh, cô lập, lặp lại được

👉 Để mock được dễ thế này, UserService phải nhận phụ thuộc qua constructor — đó chính là DIP (gốc 3). Thấy các gốc nối nhau chưa?

③ Trong code THẬT của anh

Soi test trong Asset_Platform

🔍 Săn + Build (25 phút)

Asset_Platform đã có sẵn apps/api/test, apps/web/e2e, apps/mobile/__tests__, __mocks__/. Làm:

  • Đếm hình dạng pyramid — anh đang có bao nhiêu unit vs integration vs E2E? Nó là kim tự tháp hay ice-cream-cone (ngược)?
  • Build một unit test thật — chọn MỘT service method chưa có test, viết unit test cho nó (mock phụ thuộc ngoài). Cảm cái khó: nếu khó mock → đó là tín hiệu code dính chặt (thiếu DIP). ĐÓ là vết sẹo.

→ Ghi Scar-Journal: viết test thấy gì? Chỗ nào khó test → chỗ đó thiết kế cần sửa.

④ Why-Ladder (cho Mock)

Interviewer đào sâu thế nào

1
"Test pyramid là gì?"
→ Nhiều unit (đáy), ít integration (giữa), rất ít E2E (đỉnh). (định nghĩa)
2
"Tại sao nhiều unit, ít E2E?"
→ Unit nhanh/rẻ/ổn định; E2E chậm/đắt/flaky. Tối ưu feedback nhanh + chi phí thấp. (lý do)
3
"Kể lần anh viết test cho một feature."
→ DẪN SẸO Asset_Platform: viết unit test cho service X, phải mock repo/mailer, chỗ nào khó mock. (kinh nghiệm)
4
"Service này khó test vì new-up DB bên trong. Sao sửa?"
→ Inject phụ thuộc (DIP) để mock được. Khó test = tín hiệu thiết kế xấu. (áp dụng — nối gốc 3)
5
"100% coverage có phải mục tiêu không?"
→ Không. Coverage là chỉ số, không phải mục tiêu. Test giá trị (logic phức tạp, edge case) quan trọng hơn test getter/setter cho đủ %. Test để tự tin refactor, không để khoe số. (bedrock)
Đậu gốc này khi

Anh giải thích pyramid + lý do (tầng 2), dẫn được lần viết test thật (tầng 3), nối "khó test = thiết kế xấu" sang DIP (tầng 4), và hiểu coverage không phải mục tiêu (tầng 5).
