Clean Code

📖 Neo canon: Clean Code — Robert C. Martin (Uncle Bob)

① Khái niệm (framework-agnostic)

Code được ĐỌC nhiều hơn được VIẾT

Một dòng code anh viết một lần, nhưng nó được đọc hàng chục lần — bởi anh-của-6-tháng-sau, bởi đồng đội, bởi người maintain. Clean code = code mà người khác đọc hiểu ngay, sửa được mà không sợ.

"Clean code reads like well-written prose." — Uncle Bob. Mục tiêu không phải code chạy — mà code mà 6 tháng sau đọc lại không chửi.

4 trụ cột (đúng ở MỌI ngôn ngữ)

  • Tên có ý nghĩa — tên nói rõ ý định. Đọc tên là biết nó làm gì, không cần đọc thân hàm. Reveal intent.
  • Hàm nhỏ, làm MỘT việc — một hàm = một nhiệm vụ, một mức trừu tượng. Ngắn (lý tưởng < 20 dòng).
  • Comment nói WHY, không nói WHAT — code tự nói nó LÀM gì; comment chỉ giải thích TẠI SAO (quyết định, đánh đổi). Comment giải thích code dở = mùi hôi.
  • Nhất quán & không bất ngờ — format đều, đặt tên cùng quy ước. Người đọc đoán được cái tiếp theo.
🧠 Mẹo nhớ: "Code không cần comment để giải thích nó làm gì — vì cái TÊN đã giải thích rồi."
② Smell → Fix (thấy tận mắt)

Code dở → Code sạch

Ví dụ bằng TypeScript (ngôn ngữ Asset_Platform của anh) — nhưng nguyên tắc đúng ở Python, Java, Go.

A. Đặt tên — tiết lộ ý định

❌ Smell
// d là gì? 7 là gì?
const d = u.filter(x => x.s === 1);
if (diff > 7) { ... }
✅ Fix
const activeUsers = users.filter(
  user => user.status === UserStatus.Active
);
if (daysSinceLogin > INACTIVE_THRESHOLD_DAYS) { ... }

Tên xấu bắt người đọc giải mã. Tên tốt bắt máy tính làm việc, để não người nghỉ.

B. Hàm làm một việc — tách trách nhiệm

❌ Smell — hàm ôm 3 việc
function register(dto) {
  // validate
  if (!dto.email.includes('@')) throw ...
  // hash
  const h = bcrypt.hashSync(dto.pw, 10);
  // save + email
  db.save({...dto, pw:h});
  mailer.send(dto.email);
}
✅ Fix — mỗi hàm một việc
function register(dto) {
  validateRegistration(dto);
  const user = createUser(dto);
  sendWelcomeEmail(user);
  return user;
}

Hàm register giờ đọc như mục lục: validate → create → email. Chi tiết nằm dưới, ở đúng mức trừu tượng của nó.

⚡ Đào sâu — khi hàm nhỏ gặp thế giới thật

Tách register ra rồi, interviewer hay đào tiếp: "user đã createUser xong, nhưng sendWelcomeEmail lỡ fail thì sao?" Tách hàm là bước một — bước hai là biết hàm nào được phép làm cả operation sập, hàm nào không.

→ Đây là lằn ranh critical / non-critical side-effect. Combo phòng thủ đầy đủ — Retry → Graceful Degradation → đẩy queue cho worker gửi lại — nằm ở Session 8 — Retry & Circuit Breaker ↗.

C. Comment WHAT → để code tự nói

❌ Smell
// check if user is adult
if (u.age >= 18) { ... }
✅ Fix
const isAdult = user.age >= LEGAL_AGE;
if (isAdult) { ... }
// WHY-comment thì giữ:
// LEGAL_AGE=18 theo luật VN, không phải 21
③ Trong code THẬT của anh

Lý thuyết chỉ thành kỹ năng khi anh thấy nó trong code của chính mình. Đây là bài tập tay.

🔍 Săn 3 con mồi (15 phút)

Mở /Users/tritdd/Work/Asset_Platform/apps/api (NestJS — service & controller). Tìm:

  • Một cái tên mơ hồ — data, temp, res, handle(), process(). Đổi thành tên tiết lộ ý định.
  • Một hàm > 20 dòng làm nhiều việc — một service method ôm validate + business + side-effect. Tách ra.
  • Một comment giải thích WHAT (hoặc code commented-out) — xóa, để tên/biến tự nói. Giữ lại comment WHY nếu có.

→ Mỗi con mồi anh dọn = một vết sẹo. Ghi nó vào Scar-Journal: thấy gì, đổi sao, bài học.

⚠️ Đây là sân tập, không phải PR thật. Đừng sửa code production lung tung — copy đoạn ra, refactor để HỌC, rồi quyết định có đưa vào branch không.
④ Why-Ladder (cho Mock)

Interviewer đào sâu thế nào

Họ thả keyword "clean code" rồi leo xuống. Đây là cái thang — và cách suy ra từ gốc, không đọc script. Mock "craftsmanship" sẽ kéo đúng từ đây.

1
"Clean code là gì với anh?"
→ Code được đọc nhiều hơn viết; sạch = đọc hiểu ngay, sửa không sợ. (định nghĩa)
2
"Tại sao đặt tên lại quan trọng đến vậy?"
→ Tên xấu bắt người đọc giải mã mỗi lần; tên tốt là tài liệu sống, không bao giờ lỗi thời như comment. (lý do)
3
"Kể một lần anh đổi tên/dọn một hàm — chuyện gì xảy ra?"
→ DẪN SẸO THẬT từ Asset_Platform: "Trong service X tui có hàm handle() 40 dòng làm 3 việc, một lần sửa bug tui phải đọc hết mới hiểu. Tui tách thành validate/create/notify, lần sau sửa mất 2 phút." (kinh nghiệm)
4
"Hàm này của anh validate VÀ lưu DB. Có sạch không? Vì sao?"
→ Suy từ gốc "một hàm một việc": không — nó trộn 2 mức trừu tượng, khó test riêng, khó tái dùng validate. Tách ra. (áp dụng tại chỗ)
5
"Vậy comment có phải lúc nào cũng xấu?"
→ Không. Comment WHAT (giải thích code làm gì) = mùi hôi, vì code nên tự nói. Comment WHY (tại sao chọn cách này, đánh đổi gì) = quý. (bedrock — hiểu sâu thật)
Đậu gốc này khi

Anh leo được tới tầng 5 mà tự suy ra (không đọc thuộc) + dẫn được ít nhất 1 sẹo thật từ Asset_Platform ở tầng 3. Đó là lúc Clean Code nằm trong tay anh.
