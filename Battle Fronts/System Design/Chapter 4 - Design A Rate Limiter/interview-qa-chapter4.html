How to Use This Document

These questions cover everything an interviewer might ask about rate limiter design. Each answer follows a structured format:

  • Clear definition first
  • Why it matters (the problem it solves)
  • Concrete examples and trade-offs
  • Key numbers and implementation details

Q1 What is a rate limiter and why do we need one? ▼

Complete Answer:

Definition: A rate limiter controls the rate of traffic sent by a client or service. It limits the number of client requests allowed over a specified period. If the API request count exceeds the threshold, excess calls are blocked.
Three Key Benefits:
  1. Prevent DoS attacks: Twitter limits 300 tweets/3 hours; Google Docs limits 300 read requests/user/60 seconds.
  2. Reduce cost: Limits calls to expensive third-party APIs (payments, health records).
  3. Prevent server overload: Filters out excess requests from bots or misbehaving users.
Q2 Where should you place a rate limiter? ▼

Complete Answer:

Three Options:
  • Client-side: Unreliable — client requests can be forged by malicious actors. We may not control client implementation.
  • Server-side: Rate limiter lives inside the API server itself.
  • Middleware: Rate limiter sits between client and API servers. This is the most common approach.

Q3 How does the Token Bucket algorithm work? ▼

Complete Answer:

Mechanism: A bucket holds tokens up to a maximum capacity. Tokens are added at a fixed refill rate. Each request consumes one token. If tokens are available, the request passes. If not, it's dropped. Extra tokens overflow when the bucket is full.
Two Parameters:
  • Bucket size: Maximum number of tokens the bucket can hold
  • Refill rate: Number of tokens added per second
Who uses it? Both Amazon and Stripe use token bucket for API throttling. It allows short bursts of traffic as long as tokens are available.

How many buckets?

  • Different API endpoints = different buckets per user
  • IP-based throttling = one bucket per IP
  • Global limit = one shared bucket for all requests
Q4 How does the Leaking Bucket algorithm work? ▼

Complete Answer:

Mechanism: Similar to token bucket, but uses a FIFO queue. Requests are added to the queue if not full. They are processed (leaked) at a fixed outflow rate. If the queue is full, new requests are dropped.
Two Parameters:
  • Bucket size (queue size): How many requests the queue can hold
  • Outflow rate: How many requests are processed per second
Key difference from Token Bucket: Leaking bucket processes requests at a stable, fixed rate — no bursts allowed. Good for use cases needing uniform processing speed. The downside: a burst of traffic fills the queue with old requests, and newer requests get rate limited.
Q5 How does the Fixed Window Counter work and what's its main flaw? ▼

Complete Answer:

Mechanism: Divides the timeline into fixed-size windows. Each window has a counter. Every request increments the counter. When the counter reaches the threshold, new requests are dropped until the next window.
The Edge Burst Problem:

With a limit of 5 req/min: if 5 requests come at 2:59 and 5 more at 3:01, that's 10 requests in 2 seconds — double the intended rate! Each window individually passes (5/5), but the boundary burst is the critical flaw.

Q6 How does the Sliding Window Log algorithm work? ▼

Complete Answer:

Mechanism: Tracks individual request timestamps in a sorted set (Redis). On each new request: (1) Remove outdated timestamps outside the current window, (2) Add the new timestamp, (3) If log size ≤ limit, accept; otherwise reject.
Pros: Very accurate — no boundary burst problem. In any rolling window, requests will not exceed the rate limit.
Cons: Consumes a lot of memory because even rejected requests may have their timestamps stored.
Q7 How does the Sliding Window Counter algorithm work? ▼

Complete Answer:

Mechanism: A hybrid of fixed window + sliding window log. Uses a weighted formula:
Requests = (prev_window_count × overlap%) + (current_window_count × position%) Example: prev=5, curr=3, 70% into current window = 5 × 30% + 3 × 70% = 1.5 + 2.1 = 3.6
Key insight: It's an approximation (assumes previous window requests are evenly distributed), but Cloudflare's experiments show only 0.003% of requests are wrongly handled among 400 million requests. Best balance of accuracy and memory efficiency.

Q9 Why use Redis for rate limiting? What commands? ▼

Complete Answer:

Why Redis? We need fast counter access. Database is too slow (disk access). Redis is an in-memory cache that is fast and supports time-based expiration.
Two Key Commands:
  • INCR — Atomically increases the stored counter by 1
  • EXPIRE — Sets a timeout for the counter (auto-delete after window expires)

Q12 What is the race condition problem in distributed rate limiting? ▼

Complete Answer:

The Problem: In highly concurrent environments, two threads can read the same counter value (e.g., 3) simultaneously. Both increment to 4 and write back. Expected result: 5. Actual result: 4. The counter is wrong.
Solutions (3 approaches):
  • Locks: Simple but significantly slows down the system
  • Lua scripts: Redis executes Lua scripts atomically — preferred solution
  • Redis sorted sets: Atomic operations that avoid the read-modify-write race
Q13 How do you solve the synchronization problem with multiple rate limiters? ▼

Complete Answer:

The Problem: With multiple rate limiter servers, a client's requests may go to different servers. If each server maintains its own counter, the rate limit won't work correctly (e.g., a client sends 3 requests to Server A and 3 to Server B, bypassing a limit of 5).
Solution: Use a centralized Redis data store. All rate limiter servers read/write to the same Redis instance. This ensures a single, consistent view of each client's request count.
Q14 How do you optimize rate limiter performance for multiple data centers? ▼

Complete Answer:

Multi-data center: Deploy edge servers so traffic is automatically routed to the closest server, reducing latency.
Eventual consistency: Synchronize data across data centers using an eventual consistency model. This is acceptable for rate limiting because perfect accuracy isn't required — a few extra or missed requests are tolerable.
Q15 What is the Lyft rate limiting rule format? ▼

Complete Answer:

YAML Configuration: Lyft open-sourced their rate-limiting component. Rules are written in config files stored on disk.
domain: messaging descriptors: - key: message_type value: marketing rate_limit: unit: day requests_per_unit: 5

This allows max 5 marketing messages per day. Another example limits login attempts to 5 per minute under the auth domain.

Q16 What happens when a request exceeds the rate limit? ▼

Complete Answer:

Two Options:
  1. Drop the request: Return HTTP 429 (Too Many Requests) immediately
  2. Enqueue: Put the request in a message queue to be processed later (depending on use case)
Response includes: HTTP 429 status code + X-Ratelimit-Retry-After header telling the client how long to wait before retrying.
Q17 What is hard vs soft rate limiting? ▼

Complete Answer:

Hard rate limiting: The number of requests cannot exceed the threshold. Strict enforcement.
Soft rate limiting: Requests can exceed the threshold for a short period. More flexible, allows temporary bursts.
Q18 At which OSI layer can rate limiting be applied? ▼

Complete Answer:

Layer 7 (Application): HTTP-based rate limiting — what we focused on in this chapter.
Layer 3 (Network): IP-based rate limiting using tools like iptables. Blocks traffic at the network level before it reaches the application.
OSI Model reminder: Layer 1 (Physical) → Layer 2 (Data Link) → Layer 3 (Network) → Layer 4 (Transport) → Layer 5 (Session) → Layer 6 (Presentation) → Layer 7 (Application)
Q19 How can a client avoid being rate limited? ▼

Complete Answer:

Client Best Practices:
  • Use client-side cache to avoid frequent API calls
  • Understand the limit and don't send too many requests in a short time
  • Include code to catch exceptions for graceful recovery
  • Add sufficient back-off time to retry logic (exponential backoff)
Q20 What questions should you ask the interviewer when designing a rate limiter? ▼

Complete Answer:

Key Clarifying Questions:
  1. Client-side or server-side rate limiter?
  2. Throttle based on IP, user ID, or other properties?
  3. What is the scale of the system?
  4. Will it work in a distributed environment?
  5. Is it a separate service or in application code?
  6. Do we need to inform throttled users?
Why this matters: These questions show the interviewer you think about requirements before jumping into design. It demonstrates maturity and systematic thinking.
Q21 Why is monitoring important for a rate limiter? ▼

Complete Answer:

Two things to verify:
  • The rate limiting algorithm is effective
  • The rate limiting rules are effective
Example adjustments:

If rules are too strict → relax them. If a flash sale causes spikes → switch to token bucket (supports bursts). Monitoring drives continuous improvement.

Q22 What are the 6 key requirements for a rate limiter? ▼

Complete Answer:

Requirements:
  1. Accurately limit excessive requests
  2. Low latency — must not slow down HTTP response time
  3. Memory efficient — use as little memory as possible
  4. Distributed — sharable across multiple servers/processes
  5. Exception handling — clear exceptions when throttled
  6. High fault tolerance — if rate limiter fails, the system still works
Q23 When would you choose Token Bucket over Leaking Bucket? ▼

Complete Answer:

Token Bucket: When you need to allow bursts of traffic. A user might not send any requests for a while, then send many at once (e.g., uploading multiple photos). Token bucket accommodates this because accumulated tokens allow temporary bursts.
Leaking Bucket: When you need a stable, uniform outflow rate. For example, processing payments at a fixed rate to avoid overwhelming a downstream service.
Q24 What is an API Gateway and how does it relate to rate limiting? ▼

Complete Answer:

Definition: An API Gateway is a fully managed service that supports: rate limiting, SSL termination, authentication, IP whitelisting, and serving static content. It acts as a single entry point for all API requests.
When to use: If you already use microservice architecture and have an API gateway, adding rate limiting to it is the natural choice. Building your own takes engineering time — a commercial API gateway may be more practical.
Q25 Walk through the high-level architecture of a rate limiter ▼

Complete Answer:

Step-by-step flow:
  1. Client sends request to rate limiting middleware
  2. Middleware fetches the counter from Redis
  3. Checks if limit is reached
  4. If not reached: forward to API servers, increment counter in Redis
  5. If reached: return HTTP 429, optionally enqueue the request
