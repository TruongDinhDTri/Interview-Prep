Q1 What is a load balancer and why do we need it? ▼

Complete Answer:

Definition: A load balancer is a component that evenly distributes incoming traffic among multiple web servers in a server pool. It sits between the users and your web servers, acting as a traffic director.
Why We Need It - The Core Problem:

Imagine you have a single web server handling all your traffic. Two critical problems arise:

  1. Single Point of Failure (SPOF): If that one server goes down, your ENTIRE website goes offline. No redundancy, no backup.
  2. Traffic Overload: When too many users access the server simultaneously and it reaches its load limit, users experience slower response times or complete failure to connect.

The load balancer solves both problems.

How It Solves These Problems:
1. Eliminates Single Point of Failure:

If Server 1 goes offline, the load balancer automatically routes ALL traffic to Server 2. Your website stays online. You can then add a new healthy server to the pool to restore full capacity.

2. Handles Traffic Growth Gracefully:

When traffic grows and 2 servers aren't enough, you simply add more servers to the pool. The load balancer automatically starts distributing requests to the new servers. No downtime, no complex reconfiguration.

Security Benefit: Users connect to the public IP of the load balancer, not the web servers directly. Web servers use private IPs (only reachable within the same network), making them unreachable from the internet. This adds a security layer by hiding your actual servers from direct access.

Interview Pro Tip:

When discussing load balancers, mention:

  • Algorithms: Round-robin (simplest), Least connections (server with fewest active connections), IP hash (same client → same server)
  • Health Checks: Load balancer regularly pings servers to ensure they're healthy before routing traffic
  • Layer 4 vs Layer 7: L4 (transport layer - faster, looks at IP/port), L7 (application layer - smarter, can route based on URL/headers)

Example Interview Response:

"A load balancer distributes incoming traffic across multiple servers to prevent any single server from becoming a bottleneck. This solves two critical problems: if one server fails, traffic is automatically rerouted to healthy servers, eliminating single points of failure. And when traffic grows, we can easily add more servers to handle the load. Users connect to the load balancer's public IP, while servers use private IPs for added security. Common algorithms include round-robin for simplicity or least-connections for better load distribution."

Q2 What's the difference between vertical and horizontal scaling? ▼

Complete Answer:

Aspect Vertical Scaling (Scale Up) Horizontal Scaling (Scale Out)
Definition Adding more power (CPU, RAM, disk) to your existing server Adding more servers to your pool of resources
Visual 1 powerful server → 1 MORE powerful server 2 servers → 4 servers → 8 servers
Complexity Simple - no application changes needed More complex - requires load balancer, state management
Limits Hardware limits - can't add unlimited CPU/RAM to a single machine Virtually unlimited - can keep adding servers
Failover Single Point of Failure - if the server dies, everything goes down Redundancy - if one server fails, others continue
Cost Expensive - powerful servers cost exponentially more Cost-effective - use commodity hardware
When to Use Low traffic, quick fix, simple applications Large-scale applications, need high availability
The Critical Insight:

Vertical scaling is like making one person stronger. There's a limit to how strong one person can get. Horizontal scaling is like adding more people to the team. You can keep adding people.

For large-scale applications, horizontal scaling is MORE desirable because:

  1. No single point of failure
  2. No hardware limits
  3. More cost-effective at scale
The Trade-off:

Vertical scaling is SIMPLER (no code changes), but hits a wall quickly. Horizontal scaling requires more architecture work upfront (load balancers, stateless servers, distributed data), but scales infinitely.

Real-World Example:

Vertical Scaling: Amazon RDS lets you scale a database server up to 24 TB of RAM. That's massive, but eventually you hit the limit.

Horizontal Scaling: Netflix uses thousands of servers distributed globally. If traffic spikes or servers fail, they simply add more or reroute traffic. No single machine limit.

Interview Pro Tip:

When asked about scaling, ALWAYS mention:

  • "I'd start with vertical scaling for simplicity, but plan for horizontal scaling as we grow."
  • "Horizontal scaling requires addressing state management - we'd move session data to Redis/Memcached."
  • "For the database, we might vertically scale initially, but use read replicas and sharding for horizontal scaling."

Example Interview Response:

"Vertical scaling means adding more resources like CPU and RAM to your existing server, while horizontal scaling means adding more servers. Vertical is simpler but hits hardware limits and creates a single point of failure. For large-scale systems, horizontal scaling is preferred because it provides redundancy, has no theoretical limit, and is more cost-effective. The trade-off is increased complexity - you need load balancers and stateless architecture. In practice, I'd use vertical scaling for quick wins early on, but architect for horizontal scaling from the start."

Q3 When do we use read replicas? ▼

Complete Answer:

What Are Read Replicas (Database Replication)?

Database replication is a master-slave relationship where:

  • Master Database: Handles ALL write operations (INSERT, UPDATE, DELETE)
  • Slave Databases (Read Replicas): Receive copies of data from master and handle ONLY read operations (SELECT)

When Do We Use Read Replicas?

We use read replicas when we have a read-heavy workload. Here's the key insight:

Most applications have a MUCH higher ratio of reads to writes.

Think about it:

  • Social Media: Millions of people READ posts, only the author WRITES them
  • E-commerce: Thousands browse products (READ), only a fraction buy/update (WRITE)
  • News Sites: Millions of readers (READ), only journalists write (WRITE)

Typical ratio: 90% reads, 10% writes (or even higher read percentage!)

Benefits of Read Replicas:
1. Better Performance:

All writes/updates go to master. Read operations are distributed across multiple slave nodes. This allows more queries to be processed in parallel. Instead of one database handling everything, you have 1 master + N slaves sharing the load.

2. Reliability:

If one database server is destroyed (natural disaster, hardware failure), data is still preserved because it's replicated across multiple locations. You don't worry about data loss.

3. High Availability:

If a database goes offline, your website remains operational. You can access data stored in another database server. Users don't experience downtime.

Failover Scenarios:
If a Slave Goes Down:

Read operations temporarily redirect to the master or other healthy slaves. A new slave is quickly added to replace the failed one. Minimal impact.

If the Master Goes Down:

One slave is promoted to be the new master. All database operations temporarily execute on the new master. A new slave is added to restore replication. This is more complex because the promoted slave might not have the latest data (replication lag), so data recovery scripts may be needed.

Example Scenario:

Your e-commerce site has:

  • 1,000,000 product page views per hour (READ)
  • 10,000 purchases per hour (WRITE)

That's a 100:1 read-to-write ratio!

With 1 master + 3 read replicas, you distribute the 1,000,000 reads across 3 slaves (~333,333 each), while the master handles only the 10,000 writes. Much better performance than one database handling 1,010,000 operations!

Interview Pro Tip:

When discussing read replicas, mention:

  • Replication Lag: There's a slight delay between master write and slave update. For most apps this is acceptable (eventual consistency).
  • Scaling Reads: "We can add as many read replicas as needed to handle read traffic."
  • Geographic Distribution: "We could place read replicas in different regions to reduce latency for global users."
  • Read/Write Splitting: "The application layer routes writes to master and reads to replicas, often using a library or database proxy."

Example Interview Response:

"We use read replicas when we have a read-heavy workload, which is common in most applications - typically 80-90% reads versus writes. The master database handles all write operations while read replicas handle read queries. This improves performance by distributing the read load across multiple databases, provides reliability through data redundancy, and ensures high availability if a database fails. For example, in a social media feed, millions of users read posts but only a small fraction create new ones, making read replicas essential for scalability. We'd need to handle replication lag and implement proper read/write splitting in the application layer."

Q4 What goes in cache vs database? ▼

Complete Answer:

First, What Is Cache?

A cache is a temporary storage area that stores frequently accessed data in memory (RAM) so that subsequent requests are served much faster. Think of it as a "shortcut" that avoids expensive database queries.

Speed Comparison:
  • Cache (RAM): ~1 microsecond access time
  • Database (Disk): ~10 milliseconds access time
  • That's 10,000x faster!

The Golden Rule:

"Cache for SPEED, Database for SAFETY"

Cache: Optimizes for performance, data can be lost without disaster
Database: Source of truth, data MUST be durable and consistent

Decision Framework - Ask These Questions:
1. Is it read frequently but modified rarely?

YES → Good for cache | NO → Keep in database only

2. Can you afford to lose this data temporarily?

YES → Can cache (with database as source) | NO → Database only

3. Is it expensive to compute or fetch?

YES → Excellent cache candidate | NO → Caching might not help much

4. Can you tolerate slightly stale data?

YES → Cache with TTL | NO → Database with cache invalidation on writes

Real-World Examples:

Good Cache Candidates
  • User Profile Info: Read often (every page load), rarely changes
  • Product Catalog: Thousands of users browse, products update occasionally
  • API Responses: Same query, same result, can cache for minutes/hours
  • Session Data: Accessed every request, temporary by nature
  • Popular Posts/Trending Content: Read by millions, computed hourly
Bad Cache Candidates
  • Financial Transactions: Must be accurate, cannot lose
  • Real-time Inventory: Needs to be exact (can't oversell)
  • User Passwords: Critical security data, must persist
  • Order Records: Legal/audit requirements, must be durable
  • One-time Data: If it's only read once, caching provides no benefit
Important Caching Considerations:
1. Expiration Policy (TTL):

Set a Time-To-Live so cached data doesn't become too stale. Not too short (frequent DB queries), not too long (stale data).

2. Cache Invalidation:

When data changes in the database, update or remove it from cache. Otherwise users see outdated information.

3. Cache Warming:

Pre-populate cache with commonly accessed data to avoid cold start problems.

4. Eviction Policy:

When cache is full, decide what to remove. LRU (Least Recently Used) is most common.

Interview Pro Tip:

When discussing caching strategy, mention:

  • Cache Hit Ratio: "We'd aim for 80-90% cache hit ratio for frequently accessed data."
  • Cache Aside Pattern: "Application checks cache first, if miss, fetch from DB and populate cache."
  • Write Through: "For critical data, write to both cache and DB simultaneously."
  • Cache Technologies: Redis (rich data structures), Memcached (simple key-value), CDN (static assets)

Example Interview Response:

"We cache data that's read frequently but modified infrequently, where temporary data loss is acceptable. For example, user profile information, product catalogs, and API responses are great cache candidates. The database remains the source of truth for all data, especially critical information like transactions and user accounts that cannot be lost. We'd use a cache-aside pattern where the application checks Redis first, and on a cache miss, fetches from the database and populates the cache with an appropriate TTL. For a social media feed, we might cache the rendered feed for 5 minutes, as perfect freshness isn't critical, but we'd never cache financial transactions."
