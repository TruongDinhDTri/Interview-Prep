Why Consistent Hashing?

In large distributed systems, data must be spread across many servers. The naive approach — using serverIndex = hash(key) % N — works great until you need to add or remove servers. When N changes, almost every key remaps to a different server, causing a cache miss storm. Consistent hashing solves this by ensuring only a small fraction of keys need to be remapped when topology changes.

1 The Rehashing Problem

The Naive Modular Formula

The classic approach to distribute keys across N servers:

Server Selection Formula
serverIndex = hash(key) % N
Where N = total number of servers

This works perfectly when N is stable. But distributed systems are never perfectly stable — servers go down, new capacity gets added, hardware fails.

Key Distribution Example (4 Servers)

Hash function returns values 0–7. With 4 servers (N=4):

Key hash(key) hash % 4 Server
key000 % 4 = 0server0
key111 % 4 = 1server1
key222 % 4 = 2server2
key333 % 4 = 3server3
key444 % 4 = 0server0
key555 % 4 = 1server1
key666 % 4 = 2server2
key777 % 4 = 3server3

What Happens When Server1 Goes Down (N = 3)

Now we recalculate with N=3. The results are catastrophic:

Key hash(key) hash % 3 New Server Changed?
key000 % 3 = 0server0✓ Same
key111 % 3 = 1server1 (dead)✗ MISS
key222 % 3 = 2server2✓ Same
key333 % 3 = 0server0✗ Moved
key444 % 3 = 1server1 (dead)✗ MISS
key555 % 3 = 2server2✓ Same
key666 % 3 = 0server0✗ Moved
key777 % 3 = 1server1 (dead)✗ MISS

6 out of 8 keys (75%) need to be remapped! This causes a massive wave of cache misses, potentially overloading your database as all those requests bypass the cache.

🎓 Hadriel's Insight

Think of it like musical chairs — when you remove one chair, EVERYONE scrambles to a different seat. The modular formula ties every key's destination to the total count N. Change N, and the entire mapping recalculates. It's not a bug — it's a fundamental property of modular arithmetic that makes it unsuitable for dynamic server pools.

⚠ The Real-World Impact

In production, a cache miss storm from server removal can cause a thundering herd problem: thousands of requests simultaneously bypass the cache and hit the database, potentially cascading into a full system outage. This is exactly the scenario consistent hashing was designed to prevent.

2 Consistent Hashing — The Solution

Wikipedia Definition

Consistent hashing is a special kind of hashing such that when a hash table is resized, only k/n keys need to be remapped on average, where k is the number of keys and n is the number of slots. In contrast, in most traditional hash tables, a change in the number of array slots causes nearly all keys to be remapped.

This is the key insight: instead of remapping everything when the server count changes, only the keys that have to move actually move.

Redistribution Comparison

Naive Modular Hashing

O(k) redistribution

When a server is added/removed, most or all of the k keys must be remapped. With 1M keys and 4→5 servers, ~800K keys may move.

Consistent Hashing

O(k/n) redistribution

Only the keys that were assigned to the affected server need to move. With 1M keys and 4→5 servers, ~200K keys move (roughly 1/n of total).

3 Hash Space & Hash Ring

SHA-1 Hash Space

Consistent hashing uses a hash function — SHA-1 is commonly cited. SHA-1 produces a 160-bit output:

0 → x0 ... xn → 2¹⁶⁰ − 1
SHA-1 range: 0 to 1,461,501,637,330,902,918,203,684,832,716,283,019,655,932,542,975

This is an enormous number line — about 1.46 × 10⁴⁸ positions. Every server and every key gets hashed to a position somewhere on this line.

Linear Space → Ring

The key transformation: take the linear hash space and connect the two ends — x0 connects to xn — forming a ring (circular structure).

                 x0 (0)
               /         \
          xn-1             x1
         /                   \
        |    Hash Ring 🔄     |
         \                   /
          x3               x2
               \         /
                 ...
🎓 Hadriel's Insight

Think of it like a clock face — 12 o'clock wraps back to 12. The "largest" hash value is immediately followed by the "smallest" hash value. This wrapping is what gives consistent hashing its power: there's no boundary where the calculation breaks. Every point on the ring has a well-defined "next clockwise server".

4 Hash Servers onto the Ring

Mapping Servers

Each server gets hashed onto the ring using a hash function applied to the server's IP address or name:

# Place servers on the ring hash(server0_IP) → position on ring hash(server1_IP) → position on ring hash(server2_IP) → position on ring hash(server3_IP) → position on ring

This places 4 servers at 4 different positions around the ring. Crucially: no modular operation is involved. The position is the raw hash output mapped to the ring space.

Example Ring Layout (4 servers)

           s0 (hash = 12)
          /               \
    s3 (75)              s1 (28)
          \               /
           s2 (54)

Positions are illustrative. In SHA-1 space, positions would be in the range 0 to 2¹⁶⁰-1.

5 Hash Keys onto the Ring

Mapping Keys — Same Hash Function, No Modulus

Keys are hashed using the same hash function as the servers. The critical difference from naive hashing:

ApproachFormulaDepends on N?
Naive Hashing hash(key) % N Yes — must recalculate when N changes
Consistent Hashing hash(key) → position on ring No — position is absolute on the ring
# Keys are mapped to the same ring space hash(key0) → position 5 # somewhere between s3 and s0 hash(key1) → position 15 # somewhere between s0 and s1 hash(key2) → position 38 # somewhere between s1 and s2 hash(key3) → position 65 # somewhere between s2 and s3

6 Server Lookup — Clockwise Walk

The Clockwise Rule

To find which server owns a key: Start at the key's position on the ring and walk clockwise until you hit a server. That server owns the key.

Example Lookup

        s0 (12)
       ↗         \
key0(5)          key1(15) → s1(28)
 ↓                         ↓
Goes CW →        key2(38) → s2(54)
                 key3(65) → s3(75)
  • key0 (pos 5) → walks CW → hits s0 (pos 12) → assigned to server0
  • key1 (pos 15) → walks CW → hits s1 (pos 28) → assigned to server1
  • key2 (pos 38) → walks CW → hits s2 (pos 54) → assigned to server2
  • key3 (pos 65) → walks CW → hits s3 (pos 75) → assigned to server3

7 Adding a Server

Only Adjacent Keys Relocate

When server4 is added between s3 and s0 (say at position 8):

Before: key0 → s0

key0 (pos 5) walks CW from pos 5, hits s0 at pos 12 → server0

After server4 added at pos 8:

key0 (pos 5) walks CW from pos 5, now hits s4 at pos 8 first → server4

key1, key2, key3 are unaffected — they still hit the same servers.

Rule: Only keys in the range from s4's predecessor (counterclockwise) up to s4's position need to be redistributed. All other keys remain unchanged.
🎓 Hadriel's Insight

Like inserting a new person into a relay race — only the next runner's leg changes. The new runner takes over the segment from the previous handoff point. Everyone else keeps running the same legs they already had.

8 Removing a Server

Keys Fall to the Next Server

When server1 (pos 28) is removed:

  • 1key1 (pos 15) previously walked CW to s1 (pos 28)
  • 2s1 is removed from the ring
  • 3key1 continues CW past pos 28 → hits s2 (pos 54) → now assigned to server2
  • 4key0, key2, key3 are completely unaffected
Rule: Only keys that were owned by the removed server migrate. They move to the next clockwise server. All other key-to-server mappings remain intact.

9 Two Issues with Basic Consistent Hashing

Basic Consistent Hashing Has Flaws

The algorithm was first described by Karger et al. at MIT in 1997. While the ring concept is elegant, the basic form has two structural problems in practice:

Problem 1: Unequal Partition Sizes

Servers hash to random positions on the ring. Some servers may end up with huge arcs (many keys), others with tiny arcs. With just 4 servers, random placement can cause one server to own 60% of the key space while another owns only 5%.

     s0 (3)
    /        \
s3(94)      s1 (7)
    \        /
     s2 (50)

s0 and s1 are very close (pos 3 and 7), leaving a tiny arc. s2 to s3 is a huge arc.

Problem 2: Non-Uniform Key Distribution

Even if server arcs were equal, keys don't hash uniformly. Some servers may receive disproportionately more traffic than others, creating hotspots. A "celebrity key" (one massively popular data item) could overwhelm the single server that owns it.

⚠ Why This Matters in Interviews

When asked about consistent hashing, always mention these two problems and immediately introduce virtual nodes as the solution. Interviewers expect you to know that basic consistent hashing alone isn't production-ready.

10 Virtual Nodes — The Fix

Multiple Positions Per Server

Instead of each server occupying a single position on the ring, each server gets multiple virtual nodes (vnodes) — multiple positions distributed around the ring.

# Without virtual nodes: 1 position per server s0 → pos 12 s1 → pos 28 # With virtual nodes: multiple positions per server s0_0 → pos 5, s0_1 → pos 40, s0_2 → pos 78 s1_0 → pos 15, s1_1 → pos 55, s1_2 → pos 90 s2_0 → pos 28, s2_1 → pos 65, s2_2 → pos 98

Now the ring has many more reference points. When a key walks clockwise and hits a virtual node labeled "s0_1", it gets stored on server 0.

Effect of More Virtual Nodes

Virtual Nodes Std Dev of Distribution Memory Cost
1 (basic)Very high — unpredictableMinimal

🎓 Hadriel's Insight

Like having multiple mailboxes around the neighborhood instead of one — mail (keys) gets distributed more evenly because there are more collection points. No single mailbox ends up with all the mail. The more mailboxes you add, the more uniform the distribution becomes.

The Virtual Node Tradeoff

✅ More Virtual Nodes = Better

  • More uniform key distribution
  • Lower standard deviation in load
  • Better hotspot prevention
  • Fairer data redistribution during scale events

⚠ More Virtual Nodes = Costlier

  • More entries in the ring data structure (sorted list or tree)
  • Higher memory consumption per node
  • Slightly slower lookups (more positions to scan)
  • More metadata to manage during failures
Production tip: Amazon Dynamo and Apache Cassandra both use virtual nodes. Cassandra defaults to 256 vnodes per physical node, while Dynamo originally used 150. The right number depends on your cluster size and memory budget.

11 Finding Affected Keys

Which Keys Move? Walk Counterclockwise

When a server is added or removed, we need to know exactly which keys are affected. The algorithm is symmetric for both cases:

Adding Server S_new

  1. Locate S_new's position on the ring
  2. Walk counterclockwise from S_new until you hit another server (S_prev)
  3. All keys in the range (S_prev, S_new] need to move from their current server to S_new

Removing Server S_old

  1. Locate S_old's position on the ring
  2. Walk counterclockwise from S_old until you hit another server (S_prev)
  3. All keys in the range (S_prev, S_old] need to move from S_old to the next clockwise server

Example: Removing Server s1

Walk counterclockwise from s1 → hit s0 (the predecessor). Keys in range (s0_position, s1_position] were owned by s1. They now migrate clockwise to s2.

12 Benefits & Real-World Usage

Three Core Benefits

1. Minimized Key Redistribution

When servers are added or removed, only k/n keys are redistributed. This prevents cache miss storms and allows online scaling without downtime.

2. Easy Horizontal Scaling

Add capacity by adding servers to the ring. Remove failed servers without cascading failures. The ring self-organizes around topology changes.

3. Hotspot Mitigation

Virtual nodes ensure that celebrity data (one massively popular key) doesn't overload a single server. The load distributes across multiple physical machines.

Real-World Implementations

Amazon Dynamo

One of the first large-scale consistent hashing deployments. Uses virtual nodes (called "tokens") with 150 vnodes per physical node. Basis for DynamoDB.

Apache Cassandra

Distributed by default with 256 vnodes per node. Each vnode owns a token range. Gossip protocol propagates ring membership changes.

Discord

Uses consistent hashing to route WebSocket connections. Ensures users in the same channel hit the same server for real-time messaging consistency.

Akamai CDN

Routes web requests to edge cache servers using consistent hashing. Minimizes cache invalidation when CDN nodes are added or fail.

Maglev (Google)

Google's load balancing system uses a variant of consistent hashing to distribute network packets across backend servers with minimal disruption during topology changes.

Memcached / Redis Cluster

Client-side consistent hashing in Memcached clients. Redis Cluster uses hash slots (16384 slots) — a related concept that maps hash ranges to nodes.

Chapter 5 Summary

  • Naive hash(key) % N remaps most keys when N changes → cache miss storm
  • Consistent hashing uses a ring: servers and keys share the same hash space
  • Keys assigned to the first clockwise server from their ring position
  • Adding/removing a server only affects keys in the immediately adjacent arc: O(k/n) redistribution
  • Basic consistent hashing has two problems: unequal partitions + non-uniform distribution
  • Virtual nodes fix both: each server gets multiple ring positions → even distribution
  • More vnodes = better balance, but higher memory cost (tune based on cluster size)
  • Used in: Amazon Dynamo, Cassandra, Discord, Akamai, Google Maglev
