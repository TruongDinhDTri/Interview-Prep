🎓 Why This Matters

When server 1 goes offline (N: 4→3), the formula hash(key) % 3 produces completely different server assignments. Most keys that were NOT on server 1 also get remapped — causing a storm of cache misses across the entire cluster. This is the problem consistent hashing solves.

Consistent Hash Ring

Servers and keys are placed on a ring via a hash function (no modular operation). To find which server stores a key: go clockwise until you hit a server. When a server is added or removed, only keys in the adjacent arc are affected.

🎓 Key Insight (Fig 5-8)

When s4 is added between s3 and s0: only k0 moves (from s0 → s4). k1, k2, k3 are unaffected. When s1 is removed: only k1 moves (from s1 → s2). This is O(k/n) redistribution, vs O(k) for naive hashing.

Virtual Nodes

Instead of one ring position per server, each physical server is represented by multiple virtual nodes (e.g., s0_0, s0_1, s0_2). This creates more even load distribution. At 100 vnodes/server: ~10% std dev. At 200: ~5% std dev.

🎓 Trade-off (Fig 5-12 & 5-13)

With 1 vnode/server, one server may own 60% of keys while another owns 5% (the "hotspot" problem). Increase vnodes → distribution converges to uniform. But more vnodes = more memory to store the ring metadata. Real systems (Dynamo, Cassandra) use 100–200 vnodes.

Find Affected Keys

When a server is added: go anticlockwise from the new node until hitting another server — keys in that arc are redistributed to the new server. When removed: go anticlockwise from the removed node — keys in that arc are redistributed to the next clockwise server.

🎓 The Rule

Add server s4: Affected range = arc from s4's predecessor (anticlockwise) to s4. Keys there move from old owner → s4.

Remove server s1: Affected range = arc from s1's predecessor (anticlockwise) to s1. Keys there move from s1 → s1's clockwise successor.
