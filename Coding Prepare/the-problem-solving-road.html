Before the Interview

Prepare Before You Enter the Room

Before the Interview — Prepare

Set yourself up so nothing technical distracts you.

🎯 Purpose — Why This Step Exists Clear every technical distraction now so the first 3–5 minutes go entirely to understanding — not fumbling with the webcam, the editor, or your nerves. You walk in with the self-intro, the environment, and the mindset already locked: don't touch the keyboard yet, think out loud always, it's a conversation not a test.

Self-Introduction (under 1 minute)

"Hi, I'm Tri. I'm a software developer with 2-3 years of experience working with Python/Django and React. I've built full-stack applications and recently been focused on system design and algorithms. Excited to be here."

Environment Setup

  • Pen and paper ready (for drawing data structures)
  • Headphones on. Quiet room. Door closed.
  • Test webcam and audio 5 minutes early
  • Familiarize with coding platform shortcuts (CoderPad, CodePen, HackerRank)
  • Have water nearby — you'll be talking a lot

Mindset

  • "The first 3–5 minutes are for understanding." Don't touch the keyboard yet.
  • Silence = Strong No Hire. Think out loud, always.
  • It's a conversation, not a test. The interviewer wants you to succeed.

Step 1

Understand — Clarify First, Solve Second

The first 3–5 minutes are for understanding. This is where Communication scoring begins.

Step 1 — Understand

"Do I actually understand what's being asked?"

💬 Communication 🧩 Problem Solving
🎯 Purpose — Why This Step Exists Confirm you understand WHAT is being asked — the contract — not how to solve it. Be a "brainless machine": verify that input X produces output Y because the problem says so (Definition WHY), never how code would find it (Algorithm WHY — that belongs to Step 3F). This step is intentionally shallow. Guards against: solving before you understand. The instant you think "how would I find that efficiently?" you've crossed into Step 3F — stop, and move to Step 2.
⚠️ The Trap — Two Types of WHY

The trace asks for "expected output and WHY" — but there are two completely different WHYs. Mixing them up is exactly the trap. The 5-year-old test: could a 5-year-old explain it by pointing at the picture? → that's Step 1 WHY. Does it need algorithmic reasoning? → that's Step 3F. Save it.

✅ Definition WHY — allowed "Why is this the answer according to the problem's rules?" Uses your eyes + the definition.
❌ Algorithm WHY — Step 3F, not here "How would code systematically find this answer?" (DFS, HashMap, two pointers...)
Canonical Example — Diameter of Binary Tree
✅ Step 1 WHY (Definition) "The problem says diameter = longest path between any two nodes. I look at the tree and I can SEE that 4→2→1→3 has 3 edges. No other path is longer. Output = 3. WHY? Because that's what 'diameter' means." → Done. Move to Step 2.
❌ Step 3F WHY (Algorithm — forbidden in Step 1) "But HOW would I find this for a huge tree I can't see? I'd need DFS... compute left-height + right-height at each node... track the max across all nodes..." → STOP. Save it for Step 3F.
🧭 Step 1 vs Step 3F — The Line You Must Not Cross Comprehension vs Discovery · Definition WHY vs Algorithm WHY · full guide with examples →

Four moves in order: ask clarifying questions → rephrase the problem → strip the story → trace an example by hand.

Questions to ALWAYS ask:

  • Is the input sorted? (changes BTTC dramatically — e.g., O(n) → O(log n))
  • Can values be negative? Zero? Floating point?
  • Can there be duplicates?
  • Can the input be empty or null?
  • Can I modify the original input/data structure?
  • How is the input stored? (array, linked list, tree, graph with cycles?)
  • What's the expected input size? (affects whether O(n²) is acceptable)
  • What should I return? (index, value, boolean, new array, in-place?)
  • Is there only one valid answer, or could there be multiple?

Strip the Story — Abstract the Problem:

Problem Title Strip the story → Abstract problem
"Fruits Into Baskets" "Longest subarray with at most K distinct elements"
"Busiest Time in The Mall" "Given timestamped +/− events, find timestamp where running total is maximum (group same-timestamp events before checking)"
"Number of Islands" "Count connected components in a 2D binary matrix"
"Two Sum" "Find two indices whose values sum to target"
Pre-Built Phrase
"Let me make sure I understand. [Paraphrase the problem]. So stripping the story, this is really asking: [abstract version]. A few questions..."
Concrete Example — "Busiest Time in The Mall"
"Let me make sure I understand. I'm given an array of data points, each with a timestamp, visitor count, and direction — enter or exit. I need to find the timestamp when the mall had the most visitors. A few questions:

• Is the data sorted by timestamp? (Yes)
• Can multiple events share the same timestamp? (Yes)
• If there are multiple periods with the same peak, do I return the earliest? (Yes)
• What should I return — the timestamp or the visitor count? (Timestamp)
• Can visitor count be zero? (No, at least 1)"
  • Work through 1–2 small examples by hand — write input, trace through, write expected output and the Definition WHY (not the Algorithm WHY — see the guide above)

Step 2

Approach — Pattern or First Principles?

Be honest about which road you're on. Forcing a pattern where none fits wastes more time than starting from scratch.

Step 2 — Approach

"Do I recognize a known pattern here?"

🧩 Problem Solving
🎯 Purpose — Why This Step Exists Decide which road to walk — Pattern Path or First Principles — and prove that choice. Name a candidate pattern, then justify the assumption: can you actually explain why it fits? (e.g. Binary Search: "I can eliminate half the search space from the middle-vs-target comparison.") Justification holds → you've earned the Pattern Path. Can't justify it → the gate says NO → go First Principles (3F). Guards against: committing to a pattern on a vibe → marching down the wrong road and burning the whole interview. The proof you build here is the same rule you'll formalize as the invariant in 4P — not throwaway work.

Three-question gate:

  • Does the abstract shape match a pattern signature?
  • Can I name the pattern AND explain why it applies?
  • Have I solved something like this with that pattern?
The Gate

Yes to all 3 → Pattern Path

No to any → First Principles Path

"I can think of two approaches here. The brute force would be checking every pair in O(n²). But I see this is a sorted array with a target sum — that's a Two Pointer signature, which would bring it to O(n). I'd like to go with the optimized approach — does that sound good?"

Why state multiple approaches: The rubric scores "multiple solutions with trade-off analysis" as an ADVANCED Problem Solving signal. Even 10 seconds naming the brute force before your real approach earns you points.

The Fork in the Road

Two Paths, Same Destination

Step 3P — Match

"What signals point to which pattern?"

🎯 Purpose — Why This Step Exists Turn the abstract problem into a named pattern by reading its signal keywords — and say the full sentence out loud: "I see [signal] which tells me [pattern] because [reason]." Naming without the because is a guess; the reason is what earns the points.
  • Identify the signal keywords in the problem (substring, contiguous, sorted, target sum, shortest path, connected)
  • Name the pattern and explain why: "I see [signal] which tells me [pattern] because [reason]"
Concrete Example — "Longest Substring Without Repeating Characters"
"I see 'substring' and 'contiguous' — that's a Sliding Window signature. The constraint is 'no repeating characters,' which tells me when to shrink the window. I'll use a HashSet to track what's in the current window."

Step 4P — Reason

"WHY does this pattern work here?"

🎯 Purpose — Why This Step Exists Prove the pattern works before you write a line of code. Three answers: (A) brute force + why it's too slow, (B) what the pattern does instead, (C) the invariant — the rule that stays true at every step. That invariant is the same "rule that governs the algorithm" the First-Principles path hunts for as its Rules Discovered. Different road, same destination.

Answer three questions (A, B, C) before writing a single line of code:

Concrete Example — Longest Substring Without Repeating Characters

A. Brute force, and why is it bad?

"Check every possible substring, verify each has unique characters. That's O(n³) — O(n²) substrings × O(n) to check each. Way too slow."

B. What does this pattern do instead?

"Sliding Window: maintain one window with two pointers. Expand the right pointer to include new characters. When a duplicate is found, shrink from the left until the duplicate is removed. Each character is visited at most twice → O(n)."

C. What rule keeps it valid (invariant)?

"The window must contain only unique characters at all times. The moment a character repeats, we shrink from the left. This invariant guarantees every valid window is checked without rechecking old substrings."

Step 3F — Explore

"How would I solve this without patterns?"

🎯 Purpose — Why This Step Exists Discover HOW to solve it when no known pattern fits. Flip into Detective mode: draw it, solve it by hand, and generate examples that break your assumptions until the governing rule reveals itself. Run the 6 techniques in order and stop the instant something clicks. The tricky case you invent here is where the insight lives — the exact opposite of Step 1, where inventing cases is forbidden.

Try these techniques in order. Stop when something clicks.

A. Visualize / Draw It

Draw the actual data structure on paper. For arrays, draw boxes with values. For trees, draw nodes and edges. For matrices, draw the grid.

Mall Problem — Timeline Visualization
Event Timeline
t1 = 1487799425
+14 enter −4 exit −2 exit
t2 = 1487800378
+10 enter
count: 0 → +14 = 14 → −4 = 10 → −2 = 8 check! 8 > 0 → peak = 8 → +10 = 18 check! 18 > 8 → NEW PEAK = 18

Works especially well for: trees, graphs, matrices, linked lists, any problem where spatial relationships matter.

B. Solve It Manually

Pretend you're not a programmer. Walk through the input step by step, tracking state at each point. Write down the concrete rules you discover.

Mall Problem — Step-by-Step Walkthrough

Input: [[1487799425, 14, 1], [1487799425, 4, 0], [1487799425, 2, 0], [1487800378, 10, 1]]

  1. Event: timestamp 1487799425, 14 people ENTER → count = 0 + 14 = 14
  2. Same timestamp, 4 people EXIT → count = 14 − 4 = 10
  3. Same timestamp, 2 people EXIT → count = 10 − 2 = 8
  4. ⚑ Timestamp changes next! Check peak: 8 > 0? Yes → best = 8, best_time = 1487799425
  5. Event: timestamp 1487800378, 10 people ENTER → count = 8 + 10 = 18
  6. ⚑ Last event! Check peak: 18 > 8? Yes → best = 18, best_time = 1487800378

Answer: 1487800378

Rules Discovered
  • Add on enter, subtract on exit
  • Only check for peak when timestamp changes or at the end
  • DON'T check mid-timestamp — events at same time must be batched

C. Generate More Examples

Try at least 3 inputs: a normal case, an edge case, and a tricky case. The tricky case is where the insight lives. This is Detective mode — the exact opposite of Step 1, where inventing tricky cases is forbidden.

Mall Problem

Normal: [[t1, 5, 1], [t2, 3, 0]] → peak at t1 with 5

Edge: [[t1, 1, 1]] → single event, peak is t1

Tricky: [[t1, 10, 1], [t1, 3, 0]] → same timestamp! Must process both before checking. Count = 7, not 10.

Mall Problem

"Do I need lookup? No. Counting? I just need a running counter. Stack? No nesting. Heap? No priority. BFS/DFS? No graph. This is simpler — just a single pass with a counter variable."

E. Decompose

Break the problem into smaller independent pieces. Solve each piece, then combine.

Mall Problem

Break into: (1) process each event (add/subtract), (2) detect timestamp boundaries, (3) check for new peak after each boundary.

Group Anagrams

Break into: (1) a function to hash a string into a canonical form, (2) a function to group strings by their hash.

F. Start with Brute Force

Get ANY working solution first. Often the brute force reveals the insight you need to optimize.

# First attempt — check peak after EVERY event (BUGGY)
def find_busiest_period_v1(data):
    count = 0
    max_count = 0
    max_time = 0
    for i in range(len(data)):
        if data[i][2] == 1:
            count += data[i][1]
        else:
            count -= data[i][1]
        if count > max_count:    # BUG: checking too early!
            max_count = count
            max_time = data[i][0]
    return max_time

# Returns t1 (count=14 after first event) — WRONG!
# Real peak at t1 is 8 (after all 3 events),
# peak overall is 18 at t2.
#
# Fix: only check when timestamp changes
# → that IS the optimal solution.

The brute force was 90% right. The bug (checking too early) pointed directly to the fix (check at timestamp boundaries). Brute force → insight → fix = optimal solution.

⟐

Both paths merge here. You have an approach. Present it, code it, verify it — then optimize.

🧯 If You're Stuck

Seven Lifelines — Use Them in Order

No approach is coming? Work through these before asking for a hint.

🎯 Purpose — Why The Lifelines Exist Your systematic escape from stuck — so you never go silent and never spin. Work the lifelines in order (state what you know → state the brute force → return to the 3F techniques → generate more examples), and only then ask for a hint. The goal: build the muscle to rescue yourself, because in the real room no one points at the answer.
1
State what you know — restate the constraints, inputs, and expected outputs out loud. Hearing it again unlocks new angles.
2
State the brute force — there is ALWAYS one. Say it even if it's O(n³): "I could check every pair in O(n²)..."

Can't find the brute force?

Don't stay stuck on Lifeline 2. Jump to Lifeline 3 → Draw it. Drawing the problem almost always reveals the simplest possible solution — which IS your brute force. Lifelines 3, 4, and 5 are a return to 3F Explore. Use them to find the brute force first, then optimize.

3
Draw it — return to 3F: Technique A — sketch the data structure. Boxes for arrays, nodes for trees, grid for matrices. What visually changes at each step? The drawing almost always reveals what the brute force needs to do.
4
Manual solve — return to 3F: Technique B — trace through the example by hand, step by step. Write down every rule you discover. The rules you find ARE the steps of your brute force.
5
Data structure & algorithm scan — return to 3F: Technique D — go through the full table systematically. Data structures: HashMap → Stack/Queue → Heap → Set → Trie → Graph. Algorithms: Binary Search → Sliding Window → Two Pointers → BFS/DFS → Union Find → Topological Sort. Ask "does this fit my problem?" for each.
6
Break it down — return to 3F: Technique E — can you split this into two smaller independent sub-problems? Solve each separately, then combine.

Lifelines 3–6 = Re-entering 3F Explore

If you exhausted these and still have no brute force: loop back through 3F. Try more examples (Technique C). Each additional example narrows what the solution must do.

7
Ask for a hint — only after working through 1–6. Use a pre-built phrase below. Never go silent.
"Give me a moment to think through this..."

"My first instinct is [brute force] — that's O(X). Let me see if I can improve on that."

"I'd like to start with [brute force] and optimize from there. Sound good?"

"Let me work through a small example by hand to see if I can spot the pattern..."

"I'm stuck on finding an efficient approach. Could you give me a hint on the direction?"

Step 3

Discuss — Present Your Approach, Get the Green Light

Don't touch the keyboard yet. Your job here is to explain your plan clearly and get interviewer buy-in.

Step 3 — Discuss

"Have I explained what I'm going to do AND why it works?"

💬 Communication 🧩 Problem Solving
🎯 Purpose — Why This Step Exists Say your plan out loud and earn the interviewer's green light before you write a single line of code. Discuss is storytelling, not coding: you describe what you intend to do — name the approach → walk the numbered steps → state time & space → ask "Shall I code it?". You are not figuring out loops or syntax here — that's Step 4's job. Separating what's the plan (here) from how do I type it (Step 4) is what kills blank-page freeze. The moment you panic over "how do I write the loop?" — that's Step 4 leaking backwards into Step 3. Pull yourself back up to altitude: just tell the story.
🗣️ KỂ CHUYỆN — Discuss = trình bày Ý ĐỊNH, KHÔNG phải CODE (Wiganz insight, 2026-06-03) Step 3 là nói ý định ra miệng — như kể cho một người bạn nghe cái plan. KHÔNG viết code, KHÔNG lo "loop thế nào", KHÔNG lo cú pháp. "Tôi sẽ đi qua mỗi account và nối các email trong đó lại với nhau."
— câu này đã là một câu Discuss hoàn chỉnh. Khi Wiganz hoảng vì "loop thế méo nào / cú pháp ra sao" → đó là nỗi lo của Step 4 (Code) đang rò rỉ ngược vào Step 3. Kéo mình về đúng độ cao: "Bây giờ chỉ cần kể câu chuyện — chuyện gõ-thế-nào là việc của bước sau." Tách bạch hai cái này giết được nỗi sợ trang-giấy-trắng (blank-page freeze).

Three moves: present your approach with numbered steps → explain WHY it works (the insight) → get the green light before coding.

Present the Approach — 4 Parts in Order:

  • Name the approach — pattern or strategy: "I'll use a sliding window with a HashSet"
  • Walk through the steps — numbered, in order: "Step 1: initialize... Step 2: expand right... Step 3: shrink left when duplicate found..."
  • State complexity — time and space: "Time O(n), space O(k)"
  • Get the green light — "Does that make sense? Shall I code it?"

What a Complete Discuss Sounds Like:

"I'll use a sliding window with a HashSet to track unique characters.

My steps:
1. Initialize left=0, a HashSet, and max_len=0.
2. Expand the right pointer — add s[right] to the set.
3. If s[right] is already in the set, shrink from the left: remove s[left], move left forward, until the duplicate is gone.
4. Update max_len = max(max_len, right − left + 1).
5. Return max_len.

Time O(n), space O(k) where k is the charset size. Shall I code it?"

These numbered steps are what you'll transcribe into comments in Blueprint. Say them clearly here — they become your code map.

Explain WHY It Works (the Reasoning):

  • What does brute force do? State it plainly: "Brute force checks every pair."
  • What does your approach do instead? Name the insight: "I trade space for time — store complements in a HashMap so each lookup is O(1)."
  • State the invariant (if there is one): "The sliding window maintains the constraint at all times."

Get the Green Light:

"Does that approach make sense? Shall I go ahead and code it up?"

✓ DO

  • Mention time AND space complexity
  • Explain the key insight, not just the steps
  • Briefly acknowledge brute force
  • Ask for confirmation before coding

✗ DON'T

  • Start coding before getting buy-in
  • Give only the complexity without the reasoning
  • Over-explain every detail — keep it 30–60 seconds
  • Say "I think this might work" — be confident

Pre-Built Phrases by Scenario:

Found Optimal
"My approach is [X]. Time O(n), space O(n). Since we need to look at every element at least once, O(n) is the theoretical floor — this is optimal. Shall I code this up?"
Found Better Than Brute Force
"Brute force would check every pair — O(n²). But I noticed [insight], so I can use [approach] for O(n) time with O(n) space. The tradeoff is extra memory, but we gain a lot on time. I'll go with the optimized version — sound good?"
Only Have Brute Force
"My current approach is [brute force] at O(n²). I think there might be a way to optimize this, but I'd like to get a working solution first. Does that work for you?"

Step 4

Code — Implement with Intent

Two phases: plan out loud first, then implement while narrating your thinking — not your typing.

Step 4 — Code

"Am I narrating my decisions or just my keystrokes?"

⌨️ Technical Competency 💬 Communication
🎯 Purpose — Why This Step Exists Implement with intent. Phase 1 Blueprint: transcribe the exact steps you said in Discuss as numbered comments — so you never face a blank page. Phase 2: fill in under each comment, narrating WHY (the "Cooking Show Rule"), never your keystrokes.

🗺️ Phase 1 — Blueprint (Transcribe What You Just Said)

You already planned the steps in Discuss. You already spoke them out loud.
Now write those exact steps as comments in the editor — before any real code.

Spoken → Written → Code. This is the bridge.

3 Steps:

  • Write your function signature
  • Write the algorithm steps as numbered comments — exactly what you said in Discuss
  • Add guard clauses (edge cases) at the top if needed

Example — Longest Substring Blueprint:

def lengthOfLongestSubstring(s):
    # Edge: empty string → return 0
    # 1. Initialize left=0, seen=set(), max_len=0
    # 2. Expand right pointer, add s[right] to seen
    # 3. If s[right] already in seen: shrink from left until removed
    # 4. Update max_len = max(max_len, right - left + 1)
    # 5. Return max_len

Then code fills in under each comment. No blank page. No freezing.

"Let me write out the steps as comments first — I find it helps to see the plan before I fill in the code."

If you froze in Discuss and didn't get the steps out:

  • What's my function signature?
  • What state do I need to track? (variables, data structures)
  • What does my main loop do at each step?
  • What are my edge cases? (guard clauses at the top)
  • What do I return, and when?

Phase 2 — Code with Intent Narration:

🎙️ Narrate Intent, Not Action — "The Cooking Show Rule"

A good cooking show host says "cutting against the grain for tenderness" — not "picking up knife, moving hand down."
Narrate WHY you're doing something, not what your fingers are doing.

✓ Intent (say this) ✗ Action (don't say this)
"I'm using a HashMap here because I need O(1) lookup for complements." "I'm creating a variable called hashmap equals open curly brace..."
"This condition handles the edge case where the input is empty." "I'm typing if len s equals zero..."
"I'm writing a helper function here because this logic will repeat." "Now I'm defining a function..."

When to Narrate vs. When to Stay Silent:

✓ NARRATE WHEN

  • Starting a new section of logic
  • Making a data structure choice
  • Handling an edge case
  • Writing a loop — state what it iterates and why
  • Making a tradeoff decision

✗ STAY SILENT WHEN

  • Typing obvious boilerplate (imports, function signature)
  • Writing simple syntax you've already explained
  • Deep concentration — a brief "give me a second to think" is fine

Pre-Built Narration Phrases:

"I'm using a HashMap here because I need O(1) lookup for [X]..."

"This condition handles the edge case where [X]..."

"I'm going to write a helper function for this since [reason]..."

"I'll use a two-pointer approach here because the array is sorted, so I can shrink the window from both ends..."

"Give me a moment to think through this condition..."

✓ DO

  • Use meaningful variable names
  • Modularize when logic repeats
  • Handle edge cases as you encounter them (or flag them)
  • Keep the interviewer oriented — brief updates

✗ DON'T

  • Go silent for more than 30 seconds without saying anything
  • Narrate every single keystroke
  • Start over mid-implementation without flagging it
  • Write unreadable one-liners to look clever

Step 5

Verify — Trace, Test, and Confirm

Don't just say "I think it works." Prove it. Follow the protocol in order.

Step 5 — Verify

"Have I traced through a real example out loud?"

🧪 Testing 💬 Communication
🎯 Purpose — Why This Step Exists Prove it works — don't just claim it. Scan silently for bugs, then trace a real example out loud, variable by variable, hit the edge cases by type, and state the complexity with confidence. "Looks good" earns nothing; a live trace earns Testing points.

The Verify Protocol — Follow This Order:

Phase Duration Out Loud? What You Do
Quick scan ~15–30 sec Silent Eyeball for obvious bugs: off-by-one, missing return, wrong variable name
Fix if needed Quick Brief narration "Ah, this should be <= not <" — fix it, move on
Trace example 1–2 min Out loud Walk through variable by variable with the original example input
Edge cases ~30 sec Out loud Test: empty input, single element, all same values, tricky boundary
State complexity ~10 sec Out loud "Time O(n), space O(1)." State it clearly and confidently.

Common Bugs to Check During Scan:

  • Off-by-one errors — should the loop be < or <=? Does it start at 0 or 1?
  • Missing return statement — did you return at all base cases?
  • Wrong variable — using i when you meant j, stale variable name
  • Null/empty not handled — what if input is empty list or None?
  • Mutation bug — modifying input when you shouldn't be
  • Integer overflow — sum of large ints (mention if in Java/C++)

Step 6 — Optimize

"Is my code correct first, and can I make it faster?"

🧩 Problem Solving 💬 Communication
🎯 Purpose — Why This Step Exists Correctness first, speed second. Re-read the code to confirm it's right, then run the 6-question checklist (BTTC? repeated work? better DS? redundant work? space?) to see if you can genuinely do better. Found something? Loop back: Discuss → Code → Verify.

The 6-Question Checklist:

  • BTTC — What's the Best Theoretical Time Complexity for this problem? Am I already there?

  • Redundant work — Can I terminate early? Are there unnecessary checks? Can I move work outside a loop?
  • Space — Can I modify in-place? Would a different structure use less memory?
  • Still stuck — Use the pre-built phrase below and ask for a hint.

Demo 1 — Pattern Recognition Path
Longest Substring Without Repeating Characters
Understand
"Let me make sure I understand. I'm given a string and I need to find the length of the longest substring with no repeated characters. So stripping the story: find the longest contiguous slice of the string where all chars are unique. A few questions: Can the string be empty? Can it contain spaces and special characters? Should I return the length or the substring itself? ... OK — return the length, string can be empty (return 0), all ASCII characters."
Approach
"I see signal keywords: 'substring' (contiguous), 'no repeating characters' (constraint on a window), find 'longest' (optimize). This is a Sliding Window pattern — I can use a window that expands right, and shrinks from the left when a duplicate is found. I'll store characters in a HashMap mapping char → last seen index. That way when I see a duplicate, I jump left pointer directly to one past the last occurrence."
Discuss
"Brute force would check every substring — O(n²) or O(n³). Instead, sliding window processes each character once — O(n) time, O(k) space where k is charset size. The insight is: when I hit a duplicate at position j, I don't need to restart from left+1, I can jump to last[char]+1, skipping the repeated section entirely. Since we must look at every character at least once, O(n) is optimal. Shall I code this up?"
Blueprint
Transcribing what I said in Discuss into comments: 
def lengthOfLongestSubstring(s):
    # Edge: empty string → return 0
    # 1. Initialize left=0, seen={char:index}, max_len=0
    # 2. Expand right pointer through string
    # 3. If char in seen AND inside window → jump left to seen[char]+1
    # 4. Update seen[char] = right, update max_len
    # 5. Return max_len
Code 
def length_of_longest_substring(s):
    # HashMap: char → most recent index
    seen = {}
    left = 0
    max_len = 0

    for right, char in enumerate(s):
        # Duplicate found AND it's inside current window
        if char in seen and seen[char] >= left:
            left = seen[char] + 1   # jump past the duplicate
        seen[char] = right
        max_len = max(max_len, right - left + 1)

    return max_len
"I'm using a HashMap because I need O(1) lookup to check and update last-seen index. The condition seen[char] >= left ensures I only shrink when the duplicate is actually inside the current window, not from a previous window."
Verify
"Let me trace 'abcab': a→{a:0},len=1; b→{b:1},len=2; c→{c:2},len=3; a→duplicate at 0, left=1,{a:3},len=3; b→duplicate at 1, left=2,{b:4},len=3. Result: 3 ✓. Edge case: empty string — loop never runs, returns 0 ✓. Single char 'a' — max_len becomes 1 ✓."
Optimize
"Re-reading... logic looks correct. BTTC is O(n) — must see every character. I'm already there. No repeated computation, HashMap gives O(1) ops. Space could theoretically be O(1) if we used a 128-element fixed array for ASCII, but O(k) HashMap is fine. I believe this is optimal."
Demo 2 — First Principles Path
Busiest Time in The Mall
Understand
"I'm given an array of [timestamp, count, direction] entries. Direction 1 = enter, 0 = exit. I need to find the timestamp when the most people were in the mall. Abstractly: given timestamped +/− events, find the timestamp where the running total peaks — but I must process ALL events at the same timestamp before checking. A few questions: Is the data sorted by timestamp? Can multiple events share a timestamp? Return earliest if tied?"
Approach
"No clear pattern keyword. First principles: Draw it — I visualize a counter that goes up/down, checked only at timestamp boundaries. Solve manually: process all events at t1, count=8, check peak; process t2, count=18, new peak. Key insight: DON'T check mid-timestamp. The algorithm: iterate, update count, and only check for peak when timestamp is about to change (or at last event)."
Discuss
"Brute force would check peak after every single event — O(n) but buggy (checks mid-timestamp). The insight: only check when the TIMESTAMP CHANGES. This is also O(n) time, O(1) space. Since we must see every event once, this is optimal. Shall I code it?"
Blueprint
Transcribing what I said in Discuss into comments: 
def find_busiest_period(data):
    # Edge: single event → is_last handles it
    # 1. Initialize count=0, max_count=0, best_time=0
    # 2. Iterate with index, update count by direction
    # 3. If last event OR next timestamp differs → boundary
    # 4. At boundary: if count > max_count → update max + best_time
    # 5. Return best_time
Code 
def find_busiest_period(data):
    count = 0
    max_count = 0
    best_time = 0

    for i, (ts, n, direction) in enumerate(data):
        # Update running count
        count += n if direction == 1 else -n

        # Check for peak only at timestamp boundary
        is_last = (i == len(data) - 1)
        next_different = (i + 1 < len(data) and data[i+1][0] != ts)

        if (is_last or next_different) and count > max_count:
            max_count = count
            best_time = ts

    return best_time
"The check is_last or next_different ensures we only evaluate the peak after ALL events at the same timestamp have been processed. This was the key insight from the brute force bug."
Verify
"Trace with [[t1,14,1],[t1,4,0],[t1,2,0],[t2,10,1]]: i=0, count=14, next same ts → no peak check. i=1, count=10, next same ts → no peak check. i=2, count=8, next DIFFERENT ts → check: 8>0 → best=8, best_time=t1. i=3, count=18, is_last → check: 18>8 → best=18, best_time=t2. Returns t2 ✓. Edge: single event — is_last triggers on i=0, checks peak correctly ✓."
Optimize
"Re-reading... looks correct. O(n) time — single pass. O(1) space — only counters. BTTC is O(n) since we must see every event. This is already optimal. No data structure swap would help here since we're doing arithmetic, not lookup."

Deep Optimization Techniques (Study Material)

These are moved here from Step 6 because they're too detailed for in-interview use. Study them, internalize the patterns, apply them as instincts.

Best Theoretical Time Complexity (BTTC)

BTTC is the lowest time complexity any algorithm for this problem could ever achieve. It tells you when to stop optimizing.

Problem TypeBTTCReasoning
Find one specific element in unsorted arrayO(n)Must check every element
Find element in sorted arrayO(log n)Binary search possible
Compare all pairsO(n²)n*(n-1)/2 pairs exist
Sort any comparison-based dataO(n log n)Comparison sort lower bound
Process every element onceO(n)Can't skip any element
Overlapping Computation — Trade Space for Time

When you compute the same value multiple times, cache it. This often converts O(n²) to O(n).

Example: Product of Array Except Self

Naive: For each index i, multiply all other elements — O(n²).

Optimized: Two-pass prefix product. Left pass stores prefix products, right pass accumulates suffix. O(n) time, O(1) extra space.

def product_except_self(nums):
    n = len(nums)
    result = [1] * n
    # Left pass: result[i] = product of all nums[0..i-1]
    prefix = 1
    for i in range(n):
        result[i] = prefix
        prefix *= nums[i]
    # Right pass: multiply in product of all nums[i+1..n-1]
    suffix = 1
    for i in range(n - 1, -1, -1):
        result[i] *= suffix
        suffix *= nums[i]
    return result
Data Structure Swaps — Use the Right Tool

The bottleneck operation often determines the best data structure. Swap and you often drop a log factor or convert O(n) lookup to O(1).

Example: K Closest Points to Origin

Sort approach: Sort all n points by distance — O(n log n). Return first K.

Max-Heap of size K: Maintain a heap of the K closest so far. O(n log k). Better when k << n.

import heapq

def k_closest(points, k):
    # Max-heap: push (-distance, point) to keep smallest k
    heap = []
    for x, y in points:
        dist = x*x + y*y
        heapq.heappush(heap, (-dist, [x, y]))
        if len(heap) > k:
            heapq.heappop(heap)
    return [point for _, point in heap]
Eliminating Redundant Work

Four sub-techniques to check in order:

Early Termination

Return as soon as the answer is known. In a search, stop when found. In a validation, fail fast on first violation.

def has_duplicate(nums):
    seen = set()
    for n in nums:
        if n in seen: return True   # early exit
        seen.add(n)
    return False
Caching / Memoization

Store computed results to avoid recomputation. Classic for recursive problems with overlapping subproblems.

from functools import lru_cache

@lru_cache(maxsize=None)
def fib(n):
    if n <= 1: return n
    return fib(n-1) + fib(n-2)
Move Work Outside the Loop

If something is computed on every iteration but doesn't change, compute it once before the loop.

# Slow: recomputes len(arr) every iteration
for i in range(len(arr)):
    if i < len(arr) - 1: ...

# Fast: compute once
n = len(arr)
for i in range(n):
    if i < n - 1: ...
In-Place Modification — Reduce Space

When you're allowed to modify the input, you can often eliminate an auxiliary data structure.

Example: Dutch National Flag (Sort Colors)

Sort an array of 0s, 1s, 2s in-place without extra space. Three-pointer approach: low tracks end of 0-region, high tracks start of 2-region, mid scans.

def sort_colors(nums):
    low, mid, high = 0, 0, len(nums) - 1
    while mid <= high:
        if nums[mid] == 0:
            nums[low], nums[mid] = nums[mid], nums[low]
            low += 1; mid += 1
        elif nums[mid] == 1:
            mid += 1
        else:  # nums[mid] == 2
            nums[mid], nums[high] = nums[high], nums[mid]
            high -= 1
    # O(n) time, O(1) space
Space-Efficient Structures — Trie for Prefix Problems

When multiple strings share prefixes, a Trie uses far less space than storing strings separately and enables O(m) prefix search where m is the key length.

Example: Autocomplete / Prefix Search 
class TrieNode:
    def __init__(self):
        self.children = {}
        self.is_end = False

class Trie:
    def __init__(self):
        self.root = TrieNode()

    def insert(self, word):
        node = self.root
        for char in word:
            if char not in node.children:
                node.children[char] = TrieNode()
            node = node.children[char]
        node.is_end = True

    def starts_with(self, prefix):
        node = self.root
        for char in prefix:
            if char not in node.children:
                return False
            node = node.children[char]
        return True

Insert: O(m). Search: O(m). Space: O(total characters) — much less than O(n×m) for n strings of length m.
