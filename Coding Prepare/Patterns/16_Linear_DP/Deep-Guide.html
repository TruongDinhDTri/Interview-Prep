📐 What Linear DP actually is

Most guides start with a signal table and never say what the thing is. So, first: Linear DP is the DP whose table has one row. If a single index dp[i] can name any subproblem, it's Linear. "Linear" means it literally — the table lies along a line, not a grid.

dp = [ 1    2    3    5    8 ]
ONE index → ONE row
🔲 2D DP — Unique Paths

TWO indices → a grid

Everything else in DP-land needs two numbers to name a subproblem — Unique Paths needs (row, col), Knapsack needs (item, capacity), String DP needs (position in s1, position in s2). All 2D. Linear DP is the one that needs just one.

The test: say the sentence "dp[i] is …" out loud. If one index says it completely → Linear DP. If you reach for a second number → it's a different shape.
Định nghĩa gọn: bảng chỉ cần MỘT hàng. Chữ "Linear" nghĩa đen — bảng nằm trên một đường thẳng, không phải cái lưới. Cách thử: nói thành câu "dp[i] là …" — trọn câu bằng một chỉ số → Linear DP.
🧷 Why stairs and burglary sit on the same shelf

This folder holds Climbing Stairs, Fibonacci, House Robber, Min Cost Climbing Stairs. Read that list and it feels random — what does climbing stairs have to do with robbing houses? Fair reaction. They're grouped for exactly one reason:

One sequence, and the answer at position n is built from answers at smaller positions. That's the entire criterion.

The formula inside is a separate question. Some of these add their branches, some take a max. Don't expect the four problems to look alike — expect them to share the same shape of dependency. Get that straight up front and the House Robber section later won't feel like a random jump.

Đây là chỗ dễ thấy vô lý nhất: "leo cầu thang thì liên quan gì trộm nhà?" Liên quan đúng MỘT điểm — một dãy, đáp án ở n dựng từ đáp án ở vị trí nhỏ hơn. Còn công thức bên trong (cộng hay max) là chuyện khác, tính riêng.
🪜 Climbing Stairs — do it by hand first

Stairs with n steps. Each move climbs 1 or 2 steps. How many distinct ways to reach the top? Count the small cases by hand before touching any formula:

n = 1 → (1) → 1 way n = 2 → (1,1) (2) → 2 ways n = 3 → (1,1,1) (1,2) (2,1) → 3 ways

Now stop listing. For n = 4, ask instead:

"What was the LAST move that got me to step 4?"
It was either a 1-step (so I was standing on step 3), or a 2-step (so I was standing on step 2). There is no third option — those are the only legal moves.

So every route to step 4 is some route to step 3 plus a final 1-step, or some route to step 2 plus a final 2-step. Two separate families of routes, no overlap between them, both valid:

f(4) = f(3) + f(2) = 3 + 2 = 5

No enumeration needed. That question — "what was the last move?" — is the engine for every problem in this folder.

Đừng học thuộc công thức. Hỏi "bước CUỐI CÙNG đưa tôi tới đây là gì?" — với luật leo 1 hoặc 2 bậc thì bước cuối chỉ có thể đến từ bậc n-1 hoặc n-2. Liệt kê hết khả năng rồi nối lại — đó chính là công thức.
✅ Is this really DP? — both conditions

Foundations says a problem is DP only when both conditions hold. Check them against Climbing Stairs rather than taking it on faith:

1. Overlapping subproblems — write the recursion plainly, no storage, and trace f(5). The tree is Fibonacci-shaped: f(3) gets computed under f(5) and again under f(4). f(2) shows up three times. Same work, done repeatedly. ✓
f(5) / \ f(4) f(3) ← computed twice / \ / \ f(3) f(2) f(2) f(1) / \ / \ f(2) f(1) f(1) f(0)
2. Optimal substructure — to build f(5), do you need the individual routes inside f(4) and f(3)? No. You only need their result numbers. The parent is assembled straight from the children's answers. ✓

Both hold → it's genuinely DP, not just something that resembles it. Now the recursion tree becomes a table, and nothing gets computed twice.

Hai điều kiện bắt buộc: (1) bài con bị tính lại nhiều lần — cây f(5) tính f(3) tới 2 lần, f(2) tới 3 lần ✓  (2) chỉ cần con số kết quả của bài con là ghép được bài cha, không cần biết chi tiết từng đường đi bên trong ✓
🗂️ The four questions — Foundations' frame, applied

Every DP problem, Linear or not, is four answers. This frame comes from Foundations — using it here is the actual link between the two pages, not just a hyperlink:

#QuestionClimbing Stairs
1State — what does dp[i] mean?number of ways to reach step i
2Recurrence — how do smaller cells build it?dp[i] = dp[i-1] + dp[i-2]
3Base case — which cells are filled by hand?dp[1] = 1, dp[2] = 2
4Answer — which cell do I return?dp[n] — the last one
Question 1 is the hard one. If you can't say it as a complete sentence — "dp[i] is the number of ways to reach step i" — you don't have the problem yet. Everything downstream fails from a vague state.

Why dp[1] and dp[2] are filled by hand: the recurrence looks back two cells. At i=1 and i=2 there aren't two cells behind you to look at — the formula has nothing to stand on. Those get answered directly.

Câu 1 (State) khó nhất và là nền móng — nói không trọn câu "dp[i] là …" nghĩa là chưa nắm bài. Base case tồn tại vì công thức nhìn lùi 2 ô, mà ở i=1, i=2 phía sau không đủ 2 ô để nhìn → phải điền tay.

➕ vs 🏆 Why one adds and the other takes max

You just watched both. Now the reason — because the current cheat-sheets list max(...) for House Robber without ever saying why it isn't +:

Counting → +
The branches are distinct valid paths, and every one of them counts. Reaching step 4 via "…then a 1-step" and reaching it via "…then a 2-step" are two different sets of routes, both real, no overlap. Add them to total them up.
→ Climbing Stairs, Fibonacci, Decode Ways
Optimizing → max / min
The branches are competing alternatives for the same single plan. You cannot both rob and not-rob house 3 on the same night — those aren't two routes you tally, they're two proposals. Keep the better one, discard the loser.
→ House Robber, Min Cost Climbing Stairs

The tell, if you're unsure: at house 3 in the walkthrough, the two branches were 11 and 7. Add them and you get 18 — a number that corresponds to no possible night of burglary. When adding the branches produces a meaningless number, you're in an optimizing problem.

🔧 Change the rules — proof it's a method, not a formula

If you only memorized f(n) = f(n-1) + f(n-2), changing the rules breaks you. If you internalized the question, it doesn't. Same problem, new move set:

Allowed movesWhere could the last move have come from?Recurrence
1 or 2 stepsi-1, i-2dp[i-1] + dp[i-2]
1, 2, or 3 stepsi-1, i-2, i-3dp[i-1] + dp[i-2] + dp[i-3]
1 or k stepsi-1, i-kdp[i-1] + dp[i-k]
any of moves[]one branch per legal movesum(dp[i-m] for m in moves)
The formula changes every time. The question never does. The allowed moves ARE the recurrence.
Đổi luật chơi thì công thức tự đổi theo — vì các nước đi cho phép chính là công thức truy hồi. Học thuộc công thức thì đổi luật là gãy; nắm được câu hỏi thì không.
💻 Three templates — same idea, three shapes

1 — Space-optimized (O(1) space). The default. The recurrence only ever looks back two cells, so keeping the whole row is waste — two variables suffice.

def climbingStairs(n): if n == 1: return 1 prev1, prev2 = 1, 2 # f(1), f(2) for i in range(3, n + 1): # range(3, n+1) — include n! curr = prev1 + prev2 prev1, prev2 = prev2, curr return prev2 # Time: O(n) | Space: O(1)

2 — Tabulation, full array (O(n) space). Keep the whole row when you must look back further than two cells, or when you want to inspect the table while debugging.

def climbingStairs(n): if n == 1: return 1 dp = [0] * (n + 1) dp[1], dp[2] = 1, 2 # base cases, filled by hand for i in range(3, n + 1): dp[i] = dp[i-1] + dp[i-2] return dp[n] # Time: O(n) | Space: O(n)

3 — Memoization (top-down). The recurrence written literally, plus a cache. Easiest to write once you have the recurrence; costs recursion depth.

from functools import lru_cache @lru_cache(maxsize=None) def climbingStairs(n): if n == 1: return 1 if n == 2: return 2 return climbingStairs(n-1) + climbingStairs(n-2) # Time: O(n) | Space: O(n) — cache + call stack

And House Robber, for comparison — notice how little changes. Same skeleton, max instead of +:

def rob(nums): prev2, prev1 = 0, 0 # best up to i-2, best up to i-1 for x in nums: prev2, prev1 = prev1, max(prev1, prev2 + x) return prev1 # Time: O(n) | Space: O(1)
TermMeaning
Bottom-upstart from base cases, build up to n
Tabulationfill a table (dp array) cell by cell
Loop + reusewhat it looks like in code
Space-optimized tabulationtabulation, but only keep the last K values

All four name the same approach. Top-down = recursion + cache (memoization) — the other direction.

Ba template, cùng một ý: base case → xây lên tới n. Space-optimized chỉ giữ 2 giá trị cuối vì công thức chỉ nhìn lùi 2 ô. Bốn tên gọi trong bảng đều là cùng một hướng (bottom-up); còn top-down là recursion + cache.
⚠️ Traps
1. Off-by-one in range. range(3, n) is empty when n=3 — the loop never runs. It must be range(3, n + 1).
2. Wrong swap order. prev1 = prev2 before prev2 = curr destroys prev1 while it's still needed. Use the tuple swap prev1, prev2 = prev2, curr, or save the old value first — and be consistent about which variable you return.
3. Plain recursion submitted as DP. return f(n-1) + f(n-2) with nothing else is O(2ⁿ) brute force. DP needs a cache or a loop — without one, nothing is being reused, which was the entire point.
4. Missing base-case guard. n=1 needs one (without it range(3,2) is empty and you return prev2=2 — wrong). n=2 doesn't (range(3,3) is empty and prev2=2 is correct).
5. Adding when you should be maximizing. The contrast above. If the branches are competing plans, + produces a number that means nothing.
6. Confusing DP with Backtracking. About to write "generate all paths"? Stop — that's Backtracking. "How many ways" → DP: count, don't enumerate.
Bốn cái chết người nhất: quên +1 trong range · swap sai thứ tự làm mất prev1 · nộp recursion trần tưởng là DP · cộng nhầm ở bài tối ưu.
