🗺️ DP Recognition

Two jobs, kept apart on purpose. Half A is the triage: is this DP, and which of the five shapes? Half B is the home for the three shapes that don't have a folder of their own yet.

⚡ Recognition — thẻ triage nhanh →
Half A — TriageGiven a fresh problem: what am I even looking at?
✅ Step 1 — Is this DP? (30 seconds, no theory)

You're in a room with a clock running. Don't re-derive the definitions — perform the check. Three moves, in order:

1Write the plain recursion. The obvious brute force, no storage at all. If you can't even express the problem recursively, stop — this probably isn't DP.
2Does it recompute the same argument? Trace two levels down. Does f(3) get called from more than one branch? → overlapping subproblems ✓
3Do you only need the child's RESULT? To assemble the parent, is the child's returned number enough — or do you need the details of how it got there? Number is enough → optimal substructure ✓
All three → it's DP. Any one fails → it isn't, and no amount of table-building will help.
Fastest single tell: "the answer for n depends on the answer for smaller n — and those smaller n's repeat."
🧠 Fuzzy on WHY those are the two requirements? That's theory, not triage. Foundations covers it properly: what DP is, both conditions with counter-examples, memoization vs tabulation, and the 4-question skeleton. This page assumes you have that and just want to classify a real problem quickly.
Ba bước để làm, không phải để đọc lại lý thuyết: viết recursion trần → xem nó có tính lại cùng tham số không → xem chỉ cần con số kết quả của bài con là đủ chưa. Đủ ba → DP.
🔢 Step 2 — How many indices does one subproblem need?

This is the question that actually picks the shape, and it's easy to skip past. Don't guess the shape from the story ("it's about coins, so… knapsack?"). Derive it:

1List two or three subproblems out loud. Not the whole problem — smaller versions of it.
2Ask what differs between them. That difference IS the state.
3Count how many numbers it takes to name one. One number → 1D, dp[i]. Two numbers → 2D, dp[i][j].
ProblemSubproblems differ by…Numbers neededTable
Climbing Stairswhich step you're on1 — idp[i] · one row
House Robberwhich house you're up to1 — idp[i] · one row
0/1 Knapsackwhich item, and how much room is left2 — (i, cap)dp[i][cap] · a grid
Coin Changewhich coin, and how much amount is left2 — (i, amt)dp[amt] per coin · a grid
LCS / Edit Distanceposition in s1, and position in s22 — (i, j)dp[i][j] · a grid
Unique Pathswhich row, and which column2 — (r, c)dp[r][c] · a grid
Say the sentence. "dp[…] is …", as a complete sentence, out loud. However many numbers you had to put inside the brackets to make that sentence true — that's your dimensionality, and the shape follows from it.
Đừng đoán shape từ câu chuyện của đề ("có đồng xu → chắc knapsack?"). Suy ra nó: liệt kê vài bài con → hỏi chúng khác nhau ở chỗ nào → đếm xem cần mấy con số để gọi tên MỘT bài con. Một số → 1D. Hai số → 2D.
🗺️ Step 3 — Which shape, and where to go

Numbers counted, flavour known. Route it:

📏 One sequence, a decision at each step — "take 1 or 2 steps", "rob or skip"1 index — position i Linear DP · 16 →
🎒 Items + capacity, each item used at most once2 indices — (item, capacity) · inner loop runs BACKWARD 0/1 Knapsack · 11 →
🪙 Items reusable without limit — coins, rod cuts, tiles2 indices — (item, amount) · inner loop runs FORWARD Half B, below ↓
🧵 Two strings compared, aligned, transformed2 indices — (pos in s1, pos in s2) Half B, below ↓
🟦 A grid, moving through cells (right/down)2 indices — (row, col) Half B, below ↓
And the operation? "How many ways" → join branches with +. "Min/max/best" → join with min/max. "Can you reach it" → join with or. The reasoning behind that split is worked out in 16 — Linear DP, and it holds for every shape here.
Linear và 0/1 Knapsack có folder riêng (16 và 11). Ba shape còn lại chưa có — chúng nằm ngay ở nửa B bên dưới.

🪙 Unbounded Knapsack

Signal: items can be reused as many times as you like, and there's a capacity or target to hit.

Classic problemSignal phrase
Coin Change (min coins)"any denomination, unlimited supply, make amount"
Coin Change II (count ways)"how many ways to make amount"
Rod Cutting"cut into pieces of any length, maximize value"
The one difference from 0/1 Knapsack: the inner loop runs FORWARD. That's what allows an item to be picked again — by the time you reach amount a, the cell dp[a - coin] has already been updated using this same coin. Running backward (the 0/1 pattern) reads a cell from before this coin existed, so each item gets used at most once.
def coinChange(coins, amount): dp = [float('inf')] * (amount + 1) dp[0] = 0 for coin in coins: for a in range(coin, amount + 1): # FORWARD → allows reuse dp[a] = min(dp[a], dp[a - coin] + 1) return dp[amount] if dp[amount] != float('inf') else -1 # Time: O(amount × coins) | Space: O(amount)
Trap: using the backward loop on an unbounded problem → each coin gets used at most once → wrong answer, and it will look plausible.

Deep dive — Coin Change (LC #322). Given coins of any denomination with unlimited supply, find the minimum number of coins to make amount. Return -1 if impossible.

Signal you seeWhat it tells you
"minimum number of" + selectionsOptimize DP — not counting, not reachability
Infinite supply of items + reach a targetUnbounded Knapsack — items can be reused
Subproblem inside subproblem of the same typeminCoins(15) → minCoins(10) — same question, smaller
Same subproblem reached from several pathsminCoins(10) comes from 15 via coin 5, from 11 via coin 1… → overlapping ✓
Why greedy fails here — and why that's the tell. Greedy takes the largest coin that fits:
coins = [1, 3, 4], amount = 6 Greedy: 4 + 1 + 1 = 3 coins ❌ DP: 3 + 3 = 2 coins ✅
Taking the 4 blocks the better path of two 3s. Whenever you can build a case where the locally best pick loses globally, greedy is out and DP is in.

Recurrence: dp(amt) = min(1 + dp(amt - coin)) for each coin — "to make amt, try subtracting each coin, recurse on the remainder, add 1 for the coin used, take the minimum." Base cases: dp(0) = 0 (zero coins make zero), dp(negative) = inf (impossible — don't count this path).

Top-down (recursion + memo) — easier to reason about; write the recurrence, add a cache:

def coinChange(coins, amount): memo = {} def dp(amt): if amt == 0: return 0 if amt < 0: return float('inf') if amt in memo: return memo[amt] memo[amt] = min(1 + dp(amt - c) for c in coins) return memo[amt] result = dp(amount) return result if result != float('inf') else -1 # Time: O(amount × coins) | Space: O(amount)

Bottom-up — the tabulation shown at the top of this section. Slightly faster (no recursion overhead) and the interview default once the pattern is familiar.

Điểm khác duy nhất so với 0/1: inner loop chạy TỚI (forward) — nhờ vậy khi tới amount a, ô dp[a-coin] đã được cập nhật bằng chính đồng xu này rồi, tức là được dùng lại. Chạy lùi thì đọc ô từ "trước khi có đồng xu này" → mỗi món chỉ dùng một lần. Và hễ greedy sai (chọn tốt cục bộ mà hỏng toàn cục) → rút DP ra.
🧵 String DP — LCS / Edit Distance

Signal: two strings, and you're comparing, aligning, transforming, or finding what they share.

Classic problemSignal phrasedp[i][j] means
Longest Common Subsequence"longest subsequence present in both"LCS of s1[:i] and s2[:j]
Edit Distance"min operations to turn s1 into s2"min edits for s1[:i] → s2[:j]
Longest Common Substring"contiguous common portion"length of common substring ending at i,j
Is Subsequence"can s1 be found inside s2, in order?"reachability
Why it's always 2D: a subproblem here is "how far have I got through s1, and how far through s2". Those two positions move independently — you can advance in one string without advancing in the other. Two independent numbers → two axes. There is no way around it.
def lcs(s1, s2): m, n = len(s1), len(s2) dp = [[0] * (n + 1) for _ in range(m + 1)] for i in range(1, m + 1): for j in range(1, n + 1): if s1[i-1] == s2[j-1]: dp[i][j] = dp[i-1][j-1] + 1 # chars match → extend the diagonal else: dp[i][j] = max(dp[i-1][j], dp[i][j-1]) # skip one char from either side return dp[m][n] # Time: O(m×n) | Space: O(m×n)
Trap: trying to flatten String DP to 1D. You lose the cross-string relationship — the whole point is tracking both positions at once.
Hai chuỗi so/căn/biến đổi → gần như luôn 2D: một trục cho mỗi chuỗi. Lý do: vị trí trên s1 và trên s2 di chuyển độc lập — tiến trên chuỗi này mà không tiến trên chuỗi kia được. Hai con số độc lập → hai trục. Ép về 1D là mất quan hệ giữa hai chuỗi.
🟦 2D Grid DP

Signal: a grid or matrix — move from top-left to bottom-right, counting paths or minimizing cost.

Classic problemSignal phraseNote
Unique Paths"how many ways to reach bottom-right"right/down moves only
Min Path Sum"minimum cost path, right/down only"grid values are costs
Triangle Min Path"min path from top to bottom"pyramid shape
Maximal Square"largest square of all 1s"grid of 0/1
The move that unlocks it is the same one from Linear DP, just in two directions: "what was the last move that landed me on this cell?" With right/down movement, the answer is always — from above, or from the left. There is no third option.
def uniquePaths(m, n): dp = [[1] * n for _ in range(m)] # first row & col = 1 (only one straight path) for i in range(1, m): for j in range(1, n): dp[i][j] = dp[i-1][j] + dp[i][j-1] # from above + from the left return dp[m-1][n-1] # Time: O(m×n) | Space: O(m×n) → optimizable to O(n)

Space optimization: if a cell only ever depends on the row above and the cell to its left, you never need more than one previous row in memory — collapse it to O(n).

Fill order matters here. Left→right, top→bottom, because both source cells (above, left) must already be filled when you arrive. That's exactly why the two nested loops run in that order — it isn't arbitrary.
Vẫn là câu hỏi cũ — "bước cuối cùng đưa tôi tới ô này là gì?" — chỉ khác là trong lưới: chỉ có thể từ ô TRÊN hoặc ô TRÁI. Thứ tự điền (trái→phải, trên→dưới) không phải ngẫu nhiên: nó bảo đảm hai ô nguồn đã có sẵn khi mình tới.
⚠️ Universal DP traps
1. Plain recursion ≠ DP. f(n-1) + f(n-2) with no cache and no loop is O(2ⁿ) brute force. DP requires memoization or tabulation — without one, nothing is reused, which was the whole point.
2. "Generate all" → Backtracking. If the answer is a list of solutions rather than a count/min/max, you're in the wrong family entirely.
3. Wrong loop direction in Knapsack. 0/1 goes backward, Unbounded goes forward. Reverse them and 0/1 silently permits reuse (or Unbounded silently forbids it) — both produce believable, wrong answers.
4. String DP needs 2D. One axis per string. Flatten early and the cross-string relationship is gone.
5. Off-by-one on table size. dp = [0] * (n + 1), not n — index 0 holds a base case.
6. Greedy feels right but fails. If a counter-example exists where the locally best pick blocks the globally best result, greedy is wrong. Reach for DP.
7. Deciding the shape before defining the state. The shape follows from how many indices the state needs. Say "dp[…] is …" as a full sentence first — the shape falls out of it. Guessing the shape from the story ("it's about coins…") is how people end up with the wrong table.
Bẫy hay chết nhất: recursion trần tưởng là DP · sai chiều loop knapsack (0/1 lùi, unbounded tới) · chọn shape trước khi định nghĩa state.
