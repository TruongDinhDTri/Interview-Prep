Our Learning Journey

From confusion to clarity - Every step matters

📖 The Problem Statement
🎯 The Challenge: Given an array of integers and a target sum K, find the number of continuous subarrays that sum to K.

📝 What are continuous subarrays?
A contiguous section of the array (no gaps allowed!)

💻 Example:
Input: nums = [1, 2, 3, 4, 5], k = 5
Output: 2

Why? Two subarrays sum to 5:
• [2, 3] = 5 ✓
• [5] = 5 ✓

🎨 The Twist: The array can have negative numbers, which breaks common patterns!
🤔 Initial Thoughts

When first encountering this problem, the natural question is: "Can I use sliding window?"

It seems perfect - we're looking for subarrays after all. But there's a catch...

🗺️ The Complete Journey

Step 1: The Sliding Window Attempt

The journey began with a solid instinct - use sliding window!

"Well can I use variable sliding window? Like slide across and find those windows that's valid?"

💭 The Thought Process:

This made sense! Sliding window works great for subarray problems. We could expand when the sum is too small, shrink when it's too large, right?

⚠️ But wait... What happens when we have negative numbers?

Step 2: The Breakthrough - Sliding Window Breaks!

"Ohh damn. It's not a sorted array right? The negative make this worse"
💡 The Aha Moment: Sliding window requires monotonicity - when you expand the window, the sum should consistently increase or decrease.

🎯 Let's see why it breaks:
Array: [1, -1, 1, 1, 1], K = 3

Window [1, -1] → sum = 0 (too small)
Expand: [1, -1, 1] → sum = 1 (still too small)
Expand: [1, -1, 1, 1] → sum = 2 (still too small)
Expand: [1, -1, 1, 1, 1] → sum = 3 ✓

But what if the next element is -5?
[1, -1, 1, 1, 1, -5] → sum = -2 (got smaller by expanding!)

✨ The Problem: With negatives, expanding doesn't guarantee the sum increases!

🏗️ So we need a different approach...

Step 3: Thinking About Complexity

Before jumping to the solution, there was an important discussion about what O(n²) actually means.

💭 The Question: At each position j, we know prefix[j]. We need to check if prefix[j] - K exists in our previous prefix sums. How do we do that?

The naive approach: scan from 0 to j every time to check if the value exists!

"Well I think the time complexity would be o(n)?"

🤔 The Reasoning: "To find if prefix[i] exists, I need to scan from 0 to j every time I come to another j."

This sounds reasonable - just scan through to check. But let's calculate the actual cost:

Why Scanning is O(n²) 
If we scan from 0 to j for each j:

Position 0: check 0 items
Position 1: check 1 item
Position 2: check 2 items
...
Position n: check n items

Total = 0 + 1 + 2 + ... + n

Formula: Sum = n × (n+1) / 2

Example n=5: 1+2+3+4+5 = 15

# This grows as n²/2, which is O(n²)
💡 The Realization: Even though each individual scan seems simple, when we do it n times, we get O(n²) total!

This is too slow. We need a way to check "have I seen this value?" in O(1) time instead of O(n) time.

Enter: HashMap! 🎯

📚 The Lesson: Understanding growth rates helps us see why we need a better approach!

Step 4: The Prefix Sum Discovery!

"I mean if I know the sum from 1-10 and the sum from 1-8 I can subtract them and knows the sub from 8-10 right?"
🌟 YES! This is THE breakthrough!

If you know:
  • Sum from start to index j = 10
  • Sum from start to index i-1 = 3
Then: sum(i to j) = 10 - 3 = 7

✨ The Magic: We can get ANY subarray sum in O(1) time if we precompute prefix sums!
Prefix Sum Visualization 
Array:     [1,  2,  3,  4]

Prefix:  [0,  1,  3,  6, 10]
          ↑ Start with 0 for convenience

# To get sum from index 1 to 2: [2, 3]
prefix[3] - prefix[1] = 6 - 1 = 5 ✓

# To get sum from index 0 to 3: [1, 2, 3, 4]
prefix[4] - prefix[0] = 10 - 0 = 10 ✓

Step 5: The Formula Rearrangement!

This is where everything clicks together!

We want: prefix[j] - prefix[i] = K

Rearranging: prefix[i] = prefix[j] - K

💡 The Strategy:

As we scan through at each position j:
  1. Calculate current prefix sum: prefix[j]
  2. Calculate what we need: prefix[j] - K
  3. Check if we've seen that value before!

If we've seen prefix[j] - K before, that means there's a subarray ending at j that sums to K!

Step 6: HashMap or Set?

"ohhh, set() ? or hashmap() ?"

💭 Great question! Both store values, but there's a crucial difference...

Why Counts Matter 
Array:     [1, -1,  1, -1]
Prefix:  [0,  1,  0,  1,  0]
K = 0

# At index 4, prefix = 0
# We need: prefix[j] - K = 0 - 0 = 0
# We've seen 0 twice before (indices 0, 2)
# So we have 2 valid subarrays ending here!

Step 7: Counts, Not Positions!

"Well actually We don' need the exact range, we just need to know the number right? I have seen prefix[_] = prefix[j] - K, 2 times => 2 valid subarray right?"
🎉 EXACTLY! This is key!

The HashMap stores: {prefix_sum → count}

We don't care WHERE we saw each prefix sum, only HOW MANY TIMES.

If prefix[j] - K has been seen 3 times before, that means 3 valid subarrays end at position j!

With the strategy clear, it was time to write code... and that's when the real learning began!

Each bug taught an important lesson about Python, hashmaps, and careful implementation.

Pattern Recognition

How we identified the right approach

🔍 The Detective Work

Before jumping to prefix sums, let's understand WHY the patterns you might know (Two Pointers and Sliding Window) don't work here.

❌ Why NOT Two Pointers?
🚫 Two Pointers Pattern is for:

1. Finding Pairs/Triplets in Sorted Arrays
• Example: Two Sum in sorted array
• Use left and right pointers to find target sum
• This problem: NOT about finding pairs!

2. In-Place Array Modification
• Example: Remove duplicates from sorted array
• Use slow/fast pointers to filter in-place
• This problem: NOT modifying in-place!

❌ Conclusion: No pairs, no in-place modification → NOT Two Pointers!
❌ Why NOT Sliding Window?
🚫 Sliding Window requires MONOTONICITY:

What is Monotonicity?
When you expand the window, the property (like sum) should consistently increase OR decrease.

Examples that work:
• Longest substring with K distinct characters
• Maximum sum of subarray size K
• Minimum window substring

Why THIS problem doesn't work:
• Negative numbers break monotonicity!
• Expanding can make sum go UP or DOWN
• Shrinking can make sum go UP or DOWN
• We can't maintain the sliding window invariant!

❌ Conclusion: Negative numbers = NO monotonicity = NOT Sliding Window!
✅ It's a PREFIX SUM + HASHMAP Problem!
🎯 Key Indicators for Prefix Sum + HashMap:

1. Looking for Subarrays with Specific Property
• "Find/count subarrays that sum to K"
• Need to check ALL possible subarrays
• Brute force would be O(n²) or O(n³)

2. Array Has Negative Numbers
• Rules out sliding window
• Can't use monotonicity-based approaches
• Need smarter solution!

3. Need O(1) Lookup
• Must quickly check if value exists
• HashMap provides O(1) average lookup
• Perfect for this use case!

4. Can Transform to "Find Pair" Problem
• "Find subarrays sum to K" → "Find pairs of prefixes with difference K"
• prefix[j] - prefix[i] = K
• HashMap stores previous prefixes!
🎯 The Pattern Recognition Framework
📚 When You See These → Think Prefix Sum + HashMap:

• "Count subarrays" with sum/property
• "Find subarrays" with specific condition
• "Continuous subarrays" with target sum
• "Longest/Shortest subarray" sum to K
• Array can have negative numbers
• Need better than O(n²) complexity

🎨 Related Problems:
• Contiguous Array (equal 0s and 1s)
• Binary Subarrays With Sum
• Maximum Size Subarray Sum Equals K
• Subarray Sum Divisible by K

The Key Insight

Understanding the prefix sum technique

💡 The Prefix Sum Transformation

The key insight is transforming "find subarrays with sum K" into "find pairs of prefix sums with difference K"!

🤔 What is a Prefix Sum?

A prefix sum at index i is the sum of all elements from the start up to (but not including) index i.

Prefix Sum Example 
Array:     [1,  2,  3,  4,  5]

Prefix:  [0,  1,  3,  6, 10, 15]
          ↑                    ↑
    start with 0       sum of [1,2,3,4]
✨ The Magic Formula
💡 Core Equation:

sum(i to j) = prefix[j] - prefix[i]

If we want sum(i to j) = K, then:

prefix[j] - prefix[i] = K

Rearranging:

prefix[i] = prefix[j] - K

✨ The Strategy:
At each position j, we look for prefix[j] - K in our hashmap!
🏗️ The HashMap Structure

The hashmap stores:

  • Key: A prefix sum value
  • Value: Count of how many times we've seen this prefix sum
Why Counts Matter 
# If we've seen prefix sum 5 three times:
hashmap = {
    ...
    5: 3,  # Seen prefix sum 5 three times!
    ...
}

# At position j, if prefix[j] - K = 5:
# We found 3 valid subarrays ending at j!
🎯 Why HashMap Instead of Set?
Set vs HashMap:

Set: Only tells us "yes, I've seen this value" or "no, I haven't"

HashMap: Tells us "I've seen this value X times"

Why we need HashMap:
If a prefix sum appears multiple times, each occurrence represents a different valid subarray!

Example: [1, -1, 1, -1], K = 0
Prefix 0 appears 3 times → multiple valid subarrays!
🔥 The Edge Case: seen[0] = 1
⚠️ Critical Edge Case:

What if a subarray starts from index 0?

Example: nums = [1, 2, 3], K = 6

At index 2: prefix = 6, we need prefix[j] - K = 6 - 6 = 0

But 0 isn't in our hashmap yet!

Solution: Initialize seen[0] = 1 before the loop!

This represents "the sum before we start is 0, and we've seen it once"

Complexity Analysis

Deep dive into time and space complexity

📊 Understanding the Complexity
Approach Time Space Notes
Brute Force O(n³) O(1) Check every subarray, calculate sum each time
Better Brute Force O(n²) O(1) Use running sum while iterating
Prefix + Scan O(n²) O(n) Build prefix array, scan for each position
Prefix + HashMap Optimal O(n) O(n) Single pass, O(1) lookups with HashMap
⏱️ Time Complexity: O(n)
Why O(n)?

We iterate through the array once: O(n)

At each position, we do:
  • Update prefix_sum: O(1)
  • Calculate remain: O(1)
  • HashMap lookup: O(1) average
  • HashMap update: O(1) average

Total: O(n) × O(1) = O(n)
💾 Space Complexity: O(n)
Why O(n)?

In the worst case, all prefix sums are unique.

We store up to n different prefix sums in the HashMap.

Therefore: O(n) space
🧮 The 1+2+3+...+n = O(n²) Explanation

Remember when we discussed why scanning from 0 to j is O(n²)?

Mathematical Proof 
Total operations when scanning 0 to j:

Position 0: scan 0 items
Position 1: scan 1 item
Position 2: scan 2 items
...
Position n: scan n items

Total = 0 + 1 + 2 + 3 + ... + n

Formula: Sum = n × (n+1) / 2

Example with n=5:
1+2+3+4+5 = 5×6/2 = 15

Growth pattern:
n=10:   sum = 55
n=100:  sum = 5,050
n=1000: sum = 500,500

# The sum grows as ~n²/2
# In Big-O notation: O(n²)
💡 The HashMap Magic:

The HashMap transforms what would be an O(n) lookup (scanning all previous prefixes) into an O(1) lookup!

This reduces overall complexity from O(n²) to O(n)!

Struggles & Fixes

Learning from every mistake

🐛 Code Evolution: Bug by Bug
🐛 Struggle #1: defaultdict Setup
❌ Wrong Attempts 
seen = defaultdict()  # ❌ Missing argument!
seen = defaultdict(0)  # ❌ 0 is not callable!
seen = defaultdict(int())  # ❌ Calling int(), passing 0!

The Confusion: What exactly does defaultdict need?

✅ The Fix
✅ Correct 
seen = defaultdict(int)  # ✅ Pass the function itself!

Why: defaultdict needs a callable (a function), not a value!

  • defaultdict(int) → "Call int() when you need a default" → returns 0
  • defaultdict(list) → "Call list() when you need a default" → returns []
  • defaultdict(set) → "Call set() when you need a default" → returns set()
🐛 Struggle #2: Accumulating Prefix Sum
❌ Wrong 
prefix_sum += 0  # ❌ Adding 0 doesn't help!

prefix_sum += prefix_sum + nums[j]  # ❌ DOUBLES the sum!
# This becomes: prefix_sum = 2*prefix_sum + nums[j]
✅ The Fix
✅ Correct 
prefix_sum += nums[j]  # ✅ Just add current element!

Why: We want a running sum, just add the current element!

🐛 Struggle #3: Indexing Confusion
❌ Wrong 
seen[prefix_sum[j]] += 1  # ❌ Can't index an integer!

The Problem: prefix_sum is now a variable (single number), not an array!

✅ The Fix
✅ Correct 
seen[prefix_sum] += 1  # ✅ Use the variable directly!
🐛 Struggle #4: When to Update HashMap
❌ Wrong 
if remain in seen:
    count += seen[remain]
else:
    seen[prefix_sum] += 1  # ❌ Only in else!

The Problem: We only add to hashmap when remain is NOT found. Future positions won't find this prefix!

✅ The Fix
✅ Correct 
if remain in seen:
    count += seen[remain]

# ALWAYS add (outside the if)
seen[prefix_sum] += 1  # ✅ Always update!

Why: We need to record EVERY prefix sum so future iterations can find them!

🐛 Struggle #5: The Edge Case

Testing with nums = [1, 2, 3], k = 6:

What Goes Wrong 
# At index 2: prefix_sum = 1+2+3 = 6
remain = 6 - 6 = 0

# Look for 0 in seen... but it's empty!
# We miss the subarray [1, 2, 3] which equals 6!
✅ The Fix
✅ Correct 
seen = defaultdict(int)
seen[0] = 1  # ✅ Initialize with 0!

Why: When remain = 0, it means "I need a subarray starting from index 0".

Initializing seen[0] = 1 handles this edge case!

It represents: "The sum before we start is 0, and we've seen it once"

Final Solution

Clean, commented, and correct

✅ The Complete Implementation
Python Solution 
from collections import defaultdict

class Solution:
    def subArrayEqualK(self, nums, k):
        # HashMap to store {prefix_sum: count of occurrences}
        # defaultdict(int) auto-initializes missing keys to 0
        seen = defaultdict(int)

        # Edge case: Initialize with prefix sum 0 appearing once
        # This handles subarrays that start from index 0
        # When prefix_sum - k = 0, it means the entire
        # subarray from start equals k
        seen[0] = 1

        # Running prefix sum (cumulative sum up to current index)
        prefix_sum = 0

        # Counter for total number of valid subarrays
        count = 0

        # Iterate through each element in the array
        for j in range(len(nums)):
            # Update the running prefix sum
            prefix_sum += nums[j]

            # Calculate what prefix sum we need to find
            # If prefix[j] - prefix[i] = k,
            # then prefix[i] = prefix[j] - k
            remain = prefix_sum - k

            # Check if we've seen this required prefix sum before
            # If yes, each occurrence represents one valid
            # subarray ending at j
            if remain in seen:
                count += seen[remain]

            # Add current prefix sum to hashmap
            # (or increment its count)
            # This makes it available for future iterations
            seen[prefix_sum] += 1

        return count
🎉 This solution handles all edge cases!

• Negative numbers ✓
• Subarrays starting from index 0 ✓
• Duplicate prefix sums ✓
• O(n) time complexity ✓
• O(n) space complexity ✓
