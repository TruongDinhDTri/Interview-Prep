The Core Insight

The ONE thing that makes this problem click

📖 The Problem
🎯 Given: An array of integers (can have negatives!) and a target sum K.
Find: The number of continuous subarrays that sum to K.

nums = [1, 2, 3, 4, 5], k = 5 → Output: 2 → [2,3] and [5]
📓 The Notebook Analogy (The very important part)

Imagine you're walking through the array, keeping a running sum. You carry a notebook where you write down every prefix sum you encounter. You write down every single prefix sum. Because when you encouter a new prefix sum and you look back through all the prefix sum that you've gone through. Is there any prefix_sum that I have seen before that +K step would end up with the current prefix_sum?

What goes IN the notebook?
🔑 The Key Distinction:

We STORE real prefix sums (what actually happened)
We LOOK UP prefix[j] - k (what we need to exist)

These are TWO different operations! The hashmap contains only real prefix sums — never the "remain."
Walkthrough: nums = [3, 7, 2], k = 9 
Notebook starts: {0: 1}  # "sum before we start = 0"

Index 0: prefix_sum = 3
  remain = 3 - 9 = -6
  Is -6 in notebook? ❌
  Write 3 → {0:1, 3:1}

Index 1: prefix_sum = 10
  remain = 10 - 9 = 1
  Is 1 in notebook? ❌
  Write 10 → {0:1, 3:1, 10:1}

Index 2: prefix_sum = 12
  remain = 12 - 9 = 3
  Is 3 in notebook? ✅ Yes! count += 1
  # prefix[2] - prefix[?] = 12 - 3 = 9 = k
  # → subarray [7, 2] sums to 9! ✓
⚡ Why is it guaranteed to be real?

Because we only store prefix sums that actually happened as we walked through the array. Every entry in the notebook is a real cumulative sum from index 0 to some real index.

If remain is NOT a real prefix sum → it won't be found → no false positives!
✨ The Formula
💡 The transformation:

"Find subarrays with sum K" → "Find pairs of prefix sums with difference K"

sum(i to j) = prefix[j] - prefix[i]
We want: prefix[j] - prefix[i] = K
Rearrange: prefix[i] = prefix[j] - K

At each j → compute prefix[j] - K → look it up in notebook!
Why HashMap, not Set?

A prefix sum can appear multiple times. Each occurrence = a different valid subarray. We need counts, not just existence.

Example: [1, -1, 1, -1], K = 0
Prefixes: [0, 1, 0, 1, 0]
# Prefix 0 appears 3 times → multiple valid subarrays!
# Set would say "yes, 0 exists" → count = 1 (WRONG)
# HashMap says "0 seen 2 times" → count += 2 (CORRECT)
Why seen[0] = 1?
⚠️ Đây KHÔNG phải edge case — đây là sự thật toán học!

Trước khi bắt đầu mảng, tổng tích lũy = 0. Luôn luôn đúng. Đó là sự thật, không phải trick.

Bất kỳ lúc nào prefix[j] = K (tổng từ đầu mảng tới j = K), thì remain = 0. Mình cần 0 có trong notebook để tìm ra.

Concrete example: nums = [3, 1, 2], k = 3
→ j=0, prefix=3, remain=0 → nếu không có seen[0]=1 → miss subarray [3]!

Không ghi nó vào = quên mất sự thật "trước khi bắt đầu, tổng = 0".
Nếu không có subarray nào cần nó → nó nằm im, không gây hại.
🔥 "count += seen[remain] có bị đếm trùng không?"

Đây là confusion phổ biến nhất khi học Prefix Sum + HashMap. Hãy đi qua từng bước với nums = [1, -1, 1, 1], k = 1:

Step 1 — j=0 works fine
prefix = 1, remain = 0
seen[0] = 1 → có 1 vị trí mà prefix_sum = 0 (seed)
Từ seed đi đến j=0 → subarray [1] = K ✓ → count = 1
Step 2 — j=1, seen[0] tăng lên
prefix = 0, remain = -1, không tìm thấy -1 → count vẫn = 1
Record prefix hiện tại: seen[0] += 1 → seen[0] = 2

Lúc này seen[0] = 2 nghĩa là: có 2 VỊ TRÍ mà prefix_sum = 0:
  ① seed (trước index 0)
  ② sau index 1 (prefix quay về 0)

Step 3 — THE CONFUSION 🤯 (The very important part)

❌ "Khoan! Đếm trùng rồi!"

j=2, prefix = 1, remain = 0

seen[0] = 2 → count += 2 → count = 3


"Hồi j=0 đã dùng seed (seen[0]) để tìm subarray [1] rồi mà? Sao giờ lại dùng seed LẦN NỮA? Đếm trùng rồi! Hong lẽ lại dùng lại cái seen[0] đó hoài vậy trời ?"

Step 4 — THE RESOLUTION 💡
✅ Cùng seed, nhưng j KHÁC = subarray KHÁC!

Nhìn kỹ: mỗi j tạo ra subarray kết thúc ở vị trí khác nhau:

3 subarrays hoàn toàn khác nhau
── j=0 (count từ 0→1): ──────────────────
seed(0) ──→ j=0 = [1]              ← subarray A

── j=2 (count từ 1→3): ──────────────────
seed(0) ──→ j=2 = [1, -1, 1]      ← subarray B (KHÁC A!)
idx1(0) ──→ j=2 = [1] (index 2)   ← subarray C (KHÁC A!)

• [1] ở index 0 ≠ [1] ở index 2. Khác vị trí = khác subarray.
• [1] ở index 0 ≠ [1,-1,1]. Khác length = khác subarray.

Step 5 — THE RULE 🔥
💡 Quy tắc vàng (Wiganz's own words):

"Điểm mấu chốt là tính tại điểm j. Trước đó có bao nhiêu cái prefix_sum[i] mà prefix[j] - K = prefix_sum[i]. Nếu có thì mỗi cái tạo ra 1 subarray kết thúc tại j. Khi j thay đổi → check lại → tạo ra subarray MỚI vì kết thúc ở vị trí khác. Không bao giờ trùng."
🏠 Metaphor — Prefix sum là VỊ TRÍ, không phải token dùng 1 lần:

Giống như nhà (seed) — hôm nay đi tới tiệm bánh (j=0), ngày mai đi tới công viên (j=2). Nhà không biến mất sau chuyến đi đầu tiên. Mỗi chuyến đi từ nhà tới một đích khác = một hành trình khác.

Pattern Recognition

When to reach for this technique

❌ Why NOT Sliding Window?
Sliding Window needs monotonicity:

Expanding window → sum must consistently go UP (or DOWN).
Negative numbers break this! Expanding can increase OR decrease the sum.

[1, -1, 1, 1, 1], K=3 → expand to [1,-1] sum=0, expand to [1,-1,1] sum=1... no monotonic direction!
✅ Prefix Sum + HashMap Triggers
🎯 Reach for this when you see:

• "Count/find subarrays with sum = K"
• Array can have negative numbers
• Need better than O(n²)
• Need to transform subarray problem into pair-finding problem
🎨 Related Problems:

• Contiguous Array (equal 0s and 1s)
• Binary Subarrays With Sum

Solution + Trace

The final code and a complete walkthrough

✅ The Implementation
Python Solution
from collections import defaultdict

class Solution:
    def subarraySum(self, nums, k):
        seen = defaultdict(int)
        seen[0] = 1          # seed: prefix 0 seen once
        prefix_sum = 0
        count = 0

        for num in nums:
            prefix_sum += num              # STORE: running sum
            remain = prefix_sum - k        # LOOK UP: what we need

            if remain in seen:
                count += seen[remain]      # found valid subarrays!

            seen[prefix_sum] += 1         # record this prefix sum

        return count
🔍 Step-by-Step Trace

nums = [1, -1, 1, 1], k = 1

Execution Trace
Init: seen = {0: 1}, prefix = 0, count = 0

─────────────────────────────────────
num=1:  prefix = 1,  remain = 0
  seen[0] = 1 → count = 1    ✓ [1]
  seen = {0:1, 1:1}

─────────────────────────────────────
num=-1: prefix = 0,  remain = -1
  -1 not found → count = 1
  seen = {0:2, 1:1}

─────────────────────────────────────
num=1:  prefix = 1,  remain = 0
  seen[0] = 2 → count = 3    ✓ [1,-1,1] and [1](index 2)
  seen = {0:2, 1:2}

─────────────────────────────────────
num=1:  prefix = 2,  remain = 1
  seen[1] = 2 → count = 5    ✓ [-1,1,1] and [1]
  seen = {0:2, 1:2, 2:1}

─────────────────────────────────────
Answer: 5 ✨

Pitfalls

The bugs that actually bite

🐛 Bug #1: Forgetting seen[0] = 1
❌ What goes wrong

nums = [1, 2, 3], k = 6 → prefix = 6, remain = 0

Without the seed, 0 isn't in the hashmap → we miss [1,2,3]!

✅ Fix
Always seed the notebook
seen[0] = 1  # "sum before index 0 is 0, seen once"
🐛 Bug #2: Only updating hashmap in else
❌ What goes wrong
Wrong — only stores when NOT found
if remain in seen:
    count += seen[remain]
else:
    seen[prefix_sum] += 1  # ❌ skips recording!
✅ Fix

Always record the prefix sum — outside the if/else. Future positions need it!

Correct — always store
if remain in seen:
    count += seen[remain]
seen[prefix_sum] += 1  # ✅ ALWAYS, outside the if
🐛 Bug #3: Confusing what gets stored vs looked up
❌ The confusion

Thinking we store prefix_sum - k (the remain) in the hashmap.

✅ Remember the notebook rule
📓 Two separate operations:

STORE: seen[prefix_sum] += 1 — the actual prefix sum
LOOK UP: seen[prefix_sum - k] — checking if a needed value exists

The notebook only contains real prefix sums that actually happened. That's why lookups are guaranteed valid — no fake numbers, no guesses!
