💡 The 1 điều duy nhất cần nhớ — why mid drifts LEFT

Integer division truncates toward zero. So the midpoint of two adjacent indices rounds DOWN to the lower (left) one. mid lives on left's lap.

# left=3, right=4 (adjacent)
mid = (3 + 4) // 2 = 3   # == left !
left = mid          # left = 3 again → NOBODY MOVES → 🔁 infinite loop

# THE FIX — ceil the mid so it jumps RIGHT, letting left advance:
mid = (3 + 4 + 1) // 2 = 4
left = mid          # left = 4 → progress ✅

Floor mid → mid trôi về bên trái → left = mid đứng yên → fix bằng +1 (hoặc dùng left = mid + 1).

Branch keeps via left = mid → MUST use CEIL mid Floor mid → must advance with left = mid + 1 Never mix templates

⚖️ The asymmetry — why First Bad Version never worried

Only the pointer that assigns = mid with no ±1 can freeze. Floor mid sits on left's side, so:

💀 left = mid + floor mid

left gets re-assigned to itself when adjacent → STALL. This is what THIS problem used.

✅ right = mid + floor mid

right gets pulled DOWN toward mid = always progress. This is what First Bad Version & Find Peak use — they never had this bug.

💻 The two safe templates

Template A · left = mid

left, right = 0, len(values)-1
while left < right:
    mid = (left+right+1)//2  # CEIL
    if values[mid][1] > timestamp:
        right = mid - 1
    else:
        left = mid
return values[left][0] \
  if values[left][1] <= timestamp else ""

Template B · left = mid + 1 ⭐ default

left, right = 0, len(values)  # not len-1
while left < right:
    mid = (left+right)//2   # floor OK
    if values[mid][1] <= timestamp:
        left = mid + 1
    else:
        right = mid
return values[left-1][0] \
  if left > 0 else ""

⭐ Default to Template B — it can never infinite-loop. left = count of ts ≤ t, so left==0 → "", left==len → last element.
