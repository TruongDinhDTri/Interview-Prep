Core

Base 62 vs Base 64

Base 64 uses characters +, /, and = (padding). These are URL-unsafe: + means space in query strings, / is a path separator. They'd need percent-encoding (%2B, %2F), which defeats the "short" purpose.

Base 62 uses only [0-9a-zA-Z] — all URL-safe, no encoding needed.

Base 62 vs MD5

MD5 is a hash function — it can produce collisions when truncated. Base 62 is an encoding scheme — it converts a unique ID to a unique string. No collision is mathematically possible if the underlying ID is unique.

The tradeoff: Base 62 requires a distributed unique ID generator (added complexity), while MD5 just needs a hash function but requires collision detection logic.

Interview Trap

The Problem

Should the same longURL get the same shortURL or a different one each time? This is an idempotency decision with UX and storage implications.

Option A: Return existing shortURL (Idempotent)

Check long_url index first. If exists, return existing shortURL. Requires an index on the long_url column. Saves storage. Most users expect this behavior (sharing the same link should produce the same short URL).

Option B: Create new shortURL always

Simpler logic — no dedup check. The same longURL gets multiple short aliases. Wastes storage; confusing user experience.

Recommended: Option A for known users (require login). Index on long_url makes this a single additional query. Race condition on concurrent creates: use a DB UNIQUE constraint on long_url and handle the constraint violation by returning the existing record.
🔐 Hashing & Collisions
Core

The Problem

When truncating MD5/SHA-1 to 7 chars, two different longURLs can produce the same 7-char prefix. With 365B URLs, this is not theoretical.

Algorithm

def shorten(long_url):
    url = long_url
    while True:
        short = md5(url)[:7]
        if not bloom_filter.might_contain(short):
            # Definitely new — safe to insert
            bloom_filter.add(short)
            db.save(short, long_url)
            return short
        if db.get(short).long_url == long_url:
            return short  # duplicate submission
        # True collision: different URL, same hash
        url = long_url + predefined_salt
Key insight: The Bloom filter eliminates DB reads for new URLs (true negatives are impossible in Bloom filters). Only when the filter says "might exist" do you query the DB. This keeps the hot path fast.
Advanced

What It Is

A Bloom filter is a space-efficient probabilistic data structure. It can answer "is X in this set?" with two outcomes:

  • Definitely NOT in set — 100% accurate; no false negatives
  • Probably in set — May produce false positives (says "exists" when it doesn't)

How It Works

Uses k hash functions over a bit array. To add an element: hash it k times → set k bits. To check: hash k times → if any bit is 0 → definitely not in set; all bits 1 → probably in set.

Why It's Perfect Here

For collision detection, we only need "definitely not exists" to be correct. A false positive (Bloom says "exists" when it doesn't) just causes one unnecessary DB read — acceptable. This eliminates DB reads for the majority of new URL creations.

Real-world uses: Cassandra (SSTable existence), Bitcoin (wallet lookup), Chrome Safe Browsing, PostgreSQL (join optimization). Knowing these examples impresses interviewers.

CoreScaling

Why Cache?

URL redirecting is read-heavy (10:1 ratio). Popular short URLs get hit millions of times. Without cache, every redirect hits the DB — 11,600 reads/sec to DB is manageable today but unsustainable at 10× growth.

Pareto principle: top 20% of URLs get 80% of traffic. Caching just the hot 10% eliminates ~80% of DB reads.

Cache Sizing Calculation

100M URLs/day
Cache top 10% = 10M entries
~500 bytes/entry
Total: 5 GB

5 GB fits comfortably in a single Redis node (typical 64GB). Use LRU eviction — least recently accessed URLs get evicted first.

Scaling

Write Volume Analysis

100M/day = ~1,160 writes/sec. A well-tuned MySQL instance can handle ~5,000-10,000 writes/sec. So initially, a single DB write node is sufficient. The real scaling challenge is the 10-year growth to 365TB.

Scaling Strategy (Progressive)

  1. Read replicas first: Route all redirect reads to replicas. Reduces load on primary dramatically.
  2. Vertical scaling: More RAM/CPU on write primary. Buys time cheaply.
  3. Horizontal sharding: Shard by shortURL prefix (a-z, A-Z) or consistent hashing. Each shard handles a subset of URLs.
  4. NoSQL migration: DynamoDB / Cassandra with shortURL as partition key. Native horizontal scaling, simpler than sharding MySQL.

ScalingAdvanced

The Access Pattern

URL shortener has a pure key-value access pattern: shortURL → longURL. No joins, no complex queries. This makes NoSQL a natural fit.

Option 1: MySQL Sharding

Shard by shortURL hash. Each shard handles 1/N of the keyspace. Challenge: resharding when adding nodes requires remapping keys. Solution: consistent hashing (see Chapter 5).

Option 2: DynamoDB / Cassandra

Use shortURL as partition key. Built-in horizontal scaling. DynamoDB: pay-per-request, auto-scaling. Cassandra: tunable consistency, excellent for high write throughput.

Interview insight: Mention that consistency requirements differ between reads and writes. For redirects (reads), eventual consistency is acceptable — a stale cache entry for a few seconds is fine. For URL creation (writes), you need strong consistency to prevent duplicate shortURLs.
