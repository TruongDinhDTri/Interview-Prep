Q1 What problem does consistent hashing solve? Core ▼

📋 Answer

The Rehashing Problem Naive hashing uses serverIndex = hash(key) % N. When N (server count) changes, most keys must be remapped to different servers, causing a cache miss storm.
The Solution Consistent hashing ensures that when a server is added or removed, only k/n keys on average need to be remapped (where k = total keys, n = number of servers). This is O(k/n) vs O(k) for naive hashing.
Why It Matters In a distributed cache with millions of keys, a naive server removal could force nearly all requests to bypass the cache and hit the database — potentially causing a cascading failure. Consistent hashing prevents this.

Q2 What happens with simple modular hashing when a server is added or removed? Core ▼

📋 Answer

Mathematical Root Cause With hash(key) % N, every key's server assignment depends on N. Changing N (adding/removing 1 server) causes the modular result to change for most keys.
Concrete Example With N=4: key3 → hash(key3) % 4 = 3 → server3
With N=3 (server removed): key3 → hash(key3) % 3 = 0 → server0 ← different server!
In practice, ~75% of keys may need to be remapped when going from 4→3 servers.
Real Impact All remapped keys become cache misses. The underlying database receives a sudden spike in traffic (thundering herd), potentially causing a system outage.
Q3 How does a consistent hash ring work? Core ▼

📋 Answer

The Ring Concept Take the SHA-1 hash space (0 to 2¹⁶⁰ - 1) and connect the two ends, forming a circular ring. Both servers and keys get hashed to positions on this ring.
Key Lookup Rule To find which server owns a key: start at the key's ring position and walk clockwise until you hit a server node. That server owns the key.
Why the Ring Is Stable Server and key positions are absolute on the ring (no modulus). Adding/removing a server only affects keys in the adjacent arc — everything else stays exactly where it was.
Q4 How are servers and keys mapped onto the ring? Core ▼

📋 Answer

Servers Each server is hashed using its IP address or hostname: position = hash(server_IP). This places the server at a specific point on the ring.
Keys Each key is hashed using the same hash function: position = hash(key). No modular operation — the result directly maps to a ring position.
serverIndex = hash(server_IP) [no % N]
Critical Difference Unlike naive hashing, there's no % N. This means the position is absolute and independent of the total server count. When N changes, existing positions don't change.
Q5 How do you determine which server stores a given key? Core ▼

📋 Answer

The Clockwise Walk Algorithm 1. Hash the key to find its position on the ring
2. Walk clockwise from that position
3. The first server node encountered owns the key
# Pseudocode for key lookup def find_server(key): key_pos = hash(key) # Walk clockwise through sorted server positions for server_pos in sorted_server_positions: if server_pos >= key_pos: return server_at(server_pos) # Wrap around: if no server found, use the first one return server_at(sorted_server_positions[0])
Implementation Note In practice, server positions are stored in a sorted structure (e.g., TreeMap in Java, sorted list with bisect in Python) for O(log n) lookup efficiency.
Q6 What happens when a server is added to the consistent hash ring? Operations ▼

📋 Answer

What Changes The new server S_new is hashed onto the ring. It takes ownership of all keys in the arc from S_new's predecessor (counterclockwise) up to S_new's position.
Example Before: key0 (pos 5) → s0 (pos 12)
After server4 added at pos 8: key0 (pos 5) → s4 (pos 8) ← now routes to new server
key1, key2, key3 remain unchanged.
Redistribution Cost Only ~1/n of all keys are redistributed (where n = new server count). With 5 servers, only ~20% of keys need to move.
Q7 What happens when a server is removed from the ring? Operations ▼

📋 Answer

What Changes Only the keys that were owned by the removed server need to move. They fall through to the next clockwise server.
Example s1 (pos 28) is removed. key1 (pos 15) previously routed to s1. Now key1 continues clockwise past pos 28 → hits s2 (pos 54). key1 is now stored on server2. No other keys are affected.
Graceful Degradation Even sudden server failure is handled cleanly: affected keys automatically reroute to the next server, giving remaining servers only slightly more load.
Q8 What are the two main issues with basic consistent hashing? Advanced ▼

📋 Answer

Problem 1: Unequal Partition Sizes Servers hash to random positions. With only a few servers, some may end up with huge arcs (owning most of the key space) while others have tiny arcs. One server might handle 60% of keys while another handles 5%.
Problem 2: Non-Uniform Key Distribution (Hotspots) Even with equal arc sizes, keys don't hash uniformly. Some servers may receive disproportionately more traffic. A viral piece of content (celebrity key) could overwhelm a single server.
Historical Note This was described by Karger et al. at MIT in 1997 in "Consistent Hashing and Random Trees." They also proposed virtual nodes as the solution.
Q9 What are virtual nodes and how do they solve the partition problem? Advanced ▼

📋 Answer

Definition Instead of each physical server occupying one position on the ring, each server gets multiple positions (virtual nodes or vnodes). Server s0 might appear as s0_0, s0_1, s0_2 at different ring positions.
How It Solves Partition Imbalance With many vnodes spread around the ring, each physical server's arc becomes the sum of many small arcs distributed throughout the ring. These small arcs average out, producing much more uniform distribution.
How It Solves Hotspots Popular keys that hash to a hotspot region are now spread across multiple physical servers (via their vnodes), distributing the load.
# Virtual node placement example s0_0 = hash("s0#0") → pos 5 s0_1 = hash("s0#1") → pos 42 s0_2 = hash("s0#2") → pos 78 # All 3 vnodes serve server0
Q10 What is the tradeoff with increasing the number of virtual nodes? Advanced ▼

📋 Answer

Benefits of More VNodes Better distribution uniformity. At 100 vnodes: ~10% std dev in key distribution. At 200 vnodes: ~5% std dev. Better hotspot prevention and more even load during scale events.
Costs of More VNodes More entries in the ring's sorted data structure → higher memory consumption. More metadata to store and replicate. Slightly slower lookups as the sorted structure grows.
Production Benchmarks Amazon Dynamo: 150 vnodes/physical node
Apache Cassandra: 256 vnodes/physical node (default)
The right number depends on cluster size and available memory per node.
Q11 How do you find the affected key range when adding or removing a server? Operations ▼

📋 Answer

The Counterclockwise Walk For both adding and removing, the technique is the same: from the new/removed server's position, walk counterclockwise until you reach another server node. The range between that predecessor and the target node is the affected key range.
Adding Server S_new Affected range: (predecessor_of_S_new, S_new]
Keys in this range move FROM their current server TO S_new.
Removing Server S_old Affected range: (predecessor_of_S_old, S_old]
Keys in this range move FROM S_old TO the next clockwise server after S_old.
Q12 Name real-world systems that use consistent hashing and explain how. Real World ▼

📋 Answer

Amazon Dynamo / DynamoDB Uses consistent hashing with virtual nodes (called "tokens") to partition data across nodes. Basis for the eventual-consistency model described in the Dynamo paper (2007).
Apache Cassandra Each node owns multiple token ranges. 256 vnodes per node by default. Gossip protocol propagates ring membership. Data is replicated to the next N-1 clockwise nodes.
Discord Routes WebSocket connections to gateway servers. Users in the same channel need to route to the same server for real-time consistency. Consistent hashing ensures graceful re-routing during server restarts.
Akamai CDN Routes HTTP requests to edge cache nodes. When a CDN node fails or is added, only the keys in its arc need cache invalidation — dramatically reducing cache churn.
Google Maglev Network load balancer that uses consistent hashing to route packets to backend servers. Minimizes connection disruption when backends are added or removed.
Q13 Compare consistent hashing vs modular hashing for key redistribution. Core ▼

📋 Answer

Metric Modular Hashing Consistent Hashing
Redistribution on change O(k) — almost all keys O(k/n) — only adjacent keys
Cache miss on removal Catastrophic (~75%+ miss) Minimal (~1/n miss)
Lookup time O(1) O(log n) with sorted structure
Horizontal scaling Requires full rebuild Online, incremental
Q14 What hash functions are commonly used in consistent hashing, and why SHA-1? Advanced ▼

📋 Answer

SHA-1 (Cited in the Book) Produces a 160-bit output (0 to 2¹⁶⁰ - 1). Cryptographically strong (though now broken for security use), excellent uniform distribution. The large space minimizes collision probability.
MD5 128-bit output. Widely used in early consistent hashing implementations (including Ketama, used in Memcached). No longer cryptographically secure but fine for distribution purposes.
MurmurHash / xxHash Non-cryptographic, extremely fast, excellent distribution. Preferred in modern systems (Cassandra, Redis Cluster) for performance. xxHash is ~10x faster than MD5.
Key Requirement The hash function must produce uniform distribution across the ring space. Non-uniform distribution defeats the purpose of consistent hashing.
Q15 How does consistent hashing enable horizontal scaling? Operations ▼

📋 Answer

Online Scaling Without Downtime Adding a new server is a live operation: hash it onto the ring, transfer only the affected key range from the adjacent server, and it's immediately available. No need to stop the cluster or do a full data migration.
Graceful Scale-Down Removing a server (planned or unplanned) only affects keys in its arc. Those keys automatically reroute to the next clockwise server. With virtual nodes, the lost server's keys are spread across multiple remaining servers rather than piling onto one.
Auto-Rebalancing In systems like Cassandra, adding a node with 256 vnodes automatically splits load with ~256 existing vnodes across the ring, achieving near-perfect rebalancing without manual partition assignment.
Q16 How does consistent hashing mitigate the hotspot / celebrity problem? Real World ▼

📋 Answer

The Hotspot Problem Without consistent hashing, a viral celebrity post (say, a tweet by Katy Perry) might hash to server3. Server3 receives 10x normal traffic and collapses. All other servers are idle.
How Virtual Nodes Help With many virtual nodes, what appears to be "server3's territory" is actually many small arcs spread across the ring. Very popular content still routes to a single physical server for any specific key — but the overall load from many popular keys is spread across multiple machines via their different vnode positions.
Complementary Strategies For extreme hotspots (e.g., a single key receiving millions of requests/sec), consistent hashing alone isn't enough. Common additions: adding random suffixes to keys to scatter reads across multiple cache nodes, or explicitly replicating hot keys to multiple servers.
