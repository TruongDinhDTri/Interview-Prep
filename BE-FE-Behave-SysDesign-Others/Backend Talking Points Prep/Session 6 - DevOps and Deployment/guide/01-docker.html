🏗️ Part 1: Dockerfile Anatomy — Every Line Explained

When they say "Walk me through your Dockerfile for a Django app. Why is each line in that order?" — here's the complete answer with every decision justified:

PRODUCTION DOCKERFILE — ANNOTATED
FROM python:3.12-slim
Use slim variant — strips non-essential packages. Smaller attack surface, faster pull. Never use python:3.12 (includes gcc, build tools, 800MB+) or :latest (non-reproducible builds).
CRITICAL
WORKDIR /app
Set working directory. All subsequent COPY/RUN commands are relative to this. Prevents accidental writes to / or other system paths.
GOOD PRACTICE
ENV PYTHONDONTWRITEBYTECODE=1
 PYTHONUNBUFFERED=1
PYTHONDONTWRITEBYTECODE: Don't write .pyc files — saves space, nothing needs them in containers.
PYTHONUNBUFFERED: Force stdout/stderr flush immediately — Docker captures logs; buffering = logs disappear if container crashes before flush.
CRITICAL
COPY requirements.txt .
Copy ONLY requirements.txt FIRST — before copying source code. This is the layer caching trick (see Part 2). If requirements.txt hasn't changed, Docker reuses the cached pip install layer. Code changes don't invalidate this layer.
CRITICAL
RUN pip install --no-cache-dir -r requirements.txt
--no-cache-dir: Don't store pip cache inside the image (we don't need to re-install in the container). Saves 50-200MB. Note: DO cache in CI; DON'T cache in Docker image itself.
CRITICAL
COPY . .
Copy source code AFTER pip install. This is why: if you COPY . . before pip install, every code change invalidates the dependency layer. Swapping the order = dependencies cache properly.
ORDER MATTERS
RUN python manage.py collectstatic --noinput
Collect static files into STATIC_ROOT at build time, not at runtime. Container startup is faster. For S3: often skip this and let CI upload to S3 directly.
DEPENDS
RUN useradd --create-home appuser
USER appuser
Don't run as root. If the app is compromised via a vulnerability, root inside container = easier container escape to host. Non-root user limits blast radius. Modern Docker security 101.
CRITICAL
EXPOSE 8000
Documentation ONLY. Does NOT actually publish the port. The -p flag (docker run) or ports: in compose actually publishes. EXPOSE tells other developers and tools "the app listens on 8000."
DOCS ONLY
CMD ["gunicorn", "config.wsgi", "--bind", "0.0.0.0:8000", "--workers", "3", "--max-requests", "1000", "--max-requests-jitter", "50"]
NEVER runserver. Gunicorn is multi-process, production-hardened. Bind to 0.0.0.0 (not 127.0.0.1 — that's localhost-only inside container). --max-requests recycles workers to bound memory growth from leaks.
CRITICAL
⚡ Part 2: Layer Caching — Why Order Matters

This is the most common Dockerfile mistake. The interviewer is explicitly testing if you understand this:

❌ WRONG — Cache busted every time

✅ FROM python:3.12-slim CACHE HIT
🔄 COPY . . CACHE MISS (code changed)
🔄 RUN pip install REBUILDS (even if reqs didn't change!)

Result: Every code change = full pip install = 3-5 minutes per build.

✅ RIGHT — Deps cached separately

✅ FROM python:3.12-slim CACHE HIT
✅ COPY requirements.txt . CACHE HIT (if reqs unchanged)
✅ RUN pip install CACHE HIT (deps cached!)
🔄 COPY . . CACHE MISS (code changed)

Result: Code changes = only COPY . . re-runs = 10 seconds per build.

The Rule: Docker invalidates a layer's cache when the instruction OR its inputs change. Since COPY . . copies all your source code, it misses the cache on every code change. Put it LAST — after everything that doesn't change often.
🏗️ Part 3: Multi-Stage Builds

Why: Python packages like psycopg2, cryptography, and Pillow have C extensions that require gcc and build tools to compile. You need them to BUILD but NOT in the final production image.

Without Multi-Stage

📦
~900 MB
Includes gcc, make, build-essential, header files — all the compilers. Larger image = slower pull, larger attack surface.

With Multi-Stage

🪶
~85 MB
Only compiled .so files, Python runtime, and your app code. No compilers. ~91% smaller.
# Stage 1: Builder — has all the build tools FROM python:3.12-slim AS builder RUN apt-get update && apt-get install -y \ gcc libpq-dev python3-dev \ && rm -rf /var/lib/apt/lists/* COPY requirements.txt . RUN pip install --no-cache-dir --prefix=/install -r requirements.txt # Stage 2: Runtime — lean and clean FROM python:3.12-slim AS runtime # Copy compiled packages FROM builder — no compilers come with them COPY --from=builder /install /usr/local WORKDIR /app COPY . . # Non-root user RUN useradd --create-home appuser USER appuser CMD ["gunicorn", "config.wsgi", "--bind", "0.0.0.0:8000"] # The final image has ZERO compilers, ZERO build tools — just the compiled output
🔢 Part 4: Docker Exit Codes — Memorize This Table

When asked "Your container exits immediately in production. How do you debug it?" — you need to know what the exit code means BEFORE you can fix it:

Exit Code Meaning How to Debug / Fix
0 Clean exit — process finished normally Check if CMD is a one-shot command (not a server). Add a long-running process.
1 Generic application error docker logs <container_id> — look for Python exception or config error
125 Docker daemon error Problem with Docker itself, not your app. Check Docker logs.
126 Command not executable CMD script exists but isn't executable. Run chmod +x entrypoint.sh
127 Command not found CMD references a binary not installed. Check PATH, check image has the binary.
137 SIGKILL — almost always OOMKilled docker inspect <id> | grep OOMKilled → if true: reduce workers, add --max-requests, increase memory limit.
139 Segfault (SIGSEGV) Usually a C extension bug (psycopg2 version mismatch, etc). Update/pin deps.
143 SIGTERM — graceful shutdown Normal: orchestrator sent shutdown signal. App should handle this and exit cleanly.
🔥 PRODUCTION SIGNAL LINE — Exit Code 137

"When the container died I checked docker inspect for "OOMKilled": true — turned out our Gunicorn worker count times per-worker memory exceeded the container's memory limit, so the kernel sent SIGKILL and we got exit 137. I dropped worker count from 5 to 3 and added --max-requests 1000 to recycle workers periodically, and the OOMs stopped."

🎛️ Part 5: CMD vs ENTRYPOINT

CMD — Default command

Provides default command + arguments. Can be completely overridden by arguments passed to docker run.

CMD ["gunicorn", "config.wsgi"] # User can override: docker run myimage python manage.py migrate # gunicorn is NOT run. migrate runs instead.

Use for: The main command of the container that you want to be replaceable (e.g., swap Gunicorn for a management command).

ENTRYPOINT — Fixed executable

The executable that always runs. Arguments to docker run are appended AS arguments to ENTRYPOINT, not replacing it.

ENTRYPOINT ["gunicorn"] CMD ["config.wsgi"] # default arg # User passes: docker run myimage myapp.wsgi # gunicorn myapp.wsgi (ENTRYPOINT + user arg)

Use for: Containers that always run the same executable (e.g., a CLI tool, a fixed server). CMD provides the default arguments.

In practice for Django: Most production Dockerfiles use only CMD. Using both is for when you want: always run gunicorn (ENTRYPOINT) but let the worker config be overridable (CMD). A common pattern is an entrypoint.sh script that does setup (wait for DB, run migrations) then exec "$@" to run whatever CMD provides.
🚫 Part 6: .dockerignore — The File Everyone Forgets

Forgetting .dockerignore is the #1 trap interviewers see. It causes: slow builds, bloated images, and potentially leaked secrets.

# .dockerignore — ALWAYS create this file # Virtual environments (huge — 200MB+) .venv/ venv/ env/ # Git history (large, not needed in image) .git/ .gitignore # Secrets (CRITICAL — don't bake these into the image) .env .env.local .env.*.local *.pem *.key # Python cache (useless in container) __pycache__/ *.pyc *.pyo .pytest_cache/ *.egg-info/ # IDE/OS junk .vscode/ .idea/ .DS_Store # Docs/tests (don't need in prod image) docs/ README.md
🚫 What happens without .dockerignore: The build context (everything sent to Docker daemon before building) includes .git/ (huge), __pycache__ (useless), .env (secrets!). Build context of 500MB+ makes every build slow. Worse: your .env file might end up in the image layers — anyone with pull access to your registry can extract it with docker history --no-trunc.
🎯 Part 7: All Interview Questions Answered
⭐ HIGH FREQUENCY
Q1: "Walk me through your Dockerfile for a Django app. Why is each line in that order?"
▼
❌ WEAK (3 red flags in one sentence)
"I use FROM python:3.11, then COPY . ., then RUN pip install -r requirements.txt, then CMD python manage.py runserver."

Red flags: full python:3.11 (800MB+), COPY . . before pip (cache busted every commit), runserver in CMD (dev only, single-threaded, disqualifier).
✅ SOLID ANSWER
1FROM python:3.12-slim — slim strips build tools. Full image = 800 MB+, slim = ~120 MB, multi-stage = ~85 MB. Never use :latest (non-reproducible).
2PYTHONDONTWRITEBYTECODE + PYTHONUNBUFFERED — no .pyc files + logs flush to stdout immediately. Without PYTHONUNBUFFERED, crash logs disappear before Docker captures them.
3COPY requirements.txt first → pip install → THEN COPY . . — deps layer only rebuilds when requirements.txt changes. Code edits alone = cached deps = builds in 10 seconds not 5 minutes.
4Non-root user: RUN useradd appuser + USER appuser — if app is exploited, attacker gets a locked-down user, not root inside the container.
5CMD = gunicorn, NEVER runserver — add --max-requests 1000 --max-requests-jitter 50 to recycle workers and prevent unbounded memory growth from leaks. runserver = instant disqualifier
⭐ HIGH FREQUENCY
Q2: "What's the difference between CMD and ENTRYPOINT? When would you use each?"
▼

CMD provides a default command that can be completely overridden at docker run time. ENTRYPOINT is the fixed executable — docker run arguments append to it rather than replacing it.

In practice for Django: Most setups use only CMD [gunicorn, ...]. Use ENTRYPOINT when you want the container to always run one specific executable — for example, an entrypoint.sh script that waits for the database, runs migrations, then exec's the CMD (whatever it is — could be gunicorn in prod, pytest in CI, a management command in a migration task).

Trap: Using ENTRYPOINT alone without CMD means you can't override the command easily. Using CMD alone is fine for most Django apps.
⭐ HIGH FREQUENCY
Q3: "How does Docker layer caching work, and how does it affect your COPY requirements.txt placement?"
▼
1Each Dockerfile instruction (FROM, RUN, COPY) creates a cached layer. Docker reuses a layer if the instruction AND its inputs haven't changed.
!Cache invalidation cascades down — when any layer misses, ALL layers below it also rebuild, even unchanged ones.
✓Correct order:
COPY requirements.txt . → RUN pip install → COPY . .
Code changes only bust the final COPY . . layer. Dependencies stay cached → 10-second builds instead of 5 minutes.
⭐ HIGH FREQUENCY
Q4: "Your container exits immediately in production. How do you debug it?"
▼
1Check exit code: docker ps -a → STATUS column shows the code. 137 = OOMKilled 1 = app error 0 = clean exit
2Read logs first: docker logs <container_id> — most crashes print the Python traceback before dying.
3If exit 137: docker inspect <id> | grep OOMKilled → "OOMKilled": true → kernel killed it for exceeding memory limit. Fix: reduce Gunicorn workers + add --max-requests 1000.
4If exit 1: startup crash — missing env vars, DB connection failure, or import error. Check logs for traceback.
5If exit 0: CMD was a one-shot command that finished. Your server process must be a long-running foreground process.
6Debug interactively: docker run -it --entrypoint /bin/bash myimage — drop into the container to investigate manually.
⭐ HIGH FREQUENCY
Q5: "What's a multi-stage build and why would you use one for a Python app?"
▼

"Multi-stage builds use multiple FROM statements in one Dockerfile. Each stage can be named and you can copy artifacts between them. The final image only contains what you explicitly copy into it — earlier stages are discarded."

"For Python: packages like psycopg2, cryptography, Pillow need gcc and C headers to compile their C extensions. In a single-stage build, you install gcc, compile the packages, but gcc remains in the final image — it's large (200MB+) and a security risk. With multi-stage: Stage 1 (builder) has gcc and compiles everything. Stage 2 (runtime) starts fresh from python:3.12-slim and only receives the compiled .so files via COPY --from=builder. The final image has zero compilers. Typical result: 920 MB → 85 MB."

NICE TO KNOW
Q6: "Your container died with exit code 137. What does that mean? How do you fix it?"
▼

"Exit code 137 = SIGKILL from the OS. In a container context this almost always means OOMKilled — the process exceeded the container's memory limit and the Linux kernel killed it."

Debug: docker inspect <container_id> → look for "OOMKilled": true in the State section.

Fix options:

  1. Reduce Gunicorn worker count (each worker = ~50-100MB for Django)
  2. Add --max-requests 1000 to Gunicorn — recycles workers after N requests, preventing unbounded memory growth from leaks
  3. Add --max-requests-jitter 50 — randomizes restart time to prevent all workers restarting simultaneously
  4. Increase container memory limit if workers are legitimately needed
  5. Profile memory with memory-profiler or py-spy to find the actual leak
NICE TO KNOW
Q7: "What does docker-compose give you over plain docker run, and what are its limits in production?"
▼

What it gives you: Define multi-container apps in YAML. All services start with one command. Automatic networking (services can reach each other by name). Volume management. Environment variable handling. Health checks.

Limits in production:

  • Single-host only — no distribution across multiple machines
  • No rolling updates — updating a service means downtime (stop old, start new)
  • No health-driven scheduling — if a container dies on one host, nothing moves it to another
  • No built-in secrets management
  • No built-in service discovery across hosts

Bottom line: docker-compose is excellent for local dev and tiny single-host deployments. For real production with multiple instances, rolling deploys, and HA: use ECS, Kubernetes, Nomad, or at minimum a single-host scheduler.
