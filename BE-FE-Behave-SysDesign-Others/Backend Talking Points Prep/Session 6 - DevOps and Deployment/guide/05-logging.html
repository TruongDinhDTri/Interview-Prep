🔭 Part 1: The Three Pillars — Logs, Metrics, Traces

Gate distinction: Interviewers explicitly ask this to see if you conflate them. Each answers a different question:

📝

LOGS

What happened?

Discrete events with context. "Payment failed for order 1234, user 567, gateway Stripe, error card_declined."

Tool: structlog, python-json-logger, CloudWatch, Loki, ELK

📈

METRICS

How much / how fast?

Aggregated numbers over time. "P95 latency = 230ms. Error rate = 0.3%. 5xx/min = 12."

Tool: Prometheus, Datadog, CloudWatch Metrics

🔍

TRACES

Why was it slow / where did it fail?

Follow one request across all services. "This request took 1.2s because the downstream payment service took 800ms."

Tool: Jaeger, Zipkin, Datadog APM, Sentry Performance

📋 Part 2: Structured Logging — Why JSON Over Plain Text

❌ Plain Text — Ungreppable

[2026-05-21 14:22:01] ERROR Payment failed for order 12345

To find all Stripe failures in the last hour, you'd grep through gigabytes of raw text. You can't filter by user_id. You can't build a dashboard. You can't alert on error rate by gateway.

✅ Structured JSON — Queryable

{ "ts": "2026-05-21T14:22:01Z", "level": "error", "event": "payment_failed", "order_id": 12345, "user_id": 678, "request_id": "abc-123", "amount": 42.99, "gateway": "stripe", "error_code": "card_declined" }

CloudWatch Insights query: filter event="payment_failed" and gateway="stripe". Build a dashboard. Alert when count > 50/min. Trace all events for user 678 using request_id.

# Django structured logging with structlog import structlog log = structlog.get_logger() def process_payment(order): log.info( "payment_initiated", order_id=order.id, user_id=order.user_id, amount=order.total, gateway=order.payment_gateway, ) try: result = charge(order) log.info("payment_success", order_id=order.id, charge_id=result.id) except PaymentError as e: log.error( "payment_failed", order_id=order.id, error_code=e.code, gateway=order.payment_gateway, exc_info=True, )
🔬 Part 3: Sentry Integration — Production-Sensible Config
# settings.py — the configuration that signals production experience import sentry_sdk from sentry_sdk.integrations.django import DjangoIntegration from sentry_sdk.integrations.celery import CeleryIntegration sentry_sdk.init( dsn=env("SENTRY_DSN"), integrations=[DjangoIntegration(), CeleryIntegration()], # CRITICAL: ties every error to a specific deploy environment=env("ENV"), # 'production' or 'staging' release=env("GIT_SHA"), # e.g. 'abc123def' — the deployed commit # Don't send 100% of transactions — quota burn + noisy traces_sample_rate=0.1, # 10% performance traces profiles_sample_rate=0.1, # GDPR — be explicit about PII send_default_pii=False, # Don't auto-send emails, IPs before_send=scrub_sensitive_data, # Custom scrubber for tokens/keys )
💡 The Highest-Leverage Setting: release=env("GIT_SHA"). Without it, Sentry tells you "this error is happening" but not when it started. With it, every Sentry issue shows "first seen in release abc123" — you can immediately look at that commit's diff to find the cause.
🚫 Most common Sentry mistake: traces_sample_rate=1.0 in production. Sends every single request as a transaction. Burns through quota in days (or hours for high-traffic apps). Start at 0.05-0.1, increase if you need more coverage.
🎯 Part 4: All Interview Questions Answered
⭐ HIGH FREQUENCY
Q1: "Production has a bug a user is reporting but you can't reproduce locally. Walk me through how you debug it."
▼
❌ WEAK
"I check the logs and try to reproduce locally."

Doesn't show tooling fluency. Doesn't mention Sentry, breadcrumbs, release correlation, structured log querying, trace IDs.
✅ SOLID — SYSTEMATIC APPROACH
1
Check Sentry first — groups duplicate exceptions, shows first/last seen, which release it appeared in, affected users, and breadcrumbs (SQL queries, HTTP requests, log statements leading up to the crash).
2
Release correlation — if it started after a specific deploy, that's usually the commit. Diff that SHA immediately.
3
Query structured logs — CloudWatch/Loki: filter by user_id + request_id to trace the full request timeline. NOT grep raw text
4
Distributed trace — pull trace ID from the Sentry event → see the full request path across services.
5
Last resort — replicate prod state in staging with a redacted DB dump. Never try to reproduce locally with incomplete state.
⚡ Production Signal Line
"After we shipped release abc123 we got a Sentry alert spike — the release tag immediately told me which commit, the breadcrumbs showed every failing request had the same feature flag enabled, and the trace pointed at an N+1 in a prefetch_related we missed. We flipped the flag off in seconds, rolled the deploy back in minutes, and shipped the fix the next day. We also dropped traces_sample_rate from 1.0 to 0.1 because we were burning Sentry quota on /health and /metrics."
⭐ HIGH FREQUENCY
Q2: "How is Sentry different from regular logging?"
▼
LoggingAppends events to a stream. Query after the fact. Good for "what happened at 3pm?" no grouping No release correlation. No breadcrumbs. No user impact count.
SentryGroups duplicate exceptions as one issue. Correlates to specific release (GIT_SHA). breadcrumbs trail of SQL/HTTP/logs before crash. User impact count. Alerts on spikes. Links to exact source line.
Bottom line: Logs tell you what happened. Sentry tells you what broke, when it started, who it affected, and which deploy introduced it.
⭐ HIGH FREQUENCY
Q3: "What's structured logging? Why would you use JSON logs over plain text?"
▼
def
Structured logging emits key-value pairs (typically JSON) instead of free-form strings. {event: login_failure, user_id: 123, ip: "...", ts: "..."} instead of plain text "User 123 failed to login from IP..."
Q
Queryable — CloudWatch Insights: filter event="login_failure" | stats count by ip. Can't do that with a raw text string.
D
Dashboard-able — Datadog aggregates and graphs any field. Alert when count(payment_failed) > 100/5min.
T
Traceable — bind request_id to every log in a request. Find every log entry across all services for one user's request in seconds.
⭐ HIGH FREQUENCY
Q4: "How would you investigate a sudden spike in 5xx errors?"
▼
1
Check Sentry — did a new error type appear? Which release? Grouped? release correlation
2
Check metrics dashboard — when exactly did it start? All endpoints or one specific? DB query time up? Upstream service down?
3
Check recent deploys — did a deploy happen in the 30 minutes before the spike? most common cause
4
Query structured logs — filter status=500, group by endpoint, look for patterns.
5
Check infra — DB CPU, connections, memory, disk, Redis connections.
!
If deploy-related → rollback immediately (re-deploy previous SHA). Investigate root cause after service is stable. stability first
NICE TO KNOW
Q5: "What's the difference between logs, metrics, and traces? (RED and USE methods?)"
▼
LogsWhat happened? Discrete events with context. Queryable with structured JSON.
MetricsHow much / how fast? Aggregated numbers over time. P95 latency, error rate, 5xx/min.
TracesWhy was it slow / where did it fail? Follow one request across all services. Pinpoints the slow downstream call.
RED
For services: Rate (req/s) · Errors (failing %) · Duration (P50/P95/P99) — is my API healthy for users?
USE
For resources: Utilization (capacity %) · Saturation (queue depth) · Errors — is my DB maxed out?
