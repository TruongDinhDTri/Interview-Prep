Django Security Settings

Full production checklist with WHY each setting matters. DEBUG dangers, ALLOWED_HOSTS, HSTS ramping, CSRF/SQLi. The settings that separate junior from production-ready.

📋 Part 1: Production Settings Checklist — With Every "Why"

When asked "What changes do you make to settings.py before going to production?" — weak answer: "DEBUG=False and ALLOWED_HOSTS." Solid answer: all of these, each with a specific attack vector it prevents.

DEBUG = FalseCRITICAL
Real danger: DEBUG=True renders a yellow error page on ANY unhandled exception that shows: the entire settings module (minus SECRET|PASS|TOKEN patterns), all SQL queries run, local variables in every stack frame, installed apps list. It's a complete blueprint of your backend architecture for any attacker who can trigger a 500.
ALLOWED_HOSTS = ['api.example.com']CRITICAL
Real danger: ALLOWED_HOSTS=['*'] disables Django's Host header validation. An attacker can send a forged Host header — Django might use it to construct absolute URLs (password reset links, email verification links), redirecting users to an attacker-controlled domain. Never use *.
SECRET_KEY = env('SECRET_KEY')CRITICAL
If compromised: attackers can forge session cookies (login as any user), manipulate signed data (CSRF tokens, signed cookies, password reset tokens). Never hardcode. Rotate if leaked.
SECURE_SSL_REDIRECT = TrueHIGH
Redirect all HTTP to HTTPS. Without it, users can access your site over unencrypted HTTP — credentials and session cookies are visible in plaintext on the network. Trap: If behind Cloudflare/ALB that already redirects, set to False to avoid double-redirect loop.
SESSION_COOKIE_SECURE = TrueHIGH
Prevents session cookie from being sent over HTTP. Without this, a browser on HTTP (accidental or attacker-induced) sends the session cookie in plaintext — trivial session hijacking on public WiFi.
CSRF_COOKIE_SECURE = TrueHIGH
Same as SESSION_COOKIE_SECURE but for the CSRF token. Without it, CSRF protection can be undermined on mixed HTTP/HTTPS connections.
SECURE_HSTS_SECONDS = 300 (→ 31536000)HIGH
Tells browsers "always use HTTPS for this domain for N seconds." RAMP IT UP: Start at 300 (5 min). Then 86400 (1 day). Then 31536000 (1 year). HSTS is sticky — once a browser caches it, users can't reach your site over HTTP for the full duration. Wrong rollout = users locked out.
SECURE_HSTS_INCLUDE_SUBDOMAINS = TrueMEDIUM
Apply HSTS to all subdomains. Important if you have staging.example.com on HTTP — without this, HSTS only protects the apex domain.
X_FRAME_OPTIONS = 'DENY'MEDIUM
Prevents your site from being loaded in iframes. Protects against clickjacking — attacker embeds your site invisibly in their page, tricks users into clicking on invisible elements.
SECURE_CONTENT_TYPE_NOSNIFF = TrueMEDIUM
Sets X-Content-Type-Options: nosniff header. Prevents browsers from MIME-sniffing — guessing file type from content. Blocks a class of XSS attacks where attacker uploads a file that gets executed as HTML/JS.
SECURE_PROXY_SSL_HEADERHIGH (when behind LB)
Only set if behind a load balancer that terminates TLS. Set to ('HTTP_X_FORWARDED_PROTO', 'https') so Django knows the original request was HTTPS (even though it received HTTP from the LB). TRAP: Only set this if your LB strips the header from client requests first — otherwise attackers can forge X-Forwarded-Proto: https themselves.

⚡ The One Command That Catches Everything

python manage.py check --deploy # Django's built-in production readiness checker. # Run this in CI. If it fails, fail the build. # It validates every setting above and reports what's missing. # Example output: System check identified 3 issues: WARNINGS: ?: (security.W004) DEBUG is True ?: (security.W008) ALLOWED_HOSTS is not set ?: (security.W012) SESSION_COOKIE_SECURE is False

Add this as a required CI job. It catches DEBUG=True slipping into a prod build. Without it, a developer who sets DEBUG=True locally for debugging could accidentally deploy it.

⭐ HIGH FREQUENCY
Q3: "What does ALLOWED_HOSTS do? Why is ALLOWED_HOSTS=['*'] bad?"
▼
def
ALLOWED_HOSTS validates the Host header on every incoming request. Django rejects requests with Host values not in the list.
*
Why ['*'] is dangerous: Django uses the Host header to construct absolute URLs — password reset emails, verification links, API redirects. Attacker forges Host: attacker.com, triggers a password reset → email contains link to attacker.com → attacker captures the reset token.
trap
common trap Setting ['*'] to bypass a 400 Bad Request during initial deployment. Right fix: put your actual domain names in the list. The * is a shortcut that leaves a real vulnerability.
⭐ HIGH FREQUENCY
Q4: "How does Django protect against CSRF? Where could that protection fail?"
▼
how
Token in request body (or X-CSRFToken header) must match a token stored in the session cookie. A malicious site can't read the victim's cookies (same-origin policy) → can't forge the token.
1
fail vector @csrf_exempt on a state-changing endpoint — developer slaps it on because AJAX isn't working. Now any site can POST to that endpoint using the victim's cookies.
2
fail vector CSRF_COOKIE_SECURE=False on HTTPS — cookie transmitted over HTTP → downgrade attack possible.
3
fail vector SameSite=None on session cookie — allows cross-site requests to carry the cookie.
4
fail vector XSS vulnerability — if attacker runs JS on your domain, they can read the CSRF cookie and forge requests. CSRF + XSS = full bypass.
⭐ HIGH FREQUENCY
Q5: "How does Django prevent SQL injection? Where can a developer break it?"
▼
ORM
Django ORM auto-parameterizes all queries — user input is always a separate parameter, never interpolated into the SQL string. DB receives template + values separately.
# Django ORM — SAFE (parameterized automatically) User.objects.filter(username=user_input) # → SQL: SELECT * FROM users WHERE username = %s, [user_input] # ❌ DANGEROUS — breaking the ORM's protection User.objects.raw(f"SELECT * FROM users WHERE username = '{user_input}'") # → user_input = "' OR '1'='1" → returns all users # ❌ DANGEROUS — .extra() with string formatting User.objects.extra(where=[f"name = '{user_input}'"]) # ✅ SAFE — .raw() with parameterization User.objects.raw("SELECT * FROM users WHERE username = %s", [user_input])
!
breaks it .raw(f"... WHERE username = '{user_input}'") — direct string interpolation. user_input = "' OR '1'='1" returns all users.
!
breaks it .extra(where=[f"name = '{user_input}'"]) — same issue with .extra().
✓
safe .raw("SELECT ... WHERE username = %s", [user_input]) — parameterized even in raw SQL. Rule: never f-strings or .format() to build SQL.

The rule: Never use Python string formatting (f-strings, % formatting, .format()) to build SQL. If you must use raw SQL or .extra(), always use parameterized queries with a separate values list.
