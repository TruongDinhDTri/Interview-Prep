1. Docker in Production 🐳

🎯

HIGH FREQ Questions:

  • "Walk me through your Dockerfile for a Django app. Why is each line in that order?"
  • "How does Docker layer caching work, and how does it affect your COPY requirements.txt placement?"
  • "Your container exits immediately in production. How do you debug it?"
  • "What's a multi-stage build and why would you use one for a Python app?"
  • "What's the difference between CMD and ENTRYPOINT?"

NICE TO KNOW:

  • "Your container died with exit code 137. What does that mean? How do you fix it?"
  • "Why should you not run as root inside a container?"
  • "What does docker-compose give you over plain docker run, and what are its limits in production?"
  • "What's the difference between a volume and a bind mount?"

Weak vs Solid — "Walk me through your Dockerfile"

❌

Weak (tutorial-grad):

"I use FROM python:3.11, then COPY . ., then pip install, then CMD python manage.py runserver."

Three red flags in one sentence: full image (huge), COPY . . before install (cache-busts on every code change), runserver (dev only, never production).

✅

Solid — Production Dockerfile:

  • 1Use FROM python:3.12-slim — not the full image. Full = 920 MB, slim = ~85 MB with multi-stage.
  • 2Set PYTHONDONTWRITEBYTECODE=1 + PYTHONUNBUFFERED=1 — logs flush to stdout immediately, no buffering surprises in prod.
  • 3Copy requirements.txt FIRST, then pip install, THEN copy source — dependency layer only re-runs when requirements change. Code change alone = cached deps = fast builds.
  • 4Create a non-root user + USER appuser — attacker exploiting the app gets a locked-down user, not root inside the container.
  • 5CMD = gunicorn --bind 0.0.0.0:8000 --workers 3 NEVER runserver — add --max-requests 1000 --max-requests-jitter 50 to recycle workers and prevent unbounded memory growth.

Dockerfile Anatomy — The Production Pattern

# ── STAGE 1: Builder (has gcc for compiled deps) ─────────────
FROM python:3.12-slim AS builder
WORKDIR /app
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt

# ── STAGE 2: Runtime (no gcc, no build tools) ────────────────
FROM python:3.12-slim
WORKDIR /app
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1 PATH=/home/appuser/.local/bin:$PATH

COPY --from=builder /root/.local /root/.local
COPY . .

RUN python manage.py collectstatic --noinput
RUN useradd --create-home --shell /bin/bash appuser
USER appuser

# --max-requests recycles workers → bounds memory growth from leaks
CMD ["gunicorn", "config.wsgi", "--bind", "0.0.0.0:8000",
     "--workers", "3", "--max-requests", "1000", "--max-requests-jitter", "50"]

🪤

Common Traps:

  1. COPY . . before pip install — every code change invalidates the dependency cache. Layer ordering exists; use it.
  2. runserver in CMD — instant disqualifier. Gunicorn (WSGI) or Uvicorn (ASGI) only.
  3. Running as root — if attacker exploits the app, they get root inside container → container escape vector.
  4. :latest tag in FROM or deploy scripts — non-reproducible. Pin to digest or semantic version.
  5. No .dockerignore — .git/, __pycache__/, .env end up baked into image layers pushed to registry.
  6. Not knowing exit codes — especially 137 = OOMKilled. "I just restart the container" is a fail.
  7. Confusing EXPOSE with publishing — EXPOSE is documentation only. -p 8000:8000 actually publishes.
  8. docker-compose in production — fine for local dev, not an orchestrator. No rolling updates, no health-driven scheduling, no built-in secrets.
⚡

Production Signal — Drop This Line:

"When the container died I ran docker inspect <id> and saw "OOMKilled": true — our Gunicorn worker count times per-worker memory was exceeding the container memory limit, so the kernel sent SIGKILL and we got exit 137. I dropped workers from 5 to 3 and added --max-requests 1000 to recycle workers periodically so memory doesn't grow unbounded. The OOMs stopped."

2. CI/CD Pipelines 🔁

🎯

HIGH FREQ Questions:

  • "What's the difference between Continuous Integration, Continuous Delivery, and Continuous Deployment?" (gate question — if you say "they're the same thing" the interview is usually over)
  • "Walk me through a GitHub Actions workflow for a Django project."
  • "What happens when a test fails in your pipeline? What gets blocked?"
  • "How do you handle secrets in CI?"
  • "Tell me about a time a deployment failed. What did you do?"

NICE TO KNOW:

  • "How do you handle flaky tests in CI?"
  • "What is a deployment artifact and where do you store it?"
  • "How would you roll back a bad deploy?"
  • "Why is OIDC preferable to long-lived AWS keys for CI?"

Weak vs Solid — The Three-Way Distinction

❌

Weak:

"CI/CD means automated testing and deployment. They go together."

That tells the interviewer you've heard the buzzword but can't separate the three concepts. This is a filter question almost every senior interviewer uses.

✅

Solid — Three distinct things:

CI Merge frequently into main with automated build + test on every push. Goal: keep the trunk green always.
Delivery Every passing build produces a deployable artifact that could go to prod. Human gates the release — one button press, but a human still decides when.
Deployment Every green build on main automatically ships to production. No human gate. Requires: strong test suite + feature flags + observability to detect regressions fast.

Weak vs Solid — "What happens when tests fail?"

❌

Weak:

"The pipeline goes red and I look at the logs."

✅

Solid — What exactly breaks the pipeline:

  • 1Failed test short-circuits the job — needs: [test] on the deploy job means it never starts. The DAG blocks downstream.
  • 2PR gets a red check → blocked from merging to main via required status checks. No bypass without admin override.
  • 3Flaky tests: quarantine + ticket — never auto-retry. Auto-retry masks real bugs and destroys signal.
  • 4Docker image (tagged with Git SHA) only pushes to ECR if every stage passes — which means rollback = re-deploy previous SHA, seconds not minutes.

# .github/workflows/ci.yml — production-grade Django pipeline
name: CI Pipeline

on: push: branches: [main]
    pull_request: branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:15
        env:
          POSTGRES_PASSWORD: postgres
          POSTGRES_DB: testdb
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with: {python-version: '3.12'}

      # Cache deps on lockfile hash — skips re-install if unchanged
      - uses: actions/cache@v3
        with:
          path: ~/.cache/pip
          key: ${{ runner.os }}-pip-${{ hashFiles('requirements*.txt') }}

      - run: pip install -r requirements.txt

      - run: ruff check . && black --check .          # lint
      - run: pytest --reuse-db -x                     # test vs real Postgres
      - run: python manage.py check --deploy          # security audit
      - run: python manage.py makemigrations --check --dry-run  # fail if migration missing

  build-and-push:
    needs: [test]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build & tag with Git SHA
        run: |
          IMAGE="$ECR_REGISTRY/myapp:${{ github.sha }}"
          docker build -t $IMAGE .
          docker push $IMAGE         # SHA tag = rollback in seconds
🪤

Common Traps:

  1. Saying CI/CD is one thing — interviewers want to hear all three separated.
  2. Auto-retrying flaky tests — hides bugs. Quarantine + investigate.
  3. Secrets in workflow YAML — must use GitHub Actions Secrets. Never paste an AWS key in a .yml.
  4. Building image per environment — build once, tag with SHA, promote across envs. "Works in staging, breaks in prod" is a build-per-env symptom.
  5. No rollback story — if you can't say "we redeploy the previous SHA's image," you don't sound like you've shipped.
  6. CI as tests-only — production CI also runs check --deploy, makemigrations --check --dry-run, ruff, mypy, pip-audit, bandit, gitleaks.
  7. Testing on SQLite instead of Postgres — SQLite handles JSON fields, concurrent transactions, and date functions differently. Test divergence guarantees eventual production bugs.
⚡

Production Signal — Drop This Line:

"Our pipeline tags every image with the Git SHA and pushes to ECR, so rollback is re-deploying the previous tag — never 'git revert and rebuild.' I also added python manage.py makemigrations --check --dry-run as a required CI job so the build fails if someone forgets to commit a migration file. We got bitten once — model changed but the migration didn't make the commit, and prod blew up on startup."

3. Database Migrations 🧬

⚠️

This is the topic where mid-level candidates routinely fail and production experience is hardest to fake. If you've never broken a production database, you can be exposed with one follow-up question.

🎯

HIGH FREQ Questions:

  • "Walk me through how you'd add a new non-nullable column to a 50-million-row table in production."
  • "What's the difference between a schema migration and a data migration?"
  • "Have you ever had a migration cause downtime? Walk me through it."
  • "What's your pre-migration checklist before running migrate in production?"
  • "What does python manage.py sqlmigrate <app> <num> give you?"

NICE TO KNOW:

  • "What's the expand-contract pattern?"
  • "How do you roll back a migration that included a RunPython?"
  • "Why can RunPython lock a table for the entire migration?"
  • "What's SeparateDatabaseAndState and when would you reach for it?"
  • "Why is db_default preferred over default for new not-null columns?"

Weak vs Solid — Adding a non-nullable column to a 50M-row table

❌

Weak:

"I add the field, run makemigrations, and run migrate on production."

This answer ends the interview at any production-serious shop. PostgreSQL's ALTER TABLE … ADD COLUMN … NOT NULL acquires an ACCESS EXCLUSIVE lock — no reads, no writes, until the column is added and every row is backfilled. On 50M rows: many minutes of downtime.

✅

Solid — Expand-Contract in 3 Deploys:

  • 1Deploy 1 — Expand Add column as null=True — metadata-only in Postgres 11+, milliseconds, zero ACCESS EXCLUSIVE lock. Old code ignores it.
  • 2Deploy 2 — Backfill Management command, 5,000 rows per chunk, each chunk its own transaction. NEVER a single UPDATE over 50M rows. NEVER inside the migration file itself (Django wraps migrations in a transaction → holds locks the entire backfill duration).
  • 3Deploy 3 — Contract ADD CONSTRAINT … NOT VALID skips full-table scan. Then VALIDATE CONSTRAINT — only takes SHARE UPDATE EXCLUSIVE lock, allows concurrent reads/writes. Column is now effectively NOT NULL.

# Expand-Contract Pattern — Visual

──── Deploy 1: Add nullable (instant, zero lock) ────────────
class Migration(migrations.Migration):
    operations = [
        migrations.AddField(
            model_name='order',
            name='new_status',
            field=models.CharField(max_length=20, null=True),
        ),
    ]

──── Deploy 2: Backfill in chunks (management command) ───────
def handle(self, *args, **options):
    qs = Order.objects.filter(new_status__isnull=True)
    total = qs.count()
    for i in range(0, total, 5000):
        chunk = qs[i:i+5000].values_list('id', flat=True)
        Order.objects.filter(id__in=list(chunk)).update(
            new_status=F('old_status')
        )  # each chunk its own transaction — no mega-lock

──── Deploy 3: Constrain (SHARE UPDATE EXCLUSIVE lock only) ──
migrations.RunSQL(
    "ALTER TABLE orders ADD CONSTRAINT chk_new_status_notnull "
    "CHECK (new_status IS NOT NULL) NOT VALID;",
    reverse_sql="ALTER TABLE orders DROP CONSTRAINT chk_new_status_notnull;"
)
migrations.RunSQL("ALTER TABLE orders VALIDATE CONSTRAINT chk_new_status_notnull;")

Pre-Migration Checklist — Memorize This

1
python manage.py sqlmigrate <app> <num> — eyeball the actual SQL before it runs. Look for ALTER TABLE, CREATE INDEX without CONCURRENTLY, any full-table rewrites.
2
makemigrations --check --dry-run — fail CI if a model changed without a migration committed.
3
Run on staging with a prod-data dump — time it. If it takes 45 seconds on staging's 10M rows, it takes 9 minutes on prod's 100M rows.
4
Snapshot the prod database — confirm point-in-time recovery is enabled. Know the rollback command before you run forward.
5
Check reversibility — every RunPython has a reverse function (even if migrations.RunPython.noop). Irreversible migration = no rollback.
6
Ordering — additive changes (new nullable column, new table) run before new code deploys. Destructive changes (drop column) run after old code is fully replaced.
7
Have rollback ready — python manage.py migrate <app> <previous_migration_name>. Know the command before the incident, not during it.
🪤

Common Traps:

  1. Combining schema change + data backfill in the same migration — table lock held for the entire backfill duration.
  2. RunPython importing models directly — historical models change shape; always use apps.get_model("app", "Model").
  3. makemigrations not committed — model change ships, migration doesn't. Prod blows up on startup with ProgrammingError.
  4. RunPython without a reverse function — you've made the migration irreversible. Always pass migrations.RunPython.noop if nothing to do.
  5. Renaming a column in one deploy — old workers running old code reference the old name → crash. Two-phase: add new, dual-write, deprecate old. Or use db_column='old_name' and rename only the Python attribute.
  6. Deleting a model in one deploy — same in reverse. Stop using it in code first, then drop in a later migration.
  7. Adding a standard index on a large table — CREATE INDEX takes a write lock. Use AddIndexConcurrently + atomic = False on the migration class.
⚡

Production Signal — Drop This Line:

"I once shipped a migration that combined a RunPython backfill with an AlterField to NOT NULL in the same file. Django wraps each migration in a transaction, so the ACCESS EXCLUSIVE lock queued behind the backfill and froze writes on the orders table for ~45 minutes during business hours. Postmortem: we now split every non-trivial schema change into add-nullable → backfill in 5,000-row chunks via a management command → NOT VALID constraint then VALIDATE. We also added a 5-second statement-timeout to the deploy migration runner so a runaway lock kills itself instead of blocking traffic indefinitely."

4. Secrets & Environment Variables 🔐

🎯

HIGH FREQ Questions:

  • "Where do you store your SECRET_KEY and database credentials?"
  • "What's the difference between a .env file, platform environment variables, and a secrets manager?"
  • "What do you do if you accidentally commit an AWS access key?"
  • "How do you give your CI pipeline access to AWS without storing long-lived keys?"

NICE TO KNOW:

  • "Walk me through AWS Secrets Manager vs HashiCorp Vault. When would you pick which?"
  • "Why is git rm insufficient to remove a leaked secret?"
  • "What's GitHub push protection and how can it fail?"

Weak vs Solid — "Where do you keep secrets?"

❌

Weak answers:

"I put them in settings.py and add it to .gitignore."

"I have a .env file in the repo so the team can use it."

Both are immediate disqualifiers. The second means secrets live in git history — which is effectively forever. Comparitech's honeypot study: attackers find and start abusing an exposed AWS key in under one minute.

✅

Solid — Three-Layer Architecture:

Local .env in .gitignore + committed .env.example (names, no values). Loaded via django-environ. Template in git, secrets never in git.
CI GitHub Actions Secrets → injected as env vars at job runtime. Never echoed in logs. Only the workflow can read them, not PRs from forks.
Prod AWS Secrets Manager — app's IAM role grants secretsmanager:GetSecretValue on only its own secret. Fetched at container startup. For CI→AWS: OIDC federation — GitHub Actions presents short-lived OIDC token → assumes role → temp STS creds. Zero long-lived AWS keys anywhere.
CI→AWS auth flow: GitHub OIDC token → assume IAM role → temp STS creds → push to ECR

8 Ways Secrets Actually Leak — Know All of These

1
Committed .env — most common. GitHub push protection catches it now, but git push --no-verify bypasses it.
2
Hardcoded in source "just to test" — then committed in a rush and forgotten.
3
In Docker images — ENV AWS_SECRET_KEY=… in a Dockerfile, image pushed to a public registry. Anyone who pulls it can extract the layer.
4
In CI logs — secret accidentally echoed in a script. GitHub Actions masks known secrets but not derivatives (e.g., base64-encoded versions).
5
In error pages — DEBUG=True in production exposes settings, env vars, traceback locals on every unhandled exception.
6
In Sentry / log aggregation — request bodies and tracebacks captured by error tracking can include passwords, tokens. Configure scrubbing with before_send.
7
In screenshots / Slack / Jira — non-trivial fraction of real leaks happen here. Someone pastes a curl command with a header.
8
Force-pushed git history — GitHub retains "oops commits." Researchers have built scrapers for them. Treat any exposed key as compromised immediately.
🪤

Common Traps:

  1. Thinking git rm deletes from history — it doesn't. Only git filter-repo rewrites history, and even then the remote may have cached it. Rotate immediately, always.
  2. Not knowing the rotation playbook — for an AWS key: revoke in IAM, audit CloudTrail for everything that principal touched, rotate dependent services. AWS auto-applies AWSCompromisedKeyQuarantine policy on detected-leaked keys.
  3. One giant secrets blob — every service sharing the same secret means blast radius is everything. Per-service IAM roles + per-service secrets.
  4. Never rotating — secrets without rotation policy become forever-credentials.
  5. Storing secrets in env vars on a shared host — visible to any process via /proc/<pid>/environ on Linux. Secrets Manager + fetch-at-startup is better for high-sensitivity values.
⚡

Production Signal — Drop This Line:

"We had an AWS access key end up in a commit — GitHub push protection caught it, but a teammate had pushed with --no-verify. Within minutes AWS auto-applied the AWSCompromisedKeyQuarantine policy, we rotated the key, audited CloudTrail for everything the IAM principal had touched, and moved that workload to OIDC-federated short-lived credentials. We then made push protection org-required and removed the per-user bypass."

The 3 Pillars — Don't Conflate Them

PillarWhat It RecordsToolsAnswers
📜 LogsEvents — what happened, when, to whomstructlog, CloudWatch, Loki"What happened at 3:42pm for user 678?"

Weak vs Solid — "Production bug, how do you debug?"

❌

Weak:

"I check the logs and try to reproduce locally."

Or worse: "I SSH into the server and grep the log file." SSH into production is an anti-pattern in modern infrastructure and a security risk.

✅

Solid — Debug flow:

  • 1Sentry first — groups duplicate exceptions, shows which release introduced it, affected users, breadcrumbs (previous SQL queries, last HTTP requests, log statements). Error spiked after a deploy? That diff is the smoking gun.
  • 2Not in Sentry? Query structured logs in CloudWatch/Loki/Datadog by request_id or user_id — fast, targeted, no guessing.
  • 3If distributed tracing exists: pull the trace ID from the Sentry event → follow it through every downstream call to pinpoint the slow or failing service.
  • 4Last resort: replicate prod state in staging with a redacted DB dump. NEVER grep raw text — if that's your only option, the real fix is JSON logging + request-ID middleware, not better grep skills.

Sentry — The Production-Sensible Configuration

# settings.py — Sentry config that won't bankrupt you
import sentry_sdk
from sentry_sdk.integrations.django import DjangoIntegration
from sentry_sdk.integrations.celery import CeleryIntegration

sentry_sdk.init(
    dsn=env("SENTRY_DSN"),
    integrations=[DjangoIntegration(), CeleryIntegration()],
    environment=env("ENV"),              # 'production' / 'staging'
    release=env("GIT_SHA"),             # ties every error to a specific deploy ← highest-leverage setting
    traces_sample_rate=0.1,              # 10% NOT 1.0 — 1.0 burns quota in days
    profiles_sample_rate=0.1,
    send_default_pii=False,             # GDPR — user emails, IPs, session tokens
    before_send=scrub_sensitive_data,   # custom scrubber for tokens, card numbers
)
💡

The release=GIT_SHA insight: Without it, when Sentry shows you an error spike, you can't tell which deploy introduced it. With it, every issue links to a specific commit and you see "first seen in release abc123" instantly. This is the single highest-leverage Sentry configuration — and most candidates don't know it.

Structured Logging — The Difference That Matters

❌

Plain text (grep hell):

[2026-05-21 14:22:01] ERROR Payment failed for order

Ungreppable by user, unqueryable by amount, impossible to aggregate or join with traces.

✅

Structured JSON (queryable):

{"ts":"2026-05-21T14:22:01Z","level":"error",
 "event":"payment_failed","order_id":12345,
 "user_id":678,"request_id":"abc-123",
 "amount":42.99,"gateway":"stripe",
 "error_code":"card_declined"}

Now query: all payment_failed for gateway=stripe in the last hour → dashboard → alert.

🪤

Common Traps:

  1. traces_sample_rate=1.0 in production — sends every request to Sentry as a performance transaction. Burns through quota in days, costs a fortune.
  2. Not setting release — every error looks like it could be from any deploy. Useless for post-deploy monitoring.
  3. send_default_pii=True without thought — sends user emails, IPs, session tokens. GDPR/SOC2 violation waiting to happen.
  4. Alerting on /health endpoints — health checks fail occasionally under load; you get woken up at 3am. Filter with traces_sampler.
  5. Sentry fingerprinting with dynamic messages — ValueError: Error processing order 123 and ValueError: Error processing order 124 become two separate issues instead of one recurring bug. Alert fatigue. Use static fingerprinting.
  6. Logging the entire request body — passwords, card numbers, tokens end up in your log aggregator.
  7. Conflating the three pillars — logs, metrics, traces answer different questions. An interviewer asking the difference wants to hear you don't lump them.
⚡

Production Signal — Drop This Line:

"After we shipped release abc123 we got a Sentry alert spike — the release tag immediately told me which commit, the breadcrumbs showed every failing request had the same feature flag enabled, and the trace pointed at an N+1 in a prefetch_related we missed. We flipped the flag off in seconds without redeploying. We also dropped traces_sample_rate from 1.0 to 0.1 because we were burning Sentry quota on /health and /metrics polling."

6. Django Security 🛡️

🎯

HIGH FREQ Questions:

  • "What changes do you make to settings.py before going to production?" (universal screening question — every senior interviewer asks this)
  • "Why is DEBUG=True dangerous in production? What does it actually expose?"
  • "What does ALLOWED_HOSTS do? Why is ALLOWED_HOSTS=['*'] bad?"
  • "How does Django protect against CSRF? Where could that protection fail?"
  • "How does Django prevent SQL injection? Where can a developer break it?"

NICE TO KNOW:

  • "What does SECURE_HSTS_SECONDS do, and why should you start with a small value?"
  • "Why is SECURE_PROXY_SSL_HEADER something to set carefully?"
  • "What does python manage.py check --deploy do?"

Weak vs Solid — "What do you change before going to production?"

❌

Weak:

"I set DEBUG=False and put the domain in ALLOWED_HOSTS."

Technically correct but bare minimum. You passed the junior filter and stopped there. Solid candidates rattle off the full checklist and explain what each setting prevents.

✅

Solid — Full Deployment Checklist:

  • !DEBUG=False — with it True, Django renders a yellow error page leaking: entire settings module, every SQL query, local variables in every frame, installed apps. An attacker's roadmap.
  • !ALLOWED_HOSTS from env var, never ['*'] — disabling it allows Host header injection. Django uses the Host header to build password-reset links.
  • !SECRET_KEY from env, never hardcoded or the default. Compromised = forged session cookies + manipulated signed data.
  • 🔒HTTPS bundle: SECURE_SSL_REDIRECT, SESSION_COOKIE_SECURE, CSRF_COOKIE_SECURE. For HSTS: start at 300s and ramp to 31536000 — HSTS is sticky in browsers; a bad rollout can lock users out of HTTP for a year.
  • ⚠SECURE_PROXY_SSL_HEADER — only if the LB strips the header from client requests. Otherwise an attacker can forge X-Forwarded-Proto: https → Django believes it's a secure request.
  • ✓Run python manage.py check --deploy in CI — it tells you exactly what's missing and should be a required CI step, not a manual checklist.

Production Settings — The Full Security Block

# settings/production.py — the full security block
DEBUG = False
SECRET_KEY = env("SECRET_KEY")
ALLOWED_HOSTS = env.list("ALLOWED_HOSTS")  # never ['*']

# HTTPS enforcement
SECURE_SSL_REDIRECT = True
SESSION_COOKIE_SECURE = True
CSRF_COOKIE_SECURE = True
X_FRAME_OPTIONS = 'DENY'
SECURE_CONTENT_TYPE_NOSNIFF = True

# HSTS — start low (300s), ramp to 1 year over a month
# Once browser caches it, you can't go back to HTTP for that duration
SECURE_HSTS_SECONDS = 31536000
SECURE_HSTS_INCLUDE_SUBDOMAINS = True
SECURE_HSTS_PRELOAD = True

# Only set if your LB strips X-Forwarded-Proto from client requests
# If LB doesn't strip it, attacker can forge it → security bypass
SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')
🪤

Common Traps:

  1. ALLOWED_HOSTS=['*'] in production — same severity as DEBUG=True. Disables Host header validation entirely.
  2. SECURE_SSL_REDIRECT=True behind Cloudflare that already redirects — double-redirect loop, breaks health checks. Cloudflare handles HTTPS; set to False there.
  3. SECURE_HSTS_PRELOAD=True from day one with a 1-year duration — once a browser caches HSTS, you can't go back to HTTP for that duration. Ramp from 300s over weeks.
  4. SECURE_PROXY_SSL_HEADER without the proxy stripping it — attacker sets X-Forwarded-Proto: https in their request, Django believes it's secure. Only set if your LB strips the header before forwarding.
  5. Using .raw() or .extra() with string formatting — that's how you break Django's SQLi protection. Always parameterize: Model.objects.raw("SELECT … WHERE id = %s", [user_id]).
  6. @csrf_exempt on endpoints with side effects — common shortcut for "make the AJAX call work" that's actually a CSRF hole. Use the CSRF token properly.
  7. Not running manage.py check --deploy in CI — it tells you exactly what you're missing and should be a required CI step, not a manual checklist.
  8. Not upgrading Django — almost every security release patches a CVE. Running an EOL version of Django is itself a security misconfiguration.
⚡

Production Signal — Drop This Line:

"When I joined this team I ran manage.py check --deploy on the staging settings and it lit up — DEBUG=True, ALLOWED_HOSTS=['*'], no HSTS. I moved config to django-environ, put secrets in AWS Secrets Manager, set HSTS to 300 seconds first and ramped it to a year over a month, and added check --deploy as a required CI job so DEBUG can't slip into a prod build. We caught two pull requests that would have re-enabled it within the first month."

Weak vs Solid — "How do you deploy your app?"

❌

Weak:

"I push to GitHub and Heroku/Railway deploys it."

Stops there. Couldn't go deeper if pressed. No mention of Gunicorn, migrations, health checks, rollback, or how the traffic shift happens.

✅

Solid — Full ECS Deploy Flow:

  • 1git push main → GH Actions: tests → check --deploy → makemigrations --check → build image tagged with Git SHA → push to ECR.
  • 2Migrations run FIRST — one-off ECS task before the service update. DB is in the new state before any new code reads it. Backward-compatible migrations mean old tasks keep working during the rolling window.
  • 3ECS rolling deploy: spin up new tasks → ALB health check at /health/ (checks DB + cache) must pass → drain old tasks → kill old. Zero-downtime throughout.
  • ↩Rollback = one command, ~90 seconds: aws ecs update-service --task-definition app:PREVIOUS_SHA. Not "revert PR and rebuild" — that's 10+ minutes.

Blue-Green vs Rolling — The Two-Sentence Version

🔵🟢

Blue-Green: Two identical full environments; deploy to idle one, validate, flip the load balancer. Double infrastructure cost; rollback is one traffic switch. Best when releases are big, risky, or schema changes are present.

The trap: Blue-green doesn't solve the migration problem. A destructive schema change still breaks the blue environment after the cutover — you need the same expand-contract discipline regardless.

🔄

Rolling: Replace instances one batch at a time on the same infrastructure. Old and new versions coexist briefly. Cheap — no extra infra. Rollback is slow (another rolling deploy in reverse). Default for Kubernetes/ECS.

Key constraint: Both code versions must be able to run against the same database simultaneously — which is exactly why backward-compatible migrations matter.

🪤

Common Traps:

  1. "I use runserver on the server" — instant disqualifier. Gunicorn (WSGI) or Uvicorn (ASGI) behind Nginx or an ALB.
  2. No mention of static files — the interviewer is waiting to hear S3+CloudFront or WhiteNoise. Not knowing what collectstatic does is a fail.
  3. No health check endpoint — your load balancer needs /health/ returning 200 (checking DB + cache) to know when to route to a new container.
  4. Conflating WSGI and ASGI — WSGI (Gunicorn) is fine for 95% of apps. Reach for ASGI (Uvicorn) when you have websockets, SSE, or many slow upstream calls per request to handle concurrently.
  5. No rollback story — "we'd revert the PR and redeploy" takes 10+ minutes. "We re-deploy the previous image tag" takes under 2.
  6. Not separating migration deploy from code deploy — the source of most "zero downtime" failures.
  7. Over-engineering — Kubernetes for a CRUD app with one engineer. Hiring managers explicitly look for candidates who right-size the technology, not resume-driven architectures.
⚡

Production Signal — Drop This Line:

"Our first blue-green deploy failed because the new code expected a column the migration hadn't applied yet — we'd bundled the migration in the same release as the code change. Postmortem: we split migrations into a pre-deploy phase that runs before traffic shifts, made all code changes backward-compatible with the previous release for one cycle, and added smoke tests that run manage.py migrate --check and collectstatic --dry-run plus hit /health/ on the new color before the load balancer flip. We haven't had a deploy-induced outage since."

6 Red Flags That Immediately Downgrade a Candidate

1
No specific stories. "I've used Docker" with no incident. "I've done migrations" with no specific lock type or downtime. Stories are memorable — buzzwords are forgettable. If you can't name a specific exit code, row count, or error message, the interviewer assumes you read about it.
2
No numbers. "It was slow" vs. "P95 was 1.2 seconds, we got it to 180ms by adding select_related and an index on (user_id, created_at)." Solid candidates measure.
3
Tools over outcomes. "We used Kubernetes, Sentry, and Datadog" doesn't tell the interviewer what you did. Replace tool names with verbs and outcomes.
4
Vague about own role. "We did X" on team projects is a red flag. "I owned X" is what's being listened for.
5
Can't read an error. "Exit code 137? Not sure, I just restart the container" → fail. "OOMKilled — check memory limits and worker count" → pass.
6
No mental model of failure. "What happens when X fails?" — if you've only built the happy path, you've only built half the system.
