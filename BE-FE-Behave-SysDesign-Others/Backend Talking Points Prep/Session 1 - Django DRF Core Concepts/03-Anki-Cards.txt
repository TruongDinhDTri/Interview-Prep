# Django/DRF Core Concepts - Anki Cards

## Project Structure

Q: What is the main structural difference between a ViewSet and an APIView in DRF?
A: ViewSets provide standard CRUD operations (list, create, etc.) and auto-routing. APIViews are for custom, non-resource endpoints requiring granular control.

Q: In a production Django project, why should you split settings?
A: To separate configuration for environments (Dev vs Prod), ensuring security (Debug=False in prod) and proper resource allocation (Local DB vs RDS).

Q: What is the "One app, one responsibility" principle?
A: Each Django app should encapsulate a single domain (e.g., users, payments, orders) with its own models, serializers, views, and URLs for clean architecture.

Q: What is the purpose of the apps/ folder in a Django project?
A: To group all domain logic modules (users, payments, core) in one place, keeping the root folder clean for system configuration only. Makes it easier to potentially split into microservices later.

Q: Why should you never use a single settings.py in production?
A: Split into settings/base.py (shared), dev.py (Debug=True, local DB), prod.py (Debug=False, S3, Sentry) to avoid exposing secrets and ensure environment-specific configuration.

Q: What phrase do interviewers like to hear about Django app structure?
A: "Each app owns its own business logic." This shows understanding of domain-driven architecture.

Q: What is WSGI and why is it important?
A: Web Server Gateway Interface - the bridge between Python code and web servers (Gunicorn, Nginx). Critical for deployment understanding. Rarely modified, but essential to know.

Q: What is the architect's "production line" flow in DRF?
A: Database (Models) → Máy chuyển đổi (Serializers) → Bộ điều khiển (Views/ViewSets) → Cổng giao tiếp (URLs)

Q: What is the 4-step architect flow in DRF?
A: 1) Models First (database schema), 2) Serialization (validation + transformation), 3) Logic Layer (ViewSets or APIViews), 4) Routing (urls.py with routers).

## ViewSets vs APIViews

Q: What mental model explains when to use ViewSets?
A: "Convention over configuration" - ViewSets follow REST conventions and auto-generate standard CRUD. APIViews give "full control, full responsibility" for custom logic.

Q: What metaphors explain ViewSets vs APIViews?
A: ViewSets = Automatic car 🚗 (just declare model, it auto-generates routes). APIViews = Manual car 🏎️ (you manually write each HTTP method handler).

Q: What 5 endpoints does ViewSet + DefaultRouter auto-generate?
A: GET /resource/ (list), POST /resource/ (create), GET /resource/{id}/ (retrieve), PUT /resource/{id}/ (update), DELETE /resource/{id}/ (destroy).

Q: When should you use ViewSets over APIViews?
A: For standard CRUD operations (80-90% of cases). Examples: Users, Products, Orders, Posts, Comments - any RESTful resource.

Q: When should you use APIViews over ViewSets?
A: For non-CRUD endpoints: custom analytics (/api/stats/), action endpoints (/api/trigger-report/), complex custom logic (/api/upload-file/), or logic that doesn't fit REST conventions.

Q: What's the "golden example" for ViewSets vs APIViews?
A: /api/users/ → ViewSet (CRUD resource), /api/stats/ → APIView (custom analytics, no model).

Q: What are the pros and cons of APIView?
A: Pros: Very clear, full control. Cons: Verbose, repetitive code, no auto routing.

Q: What are the pros of ViewSet with ModelViewSet?
A: Less code, auto CRUD generation, auto URL routing via DefaultRouter, convention-based consistency.

Q: How do you register a ViewSet with a router?
A: router = DefaultRouter(); router.register(r"posts", PostViewSet); urlpatterns = router.urls

Q: How do you register an APIView in urls.py?
A: path("posts/", PostAPIView.as_view()) - you must manually write each URL pattern.

## Serializers

Q: What is a SerializerMethodField used for?
A: To add a read-only field to the API response that is calculated dynamically and doesn't exist directly in the database model.

Q: What does "Serializer = gatekeeper" mean?
A: Serializers validate incoming data (POST/PUT), transform Python objects to JSON (responses), and control which fields are exposed to clients.

Q: What pattern must you follow for SerializerMethodField?
A: The method name must be `get_<field_name>`. Example: for `full_name` field, define `def get_full_name(self, obj)` to compute the value.

Q: When would you use Custom Serializer instead of ModelSerializer?
A: Use Custom Serializer for non-model-bound data: Login forms, OTP verification, Search input, Aggregation queries. Use ModelSerializer for standard CRUD operations.

Q: What is the metaphor for ModelSerializer?
A: "Máy photocopy" (Photocopy machine) - it copies the exact structure from the database Model to JSON. Fast, clean, concise.

Q: Give an example of SerializerMethodField for combining first_name and last_name.
A: full_name = serializers.SerializerMethodField(); def get_full_name(self, obj): return f"{obj.first_name} {obj.last_name}"

Q: What are the 3 main types of serializers in DRF?
A: 1) ModelSerializer (CRUD, auto-maps model fields), 2) SerializerMethodField (computed/dynamic fields), 3) Custom Serializer (non-model-bound data like Login, OTP).

Q: Where should business logic validation be placed in serializers?
A: In `validate_<field>` for field-level validation or object-level `validate()` method.

## Authentication

Q: Explain the difference between Authentication and Permissions in DRF.
A: Authentication identifies *who* the user is (e.g., via Token). Permissions determine *what* that user is allowed to do (e.g., IsAdmin, IsOwner).

Q: What's the difference between JWT Access Token and Refresh Token?
A: Access Token is short-lived (15 minutes) for API requests. Refresh Token is long-lived (7 days), stored securely, used to obtain new Access Tokens without re-login.

Q: Why is JWT called "stateless"?
A: The server doesn't store anything. All user info (User ID, expiration time) is encoded directly into the token. Server just decodes it to verify identity.

Q: What is the main advantage of JWT over Session-based auth?
A: Scalability - no server-side session storage needed. With 1 million concurrent users, sessions would overload server memory. JWT is stateless.

Q: When should you use Session-based authentication?
A: For traditional server-rendered web apps (Django templates), Admin pages, or when you need server-side session control.

Q: When should you use Token authentication?
A: For internal APIs, scripts, bots, or simple API key-based access where you don't need JWT's sophistication.

Q: What metaphor explains Access Token vs Refresh Token?
A: Access Token = key to enter the house (short-lived, if stolen limited damage). Refresh Token = backup key in safe (used to get new access keys without re-login).

Q: Why is JWT ideal for SPAs and mobile apps?
A: It's stateless, works well with React/Vue/Mobile, no need to share session state across servers in distributed systems.

## Permissions

Q: How do you implement object-level permission (e.g., only owner can edit)?
A: Create a custom permission class inheriting from BasePermission and override the `has_object_permission` method to check `obj.owner == request.user`.

Q: What are the two main built-in permissions in DRF?
A: IsAuthenticated (must be logged in) and IsAdminUser (must be Staff/Superuser).

Q: What is the difference between Auth and Permission?
A: Auth = "who you are" (identity). Permission = "what you can do" (access control).

Q: What is permissions.SAFE_METHODS in DRF?
A: A tuple containing ('GET', 'HEAD', 'OPTIONS') - read-only methods that are typically allowed for all users.

Q: How do you apply a permission class to a view?
A: Add permission_classes = [IsAuthenticated] or permission_classes = [IsOwnerOrReadOnly] to the view.

Q: Why should permission logic be decoupled from view logic?
A: For reusability - the same permission class can be used across multiple views by adding it to permission_classes list. Keeps views clean and focused on data handling.

Q: What makes custom permissions "critical for interviews"?
A: They demonstrate deep understanding of DRF's permission system and object-level security, showing you can implement business rules like "only owner can edit".

## Django vs Flask/FastAPI

Q: Why choose Django over Flask/FastAPI for a typical CRUD startup app?
A: "Batteries Included": Django provides ORM, Admin, Auth, and Security out of the box, speeding up development vs. wiring manual tools in Flask.

Q: What's the metaphor for Django vs Flask/FastAPI?
A: Flask/FastAPI = Building from bricks (manual setup). Django = Fully furnished apartment (ORM, Security, Admin pre-built, move in and start coding).

Q: What are the 3 key reasons to choose Django?
A: 1) Development Speed (batteries included), 2) Security (built-in protection against SQL Injection, XSS, CSRF), 3) Team consistency (opinionated structure prevents chaos).

Q: When is Flask/FastAPI a better choice than Django?
A: For microservices, lightweight APIs, minimal footprint requirements, or when you need total control over component choices.

Q: What security features does Django provide out of the box?
A: Built-in protection against SQL Injection, XSS (Cross-Site Scripting), and CSRF (Cross-Site Request Forgery) attacks.

Q: What 3 keywords should you emphasize when answering "Why Django"?
A: Opinionated – Scalable – Maintainable

Q: Complete the metaphor: "Flask/FastAPI is like buying bricks to build a house. Django is like..."
A: "...buying a fully furnished apartment - Kitchen (ORM), Security locks (CSRF/XSS protection), Building management (Admin panel) already included."

Q: What does "Batteries Included" mean for Django?
A: Django comes with built-in ORM, Admin interface, Authentication, Security, URL routing - no need to manually wire up separate libraries like in Flask.

## Summary & Key Phrases

Q: What is the key phrase for Django project structure?
A: "One app, one responsibility" - each app encapsulates its own domain with models, serializers, views, URLs.

Q: What is the key phrase for describing DRF experience?
A: "Models → Serializers → Views → URLs. Each layer has a clear responsibility."

Q: What is the key phrase comparing Django vs Flask?
A: "Batteries Included vs. Build it Yourself" - Django provides everything, Flask requires manual setup.

Q: What is the key phrase for ViewSets vs APIViews?
A: "Convention over configuration (ViewSets) vs. Full control, full responsibility (APIViews)"

Q: What is the key phrase for permissions?
A: "Decoupled, reusable permission classes" - separate from views, applied via permission_classes list.

Q: What is the key phrase for serializers?
A: "Gatekeeper for validation and transformation" - validates input, transforms output, controls exposed fields.

Q: What is the key phrase for JWT?
A: "Stateless, scalable, ideal for distributed systems" - no server-side storage needed.

Q: What is the senior mindset about Django's strength?
A: "Django không mạnh vì code ít. Django mạnh vì structure rõ + rule rõ" (Django is strong because of clear structure + clear rules, not just less code).

Q: What specific method must you override for custom object-level permissions in DRF?
A: You must override `has_object_permission(self, request, view, obj)` in a class inheriting from `permissions.BasePermission`.

Q: In a custom permission class, what is the standard check for Read-Only requests?
A: `if request.method in permissions.SAFE_METHODS: return True` (Allow GET, HEAD, OPTIONS).

Q: How does the "Driving a Car" metaphor explain ViewSets vs APIViews?
A: ViewSets are an "Automatic Car" (just press gas/declare model, car shifts gears/routes automatically). APIViews are a "Manual Car" (you must shift gears/write every method yourself, but have total control).

Q: Why is Django considered "opinionated" and why is that good for teams?
A: It forces a standard structure (MVT pattern, specific file organization). This ensures any Django developer can jump into any project and immediately understand the layout, preventing "spaghetti code" common in flexible frameworks.

Q: Explain the "Gatekeeper" role of a Serializer in the request-response cycle.
A: Request -> Serializer (Validates Input) -> View. View -> Serializer (Transforms/Formats Output) -> Response. It guards both entry (data integrity) and exit (data formatting).

Q: When creating a custom permission `IsOwnerOrReadOnly`, what is the final return statement logic?
A: `return obj.owner == request.user`. This ensures only the actual owner of the object can perform "unsafe" operations like PUT or DELETE.

Q: What is the "Time-to-market" advantage of Django?
A: Because of "Batteries Included" (Admin, Auth, ORM ready-to-go), you spend time building business features immediately rather than configuring boilerplate, launching products faster.

Q: In the "Architect Flow" visualization, what represents the "Controller"?
A: The **Views/ViewSets**. They contain the logic that connects the Database/Models to the Interface/URLs.

Q: Why is `wsgi.py` described as a "circuit breaker" or "bridge"?
A: It connects your Python application code to the actual Web Server (like Nginx/Gunicorn). It's the standard interface that allows Python code to handle HTTP requests from the outside world.

Q: What is the risk of using Session-based auth for a mobile app backend?
A: Scalability and State issues. Mobile apps often switch networks (WiFi/4G) or drop connections. Sessions require server memory/storage and stateful connections, which is fragile compared to stateless JWT tokens.
